## A standing freeze-policy exception for the `CS0736` conformance predicate

**Revisit when:** the next freeze-policy review, or a second request to add a compile-predicting predicate.

<details>
<summary>Recorded evidence and disposition</summary>

`ProtocolConformanceValidator.EmitsStaticPropertyUnderRequirementName` predicts a *compile* error (`CS0736` — a static member offered as an instance-interface implementation), which the prediction-gate freeze policy normally routes to the verify-recover loop instead of a new predictor. It was retained because removing it was tried end-to-end and the loop provably cannot recover the shape: `CS0736` attributes to the conforming type's whole type surface (no leaf to withdraw), bisection is leaf-only, and coarse type-scope withdrawal is unauthorized in production — the observed end state is `Kind = "RecoveryNonConvergence"`, `ReasonCode = "SWIFTBIND111"`, `Stage = "CSharpCompile"`, `Scope = "TypeSurface"`, `AuthorizationOutcome = "Unauthorized"`, `ObstructionCode = "RequiresGraphClosure"`, i.e. generator exit 1. The trade is one dropped conformance versus one dropped **library**. Reasoning is written up in code at `ProtocolConformanceValidator.cs:1023-1032`, and the emitter inconsistency that produces the shape was fixed separately. Options: (1) grant a standing exception for this predictor; (2) fund conformance-aware static/instance name arbitration in the type emitters so the shape is unreachable by construction — the better long-term fix, and note the symmetric static-*requirement* case; (3) fund `ConformanceEdge`-scope withdrawal in the recovery loop. Recommendation: (1). Absent an answer the predicate stays and the exception is de facto rather than stated, which is the outcome worth avoiding — the next predictor request will cite this one as precedent without its evidence. **Trigger:** the next freeze-policy review, or a second request to add a compile-predicting predicate.

</details>

<details>
<summary>Recorded evidence and disposition</summary>

**Genuinely blocked on completeness infrastructure — do NOT land as inert scaffolding.** `RecoveryGraph`/`RecoveryPolicy` (`SafeToDrop`/`Escalate`) exist and are unit-tested but have **zero production callers**; `InEmissionDriver.UnitLookup` derives a culprit's unit from the artifact's own classification, not a dependency lookup. ## Bounded-bisection containment over-declines when withdraw-all empties the wrapper surface

**Revisit when:** a real corpus library that fails closed **only** because its entire withdrawable surface collapses under withdraw-all (a leaf-owned-scaffolding + healthy-siblings shape where withdraw-culprit-alone is provably clean but withdraw-all is `NoWrapperSurface`) — reproduce that module as the red fixture, then make `ProbeClean`/`BoundedBisectionSearch` gate-aware so containment survives an emptied surface without weakening the confirmation gates.

<details>
<summary>Recorded evidence and disposition</summary>

**Sound-but-conservative by design (session 07 bisection); a liveness refinement, never a soundness gap.** `BoundedBisectionSearch` Gate 1 (containment) withdraws *every* candidate at once and requires that probe to come back clean before narrowing — "only a clean withdraw-all proves the culprit lies inside the candidate set." `InEmissionDriver.ProbeClean` correctly treats a *vacuous* convergence (the withdrawal emptied the whole wrapper surface → `NoWrapperSurfaceConverged`, nothing left to compile) as **NOT clean**, because a vacuous withdraw-all does not prove containment — counting it as clean would let the search falsely confirm an innocent leaf (a false isolation). The consequence: for a **degenerate module whose entire withdrawable surface is leaf/accessor candidates** (a free-function-only or all-leaf shape where withdraw-*one* leaves a real surface but withdraw-*all* empties it), containment reads not-clean and the search declines — even when a single culprit *was* isolable. This is fail-closed (the module fails closed exactly as it did pre-feature — never a wrong culprit, never a broken/reduced ship beyond the existing behavior) and confined to that degenerate shape: any module retaining non-candidate wrapper surface (a type wrapper, a non-recoverable member) under withdraw-all gets a real containment verdict and isolates normally. The correct liveness-preserving fix is **gate-aware**: reject vacuous-clean only at the confirmation gates (sufficiency/necessity, where a vacuous clean would falsely *confirm*), while giving containment a non-vacuous basis (e.g. treat a vacuous withdraw-all as *inconclusive-proceed* with the invariant re-established another way, or seed the search from a surface-preserving candidate partition) — but that changes the search algorithm and needs its own soundness argument + red fixture, so it is not landed under a review-time patch. **Trigger:** a real corpus library that fails closed **only** because its entire withdrawable surface collapses under withdraw-all (a leaf-owned-scaffolding + healthy-siblings shape where withdraw-culprit-alone is provably clean but withdraw-all is `NoWrapperSurface`) — reproduce that module as the red fixture, then make `ProbeClean`/`BoundedBisectionSearch` gate-aware so containment survives an emptied surface without weakening the confirmation gates.
