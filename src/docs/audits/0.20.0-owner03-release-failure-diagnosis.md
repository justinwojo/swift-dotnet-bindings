## Campaign acceptance contract

Every batch below is governed by these rules:

1. Prefer the generic root-cause fix over a library-specific shortcut. If the generic
   repair is too large for the release, a safe bounded mitigation is permitted only
   when the underlying issue is recorded under `src/docs` as explicit future work,
   with affected shapes and consumer limitations named. A skip, swallowed exception,
   widened timeout, unchecked narrowing cast, or relabeled crash is not a mitigation.
2. Every downstream signature must have a `swift-bindings` unit or BindingTests
   reproduction that fails before the repair and passes after it. Downstream execution
   confirms package integration; it is never the sole regression gate.
3. A batch is independently shippable only when its named first-party regression gate,
   focused owner-repository gate, and evidence update are complete. Full matrices wait
   until the focused batches are green.
4. Environment-sensitive tests fail closed on a missing prerequisite and report that
   prerequisite separately from binding behavior. They do not turn an unexercised
   product assertion into a pass.

### D01 — ActivityKit push-token request lacks the required capability

**Evidence and root cause.** Both failing cells throw `LiveActivityException` wrapping
`SessionCore.PermissionsError Code=3` when the consumer requests a live activity with
`usePushToken: true`. The test app declares `NSSupportsLiveActivities`, but the P8
evidence does not demonstrate an APNs `aps-environment` entitlement in the signed
profile. The same observer register/replace/release lifecycle is covered first-party
only with the default non-push request. This is a capability-sensitive test setup, not
evidence that callback replacement or release is broken.

**Long-term fix.** In `swift-dotnet-packages`, provision a dedicated device test app
whose signed entitlements contain the ActivityKit/APNs capability, verify the embedded
profile before launch, and separate request preflight from observer-lifetime
assertions. Keep the non-push lifetime test on simulator; do not claim that a simulator
push-token request is supported unless a native control proves it. In `swift-bindings`,
extend `BindingTests/RuntimeTestsApp/AppleSupplement/LiveActivityTests.cs` and the build
plumbing with an opt-in, entitlement-provisioned `usePushToken: true` device arm.

**First-party regression and focused gate.** Exact home:
`BindingTests/RuntimeTestsApp/AppleSupplement/LiveActivityTests.cs` plus
`BindingTests/RuntimeTestsApp/AppleSupplement/ActivityKitReadiness.cs`. The new device
test must request a push token, register, replace, and release the observer; the
readiness path must fail closed with the missing entitlement named. Gate: the opt-in
LiveActivity device smoke plus the existing simulator non-push lifecycle tests.

**Close condition.** Signed-entitlement preflight passes and the exact device lifecycle
passes; unsupported simulator behavior remains an explicit non-pass platform result.

### D02 — throwing wrappers leave stale `errorOut` on success

**Evidence and root cause.** The CryptoKit device log shows a successful AES-GCM
roundtrip, the expected typed authentication failure for a wrong key, and then the
same error escaping the immediately following correct-AAD call. The generated Swift
CSM wrappers write `errorOut.pointee` in `catch` but do not clear it before `do`.
Managed callers use an `out` pointer. NativeAOT may reuse the failed call's stack slot,
so a later successful call observes the stale retained error. Simulator stack state
happened not to expose the defect. The scope is every generated throwing C-callable
wrapper, not CryptoKit alone.

**Long-term fix.** In the common throwing-wrapper emission path, write
`errorOut.pointee = nil` at entry before executing Swift code. Centralize this invariant
so method, property, initializer, generic-specialization, and protocol thunk emitters
cannot drift. Continue retaining a real error only in `catch`.

**First-party regression and focused gate.** Add emitter tests for every throwing CSM
family asserting the nil initialization precedes the `do`. Invert the pre-fix lock in
`src/Swift.Bindings/tests/UnitTests/EmitterTests/MethodLevelGenericOpeningTests.cs`,
which currently asserts that the pre-`catch` region contains no `errorOut.pointee` and
that the whole wrapper has exactly one write; audit sibling occurrence-count assertions
at the same time. Add an exact fail-then-success fixture under
`BindingTests/Sources/SwiftBindingsTestLib/Generics` and runtime assertion under
`BindingTests/RuntimeTestsApp/ErrorHandling/ThrowingMethodTests.cs` (the test type is
currently `BasicThrowingTests`): invoke one specialization that throws, then one that
succeeds through the same wrapper shape, and prove no stale error escapes. Gate:
focused emitter unit tests plus iOS simulator and NativeAOT device runtime tests.

**Close condition.** The first-party fail-then-success test fails on the old wrapper,
passes after the generic repair, and the focused CryptoKit device cell passes with the
repacked SDK.

### D03 — Lottie pixel oracle does not identify a binding failure

**Long-term fix.** In `swift-dotnet-packages`, replace the broad production animation
with a minimal animation containing one uniquely named gradient. Record hierarchy
keypaths, pin the renderer, compare no provider, static provider, pure-Swift dynamic

not weaken the effect oracle to callback count.

**First-party regression and focused gate.** Existing exact home:
`BindingTests/Sources/SwiftBindingsTestLib/Closures/ValueProviderDelivery.swift` and
`BindingTests/RuntimeTestsApp/Closures/ValueProviderDeliveryTests.cs`. Extend that home

callback fires but the installed provider does not alter the host's rendered/observable
output. Gate: focused ValueProviderDelivery simulator/device tests, followed by the
four-arm Lottie simulator/device differential.

**Close condition.** A deterministic native/managed differential identifies and fixes
the actual layer; both downstream platforms then show a changed rendered result.

### D04 — Mappedin correctly exposes Swift `inout`

**Evidence and root cause.** Swift declares
`show3dMapOptions(_ block: (inout [String: Any]) -> Void)`. The generated API accepts
`Action<SwiftInOut<SwiftDictionary<SwiftString, ExistentialContainer0>>>`; the consumer
still passes `Action<Dictionary<string, object>>`. Restoring a by-value projection
would discard Swift writeback and silently change semantics.

**Long-term fix.** Update the downstream callback to read and assign `slot.Value`,
using the supported Swift dictionary and existential boxing helpers. Keep the
collision-free generated signature.

**First-party regression and focused gate.** Existing exact home:
`BindingTests/Sources/SwiftBindingsTestLib/Closures/InOutClosureParams.swift` and
`BindingTests/RuntimeTestsApp/Closures/InOutClosureParamTests.cs`: `ShowMapOptions`
checks the seeded dictionary and `FocusOptions` checks mutation/writeback. Gate: those
simulator/device tests plus Mappedin compile and its two focused cells.

**Close condition.** Mappedin compiles against the inout API and the runtime callback
proves the mutated dictionary is visible after return.

**First-party regression and focused gate.** Existing exact home:

full-AOT property tests; then Nuke's three and DeviceKit's two cells.

**Close condition.** Both consumers preserve full-width values and no test relies on
overflowing the compatibility projection.

### D06 — Swift-vended existential cannot forward closure parameters

**Evidence and root cause.** Nuke returns a Swift-backed `DataLoader` existential and
the consumer calls a requirement carrying success, progress, and error closures.
`ProtocolProxyEmitter.InterfaceImpl.cs` deliberately emits the existing
`Swift-backed existential container` rejection for closure-parameter requirements.
`ProtocolClosureSkipTests.cs` covers construction and the C#-implemented reverse path,
but does not invoke this forward witness-dispatch shape. This is a generic binding
capability gap.

**Long-term fix.** Implement witness-table forward dispatch for supported closure
parameters on Swift-vended existentials, including multiple closures, escaping
lifetime, typed error callbacks, disposal, and GC. Do not add a Nuke-only facade. If
that generic repair cannot fit the release, the only acceptable bounded mitigation is
a package-owned concrete Nuke shim; before using it, document the unresolved generic
shape and limitations under `src/docs` as future work.

**First-party regression and focused gate.** Extend
`BindingTests/Sources/SwiftBindingsTestLib/Protocols/ProtocolClosureSkipping.swift`
and `BindingTests/RuntimeTestsApp/Protocols/ProtocolClosureSkipTests.cs` with a Swift
factory returning `any Protocol`, a C# call through that existential, delayed Swift
invocation of success/progress/error closures, and a forced-GC lifetime arm. Emitter
tests must prove supported shapes no longer receive SB0003. Gate: focused emitter
tests and simulator, NativeAOT device, and Mono full-AOT protocol tests; then Nuke on
simulator/device/tvOS.

**Close condition.** The exact Swift-vended existential path works across the three
first-party runtime lanes and Nuke no longer throws the guard exception.

### D10 — Keychain labeled initializers intentionally became factories

**Evidence and root cause.** KeychainAccess has two one-string Swift initializers,
`init(service:)` and `init(accessGroup:)`. Collision-safe generation exposes
`CreateWithService` and `CreateWithAccessGroup`; selecting either as the bare C#
constructor would silently erase the other label's semantics. The downstream source
still calls `new Keychain(string)`, and overload resolution falls through to an
unrelated `SwiftHandle` constructor, producing 16 CS1503 errors.

**Long-term fix.** Replace each call with the factory matching its semantic label.
Do not restore an arbitrary one-string constructor or add implicit string-to-handle
conversion.

**First-party regression and focused gate.** Existing exact home:
`BindingTests/RuntimeTestsApp/Collisions/NonFailableInitLabelCollisionTests.cs` plus
constructor collision emitter tests. They assert all colliding labeled initializers are
factories and no ambiguous bare constructor exists. Gate: focused unit and
simulator/device collision tests; then both KeychainAccess builds/runs.

**Close condition.** All 16 call sites use the correct named factory and both lanes
pass without changing generator policy.

### D11 — zero-count shell aggregation emits two values

**Evidence and root cause.** `run-all-sim.sh` uses command substitutions of the form
`grep -c ... || echo 0`. GNU/BSD grep prints `0` and returns 1 for no matches, so the
fallback prints a second `0`. Arithmetic at line 287 receives a multi-line value and
the later `FAIL_LIBS` reference is unbound. `run-all-device.sh` carries the same defect
at lines 146-147 even though P8 triggered it only in the simulator summary. The
authoritative per-cell JSON survived; the summary harness did not.

**Long-term fix.** Stop deriving qualification truth from ad-hoc shell text. Define a
structured downstream receipt contract in `swift-bindings` with a small parser/model,
then have the internal harness emit and validate that format. As an immediate part of
the same downstream batch, initialize counters and use a helper that emits exactly one
scalar for zero or positive matches. Do not mask parser errors with `|| true` at the
top level.

**First-party regression and focused gate.** Add
`src/Swift.Bindings/tests/UnitTests/DownstreamQualificationReceiptTests.cs` with
checked-in zero-match, positive-match, malformed, incomplete, and duplicate-terminal
fixtures. The zero-match fixture must reproduce this signature. Gate: focused UnitTests
plus an internal `bash -u` harness self-test that consumes the same fixtures.

**Close condition.** The shared contract rejects malformed/incomplete receipts, the
zero-count case produces one numeric value, and a focused 15-cell internal summary
finishes with a terminal result.
