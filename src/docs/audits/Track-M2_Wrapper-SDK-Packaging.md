# Track M2 — Wrapper Compilation / SDK / Packaging / Arch

**Scope:** Verification audit of the wrapper-compilation, SwiftUI-bridge-compilation, SDK two-pass packaging, and CPU-architecture-folding pipeline. Files audited: `Program.cs`, `BindingsGeneratorCommand.cs`, `Configuration/SwiftWrapperCompiler.cs`, `Configuration/CSharpWrapperCoGater.cs`, `Configuration/WrapperXCFrameworkMerger.cs`, `Emitter/ConsumerTargetsEmitter.cs`, `Emitter/BindingProjectEmitter.cs`, plus `Swift.Bindings.Sdk/Sdk/Sdk.props` and `Sdk.targets`.

**Overall risk rating: 5 / 5 — high confidence.** Nine distinct defects confirmed by direct compile/execute probes against the built generator (one P0 co-gater coverage gap that produces dangling P/Invokes; the rest a coherent cluster of P1s that all make the SwiftUI **bridge** xcframework second-class to the **wrapper** xcframework — wrong arch, dropped from pack/consumer-targets, or guarded by stale slice-id defaults). The cluster collapses to two root causes: (a) the SwiftFramework/SDK bridge-compile path never threads `--target-architectures` / `WithArchitecture` so the bridge can never fatten; (b) the standalone Apple-direct emission branch hard-codes the bridge "off" while having just compiled it. Confidence is high because every confirmed item was reproduced with a probe (co-gater run, swiftc+lipo arch inspection, or emitter call with each branch's exact options), not inferred from reading alone.

### Per-item detail

**[P0] Co-gater cannot remove DllImport-shaped dangling P/Invokes (`CSharpWrapperCoGater.cs:51`).** The co-gater's candidate finder (`FindStrippedPInvokeCandidates`) skips any line failing `IsWrapperLibraryImportLine`, which requires `WrapperLibraryImportRegex` = `LibraryImport\("(\w*SwiftBindings)"` (line 51-53) **and** the literal `EntryPoint` (line 760). A `[System.Runtime.InteropServices.DllImport("…SwiftBindings", EntryPoint=…)]` line never matches the `LibraryImport(` substring, so it is never a candidate. `FindPartialDeclaration` (line 763-771) is a second independent block: it only matches lines containing ` partial ` ending in `;`, which a `private static extern …;` declaration is not. Four emitters emit exactly this unguarded shape — `KeyPathSingletonEmitter.cs:393-394`, `AppEntityKeyPathSingletonEmitter.cs:250-251`, `KeyPathBagValueSpecializationEmitter.cs:443`, `ModuleHandler.cs:433` (simple-enum metadata accessors) — each paired with a Swift `@_cdecl("{symbol}")` trampoline using the **same** symbol as the DllImport `EntryPoint`, so `SwiftWrapperPostProcessor` (cs:164-177, 207) can strip it (internal-type reference path) and feed the symbol into `StrippedSymbols`. That set flows to `CSharpWrapperCoGater.ProcessDirectory` (`BindingsGeneratorCommand.cs:851-854`, `Program.cs:1191-1194`), which then skips every DllImport-emitted symbol → surviving `[DllImport(…EntryPoint="<stripped>")]` + `static extern` → `EntryPointNotFoundException`/`DllNotFoundException`. `KeyPathBagValueSpecializationEmitter.cs:392` names this exact failure mode in a comment; its only mitigation (lifting the Swift availability floor) does not cover the internal-type strip path. No co-gater unit test exercises the DllImport+static-extern form. The probe proves the unit-level coverage gap decisively; the full runtime DllNotFound additionally needs a real binding where one of those KeyPath/AppEntity/metadata wrappers references an internal type and gets stripped (not end-to-end reproduced, but the maintainers' own comment treats the orphaned-P/Invoke outcome as a known hazard).

**[P1] SwiftFramework bridge sim slice is arm64-only (`Program.cs:1225` / `SwiftWrapperCompiler.cs:987` / `Sdk.targets:2153`).** These three confirmed items are one defect observed at the three layers it spans, plus a fourth (`SwiftWrapperCompiler.cs:987` "Info.plist arm64 regardless of resolved arch") that is the underlying primitive. The wrapper is fattened via `--target-architectures` → `CompileWrapperForArchitectures` (`Program.cs:887`) lipo-fold; the bridge has nothing analogous: `RunCompileBridgeOnly` takes no `targetArchitectures` and routes to `CompileBridgeAll`/`CompileBridge`/`CompileBridgeSlice`, which use bare `pi.GetSlice(true)`/`pi.DeviceSlice` (no `WithArchitecture`, no per-arch fan-out, no lipo). `SliceVariant.Architecture` defaults to `"arm64"` (cs:19), driving the binary triple, the slice dir name, and the plist `SupportedArchitectures` all to arm64. The SDK omits `--target-architectures` from `_CompileSwiftUIBridge` (`Sdk.targets:2146-2158` vs `_CompileSwiftWrapper:2072`), and the only fat-sim bridge fold (`_CompileAppleFrameworkSecondBridgeSlice`, `Sdk.targets:1143`) is gated `_SwiftBindingTargetKind=='AppleFramework'`. The bridge NativeReference is emitted per-RID unconditionally (`ConsumerTargetsEmitter.cs:104`), so an iossimulator-x64/tvossimulator-x64/Rosetta consumer resolves the fat wrapper but DllNotFounds the arm64-only `{Module}Bridge`. The Apple-direct inline path (`BindingsGeneratorCommand.cs:1035-1056`) is **not** affected — it routes the bridge through `CompileWrapperForArchitectures` + `WithArchitecture`. A complete fix needs all of: a `targetArchitectures` param on `RunCompileBridgeOnly` threaded through `CompileBridge*`/`WithArchitecture` + lipo fold, the `--target-architectures` line added to `_CompileSwiftUIBridge`, **and** `$(SwiftTargetArchitectures)` added to the SDK fingerprint echo (`Sdk.targets:601`) so `_SwiftBridgeSkip` does not reuse a stale arm64-only bridge.

**[P1] Standalone direct-mode drops the (fat-folded) bridge from pack + consumer targets (`BindingsGeneratorCommand.cs:1316` / `:1044`).** The `else if (isSystemFrameworkTarget && !sdkMode && …)` branch (lines 1248-1319) calls `BindingProjectEmitter.Emit` without `HasBridgeSwift`/`BridgeXCFrameworkPath` and `ConsumerTargetsEmitter.Emit` with `HasBridgeXCFramework=false` (line 1316) — even though lines 1032-1056 just compiled (and in the Apple-direct sub-path, fat-folded via `CompileWrapperForArchitectures` over `CompileBridgeForArch`) `{Module}Bridge.xcframework` onto disk. `BindingProjectEmitter.cs:177-198` gates both the bridge NativeReference and the `<None Pack="true">` pack item on `HasBridgeSwift || (BridgeXCFrameworkPath != null && Exists)`; `ConsumerTargetsEmitter.cs:102-109,222-229` gates the consumer reference on `HasBridgeXCFramework` — all false here. The `.SwiftUIBridge.cs` Compile item is still emitted (`BindingProjectEmitter.cs:213`, gated only on its own `Exists()`), so the `[LibraryImport("{Module}Bridge")]` P/Invokes compile into the assembly with no native backing → `DllNotFoundException("{Module}Bridge")` at runtime for `ProjectReference` and packed consumers, exactly as the in-code comment at lines 1019-1031 warns. The xcframework branch (line 1158/1185) and the SDK Apple path (`_SynthesizeAppleFrameworkConsumerTargets`, `Sdk.targets:2461-2507`, sdkMode-only) are correct; this `!sdkMode` standalone/packed flow has no rescue. Fix mirrors the xcframework branch: thread `HasBridgeSwift`/`BridgeXCFrameworkPath` and set `HasBridgeXCFramework = hasBridgeSwift` (the inline bridge refs carry their own `Exists()` guards, so passing the "will be produced" signal is safe per the constraints.md rule).

**[P1] SWIFTBIND031 Guard 2a uses static slice-id defaults (`Sdk.targets:2441`).** Guard 2a checks `Exists('…wrapper.xcframework/$(_SwiftBindingSimulatorSliceId)/')` against the hardcoded defaults `ios-arm64-simulator`/`ios-arm64` (`Sdk.targets:46-47`). The disk-resync that would correct them, `_ResyncAppleFrameworkWrapperSliceIds` (line 1581, `find … -name '*-simulator'`), is gated `_SwiftBindingTargetKind=='AppleFramework'` and never runs for a third-party SwiftFramework binding. When `SelectArchitecture`/`WithArchitecture` rename the sim slice (x86_64-only source → `ios-x86_64-simulator`), the `Exists()` check on the static default fails and pack hard-errors SWIFTBIND031 despite a valid wrapper on disk. The MSBuild probe reproduced this (FAIL on the static default; PASS after rename or after enabling the AppleFramework-only resync). Correction to the original claim: the arm64e-simulator illustration is unbuildable (the iOS simulator SDK ships no arm64e stdlib), and the common fat arm64+x86_64 sim case does **not** trip it (the lipo-fold keeps the primary `ios-arm64-simulator` dir name). The realizable trigger is an x86_64-only-simulator source (legacy Intel-sim + arm64-device shape). Fix: a SwiftFramework-path slice-id resync from disk, or glob the actual `*-simulator` dir in Guard 2a instead of trusting the default.

**[P1] `WrapperXCFrameworkMerger` non-transactional fat-fold (`WrapperXCFrameworkMerger.cs:116`).** `LipoCreate` (lines 145-156) does temp-then-replace **per individual binary** (`File.Delete(primaryBin); File.Move(tmp, primaryBin)`) inside the per-slice loop, while `WritePrunedInfoPlist` runs once at line 116 after the loop. A later-step throw (missing secondary binary 82-83, lipo failure 151-153, or a secondary-only ditto failure 108-110) leaves an already-fattened slice binary on disk paired with the original single-arch plist. The caller `CompileWrapperForArchitectures` (`Program.cs:887`) swallows the exception, returns non-null, and restores the corrupted primary — so the SDK records `HasWrapperXCFramework=True` and ships a wrapper whose Mach-O contains x86_64 the plist hides. Because `XCFrameworkResolver.SelectArchitecture` (`XCFrameworkResolver.cs:297-315`) keys slice selection off the plist's `SupportedArchitectures` with no Mach-O cross-check, an x86_64/Rosetta consumer is denied a slice whose binary physically contains x86_64 → DllNotFound, silently defeating the Intel/Rosetta coverage the fold exists for (arm64 consumers still work — the disagreement is always a superset, so this is a denied-slice/wasted-fold defect, not arm64 corruption). The single-matched-slice variant (path 3) is the load-bearing reachability point; the multi-matched-slice variants (paths 1-2) need a single call to produce 2+ x86_64-bearing matched slices. Fix: make the lipo-overwrite + plist-rewrite atomic (write the union plist before/with each overwrite, or stage all lipos and commit binaries+plist together) and delete/correct the `Program.cs:943-945` comment.

## 4. Checked & refuted

- **`WrapperXCFrameworkMerger.cs:85` — "lipos each shared slice in place before writing the union plist, so a later-slice failure leaves a fat binary with a stale single-arch plist" (claimed P1, REFUTED as a reachable defect via the multi-shared-slice path).** The described mechanism is real in isolation and was reproduced, but the triggering precondition (a primary wrapper xcframework presenting >1 slice sharing the same platform+variant) is **never produced** by the generator: a wrapper is always single-platform, `PlatformInfoFactory` yields at most one simulator + one device slice, and the x86_64 secondary pass adds at most one sim slice — so at most one shared (platform, variant) slice ever exists. With a single shared slice, the missing-binary check runs **before** that slice's own `LipoCreate`, closing the fatten-then-skip-plist window, and the `Program.cs:942-945` comment is accurate for every topology the generator emits. **Note:** the *separate* confirmed `WrapperXCFrameworkMerger.cs:116` finding established a different, genuinely reachable corruption window (single fattened slice + secondary-only ditto failure, path 3), so the merger is still defective — just not via the multi-shared-slice route this refuted item proposed. Future agents: don't re-chase the multi-shared-slice topology; do honor the confirmed single-slice/ditto-failure window.

## 5. Coverage gaps (what this track did NOT reach)

- **No live `dotnet build -r iossimulator-x64` consumer round-trip.** The bridge-arch P1s were proven at the build-time arch level (lipo/plist) and the runtime DllNotFound follows necessarily from a missing x86_64 slice, but no published third-party SwiftUI nupkg was consumed under Rosetta to observe the literal exception. Same caveat for the SWIFTBIND052 NativeReference-resolution error text.
- **No end-to-end strip→co-gate→link reproduction for the P0.** The co-gater coverage gap was proven at the unit level (real `Process` call). A binding where one of the four KeyPath/AppEntity/metadata wrappers references an internal type, gets stripped, and then fails to load was not built.
- **macOS / Mac Catalyst / tvOS bridge topology** beyond the macOS double-device-slice candidate (#13) was not exercised; the device-vs-simulator axis of the bridge gap (vs the confirmed CPU-arch axis) was not separately probed.
- **The 25 deferred P2 candidates** (arg-length, sanitization, brace-walkers, `ResolveAutoArchBasis` catch-all, explicit-arch ordering, restore-Move guard, bridge `-F` dependency asymmetry, `_AFW_OtherIsFatSim` single-pin gate) received source reads but no decisive probe.
- **Fingerprint/skip-cache interaction** (`_SwiftBridgeSkip` / `_SwiftWrapperSkip` reusing a stale arm64-only bridge when `SwiftTargetArchitectures` flips) was identified as a required part of any P1 fix but not independently probed.

## 6. Recommended BindingTests fixtures (Swift shapes to lock down each confirmed defect)

These describe the Swift/binding **shape** to add; they are not fix proposals.

1. **Co-gater DllImport gap (P0).** A binding where a KeyPath-singleton (or `@AppEntity` KeyPath, KeyPath-bag value specialization, or simple-enum metadata) wrapper references an **internal** type so `SwiftWrapperPostProcessor` strips its `@_cdecl`. Assert (a) `stripped-symbols.json` lists the symbol, and (b) the generated `.cs` contains **no** surviving `[DllImport(…EntryPoint="<that symbol>")]` + `static extern`. Pair with an equivalent `[LibraryImport]`+`partial` P/Invoke for the same stripped symbol as the (passing) control. This is the cheapest permanent guard and exercises the exact emitter shapes.

2. **Third-party SwiftFramework SwiftUI bridge on x64 sim (the bridge-arch cluster).** A tiny third-party Swift package exposing a public `SwiftUI.View` (so the generator emits `*.SwiftUIBridge.swift`), built against a fat (arm64+x86_64) simulator source via the SDK with `SwiftTargetArchitectures=auto`. Assert via `lipo -archs`/`Info.plist` that **both** `{Module}SwiftBindings.xcframework` and `{Module}Bridge.xcframework` simulator slices list `arm64 x86_64`. The asymmetry (wrapper fat, bridge arm64-only) is the regression signal; ideally extend to a `dotnet build -r iossimulator-x64` consumer of a bridged view.

3. **Standalone direct-mode SwiftUI bridge pack (the two `BindingsGeneratorCommand.cs:1316` findings).** A standalone (non-SDK) generator run against an Apple system framework (or `--tbd`/direct-mode input) that emits a SwiftUI bridge view, followed by `dotnet pack`. Assert that `{Module}Bridge.xcframework` exists on disk **and** that both emitted `.targets` files and the `.csproj` carry a `{Module}Bridge.xcframework` NativeReference + a `None Pack="true"` item, and that the nupkg's `runtimes/<rid>/native/` contains the bridge. Cover both the Apple-direct (fat-folded) and the generic system-framework sub-paths.

4. **SWIFTBIND031 on a renamed sim slice (Guard 2a).** A third-party SwiftFramework binding for an xcframework whose simulator slice is **x86_64-only** (legacy Intel-sim + arm64-device shape), packed via the SDK. Assert `dotnet pack` succeeds (no SWIFTBIND031) and the wrapper's actual `ios-x86_64-simulator` slice is resolved — i.e. the guard globs the real slice dir rather than asserting the static `ios-arm64-simulator` default.

5. **Fat-fold atomicity (`WrapperXCFrameworkMerger.cs:116`).** A unit/integration fixture that injects a fault into the second lipo step (or a secondary-only ditto failure with a single matched slice) and asserts that after the throw **no** slice binary on disk disagrees with its plist `SupportedArchitectures` — i.e. either the union plist is written transactionally with each overwrite, or the binary is rolled back. This locks down the path-3 single-slice window that the refuted multi-slice topology does not cover.
