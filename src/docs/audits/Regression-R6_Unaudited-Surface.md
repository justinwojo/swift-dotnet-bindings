### 1 — `SwiftWrapperPostProcessor.ReferencesInternalType` cross-module short-name collision (P1, silent public-API loss) — **FIXED**

The post-processor strips any `@_cdecl`/`@_silgen_name` wrapper block whose body references an internal type, matching the **bare short name** of every entry in `internalTypeNames` with `\b<name>\b` (`:519`). The internal-name set (`Program.CollectInternalTypeNames`, `:1672–1709`) adds each internal type's unqualified short name (`:1701`) and de-collides **only** against the current module's public short names (`:1678`); cross-module types are `continue`-skipped before the `publicNames.Add` branch. So a public type from a dependency, an Apple framework, or the Swift stdlib whose short name equals a local internal helper (`Data`, `Box`, `Storage`, `Node`, `State`, `Cache`…) is never in `publicNames`, the internal short name survives, and `\bData\b` matches the suffix of a qualified `Foundation.Data` (the `.` is a regex word boundary). The whole block is removed and its symbol harvested into `StrippedSymbols`, so `CSharpWrapperCoGater` then suppresses the matching C# P/Invoke — silent deletion of correct public API (or `EntryPointNotFound`/`DllNotFound` if a P/Invoke survives without its symbol). The generator **already** owns a correctly module-aware matcher for the same set — `InternalTypeReferenceWalker.NamedTypeReaches` (used at emission time by `MemberValidationPipeline`) explicitly refuses to short-name-match a cross-module qualified type — so the emission gate emits the member and the naive post-processor wrongly strips it: the two stages disagree and the buggy stripper wins. The review flagged `ReferencesInternalType` only for performance (~L1955) and Finding 2's "over-stripping is silent" note never identifies this cross-module mechanism.

**Fix (two complementary layers).** *Layer 1 — don't manufacture the unreachable short name.* `Program.CollectInternalTypeNames` now adds the bare leaf short name **only for top-level internal types**. A NESTED internal type (e.g. `ShortNameCollisionFixture.Data`) is unreachable from the generated wrapper via its bare leaf name — the wrapper's top-level `@_cdecl` functions and cross-type extensions must spell a nested type qualified (`Parent.Nested` / `Module.Parent.Nested`), and those qualified forms are still added — so emitting the bare `Data` only ever false-positives the text matcher against a same-named foreign type emitters print unqualified. This was not academic: with the BindingTests fixture present, the bare `Data` matched the `_ data: Data` parameter of every emitted hasher `_dbw_append` shim (a bare `Foundation.Data`), so 37 unrelated wrapper blocks were stripped and the wrapper failed to compile (the only legitimate strip is the one `InternalHolder.describe` block). *Layer 2 — match the surviving short names module-aware.* `ReferencesInternalType` threads the current Swift module name (`currentModuleName`) from `SwiftWrapperCompiler` (both `CompileAll` and `CompileSlice` call sites) and mirrors the rule the generator's emission-time gate `InternalTypeReferenceWalker.NamedTypeReaches` already enforces: a SHORT (unqualified) internal-name entry — now only ever a top-level type — matches a reference only when it denotes the **current** module's type, written bare (negative lookbehind `(?<!\.)`, never the `.Data` suffix of a qualified `Foundation.Data`) **or** qualified with the current module (`<currentModule>.X`), and never when qualified with a foreign module. The current-module-qualified clause is the load-bearing half: generated wrappers spell a current-module internal type qualified (`SwiftBindingsTestLib.InternalHolder`), syntactically identical to a foreign `Foundation.Data`, so a bare-only lookbehind would *under*-strip it and leave an uncompilable wrapper. Qualified set entries (`Module.Type[.Nested]`) carry their own prefix and keep the plain word-boundary match. When the module name is unknown (`null`), short entries fall back to bare-only matching (legacy behavior). Locked down by `PostProcessorInternalTypeTests`: `Process_QualifiedCrossModuleType_NotStrippedByShortNameCollision` (the regression — `Foundation.Data` survives), `Process_BareInternalShortName_StillStripped` (no over-correction), `Process_SelfModuleQualifiedInternalType_StillStripped` (qualified self-reference still caught), `Process_CurrentModuleQualifiedShortNameOnly_StrippedWhenModuleKnown`, `Process_RealCdeclBlockReferencingQualifiedInternalType_IsStripped` (the exact real-world `InternalHolder.describe` block), and `Process_ForeignModuleQualifiedShortNameCollision_KeptEvenWhenModuleKnown`; plus `CollectInternalTypeNamesTests.CollectInternalTypeNames_NestedInternalType_ContributesNoBareShortName` (layer 1 — nested ⇒ qualified-only, top-level ⇒ bare kept). End-to-end coverage: `BindingTests/Sources/SwiftBindingsTestLib/CrossModule/CrossModuleShortNameCollision.swift` (`@usableFromInline internal` nested `Data` collision + public `makeCollisionData() -> Foundation.Data`) with the round-trip gate `CrossModuleShortNameCollisionTests.TestMakeCollisionData_RoundTripsBytes`.

**Residual latent gap (not reachable in current code; recorded for the architectural fix, not deferred silently).** Layer 1 closes the *nested* internal-type vector outright (a nested type never contributes a bare short name), and layer 2's module-aware matcher closes the *qualified* cross-module suffix vector for the surviving top-level short names — together the realistic and originally-reported cases. A distinct sub-vector survives, now narrowed to **top-level** internal types only: a top-level current-module internal type whose short name equals a **Swift stdlib spelling that emitters print *unqualified*** (`String`, `Int`, `Bool`, `Double`, …). The module-aware emission gate keeps such a member (the real type is `Swift.String`, module `Swift` ≠ current, so its short name never matches), but emitters write the bare spelling (`let result: String = …`, `load(as: Int.self)`) into the wrapper body, and the text matcher's `(?<!\.)\bString\b` matches it → false-positive strip → silent API loss. This is **not reachable in the code as it exists** — no internal type is named after a bare-emitted stdlib primitive anywhere in the validation libs, BindingTests, or any fixture, and shadowing a stdlib primitive is a recognized Swift anti-pattern — so by the severity rubric it is Low/Info, not P1. The root cause is the same as Finding 1's: the post-processor re-derives a stripping decision *textually* that the semantic, module-aware `InternalTypeReferenceWalker` already makes correctly. The only durable fix is architectural — have the post-processor consult the semantic gate's module-awareness (or de-collide internal short names against the cross-module short names the public surface references) rather than re-deriving it over raw text. A bare-stdlib-name denylist or an ABI-JSON-descriptor heuristic would each be a partial band-aid and were rejected. Left for a scoped owner decision because it changes the post-processor↔emission-gate contract, not R6-1's matcher.

### 2 — `SimulatorOnlyMemberDetector.MatchesThunkBlock` name-only fallback strips a device-needed sibling thunk (P1, device-only crash) — **FIXED**

For property (`Var`) entries the detector deliberately clears the mangled-name hash (`ExtractMembers` sets `patchedMangledName=""` for `kind=="Var"` at `:253`; `Add` stores `Hash==null`). `MatchesThunkBlock` then falls back to requiring only that each `{len}{part}` token of the qualified name appears **somewhere independently** in the thunk block — no adjacency, no single-symbol requirement (`:79–138`). `FilterThunkAssembly` removes any block this returns true for. The probe used swiftc-6.2.4-real iOS-18 slices: a `#if targetEnvironment(simulator)` stored property `Card.id` (sim-only, Hash null) and a normal device method `Card.find(id:)` whose real mangled symbol `_$s8Identity4CardC4find2idS2i_tF` literally contains both `4Card` and `2id` (the `id:` label mangles to `2id`). `Detect` flagged `Card.id`; `MatchesThunkBlock` returned true against `find(id:)`'s device thunk; `FilterThunkAssembly` removed the live `find(id:)` block (RemovedCount=1, target symbol and label both absent from the filtered `.arm64.s`). Because the generated P/Invoke EntryPoint is the thunk symbol, the device/NativeAOT app throws `EntryPointNotFoundException` — sim is unaffected (only the device slice is filtered). `2id` is extremely common (any `id:` label, anything `Identifiable`) and the type token is present in every sibling member's thunk, so the collision is realistic. This file was never reached by the review's wave-3/4 clean bills.

**Fix.** `MatchesThunkBlock`'s name-only fallback (for hashless `Var`/property entries) is now ADJACENCY-aware. A new `MatchesByMangledName` requires the qualified name's dotted parts (`Card.id` → `Card`, `id`) to mangle as a CONTIGUOUS run inside a single thunk symbol — each consecutive part separated from the previous ONLY by Swift nominal-kind / substitution-terminator characters (single uppercase letters such as the `C`/`O`/`V` type-kind suffix), never by another length-prefixed identifier. It anchors on every occurrence of the first part (literal `{len}{name}` form OR a substitution-compressed suffix preceded by an uppercase terminator — preserving the existing `0B17VerificationSheet` substitution case), then `RemainingPartsFollowAdjacently`/`MatchPartAt` verify the rest follow with uppercase-only gaps. This keeps the property's OWN accessor thunk matched and removed for the device slice (`…4CardC2idSivg` — `4Card` adjacent to `2id`, separated only by `C`), while the sibling method thunk (`…4CardC4find2id…` for `find(id:)`) is NOT matched because `4Card` and `2id` are separated by the length-prefixed method name `4find`. The fallback stays load-bearing — precision is tightened, not removed. All 12 pre-existing `FilterThunkAssembly_Fallback_*`/hash tests stay green (every legitimate "should match" case has adjacent parts; both "should NOT match" cases already fail at the first part), and the regression is locked by two new tests in `SimulatorOnlyThunkFilterTests`: `FilterThunkAssembly_Fallback_SimOnlyProperty_DoesNotStripSiblingMethodThunk` (the exact `Card.id` vs `Card.find(id:)` collision) and `DetectThenFilter_SimOnlyProperty_PreservesSiblingDeviceMethodThunk` (the full `Detect` → `FilterThunkAssembly` chain off a synthetic sim-vs-device ABI diff, proving the hashless property entry flows from detection into the filter).

**Integration coverage boundary (assessed, not silently deferred).** The decisive gate for this matching-logic fix is the unit layer above — the correct abstraction for "which thunk block matches." The end-to-end fixture recommended below (#2 — a `#if targetEnvironment(simulator)` member run on `--device`) is **not wireable on the current BindingTests harness**: `nuke binding-tests --device` does not invoke `FilterThunkAssembly` at all. `RunBuildDeviceWrappers` (`build/Build.RuntimeTests.cs:~2890`) regenerates wrappers in simulator-only mode and hand-compiles the device wrapper from UNFILTERED `.arm64.s` via `clang -c`, relying on swiftc error-retry stripping; `Detect`/`ApplySimulatorGuards`/`FilterThunkAssembly` run ONLY inside `SwiftWrapperCompiler.CompileAll` (`--wrapper-architectures all`), the production path the SDK uses (`SwiftWrapperArchitectures=all` default → `RunCompileWrapperOnly`). Adding a sim-only member to BindingTests today would therefore BREAK the device build (the unfiltered sim-only thunk references a device-absent Swift symbol → link failure), not gate this fix. `nuke validate` likewise does not exercise `CompileAll`'s filter (simulator-default wrapper compile; Apple-framework targets hand-build the device slice in a separate pass). The remaining genuine subsystem-level gap — a `CompileAll`-level integration test that builds a real 2-slice xcframework (one shared member + one `#if targetEnvironment(simulator)` thunked member) and asserts the device wrapper links with the sibling thunk retained — is recorded as scoped follow-on test infrastructure: it needs the Apple toolchain and a project-referenced fixture in `Swift.Bindings/tests`, is swiftc-mangling-version-sensitive, and is broader subsystem coverage, not part of closing the R6-2 matching defect (which is fixed and gated above). Independent review (Codex + Grok) confirmed the wiring facts and endorsed the unit layer as the decisive gate for this fix while classifying the `CompileAll` E2E as separate, heavier work.

### 3 — `AbiContractChecker` mis-reads the calling convention for the real emitted P/Invoke shape (P1, crash-class check silently skipped + false positive) — **FIXED**

`ExtractPInvokes` scans **backward** up to 3 lines from `[LibraryImport]` for `[UnmanagedCallConv]` (`:372–389`), and `CallingConvRegex` requires the literal `new ... Type[]` (`:108–110`). The real metadata-accessor P/Invoke (`PInvokeHelperEmitter.cs:683–686`) writes `[LibraryImport(...)]` **then** `[UnmanagedCallConv(CallConvs = new[] { typeof(...CallConvSwift) })]` — LibraryImport-first (the line is never scanned) and target-typed `new[]` (the regex never matches). Two independently-sufficient defects: the backward scan misses the line *after* the LibraryImport, and the regex misses `new[]`. Result: `callingConvention` defaults to `CallConvCdecl` (`:389`). Consequences for a real `$s…Ma` CallConvSwift symbol: (a) `CheckCC001`/`CheckCC002` early-return on `!= "CallConvSwift"`, so the InvalidProgramException crash-class the checker exists to catch is silently skipped (a deliberately non-blittable `SwiftSafeHandle` param produced no SWIFTBIND090 in the probe); and (b) `CheckCC004` fires a spurious SWIFTBIND094 on correct code. The probe isolated each factor: control (UnmanagedCallConv-first + `new global::System.Type[]`) resolves correctly and fires SWIFTBIND090; flipping either order or `new[]` breaks it. The emitted block trips both at once. Note this is a defect in the post-gen *checker*, not the runtime ABI — `new[]` is valid C# the compiler resolves to CallConvSwift correctly. Wired into production at `ModuleEmitter.cs:133`; the unit tests only ever build the happy-path layout (`AbiContractCheckerTests.cs:700–701, 718–719`).

**Fix.** Both independently-sufficient defects closed in `AbiContractChecker.cs`. (1) `ExtractPInvokes` now scans **both directions**: the existing backward pass (for the `[UnmanagedCallConv]`-first main-method layout) plus a forward pass folded into the signature scan that picks up a convention attribute emitted *after* `[LibraryImport]` (only if the backward pass didn't already resolve one; the forward scan stops at this P/Invoke's signature, so it can never absorb the next declaration's attribute). (2) `CallingConvRegex` now recognizes all four emitted `CallConvs` forms — `new global::System.Type[] { … }`, `new Type[] { … }`, target-typed `new[] { … }` (PInvokeHelperEmitter, KvoExtensionEmitter), and the C# 12 collection-expression `[typeof(…)]` (AppleTypesCsEmitter) — via an optional `new …`/`new[]` prefix and a `{`/`[` bracket-pair class. A whole-codebase grep confirmed `AbiContractChecker` is the **only** post-generation parser of these attributes (every other `UnmanagedCallConv`/`LibraryImport` site is an emitter), so there is no sibling instance of the pattern to fix. Five `AbiContractCheckerTests` added under the `R6-3` region pin: the metadata-accessor layout reads CallConvSwift (`Extract_CallConvAfterLibraryImport_TargetTypedNewArray_ReadsSwift`), no false CC-004 on it (`Validate_MetadataAccessorHelper_NoFalseCC004`), the `new[]` (`Extract_TargetTypedNewArray_CallConvFirst_ReadsSwift`) and collection-expression (`Extract_CollectionExpressionCallConvs_ReadsSwift`) forms, and the re-enabled CC-001 fires on a non-blittable param under the LibraryImport-first layout (`CC001_CallConvAfterLibraryImport_NonBlittable_DetectsViolation`). All 51 `AbiContractCheckerTests` green (46 prior + 5 new). The checker emits SWIFTBIND diagnostics to the log without changing emitted code, so the unit layer — exercising the exact attribute text the emitters produce — is the decisive gate; BindingTests assert runtime behavior, not generation-time log warnings. Coverage gap #3 below is closed by these tests; recommended-fixture #3 (a `$s…Ma` member as an integration witness) remains a nice-to-have, not a gate.

### 4 — `TypeLowering.LowerOptional` ignores Swift's spare-inhabitant rule (P2, currently muted, latent corruption) — **FIXED**

`LowerOptional` unconditionally appends a +1 integer tag slot and +1 byte for any non-class value-type inner (`:367–377`), with no spare-inhabitant check. Swift only adds the discriminator tag for the fixed-width scalars in `ModuleProcessor`'s `s_optionalTagAddingScalars` set (the oracle Finding 44 fixed for *struct fields*); `Bool`, frozen simple enums, and pointers fold `.none` into a spare inhabitant and keep the **same** size with **no** tag. Direct call into the built dll: `Optional<Bool>`→2 slots/2 bytes (Swift 1/1), `Optional<OpaquePointer>`/`Optional<UnsafeRawPointer>`→9 bytes (Swift 8), `Optional<frozen-enum>`→2/2 (Swift 1); `Optional<Int>`→9 is correct (control). swiftc `MemoryLayout -O` confirms the ABI. The impact is muted today, not corrupting: Optional **returns** are rejected before lowering matters (`NativeThunkEmitter.cs:227–231`), and the inflated 2-slot **param** result trips `AreAllParametersLowerable`'s `Slots.Count > 1` reject (`:638–639`), so these params over-decline to the `@_cdecl` wrapper rather than mis-thunking — correctness-safe but performance-losing, and a latent corruption hazard if any future caller consumes `LowerOptional`'s `TotalByteSize`/slot list directly past the `Slots.Count>1` gate. Finding 44 fixed the parser-side oracle (`ClassifyFieldType`) but explicitly said the trace's end was "not reached"; `LowerOptional` is that un-reached register-lowering oracle, still carrying the un-guarded tag. The two oracles should share the spare-inhabitant rule rather than reimplement Optional layout divergently.

**Fix (shared classifier + decline the spare-inhabitant inners).** The two oracles now consult one source of truth: a new `OptionalAbiClassifier` (`src/Swift.Bindings/src/TypeDatabase/OptionalAbiClassifier.cs`) owns the tag-adding scalar set (the fixed-width integer/float scalars — `Int`/`UInt` and their sized forms, `Float`, `Double`, `CGFloat` — with `Bool` and the pointer types intentionally EXCLUDED) and exposes `HasAppendedOptionalTag(swiftTypeName)`. `ModuleProcessor.ClassifyFieldType` dropped its private `s_optionalTagAddingScalars` set and calls the shared classifier; `LowerOptional` now, after the existing class check (`Optional<class>` = 1 nullable-pointer slot, unchanged), **declines** — `return null` — for any inner the classifier rejects, before it ever fabricates a tag. The decline (not a faithful 1-slot pass) is the correct move because the thunk path forwards raw registers and has **no** spare-inhabitant encode/decode layer; routing those Optionals to the `@_cdecl` wrapper lets its managed marshalling encode them. Tag-adding scalars still lower exactly as before: `Optional<Int32>` stays 2 slots / 5 bytes, `Optional<Double>` stays its int+float pair, `Optional<Int>` stays 2-slot — both Codex and Grok independently confirmed the divergence is ONLY on spare-inhabitant payloads and that the integer/float Optionals must remain 2-slot. Locked down by four tests in `TypeLoweringTests.cs`'s Optional region: `LowerReturnType_OptionalBool_DeclinesToCdecl`, `LowerReturnType_OptionalPointer_DeclinesToCdecl` (Theory over `OpaquePointer`/`UnsafeRawPointer`/`UnsafeMutableRawPointer`), `LowerReturnType_OptionalSimpleEnum_DeclinesToCdecl` (a frozen simple enum), and the control `LowerReturnType_OptionalInt32_TagAddingScalarStillLowers` (asserts 2 slots, a 4-byte + 1-byte tag, `TotalByteSize == 5`); the pre-existing `Optional<Int>`/`Optional<Double>`/`Optional<Class>` tests stay green and unchanged. This is the minimal sound move — full unification of all three layout oracles (`ClassifyFieldType`, `LowerOptional`, `FrozenStructHandler.TryComputeOptionalInlineSize`) behind one `SwiftValueLayout` is the separately-documented S08 work, out of scope here; what closes this finding is that the register oracle no longer disagrees with the field oracle.

### 5 — `DepModuleCollisionDetector.SwiftPublicTypeRegex` modifier-blindness past `final` (P2, wrapper compile failure) — **FIXED**

`SwiftPublicTypeRegex` (`:55–57`) tolerates only `final` adjacent to the access keyword. A C# regex probe (verbatim source regex) plus swiftc-6.2.4 emission confirm: swiftc emits canonical `indirect public enum Modular {` and `nonisolated public class Noniso {` (modifier **before** `public`), and the regex returns False on both — `HasSwiftPublicTypeWithName` returns false, `SwiftWrapperCompiler.PrecompileCollidingModule` (`:2438`) never strips the `<Module>.` qualifier, and the bound wrapper fails swiftc with `type '<Module>' has no member …`. This is the regex-modifier-blindness class the review flagged for the SwiftSyntax parser (Finding 26) but in a different, unaudited C# file. Two corrections to the original claim, neither changing the verdict: swiftc emits the modifier *before* `public` (the probe verified the regex misses the real emitted form too), and the `dynamic` arm is **refuted** — `dynamic` is a member-level modifier swiftc rejects on a type declaration, so it can never appear in a swiftinterface. A real dependency whose name equals an exported `public indirect enum`/`public nonisolated class` of the same name slips the detector (swiftc emits only a non-fatal shadowing warning; the file's own GTMSessionFetcher precedent shows same-name module/type pairs ship in practice).

**Fix.** `SwiftPublicTypeRegex` now tolerates a run of declaration modifiers on **either** side of the access keyword. The literal `final?` allowance is replaced by a shared `TypeDeclModifiers` fragment — `(?:(?:final|indirect|nonisolated)(?:\s*\([^)]*\))?\s+)*` — spliced both before `(?:public|open)` and after it, so the canonical `indirect public enum`, `nonisolated public class`, and `public final class` orderings all match, as does `nonisolated(unsafe) public class` (the optional `(…)` arm covers the parenthesized `nonisolated` argument). The captured module name keeps its trailing `\b` so `public class FooBar` still does not match for module `Foo`. The `dynamic` arm is deliberately absent (it is a member-only modifier swiftc rejects on a type declaration — recorded in the code comment). Locked by `DepModuleCollisionDetectorTests` `[InlineData]` rows for `indirect public enum Modular`, `nonisolated public class Noniso`, and `nonisolated(unsafe) public class Noniso`, plus a negative row asserting `indirect public enum ModularKit` does **not** match module `Modular` (trailing word-boundary). The `final`/`@objc`/word-boundary cases stay green.

## Checked & refuted

- **`SwiftInterfaceAccessParser` internal-member regex modifier-order / missing `package`** (`SwiftInterfaceAccessParser.cs:45`, P2). **Refuted.** The claim's headline string `internal static final func foo()` is invalid Swift (swiftc: "static declarations are already final"); swiftc-6.2.4's real orderings are `final internal func` and `internal static func`, and `InternalFuncRegex` is **unanchored** so a leading `final` is harmless — the built parser's `GetInternalMembers` captured both real shapes against a production swiftinterface, and existing tests (`SwiftInterfaceAccessParserTests.cs:18,43`) already use `final internal func`. The `package` sub-claim is true only at the regex layer but is not a defect: `package` members are stripped from the public swiftinterface entirely (the parser's only input) and in ABI JSON carry `isInternal:true`, caught by `IsNodeModuleInternal` (`SwiftABIParser.cs:259`) with zero regex involvement. A separate incidental anomaly surfaced — package *methods* emitted as public C# while package *properties* and *free functions* are suppressed despite all carrying `isInternal:true` — which is orthogonal to the regex claim and worth a separate look, but does not validate this finding.
