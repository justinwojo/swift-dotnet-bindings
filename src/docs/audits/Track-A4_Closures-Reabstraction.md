# Track A4 Audit — Closures / Optional-Closure / Reabstraction

**Scope:** Closure marshalling across both emission engines — the string-emitter (`ClosureEmitter.*`, `MethodClosureBridge`, `NestedClosureBridge`, `GenericClosureBridgeEmitter`) and the projection engine (`ClosureProjection`, `OptionalProjection`) — plus the C#↔Swift `@_cdecl`/`@convention(c)` adapter ABI, escaping/optional-closure lifetime, throwing-closure error channels, and the Mono-JIT `!ji->async` return-marshalling pattern.

**Overall risk rating: 5 / 5 (Critical).** Confidence: high. Six defects confirmed by probe (five P0, one P1), every one demonstrated either at the runtime level (faithful SIGSEGV/SIGABRT/leak probes) or against the generator's own committed output in `BindingTests/output/`. The dominant theme is a class of crash-on-error bugs: a managed exception or a Swift-signalled failure crossing the C#↔Swift boundary aborts the process, and the throwing/indirect-return paths additionally dereference NULL or uninitialized storage. Five of six confirmed defects are unguarded boundary-crossing / null-deref / lifetime bugs that crash rather than fail gracefully, and they sit on live, shipped emission paths. Confidence is high on the *defects*; it is moderate that the full population is covered (see Coverage gaps) — the per-track cap left a large block of credible P1/P2 candidates probe-unverified.

### 1.1 Throwing closure with non-primitive return derefs NULL — `ClosureEmitter.SwiftWrapper.cs:492` (P0)

For an `@escaping` throwing closure whose return type is non-primitive (String, struct, class, simple enum), `BuildAdapterClosureBody`'s throwing branch (lines 481-509) computes `let rawResult = GetSwiftReturnConversion(returnType, "cdecl(...&errorPtr, context)")` **unconditionally** (line 492-493), *then* checks `if let error = errorPtr { throw ... }` (line 500-502). For a non-primitive return `GetSwiftReturnConversion` emits `…assumingMemoryBound(to: T.self).move()` (struct/String) or `Unmanaged<T>.fromOpaque(…).takeUnretainedValue()` (class). On the C# failure path the callback does `*errorOut = swiftResult.Failure; return default;` — a NULL `void*` with no result buffer — so the Swift adapter runs `NULL.move()`/`Unmanaged.fromOpaque(NULL)` before the error is ever observed. Confirmed by replicating the exact adapter (real generated form at `SwiftBindingsTestLib.Wrapper.swift:15350`): SIGSEGV in `__swift_memcpy16_8` from the `.move()` line; the Int32 control (direct scalar, no deref, `Wrapper.swift:15332`) survives. The defect reaches the idiomatic convenience overload too (`CallThrowingWithParam(Func<int,string>)` → `FromFailure` → same path). Primitive returns are immune. Fix: check `errorPtr` *before* consuming the result pointer; same hazard in the class form (lines 613-617).

### 1.2 Throwing-closure *return* emits the Mono `!ji->async` crash lambda — `ClosureEmitter.Throwing.cs:218` (P0)

`EmitThrowingClosureReturnMarshalling` declares `invokeThunkPInvokeName` (line 176) but never references it in the body; it unconditionally emits `{delegateType} _invoker = (...) => { var _fp = (...)_closureWrapper.FunctionPointer; var _rawResult = _fp(...); }` — a `delegate* unmanaged[Swift]` call from inside a lambda/display class, the exact pattern the non-throwing path was rewritten to avoid (`ClosureEmitter.cs:256-272`, documented "Mono JIT crashes with !ji->async … from display class methods"). The safe throwing invoker class **is** generated (`ClosureEmitter.InvokeThunk.cs` has full `isThrowing` support; `WrapperEmitter.Marshalling.cs:923-947` emits it) and the callers pass a real thunk name (`WrapperEmitter.Return.cs:222/408/688`) — both are silently discarded. Decisive proof in the generator's committed output for the in-repo fixture `makeAlwaysThrowingIntClosure() -> () throws -> Int32`: `SwiftBindingsTestLib.cs:24972-24982` emits `_ClosureInv_9A486290` (dead, referenced only at its own definition) while `25006-25021` emits the crash lambda. Note this fixture has no end-to-end runtime test, so no live SIGABRT was observed — the structural defect is conclusive but a Simulator runtime gate is missing. The throwing emitter is also passed only the entry point, not the helper name the invoker class needs — both must be threaded through.

### 1.3 Struct-param / non-frozen-param closure *return* emits the crash lambda — `ClosureEmitter.StructParams.cs:51` (P0)

`EmitClosureReturnMarshallingWithStructParams` and `…WithNonFrozenParams` both emit a capturing lambda whose body calls the native fp (`return _fp(_arg0Buffer, _swiftSelf)`), confirmed by live generator probes for frozen `((Config)->Int)` and non-frozen `((Widget)->Int)`. This is the same `!ji->async` display-class crash shape; the plain path diverges to `_inv.Invoke`. **Correction to the original sub-claim:** the framing "the mitigation is discarded *even when a thunk exists*" is inaccurate — `CanUseInvokeThunk` returns false for any struct-arg closure (`IsInvokeThunkCompatibleArg` accepts only Cdecl-primitive / simple-enum / complex-enum, `InvokeThunk.cs:496-506`), so `GetInvokeThunkInfoIfAvailable` always returns null and `invokeThunkPInvokeName` is genuinely dead, not a silently-dropped usable thunk. The substantive defect stands: **no** invoker-class mitigation path exists for struct-param closure returns under `@_cdecl` on Mono JIT. The correct fix is broader than threading a param — it requires extending invoke-thunk support to struct args (marshal the struct buffer through the `@_cdecl` thunk so the CallConvSwift call moves into a regular method body). Caveat: verified at the emitted-code / static-crash-pattern level, not via a live Mono-JIT SIGABRT.

### 1.4 Main escaping-closure callback has no try/catch — `ClosureEmitter.cs:132` (P0)

`EmitEscapingClosureCallback` emits the `[UnmanagedCallersOnly]` body as `var del = …; <returnStatement>;` with no guard; `returnStatement` invokes the arbitrary user delegate directly. Live caller: `WrapperEmitter.Marshalling.cs:910` (the non-throwing escaping/non-escaping path of the main method-wrapper pipeline). Both probes (CoreCLR JIT and NativeAOT) abort at exit 134 when the user delegate throws; the Swift "callback returned normally" line never prints and the outer managed catch never fires. The try/catch control variant returns cleanly (exit 0), isolating the missing guard as the load-bearing cause. Fix-scope note: a bare swallow drops the user's exception silently — convert to a defined outcome (route to `SwiftError*` for throwing closures; FailFast-with-diagnostic or documented swallow for non-throwing). This is the same defect class as 1.5 and 1.6, and `EmitConventionCCallback` (`WrapperEmitter.Marshalling.cs:1003-1020`) shares the unguarded shape.

### 1.5 Throwing callback only handles `SwiftResult.Failure`, not a thrown exception — `ClosureEmitter.Throwing.cs:86` (P0)

The throwing callback does `var swiftResult = del(...); if (swiftResult.IsFailure) { *errorOut = swiftResult.Failure; … }` with no try/catch. The cooperative `FromFailure` path is safe (probe exit 0), but an actual `throw` — or a latent `NullReferenceException` — unwinds out of `[UnmanagedCallersOnly]` (probe exit 134, SIGABRT). The throwing path is exactly where users are most likely to `throw`, and the error channel (`SwiftError* errorOut`) already exists and should be used. The generated *simplified* overload (`ThrowingClosureSimplificationEmitter`) only catches `Swift.SwiftErrorException` — a `NullReferenceException` escapes it into the unguarded `del()`. The async-throwing path *does* forward exceptions via Task machinery, making the synchronous omission an inconsistency, not an ABI constraint. Coverage gap: `ClosureEdgeCaseTests.cs:222-262` uses only `FromSuccess`/`FromFailure`; the thrown-exception direction is untested.

### 1.6 Indirect-return callback: no try/catch + uninitialized result buffer — `ClosureEmitter.IndirectReturn.cs:83` (P0)

All six branches (plain string `:83`, optional string `:98`, array string `:118`, ObjC-bridged `:145`, class `:160`, default `:180`) emit `var result = del(...);` with no guard, then marshal into `indirectResult` only at the trailing write. Reachable: `WrapperEmitter.Marshalling.cs:896-899` dispatches here for `() -> String?` (`RequiresIndirectReturnMarshalling` → true). Hazard 1 (boundary crash): `del()` throwing → exit 134. Hazard 2 (unique to indirect return): if `del` throws before the buffer write, the Swift adapter's `let result = resultBuf.assumingMemoryBound(to: T.self).move()` (`ClosureEmitter.SwiftWrapper.cs:476`) reads never-written storage. Probes: zeroed buffer reads as benign `.none` (works by accident); `0xAB` bytes read as a *valid* String (silent corruption); `0xFF`/stale-heap-String bytes → SIGSEGV in `swift_retain` (exit 139). The all-zero-masks-it case is allocator-incidental and shape-specific — class/struct returns lack a benign all-zero representation.

### 1.7 NestedClosureBridge inner-trampoline leaks one box per invocation — `NestedClosureBridge.cs:668` (P1)

`EmitOuterAdapterBody` emits `let __innerBox = Unmanaged.passRetained(__op as AnyObject).toOpaque()` (+1) *inside* the per-outer-call adapter body; the inner trampoline reads it via `takeUnretainedValue()` (no balance) at line 486, with a comment self-describing it as a "bounded leak (one AnyObject per invocation)". Per-invocation = unbounded. The C# side (`SwiftBindingsTestLib.cs:230715-230729`) also never frees `innerContext`; the `_box_N` owner-token mechanism (`:570-573`) frees only the *outer* GCHandle. Real-generator end-to-end probe: live count == N exactly (1000, 100000); the single missing `Unmanaged<AnyObject>.fromOpaque(innerContext!).release()` control returns to 0. For a per-element enumeration callback that supplies an inner continuation, this leaks one box plus the inner closure's entire captured environment per element, forever. A correct fix must release exactly once per box at the right lifetime point (the inner closure can be called zero or many times per box), e.g. `takeRetainedValue()` only if single-shot, else an owner-token analogous to `_box_N`. Note `NestedClosureBridgeTests.cs:664-680` asserts the current behavior and bakes in the "bounded" assumption.

## 2. Inconclusive / needs deeper probe

### 2.1 `ClosureProjection` escaping callback has no try/catch (`ClosureProjection.cs:200`) — split vote

Both reviewers agree a true unguarded-boundary defect exists, but disagree on attribution. The literal code in `ClosureProjection.CallbackDeclarations` *is* unguarded (no try/catch, no `errorOut`), and the three sibling bridges (`MethodClosureBridge`, `NestedClosureBridge`, `GenericClosureBridgeEmitter`) all guard the same boundary. **However**, grep + generation probe show no production emitter reads `ITypeProjection.CallbackDeclarations` — it is referenced only by unit tests (the `MethodMarshalPlan` projection-driven emission is not yet wired). The probe-generated `func run(_ cb:@escaping (Int)->Int)` callback was produced by `ClosureEmitter.EmitEscapingClosureCallback` (the `readonly` static-field shape, attributable to `ClosureEmitter.cs:169`), *not* `ClosureProjection`. So: the named file is effectively dead for emission, but the **real, live** equivalent gap is already captured as confirmed finding 1.4 (`ClosureEmitter.cs:132`). Net: the *concern* is real and confirmed elsewhere; this specific localization in `ClosureProjection.cs` is test-only. Treat as resolved-by-1.4; no separate fix needed in `ClosureProjection` unless/until the projection emission path goes live.

## 3. Deferred (candidate, unverified)

These are credible candidates not probed due to the per-track cap. Listed so none is silently dropped; severity is the finder's estimate.

1. **`MethodClosureBridge.cs:952` (P1)** — Cdecl trampoline silently swallows C# exceptions from the user closure (`catch { return 0; }` for Bool, `catch { }` for void), fabricating success/`false` to Swift instead of converting to a Swift error via `SBW_CreateError` (as `GenericClosureBridge` does). Silent control-flow corruption (a predicate that throws is treated as "no match").
2. **`ClosureProjection.cs:154` (P1)** — `GetReturnPlan` emits a raw lambda calling the native fp (the `!ji->async` shape `ClosureEmitter` avoids). *Note: separately probed and refuted as a live crash because the projection return path is unreachable for closure returns (see §5.3); listed here only because the deferred list carried it.*
3. **`ClosureProjection.cs:306` (P1)** — `BuildFuncPtrType` uses `unmanaged[Swift]` while the callback static field is `unmanaged[Cdecl]`, with context passed as a trailing positional arg (Cdecl shape, not Swift CC). Potential CC mismatch / arg mis-placement *if this path were live*.
4. **`GenericClosureBridgeEmitter.cs:235` (P1)** — Concrete value-type closure args boxed via `passUnretained(_argN as AnyObject)` then read via `MarshalBorrowedFromSwift<T>` — `passUnretained` on a transient box is a lifetime hazard, and value-type reads are at the wrong offset (box header vs in-memory rep). Possible dangling/garbage for concrete value-type closure args.
5. **`ClosureProjection.cs:62` (P1, dup)** — Escaping GCHandle leak in projection path; "matches MethodClosureBridge's pattern" comment is false. *Refuted as a live leak (§5.4): projection path is bypassed for escaping closure params.* Listed for completeness.
6. **`GenericClosureBridgeEmitter.cs:498` (P1)** — Returning callback leaves `resultBuf` uninitialized if the C# closure throws, while a non-throwing method unconditionally does `MarshalFromSwift<T>(resultBuf)` on `NativeMemory.AlignedAlloc` (not zeroed). Eligibility (`IsMethodGenericClosureEligible`) gates on *closure* throws, not *method* throws. Uninitialized-buffer read for class/`ISwiftObject` T.
7. **`ClosureEmitter.cs:379` (P1)** — Closure-return *fallback* (no invoke thunk) emits the same crash lambda. Confirmed to ship in production 2× (`SwiftBindingsTestLib.cs:25006`, throwing closure returns) per finding 1.2's investigation; this is the actual live raw-lambda surface for the `!ji->async` concern.
8. **`NestedClosureBridge.cs:1046` (P1)** — Purely non-escaping outer nested closures allocate a raw GCHandle per call but free is gated on `anyEscaping` → deterministic per-call GCHandle leak; the "matches MCB output" comment is claimed false (MCB always emits the disposing finally).
9. **`GenericClosureBridgeEmitter.cs:769` (P1)** — Returning method frees `resultBuf` (`AlignedFree`) in a finally that always runs, after `MarshalFromSwift<T>` may have *adopted* the buffer pointer (some `ISwiftObject` wrappers) → UAF + double-free, plus `AlignedAlloc` vs `NativeMemory.Free` allocator mismatch.
10. **`ClosureEmitter.Throwing.cs:261` (P1)** — Throwing-closure return with class/ObjC-class return: gate (`IsDirectInvokeReturnSupported`) allows class returns (`:1628`) but `EmitThrowingClosureReturnMarshalling` has no class branch → `FromSuccess(_rawResult)` with `_rawResult` a `void*` → CS1503 compile break. Latent (only primitive fixture exists).
11. **`ClosureEmitter.Throwing.cs:176` (P1)** — Throwing return ignores the available invoke thunk (the dead-param half of confirmed finding 1.2; restated in the deferred list).
12. **`ClosureEmitter.Throwing.cs:259` (P1)** — Simple-enum throwing-closure return: gate allows simple enums (`:1624`) but emitter falls through to bare `else` `FromSuccess(_rawResult)` where `_rawResult` is the underlying scalar → CS1503/CS0266. Same root as #10.
13. **`MethodClosureBridge.cs:952` / NCB (P2)** — Same exception-swallow as #1, framed as silent error loss vs. `GenericClosureBridge`'s `errorOut` propagation.
14. **`GenericClosureBridgeEmitter.cs:242` (P2)** — Wrapper unconditionally emits `throw` but gates `throws`/`out SwiftError` on `methodDecl.Throws`; a `rethrows` function whose ABI `throwing` flag is false → uncompilable Swift / silent error loss. Hinges on `rethrows → throwing=true`, unasserted.
15. **`NestedClosureBridge.cs:484` / `:668` (P2, dup of confirmed 1.7)** — Same per-invocation box leak, restated at P2.
16. **`ClosureProjection.cs:1` (P2)** — Architectural: four+ parallel closure marshalling engines re-derive escaping/CC/leak/return policy independently and have already drifted (the confirmed findings *are* the drift). Maintainability/correctness-risk surface; the file's own NOTE acknowledges it.
17. **`NestedClosureBridge.cs:837` / MCB (P2)** — MCB/NCB cdecl callbacks silently swallow all managed exceptions (`catch {}` / `catch { return 0; }`); gated to non-throwing closures so no `SwiftError*` channel to carry the failure.
18. **`ClosureHandler.cs:635` (P2)** — `IsMethodGenericClosureEligible` gates on closure-throws but not method-throws; a throwing closure in a non-throwing method emits an invalid `throw` in a non-throwing Swift context → compile break (caught by the fail-closed gate, but should be screened earlier).
19. **`ClosureEmitter.SwiftWrapper.cs:1313` (P2)** — `HasConventionCInMangledName` uses an over-broad `Contains("XC")` substring match → potential `@convention(c)` mis-classification / wrong wrapper shape. The sibling `ClosureHandler.IsConventionC` notes this is only safe for a single closure param.
20. **`ClosureHandler.cs:1599` (P2)** — `CanInvokeReturnedThrowingClosure` docstring points at `EmitClosureReturnMarshalling` but the throwing case routes to `EmitThrowingClosureReturnMarshalling` (a strict subset of branches) — the mis-pointed "load-bearing" contract is the maintainability root behind #10 and #12.
21. **`ClosureEmitter.Throwing.cs:176` (P2)** — Dead `invokeThunkPInvokeName` param (maintainability half of 1.2).
22. **`ClosureHandler.cs:161` (P2)** — `@MainActor`/`@Sendable` closure attributes are detected (`IsMainActor`, `IsSendable`) but have **zero callers** in the generator — adapters can run `@MainActor` closures off the main thread. Latent UI-thread / data-race correctness bug, not a guaranteed crash.

## 5. Checked & refuted

So future agents do not re-chase these. All four were probed end-to-end (real generator + emitted-output inspection).

### 5.1 "Projection path treats Optional<Closure> as non-escaping (bare `_isEscaping`)" — `ClosureProjection.cs:60` — REFUTED
The code observation is accurate (`ClosureProjection` branches only on `_isEscaping`; `ProjectClosure` feeds the raw flag), but Optional<Closure> *parameters* never reach the projection: `WrapperEmitter.Marshalling.cs:500-501` does `if (IsOptionalClosure(...)) continue;` before the projection path, and `EmitClosureMarshalling` uses the canonical `IsEffectivelyEscaping`. Generated output for `setOpt(((Int32)->Void)?)` is byte-for-byte the escaping shape (GCHandle.Alloc + `_SBClosureCtx` box + transfer flag) — identical to the explicit `@escaping` control. No thin function pointer, no UAF.

### 5.2 "`TypeProjectionFactory.ProjectClosure` uses raw `IsEscaping`" — `TypeProjectionFactory.cs:505` — REFUTED
Same root as 5.1. The bare-flag construction is real but latent/harmless because the projection path is gated off upstream for optional closures (and OptionalProjection does not delegate `GetParameterPlan`/`CallbackDeclarations` to the inner closure). End-to-end generation of `setHandler`/`executeIfPresent` emits the full escaping treatment.

### 5.3 "`ClosureProjection.GetReturnPlan` emits the Mono `!ji->async` lambda" — `ClosureProjection.cs:153` — REFUTED (as a live crash)
The raw-lambda return shape is real, but `GetReturnPlan` is unreachable for closure returns: its sole production caller `WrapperEmitter.Return.cs:934` (`TryEmitReturnViaProjection`) bails at `:916` (`if (IsClosure(returnArg)) return false;`), and `ClosureProjection` does not override `GetReturnElementConversion`/`GetReturnContainerConversion` (so nested-in-container closures also can't reach it). `makeAdder` generates the mitigated `_ClosureInv_*` + `_inv.Invoke` shape; whole-file grep of the 5.3 MB generated output: `closureResult` = 0, invoker-class marker = 16. (The *live* raw-lambda surface is `ClosureEmitter.cs:374-390`, deferred item #7.)

### 5.4 "Escaping closure GCHandle permanently leaked in projection path" — `ClosureProjection.cs:62` — REFUTED
Escaping closure *parameters* are handled by `EmitClosureMarshalling`, not the projection (`EmitTypeConversions` only routes `IsConvertibleType`/optional-existential/native-remap types to the projection; a `ClosureTypeSpec` is none). Generated C# carries the `valueTransferred`-flag + finally-free; the Swift wrapper boxes the context via `_sbWrapClosureContext` whose `_SBClosureCtx.deinit` upcalls `DestroyClosureContext` → `GCHandle.Free` exactly once. The projection's leak branch is real but dead for escaping closure params.

## 6. Coverage gaps — what this track did NOT reach

- **No live Mono-JIT Simulator run for the three `!ji->async` return findings (1.2, 1.3, and deferred #7).** All three are confirmed at the emitted-code / static-crash-pattern level (and against committed generator output), but none was executed on an actual Mono JIT simulator to observe the SIGABRT. The crash linkage rests on the codebase's own documentation of the pattern plus structural match — strong, one step short of a live repro. `makeAlwaysThrowingIntClosure` has no end-to-end test, so 1.2 has no runtime gate at all.
- **GenericClosureBridge deferred items (#4, #6, #9, #14) entirely unprobed.** Value-type boxing lifetime, uninitialized result buffer on throw, AlignedFree-after-adopt UAF/double-free, and the `rethrows`/`throwing`-flag gate are all credible P1s with no compile or runtime probe. The GenericClosureBridge surface is the least-verified emission engine in this track.
- **MethodClosureBridge / NestedClosureBridge exception-swallow (deferred #1, #8, #13, #17, #18)** — the silent-error-loss behavior was read in source but not demonstrated with a runtime probe showing Swift proceeding on a fabricated result.
- **`@MainActor`/`@Sendable` enforcement gap (#22)** — confirmed dead-code by grep but not demonstrated as an off-main-thread invocation at runtime.
- **Async closures** — the async path (`ClosureEmitter.Async.cs`, `AsyncMethodGenericBridgeEmitter`) was touched only tangentially (noted as the *correct* exception-forwarding contrast in 1.5). Async-specific marshalling, cancellation, and continuation lifetime were not audited.
- **Cross-engine drift table (#16)** was scoped but not produced as a deliverable — only the concrete drifts surfaced as findings.

7. **Nested-closure leak under repeated outer invocation (locks 1.7).** Swift: `func forEach(_ count: Int, _ body: @escaping (Int, @escaping () -> Void) -> Void) { for i in 0..<count { body(i) {} } }` with the inner closure capturing a deinit-tracked sentinel.
