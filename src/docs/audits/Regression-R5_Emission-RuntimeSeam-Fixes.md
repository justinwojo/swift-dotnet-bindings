# Regression Audit R5 — Phase-1 Emission + Runtime-Seam Fixes (Sessions 3 & 5)

**Scope:** Regression hunt over commits `c4d260fc` and `9ae9c2c0` — runtime-flavor injection (`SwiftRuntimeInfo`), cache-first dispatch + the de-reflected borrowed-marshal finalizer seam (Finding 56a), and generator emission hardening across enums, frozen-struct layout, and existential degradation. Surfaces audited: `SwiftMarshal.cs`, `ISwiftObject.cs`, `SwiftRuntimeInfo.cs`, `RuntimeContract.cs`, and the witness-dispatch / enum / module-init emitters.

**Overall risk: 3 / 5** (medium; high confidence). Two defects are probe-confirmed. One is a latent runtime-crash bug with a clear ABI-mismatch failure mode (`EntryPointNotFoundException`); the other is a diagnostics-degradation bug (poisoned-type cascade) that masks an otherwise-correct fail-fast message. Neither fires on a clean, current build today — both require a specific input shape or misconfiguration — which is why overall risk is medium rather than high.

**Confirmed defects: 2.** Of those, **1 is a true regression** introduced by this track (the `SwiftRuntimeInfo` cctor-throw poisoning, new in `c4d260fc`) and **1 is a pre-existing-unaudited defect** surfaced (not introduced) by this track — the witness-dispatch index divergence is structural and not newly created by these commits, though the commit's own comment now falsely *claims* lockstep.

**Headline issue:** the three witness-dispatch walks do **not** index protocol methods in true lockstep — the Swift wrapper walk dedups on the raw Swift type-spec while both C# walks dedup on the projected C# type, so two method overloads that collapse to `Swift.AnyType` on the C# side consume one index there but two on the Swift side, shifting the SBW symbol index of any later dispatchable method and producing an `EntryPointNotFoundException` at runtime.

### 1a. Witness-dispatch method index is not in true lockstep (AnyType-collapse divergence) — **FIXED**

**`WitnessDispatchEmitter.cs:2491` · P1 · not a regression (pre-existing, surfaced by this track)**

The commit factored protocol-member *eligibility* into a shared predicate (`IsMethodWitnessDispatchEligible`) so all three witness-dispatch walks agree on *which* members get an index, and added inline comments asserting the SBW method index is now in lockstep. The index agreement does **not** hold, because the running `methodIndex` is incremented per *unique dedup key* and the three walks still use **two different key functions**. The Swift wrapper walk keys on `WitnessDispatchEmitter.GetMethodKey` — `method.Name` plus the **raw** `SwiftTypeSpec.ToString()` of each parameter. Both C# walks (`ProtocolProxyEmitter.SwiftObject.cs:608` and `ProtocolProxyEmitter.InterfaceImpl.cs:112`) key on `ProtocolSignatureHelper.GetMethodSignatureKey` — the **projected** `CSharpTypeName.FullyQualifiedName`.

For two protocol method overloads whose parameter types have distinct Swift specs but both resolve to `AnyType` (any unresolved/unsupported type — `GetTypeRecordOrAnyType` returns the single shared `AnyType` record whose C# name is `Swift.AnyType`), the Swift walk treats them as two distinct keys (consuming two indices) while the C# walks collapse them to one key (one index). Because the index is assigned (`idx = methodIndex++`) **before** the dispatchability classification, any later dispatchable required method gets a different SBW index baked into its symbol on the Swift `@_cdecl` side versus the C# call site.

The probe loaded the actual Debug `Swift.Bindings.dll` and replicated each walk's index-assignment loop using the real, reflected key functions over `[f(UnknownModule.Foo), f(UnknownModule.Bar), g(Swift.Int)]`:

```
f(UnknownModule.Foo): Swift key = "f(UnknownModule.Foo)"; C# key = "f(Swift.AnyType)"
f(UnknownModule.Bar): Swift key = "f(UnknownModule.Bar)"; C# key = "f(Swift.AnyType)"
g(Swift.Int):         Swift key = "g(Swift.Int)";          C# key = "g(long)"
Distinct Swift keys = 3; distinct C# keys = 2
SBW index for trailing g: Swift wrapper = 2 (SBW_<Proto>_method_g_2);
                          C# P/Invoke   = 1 (SBW_<Proto>_method_g_1).  DIVERGE.
```

Causal chain, all verified in source: eligibility (`WitnessDispatchEmitter.cs:1073-1078`) excludes only constructors / static / `@objc`-optional, so both unresolvable-param overloads are eligible; the index is assigned before classification and gated by the divergent key (`WitnessDispatchEmitter.cs:276` vs `ProtocolProxyEmitter.SwiftObject.cs:612` and `InterfaceImpl.cs:115`); the AnyType collapse comes from `GetTypeRecordOrAnyType` (`TypeDatabaseExtensions.cs:96-105`) → `CSharpTypeName` `Swift.AnyType` (`CSharpTypeName.cs:115`); the divergent `idx` is baked into the symbol on both sides via `GetAccessorSymbol(...)` (`WitnessDispatchEmitter.cs:1107-1110`, `ProtocolProxyEmitter.SwiftObject.cs:627`); the ABI parser preserves both overloads as distinct `MethodDecl`s and all three walks iterate the same `protocolDecl.Methods`, so the divergence is purely in the key function. The `SwiftObject.cs` secondary `emittedCSharpKeys` dedup runs *after* the index is assigned and cannot realign it.

Net: a required dispatchable method declared after such an overload pair gets a mismatched SBW index — `EntryPointNotFoundException` at runtime, not a compile error. The commit comment at `WitnessDispatchEmitter.cs:2489` claiming `GetMethodKey` "mirrors `ProtocolSignatureHelper.GetMethodSignatureKey`'s default" is misleading: matching the async-suffix rule does not make the param-type key domains equal (raw-Swift vs projected-C#), which is exactly the divergence axis. **Fix direction (not in scope to apply):** gate the index counter by the *same* key on all three walks — either project the Swift walk's param key to the C# name (so two AnyType overloads consume one index) or key all three on the raw Swift spec; the gating key must be identical across producer and both consumers.

**Fix (key the slot index on the raw-Swift requirement key across all three walks).** The second of the two fix directions was taken — the SBW slot index is now allocated on the producer's raw-Swift key everywhere, never the projected C# key. `WitnessDispatchEmitter.GetMethodKey` (method name + each parameter's raw `SwiftTypeSpec.ToString()`) is promoted to `internal` and documented as the single canonical slot-index key the three walks must share. Both C# consumer walks now compute `slotKey = WitnessDispatchEmitter.GetMethodKey(method)` and allocate/gate `methodIndices[slotKey]` on it (`ProtocolProxyEmitter.InterfaceImpl.cs:~118`, `ProtocolProxyEmitter.SwiftObject.cs:~611`), so two overloads whose distinct Swift parameter types both collapse to `Swift.AnyType` consume **two** indices on the consumer side too — matching the producer — and every later dispatchable method keeps its producer index. The projected C# key (`GetMethodSignatureKey` / `GetProjectedCSharpMethodKey`) is retained for a **separate** concern: member-emission collapse. Because the two AnyType-degrading overloads emit the *same* C# member signature, only the first may emit (the rest would be CS0111 duplicates) — so a distinct `emittedMethodSignatureKeys`/`emittedCSharpKeys` set, keyed on the projected key, gates emission *after* the index has already advanced on the raw key. The two keys are now explicitly orthogonal: raw key drives the ABI slot index, projected key drives C# member dedup. The supporting walks that compute companion accessor symbols (`ProtocolProxyEmitter.Vtables.cs`, `.Receivers.cs`, `.StaticInit.cs`, `.CrossModuleParent.cs`, `EveryProtocolEmitter.cs`) were aligned to the same raw-key indexing so the producer `@_cdecl` symbols, the P/Invoke decls, the receiver thunks, and the static-init registrations all land on identical `SBW_<Proto>_method_<name>_<idx>` numbers. The now-accurate intent is captured in the promoted `GetMethodKey` doc comment (replacing the misleading "mirrors GetMethodSignatureKey" claim). Gated end-to-end by `BindingTests/Sources/SwiftBindingsTestLib/EdgeCases/WitnessDispatchIndexLockstep.swift` — `WitnessIndexProto` with two `consume` overloads taking distinct parameterized-PAT existentials (`any WitnessIndexPayloadA`/`B`, both projecting to the same C# fallback) followed by the dispatchable `tag(_:Int32) -> Int32` — and `WitnessDispatchIndexLockstepTests.TestForwardDispatchTagIndexUnshiftedAfterAnyTypeOverloads`, which obtains a Swift-vended `any WitnessIndexProto` via `Functions.MakeWitnessIndexConformer()` and calls `tag(41)` through the forward witness path, asserting `42` (a shifted index would resolve the nonexistent `SBW_..._tag_1` and throw `EntryPointNotFoundException` before returning). `WitnessIndexProto` is registered in `PreservedProtocols` (`build/Helpers/SwiftSourceStripper.cs:44`) so the harness keeps its conformance + witness-table getter.

### 1b. Throw inside `SwiftRuntimeInfo` static cctor poisons the type — **FIXED**

**`src/Swift.Runtime/src/Swift/Runtime/SwiftRuntimeInfo.cs:117` · P2 · regression (new in `c4d260fc`)**

`ResolveIsNativeAot` throws `InvalidOperationException` on the `switchValue=true` + `conclusivelyMono` conflict (lines 116-123), and it is invoked from the eager `static SwiftRuntimeInfo()` cctor (lines 84-94) that assigns both `static readonly` fields. A throw in a static constructor is wrapped in `TypeInitializationException` and permanently faults the type: every subsequent read of `SwiftRuntimeInfo.IsMonoRuntime` / `IsNativeAotRuntime` — touched on virtually every marshal path and from generated `[ModuleInitializer]`s — re-throws the cached `TypeInitializationException`, because the cctor will not re-run. Pre-commit, `SwiftRuntimeInfo`'s field initializers could not throw, so this is a new failure mode.

The probe (a faithful replica of the cctor + `ResolveIsNativeAot`, only the RID source made injectable, driven by `AppContext.SetSwitch("Swift.Runtime.IsNativeAot", true)` + `PROBE_FORCE_RID=iossimulator-arm64`) showed: (1) the first read of `IsMonoRuntime` throws `TypeInitializationException` whose top-level `.Message` is the generic "The type initializer for … threw an exception" and does **not** contain the runtime-flavor-conflict text — that text is reachable only via `.InnerException`; (2) the type is poisoned: 2nd and 3rd reads also throw `TypeInitializationException`; (3) a counterfactual lazy-property model with a non-throwing cctor throws the bare `InvalidOperationException` with the conflict text at top level, confirming the proposed shape preserves the actionable message.

The conflict path is genuinely reachable: `SwiftBindings.Runtime.targets:37` injects `Swift.Runtime.IsNativeAot=true` for `SwiftBindingsInteropMode=Direct` independent of RID, so a Direct build run on the iOS Simulator trips it — a real user misconfiguration the throw is *meant* to catch. The fail-fast *intent* is sound; routing it through a cctor is the defect. **Severity refinement:** when the exception is unhandled (no real consumer catches it), .NET's default crash printer walks the `--->` inner-exception chain, so the actionable text *is* visible in a crash log. The message is truly lost only for code that catches and inspects `.Message`, or logging that records only `.Message`; the poisoned-type re-throw behavior holds regardless. **Fix direction (not in scope to apply):** move the conflict check off the eager cctor — a `Lazy`/factory that performs the check on first explicit call (or deliberately surfaces `.InnerException`) preserves the message without poisoning the type.

**Fix (defer the check off the cctor into a `Lazy` factory).** The two eager `static readonly` fields and the eager `static SwiftRuntimeInfo()` cctor are gone; the runtime flavor is now resolved by a single `private static readonly Lazy<RuntimeFlavor> s_flavor = new(ResolveFlavor)` (`SwiftRuntimeInfo.cs:83`), and `IsNativeAotRuntime`/`IsMonoRuntime` read `s_flavor.Value` (`:93`, `:101`). `ResolveFlavor` gathers the switch/RID/Mono signals and calls the unchanged pure `ResolveIsNativeAot`, whose conflict check throws the same `InvalidOperationException` (`:137`) — but now on the first property *read*, not from a type initializer. Because the throw no longer originates in a static constructor, .NET does not wrap it: the bare `InvalidOperationException` surfaces with the runtime-flavor-conflict text at **top level** (`.Message`), and the type is not permanently poisoned with a `TypeInitializationException` cascade. The fail-fast intent the commit added is fully preserved — the Direct-on-simulator misconfiguration still throws immediately on first use, just with the actionable message readable directly. Locked by `SwiftRuntimeInfoClassificationTests`: `NativeAot_HardConflict_SwitchSaysAotButMonoIsLive_Throws` / `…SwitchSaysAotButSimulatorRid_Throws` pin the two conflict shapes, and `NativeAot_HardConflict_ExceptionMessageIsTopLevel` asserts the thrown exception is *not* a `TypeInitializationException` and that its top-level `.Message` carries the conflict text with `.InnerException == null` (the exact poisoning/message-demotion the defect introduced). The full classification matrix (switch true/false/absent, simulator/device/desktop, Mono indicator) is re-pinned by the surrounding tests in the same file.

## 2. Inconclusive / needs deeper probe

### RuntimeContract.AssertCompatible strict-equality in an unconditional `[ModuleInitializer]`

**`src/Swift.Runtime/src/Swift/Runtime/RuntimeContract.cs:45` · P1-candidate · regression-shaped · INCONCLUSIVE**

`AssertCompatible` throws on **any** inequality (`generatedAgainstVersion != Version`) and is emitted as the **first, unconditional** statement of every generated binding's `[ModuleInitializer]` (`ModuleHandler.cs:383`), *outside* the try/catch that wraps the subsequent factory registrations. The probe **confirmed the mechanism**: with the runtime bumped to v2 under a v1-emitted binding, the app died with `TypeInitializationException` wrapping `SwiftRuntimeContractMismatchException` from `<Module>`.cctor (exit 134 / SIGABRT); the consumer's try/catch was bypassed entirely (not even the first `Console.WriteLine` ran). So a forward-incompatible runtime fires an uncatchable, app-wide load abort on a code path unrelated to any v2 feature, and strict equality gives zero forward-compat window.

**Why inconclusive (adversarial mitigation found):** the generator stamps a *bounded* NuGet range `[X.Y.Z, X.(Y+1).0)` into every binding's `SwiftBindings.Runtime` PackageReference (`RuntimeVersionRange.cs:71`). The documented discipline ties a real `RuntimeContract.Version` bump to an ABI-breaking Runtime **minor** bump, and the bounded range makes two bindings a Runtime-minor apart mutually uninstallable in one project (NuGet NU1107) at restore time — explicit "intended protection" (`RuntimeVersionRange.cs:32-36`). In a well-formed graph the diamond the claim relies on is therefore blocked at *restore*, not unified to v2 and crashed at load. So the strict-`!=` abort is a defensible defense-in-depth backstop, not the broadly-firing trap the framing implies.

**Residual risk (why not refuted):** the backstop's safety rests on an **unenforced convention** — nothing in code ties `RuntimeContract.Version` to the package minor. If a contract bump ever shipped inside a Runtime **patch** (within the `[X.Y.Z, X.(Y+1).0)` float window), NuGet would silently unify forward and the uncatchable load-time abort fires exactly as the probe showed. There is no minimum-floor / `>=` window anywhere (only strict `!=`; the throw is pinned by `CacheFirstDispatchTests.cs:137`). The design question — strict `!=` vs `>=`-with-floor — is legitimate but the bounded range already supplies the intended coexistence protection. **Deeper probe needed:** an end-to-end restore-time test asserting NU1107 actually blocks the cross-minor diamond, plus a guard tying `RuntimeContract.Version` to the package minor so a contract bump cannot ride a patch.

## 3. Deferred (candidate, unverified)

These are real candidates that exceeded the per-track verification cap; none has a decisive probe yet.

1. **Switch-less runtime-flavor fallback misclassifies iOS-device Mono full-AOT as NativeAOT** (`SwiftRuntimeInfo.cs:135`, P2, regression-shaped). The switch-absent branch returns `!isDynamicCodeSupported`; for a device Mono full-AOT (rid `ios-arm64`, no `Mono.Runtime`, not a simulator RID, `IsDynamicCodeSupported=false`) it returns `true` → `IsNativeAotRuntime=true` → jit-info.c:918 path. A console-mirror probe reproduces the pure-logic misclassification. **Note:** a *separate, fuller* probe in this same audit (see §5) refuted the production-reachability of this exact gap for published-binding PackageReference **and** ProjectReference consumers; the residual is a local-dev-only ProjectReference chain. Treat this deferred item as superseded by the refutation unless device Mono full-AOT under the dev-sentinel ProjectReference chain is shown to be a shipped config.

2. **`MarshalBorrowedFromSwift` double-release protection silently degrades to a no-op for any ISwiftObject whose handler omits the `SuppressPayloadFinalizer` override** (`SwiftMarshal.cs:1003`, P2, regression-shaped). The seam moved from reflective `GetProperty("Payload")` + `GC.SuppressFinalize` (worked uniformly) to a DIM whose default is a no-op (`ISwiftObject.cs:58`). A missing override is a *silent* no-op, not a compile error; a future ISwiftObject root with a finalizable payload but no override would double-release a borrowed (+0) handle. All current emitters carry the override (see §5 refutation), so this is latent fragility, not a present defect — needs a generator-side guard test that every `_handle`/`_payload`-owning ISwiftObject also emits the override.

3. **`GetSwiftAbiMetadataType` (tuple element metadata, `nint`/8B) vs `GetSwiftRawValueType` (`Int32`/4B) width disagreement for tag-only / unrecognized raw values** (`EnumHandler.Marshalling.cs:259`, P2, not a regression). Session 5 narrowed the sibling mapper to `Int32` but left the metadata-path fallback at `nint`, widening the inconsistency for a tag-only enum used as a tuple element. `EnumAbiWidthConsistencyTests` explicitly excludes null/""/unrecognized, leaving the gap unpinned. Needs a `(Tag, Int32)` tuple round-trip probe to show whether the 8B element metadata over-pads the first element.

4. **`RuntimeContract.AssertCompatible` strict inequality contradicts the documented "additive bump is backward-compatible" policy** (`RuntimeContract.cs:45`, P2, regression-shaped). The doc (lines 19-25) says additive changes keep older initializers valid, but strict `!=` bricks every older binding the moment the runtime is bumped for any reason. This is the same surface as the §2 inconclusive item from the policy-consistency angle; the fix candidate is `generatedAgainstVersion > Version` as the only error.

5. **Cache-first conformance/NewFromPayload dispatch — inspected, no recursion / no spurious-throw / exact-Type keying** (`ProtocolConformanceDescriptor.cs:110`, P2, not a regression). A three-way inspection refuted recursion, spurious factory throw, and Base/Derived key bleed. Candidate only in the sense that a live simulator round-trip would convert the inspection to a probe.

6. **`NewFromPayloadDispatcher.TryCreate` conflates "no factory" with "factory returned null"** (`SwiftMarshal.cs:39`, P2, regression-shaped). `TryCreate` returns `null` both for a cache miss and for a registered factory that legitimately returns null, so a null-returning factory falls through to reflection — asymmetric with `ConformanceDispatcher.TryGet`, which uses a nullable-struct sentinel so a registered `Zero` is still authoritative. Production factories return non-null, so severity is low; the asymmetry is latent fragility. Needs a factory-returns-null probe.

7. **`RegisterConformanceFactory` has no Mono guard while sibling `RegisterWitnessTable` does** (`SwiftMarshal.cs:671`, P2, regression-shaped). `RegisterWitnessTable` early-returns on non-NativeAOT (`:694`) to avoid the static-virtual jit-info.c:918 hazard; `RegisterConformanceFactory` registers `() => TType.GetProtocolConformanceDescriptor<TProtocol>()` on all runtimes, and conformance dispatch now consults the cache first on all runtimes, so the registered static-abstract factory runs on Mono on the hot path. Almost certainly safe *because every emitted call site is a closed concrete literal* (`ModuleHandler.cs:409`), which the memory note pins as Mono-safe — but the guard asymmetry is a maintenance smell that would reintroduce the crash if any registration site ever became open/shared-generic. Needs a grep-confirmation that **every** `RegisterConformanceFactory<…>` call site is concrete-literal, plus a simulator exercise.

If the runtime grows a Swift end-to-end leg for Direct-on-simulator misconfiguration, mirror it in BindingTests as a clear-message assertion.

## 5. Checked & refuted (brief)

- **Switch-absent fallback misclassifies device Mono full-AOT as NativeAOT for ProjectReference (path c) consumers** (`SwiftRuntimeInfo.cs:135`). *Refuted.* The pure-logic misclassification is real and already tested, but the load-bearing reachability premise — "buildTransitive does not propagate across a ProjectReference" — is false. An MSBuild/NuGet propagation probe showed `Swift.Runtime.IsNativeAot=false` lands in the runtimeconfig.json of **both** a PackageReference app and a published-binding ProjectReference app (NuGet imports the package's `buildTransitive` targets transitively across the ProjectReference edge). The only switch-absent config is the all-ProjectReference dev-sentinel chain, which is `IsPackable=false`, local-compile-only, never device-distributed, and runs on the simulator/macOS where the heuristic answers correctly anyway. No production hazard.

- **Non-generic enum nested in a generic parent fail-closed by `IsInheritedGenericContext` (empty `.All()` == true)** (`EnumCaseWrapperEmitter.cs:45`). *Refuted.* The alleged over-decline is unreachable: the swift-api-digester (6.2.4) stamps the parent's generic signature onto the nested enum (`genericSig='<τ_0_0>'`), so `Outer.E.IsGeneric==true` and the `enumDecl.IsGeneric ||` branch short-circuits — the vacuous-true is never the deciding factor. A live generator run emitted `Outer.E` as a generic class and skipped its factory correctly while binding a non-generic top-level enum; `nm -gU` shows no exported case-constructor symbol for the nested enum; a metadata-free `@_cdecl` wrapper constructing the nested case fails to compile (`generic parameter 'T' could not be inferred`), proving the fail-close is correct. 28/28 tests pass.

- **Cache-first dispatch + de-reflected borrowed-marshal finalizer seam** (`ISwiftObject.cs:124`). *Refuted (no defect).* A live generation probe showed the current generator emits `void ISwiftObject.SuppressPayloadFinalizer() => GC.SuppressFinalize(_handle)` for classes and `(_payload)` for non-frozen structs/enums, each matching its backing field, and the generated binding compiles cleanly. All 17 runtime ISwiftObject heap types with a `Payload` property carry the override; the no-override types (SwiftKeyPath *is* the SafeHandle, Binding is not an ISwiftObject, EveryProtocol never exposed `Payload`) are correct by construction. Cache-first registration only ever sees closed concrete literals. **Caveat worth recording:** the in-repo `BorrowedMarshalFinalizerTests` use fake types, so they prove the seam *wiring* but **not** per-emitter field-name correctness — that assurance came only from the live generation probe, not the unit suite. The `BindingTests/output-macos/SwiftBindingsTestLib.cs` artifact (2026-04-11) is **stale** (shows 0 overrides) and is a red herring.

Deferred item #2 captures the missing guard.
- ~~**Witness-dispatch index lockstep is asserted only at the eligibility layer.** The shared `IsMethodWitnessDispatchEligible` predicate is tested, but no test asserts the three walks consume the **same number of indices** for an AnyType-collapsing overload set — the exact axis 1a fails on.~~ **CLOSED by 1a's fix** — the slot index is now keyed on the raw-Swift requirement key across all three walks, and `WitnessDispatchIndexLockstepTests` exercises the exact AnyType-collapsing overload-then-dispatchable shape end-to-end (forward `tag()` dispatch lands on the unshifted SBW index).
