# Track A2 — Struct Layout / Register Passing / Value Witness Audit

**Scope:** Frozen/non-frozen struct emission (`FrozenStructHandler.cs`, register-slot lowering in `TypeLowering.cs`) and the runtime value-witness / Optional layer (`ValueWitnessTable.cs`, `SwiftMarshal.cs`, `SwiftOptional.cs`, `SwiftHandle.cs`), plus the `TypeLoweringTests` and the `binding-structs` / `binding-value-witness-table` design docs.

**Overall risk rating: 4 / 5 (High).** Confidence: high for the confirmed set (each was probe-demonstrated against the real generator binary and/or `swiftc` ABI output on arm64). One confirmed item is a P0 silent-garbage-return ABI bug; three are P1 memory-safety / correctness bugs. The risk is bounded mainly by reachability — the P0 wedge requires a specific (but legal and easy-to-write) struct shape, and two of the P1s are latent until a guard page / direct-API-consumer triggers them.

### 1.1 — P0: eightbyte mis-count in `LowerStruct` (silent garbage return)

`TypeLowering.LowerStruct` (`TypeLowering.cs:205-238`) adds **one `RegisterSlot` per ABI field fragment** and then flips `IsIndirect=true` when `slots.Count > MaxDirectSlots` (4). It never coalesces consecutive sub-8-byte fields into a shared 8-byte "eightbyte." The Swift CC (and AAPCS64) pack small fields into a single GPR and return a struct **directly in registers when the eightbyte count ≤ 4** — the decision is on eightbyte count, *not* field count. The minimal trigger is a `@frozen` struct that is **>16 bytes** (so the C# cdecl P/Invoke uses the hidden `x8` sret buffer per AArch64), **≤4 eightbytes** (so swiftcc returns it in registers), and has **>4 fields**: e.g. `{Int8 a,b,c,d,e; Int64 f,g}` (24 bytes / 3 eightbytes / 7 fields), or the all-32-bit `{Int32×6}` (24 bytes / 3 eightbytes / 6 fields).

When this trips, `ThunkAssemblyEmitter.NeedsReturnBridge` short-circuits `if (descriptor.ReturnLowering.IsIndirect) return false;` (`ThunkAssemblyEmitter.cs:158-164`), so `ClassifyThunk` selects a plain tail call. The emitted thunk is exactly `b _$s...makePacked7...` — no `x8` setup, no field-wise return store. The C# side (`PInvokeEmitter.cs:364-365`) returns the 24-byte struct by value, so the AArch64 cdecl caller passes its return-buffer address in `x8` and reads the result back from it; swiftcc ignores `x8` and returns in `x0/x1/x2`; the caller's `x8` buffer is never written → uninitialized garbage / potential SIGSEGV. A free function of this shape is **not** rejected by `ShouldEmitThunk` (traced each gate: `SmallStructReturnDivergesFromCAbi` early-returns for >16-byte returns at `NativeThunkEmitter.cs:322`; `IsTypeInherentlyIndirect` returns false for a frozen struct on this path because the cdecl flags are not yet set when `ShouldEmitThunk` runs). The developers' own comment at `NativeThunkEmitter.cs:246-251` assumes every `IsIndirect` frozen struct uses `x8` on both sides — true for genuinely-large 5+ eightbyte structs (`Big5`), false for this over-counted 3-eightbyte/7-field wedge. Boundary control: a 32B/4-eightbyte struct returns directly in `x0-x3`; a 40B/5-eightbyte struct returns via `x8` — confirming Swift's threshold is the eightbyte count. Existing tests (`TypeLoweringTests.cs`) only use full-8-byte-per-field layouts, so none exercise `slots.Count > eightbyte-count`.

**Fix surface (not implemented):** `LowerStruct` should bucket field fragments into eightbytes (`offset/8` with natural alignment) and compare the *eightbyte* count to `MaxDirectSlots`; and `NeedsReturnBridge` must bridge the >16-byte **direct**-return case (store `x0..x3` into the `x8` buffer) instead of treating `IsIndirect` as "no bridge needed" for a struct that is actually returned in registers.

### 1.2 — P1: `PayloadBuffer<IntPtr>.Buffer` 7-byte over-read of sub-8-byte Optionals

`PayloadBuffer<T>.Buffer` (`SwiftHandle.cs:295`) is `*(T*)_payload.DangerousGetHandle()`, a fixed `sizeof(T)` read. `SwiftOptional<T>.PayloadBuffer` (`SwiftOptional.cs:77-87`) constructs `PayloadBuffer<IntPtr>` whenever the value-type Optional default path is taken, guarded only by `Debug.Assert(_payloadSize <= IntPtr.Size)`. For `SwiftOptional<bool>` the backing allocation is 1 byte (`Optional<Bool>.Size==1`), so the guard is `1 <= 8` (passes, and is compiled out in Release) while `.Buffer` dereferences a full 8 bytes — a 7-byte out-of-bounds read. This is live in generated code: `IncludeArchived_Set(SwiftOptional<bool> value)` emits `using PayloadBuffer<IntPtr> ... = value.PayloadBuffer; IntPtr ... = valueDisposable.Buffer;` (the emitter default `else` branch, `WrapperEmitter.Marshalling.cs:303-307`; the only `useDangerousGetHandle:true` override at `:641-666` is not triggered for this `Bag<TItem>` property setter, which calls the real Swift symbol `...includeArchivedSbSgvs` via CallConvSwift).

Two honest caveats that do **not** refute the defect: (1) the crash is *latent* — the 7 over-read bytes usually come from the same heap arena and are read benignly; the guard-page probe forced a page boundary to make it observable. It is still UB on every call. (2) The *value* is not corrupted here — the real Swift setter reads only the low byte (`and w8, w0, #0xff`), masking the garbage. This is a memory-safety bug, not (in this instance) a value bug. **Fix direction:** pass the buffer address (`DangerousGetHandle`) or size the read to the actual payload, and flip the guard to `_payloadSize >= IntPtr.Size` (the current `<=` is backwards relative to the risk).

### 1.3 — P1: `TryComputeOptionalInlineSize` flag heuristic mis-sizes `Optional<T>` Buffer fields

`TryComputeOptionalInlineSize` (`FrozenStructHandler.cs:495-546`) derives both the inner size and the extra-inhabitant bit from coarse flags when concrete VWT metadata is unavailable (the standard cross-compile case — the iOS dylib's metadata accessor can't run on the macOS host, leaving `SwiftTypeInfo.MetadataPtr=Zero`, `InlineSize=null`). The dominant fault is the `innerSize = IntPtr.Size` fallback at lines 518-524: any RMM type **larger than one word** without a persisted `InlineSize` is clamped to 8 bytes. Reflection probes against the real method produced `Optional<ClosedRange<Int>>` = 8 bytes (Swift 17 → under-size by 9 → heap overflow / SIGSEGV on round-trip) and `Optional<AnyHashable>` would be 8 vs 40. A frozen struct storing `var r: ClosedRange<Int>?` stays Frozen+RMM, so it is projected as a Buffer (`IsFrozenStructProjectedAsClass`) and reaches `EmitIntPtrFields` with the undersized value. The secondary extra-inhabitant heuristic (line 541) also over-sizes `Optional<UnownedSerialExecutor>` (emitted 17 vs Swift 16), though that type is only ever an actor's `unownedExecutor` return, never a stored field — low practical impact. Both directions confirm the static guess diverges from the runtime `SwiftOptional.GetTagByteOffset` metadata decision.

Two voters split on *which line* is the primary culprit (line 544 extra-inhabitant heuristic vs lines 518-524 innerSize clamp); the consensus is that the **innerSize clamp is the reachable, dangerous bug** and the +1 heuristic compounds it. Real XML records that exercise this: `SwiftDatabase.xml` `ClosedRange` and `AnyHashable`, `_ConcurrencyDatabase.xml` `UnownedSerialExecutor`. **Fix direction:** persist a real per-instantiation `Optional` size / inner extra-inhabitant bit (extend the XML/parser to carry it) rather than guessing from flags.

### 1.4 — P1: `SwiftOptional<T>.Value` / `ToNullable` / `implicit operator T?` lose `None` for value-type `T`

`SwiftOptional<T>` is declared with an **unconstrained** `T` (`SwiftOptional.cs:27`, no `where T`). For unconstrained `T`, `T?` is merely a nullable-reference annotation that erases to bare `T` for value types — it is *not* `Nullable<T>`. `Value` (line 518: `None => default(T)`), `ToNullable` (line 553: `Case == Some ? Some : default`), and `implicit operator T?` (line 559) therefore all return `default(T)` for a `None` optional. For value-type `T` (int/double/bool/frozen value struct/enum) that is the **zero** value, indistinguishable from `Some(default(T))`. Reflection over the shipped DLL confirms all three members return `System.Int32` (not `Nullable<Int32>`) for `T=int`, and the C# compiler emits `CS0472` ("a value of type 'int' is never equal to 'null' of type 'int?'") on the `None==null` comparison — direct compiler confirmation of the erasure. The generated bindings are unaffected (they emit `HasValue ? (int?)Some : null` with an explicit concrete cast that yields a true `Nullable<T>`), so this is a **latent public-API correctness bug for direct consumers**, not a hot-path crash. **Fix direction:** the API cannot faithfully express `None` for value-type `T` over an unconstrained parameter without a `where T : class` constraint (breaks value-type usage), paired struct/class overloads, or a different return shape (`object?` / `(bool, T)`). The generator already works around it; the API surface is the gap.

## 2. Inconclusive / needs deeper probe

**`SwiftOptional<simple-enum>` uses the C# enum integer VALUE as the Swift discriminator instead of the declaration-order case tag** (`SwiftOptional.cs:255` NewSome, `:327` NewNone, `:410` Case, `:488` Some). Two voters split.

- The **refuting** vote ran the full generator on `enum Cmp: Int {orderedAscending = -1; ...}` and found the generator emits **declaration indices** (`OrderedAscending = 0, OrderedSame = 1, ...`), *not* the raw values (-1, 0, 1), because integer raw values are stripped from the `.swiftinterface` / ABI JSON and both fact producers extract only string-literal raw values. So for every enum the SwiftOptional-consuming pipeline actually produces, member value == declaration index and the fast path is correct. It also noted a *separate, lower-severity* rawValue-fidelity bug (the generator surfaces `OrderedAscending` as 0 instead of -1) — which is precisely what keeps SwiftOptional correct.
- The **confirming** vote proved via swiftc that the in-memory single-byte discriminator IS the declaration-order tag (never the rawValue) and that a C# enum with non-index member values (`{-1,0,1}`) would be misread as `None` (`0xFF < 3` is false) and/or hand a wrong byte to native Swift.

**Net:** the runtime code IS fragile (it encodes by value where Swift encodes by tag) but is currently saved by the generator never assigning non-index member values to enums that flow through `SwiftOptional<T>`. The exposure is any consumer-supplied non-contiguous enum used as `SwiftOptional<E>`, plus a latent break if the generator ever starts emitting true integer raw values. Worth a dedicated probe that drives a hand-written non-contiguous C# enum through `SwiftOptional<E>.NewSome/.Case/.Some` to lock the behavior (and decide whether to harden `NewSome` to use `GetCaseTag` rather than the raw value).

## 4. Checked & refuted (do not re-chase)

- **`LowerStruct` marks mixed int/float returns indirect with a COMBINED 4-slot budget; swiftcc uses separate 4-GPR+4-FPR files** — `TypeLowering.cs:228`. **REFUTED.** swiftcc's IR (`-emit-ir`) for `{Int,Double,Int,Double,Int}` (40B) and `{Double×3,Int×3}` (48B) is `sret`/indirect; `{Int,Double,Int,Double}` (4 slots) is direct. The real rule is a **combined ≤4-slot** budget — exactly what the generator implements. The 5-slot test `LowerReturnType_Mixed5Slots_3Int2Float_Indirect` encodes correct behavior.
- **`SwiftOptional.MarshalToSwift` lacks the POD-tag-byte memcpy fast path the constructor has** — `SwiftOptional.cs:166`. **REFUTED.** Direct VWT `InitializeWithCopy`/`InitializeWithTake` probes (`Optional<CGRect/CGPoint/CGSize>` + pure-Swift POD) preserve the `None` tag byte on every testable platform; the claim's "InitializeWithCopy drops the tag" premise is false. Also, `Optional<CGRect>` by value never reaches `MarshalToSwift` (generator emits `NewNone()` → `Payload.DangerousGetHandle()`).
- **Frozen-struct backing fields round non-trivial fields up to 8-byte words, drifting interior offsets** — `FrozenStructHandler.cs:552`. **REFUTED.** The IntPtr-word emission and the C#/Swift interior-offset drift are real, but inert: every such struct is projected as `ClassWithBufferStruct` (opaque Buffer = size carrier only), crosses the boundary by pointer, is over-allocated (never under), and all field access routes through Swift `@_cdecl` accessors at Swift's own offsets. End-to-end `DriftStruct` round-trips every field. The cited `BatchConfig.TagCount` "Not enough bits" evidence is a different (`Optional<Array>`) issue.
- **`Case`/`NewNone` tag-byte fast path assumes None==1 / Some==0 for all appended-tag optionals** — `SwiftOptional.cs:420`. **REFUTED.** The appended byte appears only when the inner type has zero extra inhabitants; in that exhausted case swiftcc unconditionally encodes Some=0/None=1 (asm: `mov w1, #1` for None). Partial-EI types keep `optionalSize==innerSize` and correctly route to the VWT path.
- **`TryComputeOptionalInlineSize` extra-inhabitant heuristic mis-sizes multi-field frozen-struct payloads** (the *frozen-struct-embedding-a-class-ref* variant) — `FrozenStructHandler.cs:544`. **REFUTED** for the posited shape: a class pointer carries an inexhaustible extra-inhabitant pool, so `Optional<T>.size == T.size` for the entire pointer-backed RMM category. (The *genuine* mis-sizing bug is the `innerSize=IntPtr.Size` fallback for multi-word RMM types — captured as confirmed finding 1.3, not this refuted variant.)
- **`LowerOptional` uses the combined 4-budget for `Optional<mixed-struct>`** — `TypeLowering.cs:304`. **REFUTED.** swiftcc returns/passes `Optional<Mix4>` (and `Optional<4-Double>`, `Optional<2Int+2Double>`) **indirectly** via `x8`/`sret` — matching the generator. The combined-slot rule is the true ABI; the boundary at 4 combined slots is exact.
- **`LowerOptional` only suppresses the tag slot for inner CLASS types, not value types with extra inhabitants** — `TypeLowering.cs:286`. **REFUTED (impact).** The over-count is real (`Optional<Holder>` → 2 slots vs swiftcc's 1) but inert: `ShouldEmitThunk` rejects every `Optional` return (`NativeThunkEmitter.cs:228-230`) and `AreAllParametersLowerable` rejects any param with >1 slot (`:620-621`), so the inflated lowering forces a conservative `@_cdecl` fallback rather than a wrong-register thunk. Latent imprecision, not live corruption.

## 5. Coverage gaps (what this track did NOT reach)

- **The tuple-marshalling cluster in `SwiftMarshal.cs`** (deferred items 4, 13–16, 19) — the generic reflection tuple path has no probe-level verification for value-type-Optional, simple-enum, nested-tuple elements, bounds-checking asymmetry, or the alignment-mask blast radius. Generated bindings emit inline tuple code, so impact is the runtime fallback, but the *shape* of failure (throw vs silent offset drift) is unverified.
- **The `ValueWitnessFlags.AlignmentMask` ABI divergence** (item 12) — confirmed as a constant mismatch against `MetadataValues.h` but latent; no probe constructed a synthetic over-aligned VWT to demonstrate the failure mode, and no test guards the masked-alignment path.
- **NativeAOT / physical-device behavior** — every probe ran on native macOS arm64 or the iOS Simulator. The constructor's POD-tag-byte fast path and its "VWT drops the tag" comment originate from a NativeAOT *device* fix (commit `711f04d3`); the refutation of the `MarshalToSwift`-asymmetry claim could not run on a physical device.
- **The non-frozen struct handler** (`NonFrozenStructHandler.cs`) — named in scope but no confirmed/refuted finding landed against it; its opaque-payload / SafeHandle path was not independently probed for layout or VWT-lifetime defects.
- **ARC accounting on the class-Optional construct-then-extract path** (item 21) — a leak/over-release probe with a counting deinit was not run.

## 6. Recommended BindingTests fixtures (Swift shapes — no fixes proposed)

1. **P0 eightbyte mis-count (finding 1.1).** `@frozen public struct Packed7 { public var a:Int8; public var b:Int8; public var c:Int8; public var d:Int8; public var e:Int8; public var f:Int64; public var g:Int64 }` + free func `makePacked7() -> Packed7` returning `(1,2,3,4,5,6,7)`. Assert all 7 fields round-trip from C#. Add the all-32-bit sibling `@frozen struct Packed6i32 { var a,b,c,d,e,f: Int32 }` (24B / 3 eightbytes / 6 fields). Both should be **thunked** (not `@_cdecl`); expect `e/f/g` garbage today. Pair with a genuinely-indirect control (`{Int64×5}`, 40B / 5 eightbytes) that must still round-trip.
2. **Direct-return bridge register packing (deferred item 3).** `@frozen struct R { var lo:Int32; var hi:Int32; var big:Int64; var big2:Int64 }` (24B: eightbyte0 = `{lo,hi}`, 4 fields → reaches the >16B direct-return bridge once 1.1 is fixed). Return from a thunked free func; assert `lo` AND `hi` round-trip (today `hi` reads from the wrong register half).
3. **`SwiftOptional<bool>` over-read (finding 1.2).** A frozen struct with an `Optional<Bool>` stored property whose setter routes through `value.PayloadBuffer` (the `Bag.includeArchived` shape). Run the BindingTests suite under a guard-page / ASan-style harness so the 7-byte over-read faults rather than silently passing.
4. **`Optional<multi-word-RMM>` Buffer sizing (finding 1.3).** A `@frozen public struct Holder { public var r: ClosedRange<Int>? }` (or wrapping any Apple value type ≥16B such as `UUID?`/`Date?`). Cross-check `Marshal.OffsetOf`/`sizeof` of the generated Buffer against the Swift `MemoryLayout<Holder>.size` and round-trip the optional field; expect heap overflow / SIGSEGV today on the cross-compile (no-metadata) path.
5. **Public `SwiftOptional<value-type>` API (finding 1.4).** A C#-only runtime test: `SwiftOptional<int>.NewNone()` then assert `ToNullable() == null`, `(int?)opt == null`, and `Value` distinguishes `None` from `Some(0)`. Repeat for `double`, `bool`, a frozen value struct, and an enum. Fails today (returns the zero value).
6. **Simple-enum discriminator (inconclusive item).** A non-contiguous C# enum (e.g. `{ A = -1, B = 0, C = 1 }`) driven through `SwiftOptional<E>.NewSome(E.A)` → assert `Case == Some` and `Some == E.A`. Pair with a contiguous control `{ X, Y, Z }` to isolate the value-vs-tag behavior and lock down whichever invariant is chosen.
