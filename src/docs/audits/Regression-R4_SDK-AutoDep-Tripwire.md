# Regression Audit R4 — SDK Auto-Dep Verb + Wiring Tripwire (Session 14)

**Scope:** Regression hunt over commit `8ec160df` ("Move auto-dep resolution into a generator verb and add an MSBuild wiring tripwire"). Targets: the `--resolve-auto-deps` generator verb + `AutoDepResolver`; the removed escaped-POSIX-sh `_ResolveSwiftAutoDetectedDependencies` shell path; the fail-closed MSBuild wiring tripwire (SWIFTBIND062–065, applicability-gated); the relevant `Sdk.targets` regions.

**Overall risk: 2 / 5** (confidence: high). Every confirmed defect is genuinely a regression introduced by `8ec160df`, but all four are narrow-blast-radius: three are documentation/parity-contract violations on inputs that cannot arise from the real producer, and the fourth (the tripwire false-positive) only breaks an already-non-functional standalone `-t:CoreCompile` invocation. No confirmed defect breaks a real `dotnet build`, `dotnet pack`, or the SDK's normal auto-dep resolution flow.

**Confirmed count: 4** (after merging the two duplicate semicolon-dedup votes into one finding). **All 4 are regressions** introduced by `8ec160df`; **0 are pre-existing-unaudited**. The headline issue is the wiring tripwire's `DesignTimeBuild`-only guard (missing the canonical `BuildingProject` companion), which can hard-fail a standalone `-t:CoreCompile` with a bogus SWIFTBIND062.

### C1 — Tripwire false-positives on a standalone `CoreCompile` (DesignTimeBuild guard is insufficient) — **FIXED**

`_AssertSwiftBindingHookWiring` (`Sdk.targets:1961`) is anchored `BeforeTargets="CoreCompile"` and gated **only** on `Condition="'$(DesignTimeBuild)' != 'true'"` (line 1963). The stamp it asserts (`_SwiftHookRan_GenerateSwiftBindings`) is set by `_GenerateSwiftBindings`, which is anchored `BeforeTargets="ResolveProjectReferences"`. When `CoreCompile` is entered through a path that does **not** first pull in `ResolveProjectReferences` — i.e. a direct `dotnet build <proj> -t:CoreCompile` with `DesignTimeBuild` unset — the stamp is absent and SWIFTBIND062 fails the build. `DesignTimeBuild` is *empty* (not `'true'`) in both this misfire and a real full build, so the lone guard cannot distinguish them; only `BuildingProject` differs (`[false]` standalone vs `[true]` full build, where `BuildOnlySettings` flips it true ahead of `CoreCompile`).

The probe reproduced this exactly in `/tmp/tw-probe` and confirmed the fix: adding `AND '$(BuildingProject)' == 'true'` to the condition eliminates the false positive (BuildingProject is false under standalone `CoreCompile`) **while fully preserving fail-closed detection** — a genuinely disconnected generate hook on an actual `-t:Build` still fires the tripwire because BuildingProject is true there. This is Microsoft's canonical "real-build-only" guard idiom.

**Severity caveat (why P1 nominal but ~P3 real-world):** the only path that triggers the misfire is a standalone `-t:CoreCompile` (or an external tool driving `CoreCompile` outside the CoreBuild chain with `DesignTimeBuild` unset). That invocation (a) is used by no tooling in this repo (grepped — nothing runs `-t:CoreCompile`), (b) is not part of the normal `dotnet build`/`publish` graph, and (c) cannot produce a successful compile anyway, since it skips reference resolution (CS0518/CS0246). So the tripwire breaks an invocation that was already non-functional. It is a real robustness/correctness gap in the guard (the `BuildingProject` pairing is the right idiomatic fix and worth adopting), but the live blast radius is narrow — hence P1 on the guard's correctness, ~P3 on actual user impact.

The existing unit test `HookWiringAssertion_SkippedUnderDesignTimeBuild` (`SdkTargetsBehaviorTests.cs:780`) only exercises `DesignTimeBuild=true` and drives the target in isolation via `-t:_AssertSwiftBindingHookWiring` (`:977`), so it never runs a real `CoreCompile` graph and cannot catch this gap.

**Fix (add the canonical `BuildingProject == 'true'` companion).** `_AssertSwiftBindingHookWiring`'s condition is now `Condition="'$(DesignTimeBuild)' != 'true' AND '$(BuildingProject)' == 'true'"` (`Sdk.targets:1973`), with the preceding comment expanded to record why (`:1964–1968`): `DesignTimeBuild` is empty in both the misfire and a real full build, so it cannot distinguish them, but `BuildingProject` is `false` under a standalone `-t:CoreCompile` and `true` in a real `-t:Build` (where `BuildOnlySettings`, item #1 of `CoreBuildDependsOn`, flips it true ahead of Compile). The pairing eliminates the false positive while fully preserving fail-closed detection — a genuinely disconnected generate hook on an actual `-t:Build` still fires SWIFTBIND062 because `BuildingProject` is true there. This was empirically de-risked before landing: a probe confirmed `BuildingProject` is `false` for a direct `-t:<target>` invocation (including standalone `-t:CoreCompile`) and only `true` for a full `-t:Build`. The de-risking surfaced a test-suite hazard and resolved it at root: the existing SWIFTBIND062–065 failure-expecting tests drive `-t:_AssertSwiftBindingHookWiring` directly (where `BuildingProject` is naturally `false`), so the new clause would have skipped the assert and broken their `exit != 0` expectation. Rather than weaken those assertions, `RunHookWiringAssertion` gained a `bool buildingProject = true` default parameter that appends `-p:BuildingProject=true` (`SdkTargetsBehaviorTests.cs:1007`) — faithfully modeling the real-build context in which the tripwire fires — so the 062–065 tests keep forcing the failure they assert. The regression itself is locked by the new `HookWiringAssertion_SkippedUnderStandaloneCoreCompile` (`:796`), which passes `buildingProject: false` and asserts exit 0 with no SWIFTBIND062/063/064/065 emitted — the exact standalone-`CoreCompile` false positive, now proven gone. C2 and C3 in this audit are comment-accuracy parity violations the audit explicitly classifies as warranting no functional change; they are addressed as comment corrections (see below), not logic edits.

### C2 — AutoDepResolver dedup diverges from the old shell on a decoded `;` in a module name — **FIXED (comment)**

The old shell deduped with a delimiter-bounded substring match `case ";$EXPLICIT_DEPS;" in *";$MOD_NAME;"*`, where `$MOD_NAME` is the **decoded** module. The C# port instead splits `explicitDeps` on `;` into a `HashSet` (`AutoDepResolver.cs:66`) and tests `explicitSet.Contains(module)` against the decoded module (`:95`). A module decoding to `A;B` (from `A%3BB`) can never equal a split element `{A, B}`, so a dependency the shell would have suppressed is now emitted. The differential oracle confirmed this is the *sole* divergence across 10+ fuzz cases (plain dedup, encoded pipe, double-encoded percent, empty record, glob chars all matched byte-for-byte).

The comment at `:60–62` asserts the two forms are "exact-element membership" — true only because the shell's `";$MOD_NAME;"` segment is **quoted** (which is also why the input's secondary claim about glob chars `*`/`?`/`[` causing divergence is **wrong**: quoting disables glob expansion, so `F*` vs `Foo` is no-match in `/bin/sh`, identical to C#'s ordinal `Contains`). The comment overlooks that the shell compared the *decoded* module while C# cannot reconstruct a `;` across the split — the one un-preserved corner of the FROZEN-grammar claim.

**Reachability:** practically unreachable. Swift module names are identifiers (no `;`), and the producer side (`XCFrameworkMetadataExtractor.DelimiterEscape`, `:549–555`) only encodes a `;` to `%3B` if a module name contained one. The C# behavior is arguably *more* correct (explicit deps genuinely are a `;`-list). The defect is a documentation-accuracy violation, not a live bug. Recommended remediation is to the comment, not the logic.

**Fix (comment).** The dedup comment at `AutoDepResolver.cs:60` no longer claims byte-for-byte "exact-element membership" parity. It now states the set-membership form matches the shell for every real input, names the single decoded-`;` corner where the two diverge (emitted here, deduped by the shell), notes that input cannot arise from the producer, and records that the set-membership reading is the intentional, arguably-more-correct behavior — not a parity bug. The logic is unchanged (correct as-is); only the inaccurate parity claim is corrected.

### C3 — PROJREF path diverges from `cd && pwd` for a relative xcframework path — **FIXED (comment)**

`Run` passes `Path.GetFullPath` as the absolute-path normalizer (`:145`), which the comment (`:121–123`) claims is the analog of the shell's `cd "$FOUND_DIR" && pwd` (logical `pwd -L`). For a **relative** candidate path the two diverge: `Path.GetFullPath` prepends `Environment.CurrentDirectory`, which macOS realpath-resolves (`/private/tmp/...`), resolving the very symlink `pwd -L` deliberately preserves (`/tmp/...`). The real verb emitted `PROJREF|/private/tmp/...` where the shell emitted `PROJREF|/tmp/...`.

**Reachability / impact:** not reachable in normal SDK use — the dependency `XCFrameworkPath` in `binding-metadata.props` is always absolutized by `Program.cs:1831` (`depFullPath = Path.GetFullPath(depPath)`) before the resolver sees it, and an absolute `/tmp` candidate does **not** diverge (`GetFullPath` leaves it untouched). Even when forced to diverge, `/tmp` and `/private/tmp` are the same inode, so the injected `ProjectReference` resolves to the identical project. Cosmetic parity-contract / comment-accuracy violation; no functional change warranted beyond correcting the comment.

**Fix (comment).** The PROJREF comment at `AutoDepResolver.cs:129` no longer claims unqualified `pwd -L` parity. It now states `GetFullPath` matches `pwd -L` for an ABSOLUTE candidate (the real input, since `Program.cs` absolutizes the dependency path upstream), names the relative-path divergence (`GetFullPath` realpath-resolves the cwd's symlinks where `pwd -L` preserves them), and records that the path is unreachable in normal SDK use and resolves to the same inode anyway — cosmetic, not functional. The logic is unchanged.

## 3. Deferred (candidate, unverified)

These are real candidates past the per-track verification cap. Several restate the C1 family (tripwire guard) from different angles or extend it to pack; the AutoDepResolver-grammar and stdout/stderr items are independent and worth a probe.

- **D1 — SWIFTBIND062 false-positive on isolated `-t:CoreCompile`** (`Sdk.targets:1968`, P2). Same root cause as C1, framed as "CoreCompile not always preceded by ResolveProjectReferences." Subsumed by C1's confirmed result; listed for completeness. Probe: run `dotnet build -t:CoreCompile <Module>.Swift.iOS.csproj` on a clean obj dir with `DesignTimeBuild` unset; observe SWIFTBIND062.

- **D2 — Guard omits the canonical `BuildingProject` companion** (`Sdk.targets:1963`, P2). The expression-completeness framing of C1. The .NET SDK's own codegen-style targets gate on `DesignTimeBuild != 'true' AND BuildingProject == 'true'` (`Microsoft.Common.CurrentVersion.targets:2557`). The fix is exactly the one C1's probe validated. (Note: a *related* phrasing using the disjunction `BuildingProject == 'false'` was **refuted** below — the correct companion is the *conjunction* with `== 'true'`, which C1 demonstrates.)

- **D3 — Tripwire fires during `dotnet pack` of an Apple-framework binding** (`Sdk.targets:1961`, P2). Because the assert anchors on `CoreCompile` (which pack runs via Build), it now also runs at pack time; the commit's own `AppleFrameworkCrossModuleDepsInjectionTests` fixture had to re-add `BeforeTargets`+stamps to a bare `<Target>` stub. The SWIFTBIND062/065 text says "before **compilation**", which mis-describes a pack-time failure. Probe: author an Apple-framework fixture, `dotnet pack` once (passes), then disconnect only the generate hook's anchor and `dotnet pack` again — observe SWIFTBIND062 fail the **pack** with a "before compilation" message; decide whether pack should be in scope or the wording corrected.

- **D4 — `Split('|', 4)` vs SWIFTBIND080 uncapped `Split('|')[4]` truncation** (`Sdk.targets:1930`, P2). The resolver folds a 5th+ pipe remainder into the xcframework field (4-way split, mirroring `read -r a b c d`), so a WARN line can legitimately carry >4 `|`. The SDK then reconstructs the SWIFTBIND080 `SwiftFrameworkDependency Include=` via uncapped `.Split('|')[4]`, capturing only the first segment of a pipe-bearing path. Pinned indirectly by `AutoDepResolverTests.OverlongRecord_PutsRemainderInXcframeworkField` (`:222`). Reachable only via a hand-crafted/malformed `_SwiftBindingDependencies` (the producer percent-encodes literal `|` as `%7C`). Probe: drive the SWIFTBIND080 Text expression on item `WARN|Mod|Pkg|1.0.0|/root/a|b.xcframework` and assert the rendered `Include=` shows `/root/a` instead of `/root/a|b.xcframework`.

- **D5 — resolve-auto-deps error path logs to stdout, captured by `ConsoleToMSBuild`** (`BindingsGeneratorCommand.cs:194`, P2). On the failure path the verb calls `logger.LogError(...)`; `CreateLoggerFactory` (`Program.cs:2394`) uses `AddConsole()` with no `LogToStandardErrorThreshold`. The SDK Exec (`Sdk.targets:1916`) captures stdout into `_SwiftAutoDepResult` via `ConsoleToMSBuild=true`. Today the happy path emits only PROJREF/WARN (verified clean at `-v 1`/`-v 2`), so no live pollution, but the coupling is fragile: any future informational stdout line during this verb pollutes the item list. Probe: force the catch block and capture stdout; confirm the LogError text lands on stdout (then route diagnostics to stderr / set `LogToStandardErrorThreshold`).

- **D6 — "stdout = grammar only" invariant is unpinned** (`BindingsGeneratorCommand.cs:185`, P2, *not* flagged a regression by its author). The migration from inline `echo` to `dotnet exec --resolve-auto-deps` introduces an implicit contract: stdout must contain ONLY frozen-grammar lines or extra lines become spurious items. Holds today (resolve branch returns before pipeline logging; `AutoDepResolver.Run` writes only `Console.Out`; logger writes to stderr) but is uncovered by tests. Probe: add a behavioral test that runs the real verb with resolvable + unresolvable specs at default verbosity, captures stdout only, and asserts every line `StartsWith("PROJREF|")` or `StartsWith("WARN|")`.

## 4. Checked & refuted

- **R1 — "Tripwire omits the `BuildingProject == 'false'` design-time disjunction, so a `BuildingProject=false` non-DesignTimeBuild build hard-errors"** (`Sdk.targets:1963`). REFUTED (high confidence). The factual sub-claims hold (guard is `DesignTimeBuild`-only; `BuildingProject` is never referenced), but the *causal* claim fails: the control run `-t:CoreCompile` with **no** `BuildingProject` property emits the identical SWIFTBIND062, so `BuildingProject=false` is a red herring — the error is caused by bypassing `ResolveProjectReferences`, not by the build flavor. A pass with `BuildingProject=false` cannot reach `CoreCompile` through the real Build graph because `BuildOnlySettings` (item #1 of `CoreBuildDependsOn`, ahead of Compile) flips `BuildingProject=true` via a target-body assignment that overrides even a command-line `-p:BuildingProject=false`. The correct guard is the *conjunction* `... AND BuildingProject == 'true'` (confirmed as C1), not the asserted disjunction.

- **R2 — "Tripwire stamps only 4 of many hooks; `_DetectSwiftBindingTargetKind` anchor drift can gate SWIFTBIND065 OFF while 062 still passes"** (`Sdk.targets:1976`). REFUTED (high confidence). The premise — that the `DependsOnTargets` reachability of `_DetectSwiftBindingTargetKind` is "incidental, not guaranteed" and could "drift silently" — is wrong. Probe Config 2 (rename ALL of its `BeforeTargets` anchors, leave `DependsOnTargets` intact, as in the real file): `_SwiftBindingTargetKind` STILL resolves to `AppleFramework`, gate stays ON — because the detect target is in the transitive `DependsOnTargets` closure of `_GenerateSwiftBindingsAppleFramework` (the very target 065 checks). Configs 3/4/5 (also break the `DependsOnTargets` paths) **hard-fail with MSB4057** — a dangling `DependsOnTargets` is a *build error*, not a silent drop, i.e. it is fail-closed, not fragile. Reproducing the abstract gap (Config 6) required removing `_DetectSwiftBindingTargetKind` from *every* `DependsOnTargets` list AND breaking its `BeforeTargets` — a deliberate, reviewable multi-site edit, not the silent anchor drift the tripwire exists to catch. Part A (only 4 hooks stamped) is factually accurate but a defensible design-scope choice: the unstamped hooks either fail loud (missing generated sources → compile errors) or are `DependsOnTargets`-reachable.

## 6. Recommended BindingTests fixtures (Swift shapes — no fixes proposed)

The confirmed defects are SDK-targets and resolver-grammar concerns, so the durable coverage is at the **MSBuild behavior-test / resolver-unit** layer rather than ABI/runtime. Where a BindingTests-shaped end-to-end fixture adds value, it is the cross-module dependency graph that exercises the auto-dep verb. Suggested shapes:

1. **Two-module cross-dependency binding (locks the auto-dep happy path + C1 context).** A Swift package `Core` (a `public struct`/`public func` with no deps) and a second package `Sheet` that `import Core` and exposes a `public func` consuming a `Core` type, each built into its own `.xcframework`. Generate both bindings as sibling projects so `Sheet`'s `binding-metadata.props` records `Core` as a cross-module dependency. This drives `_ResolveSwiftAutoDetectedDependencies` → the `--resolve-auto-deps` verb → a real `PROJREF|` injection, and is the realistic graph against which the tripwire and a future standalone-`CoreCompile` assertion run. Build it through a full `dotnet build` and assert the `Sheet` binding picks up the `Core` `ProjectReference` and the types round-trip.

2. **Unresolved cross-module dependency (locks the `WARN|` / SWIFTBIND080 path + D4).** Same `Sheet`→`Core` shape, but build `Sheet`'s binding with **no** sibling `Core` project on disk (only the framework dependency recorded). Assert exactly one SWIFTBIND080 warning is emitted and its suggested `SwiftFrameworkDependency Include=`/`PackageReference Include=` fields reconstruct the full module/package/version/xcframework values (this is the natural place to extend toward the pipe-bearing-path edge once D4 is decided).

3. **Cross-module dependency whose module/package names are plain identifiers (negative control for C2).** A `Sheet`→`Core` graph where neither module name contains a `;` (the real-world case). Assert the dedup against an explicit `SwiftFrameworkDependency Include="Core..."` correctly suppresses re-injection — pinning that the *normal* dedup path is unaffected, so the C2 fix (comment-only) does not regress real behavior.

These belong in `BindingTests/Sources/SwiftBindingsTestLib/` (the two Swift packages) plus the SDK/MSBuild behavior-test layer (`SdkTargetsBehaviorTests` / `AutoDepResolverTests`) for the tripwire-graph and resolver-grammar assertions, which is where C1–C3 actually live.
