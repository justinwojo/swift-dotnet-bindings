# Track M1 — SwiftUI Bridge Support Matrix Audit

**Scope:** Read-only audit of the SwiftUI bridge emission path — `SwiftUIBridgeEmitter.cs`, `SwiftUIBridgeEmitter.AsyncPattern.cs`, `SwiftUIBridgeEmitter.InitAnalyzer.cs`, `SwiftUIViewDetector.cs`, the `BindingTests/RuntimeTestsApp/SwiftUIBridge` fixtures, and `.claude/rules/swiftui-bridge.md`.

**Overall risk rating: 4 / 5 (high).** Confidence: high for the confirmed set. Five distinct defects were probe-confirmed, two of them P0 memory-safety / type-confusion issues reachable from valid managed input, plus a third P0/P1 family of force-unwrap traps replicated across six emission sites. The reason this is a 4 and not a 5 is reach: most of the confirmed defects require a specific (and currently *untested*) param shape — an ObjC-bridgeable struct param, an out-of-range enum raw value, or a frozen-with-ref-fields struct closure arg — none of which any shipping BindingTests fixture exercises. They are latent in the support matrix but trivially triggerable the moment a consumer uses those shapes. The large `deferred_unverified` queue (22 candidates) suggests further P1/P2 surface remains unprobed in the async and closure paths.

### Detail

**1. ObjC-bridgeable BoundStruct init param — type confusion (P0).** The C# `Create` call passes `param.IsObjCBridgeable ? "{name}.Handle" : "{name}.Payload.DangerousGetHandle()"` (line 2954), which for `Foundation.URL` hands over an `NSURL*` object pointer — the *correct* ABI per `MarshallingHelpers.IsObjCBridgeable` (`MarshallingHelpers.cs:464`) and the canonical `WrapperEmitter.Async.cs:488-491` contract. The Swift side, however, unconditionally reinterprets that pointer as raw Swift struct bytes via `assumingMemoryBound(to: {BridgeTypeName}.self).pointee` (line 1316) with **no `IsObjCBridgeable` branch**, unlike the closure Result path (3854-3873) which the maintainers got right. Because `URL` is a non-trivial reference-holding struct, copying the misinterpreted 16-byte window retains garbage as object references → SIGSEGV. The same defective pattern repeats at the Session init (837), Optional `BoundStruct` Create (1333), and both Update sites (1550, 1566). A trivial ObjC-bridgeable struct would produce a silently-wrong value instead of a crash. No fixture covers this shape.

**2. BoundEnum force-unwrap family (P0 across sites / P1 root).** `BridgeTypeName(rawValue: x)!` is independently emitted at six sites: Create scalar (1295), Create Optional (1340), Update (1532), Update Optional (1573), modifier Set (2013), and BridgeArray element (843). The C# side passes the raw value with zero range validation (1771 `newValue.RawValue`, 2820 `({rawArrayType}){name}[i]`). For a `SimpleEnum`, C# emits a genuine value-type enum where `(MyEnum)999` is legal and unchecked; that out-of-range value crosses to Swift, `init(rawValue:)` returns nil, and the `!` traps. This is an externally-triggerable hard crash from valid, type-correct managed input. A correct fix must harden all six sites uniformly (guard + graceful surfacing, or C#-side range validation) — patching the init site alone is insufficient. The two confirmed entries above (the P0 "five distinct sites" and the P1 root finding) are the same underlying defect captured at different granularities; treat them as one fix spanning all six emission points. Note: the Optional paths (1340/1573/2013) are guarded by `hasValue != 0`, so they trap only on a *present* out-of-range value, not on null.

**3. ResultClosure ObjC-bridgeable BoundStruct use-after-free (P1).** `value as AnyObject` produces a freshly-bridged class temporary whose lifetime ends at the end of the expression statement; `passUnretained` does not retain it, and the `case .success(let value)` binding keeps only the *struct* alive. The C# trampoline's `GetNSObject<T>(value)` (3772) then wraps a freed pointer. The crash is type-dependent: `Data → NSData` (and custom bridgeable structs) crash deterministically; `URL → NSURL` and `Date → NSDate` happen to survive on undocumented Foundation backing behavior. The proposed remedy (bind to a local before `passUnretained`) was probe-verified to fix it. The `.failure`/error branch shares the same line and is equally affected. The sibling `BoundType` (class) branch at 3847 is **not** affected — there `value` is already a class and the `let value` binding holds it.

**4. Frozen-with-ref-fields closure-arg buffer leak (P1).** `BridgeParameterKind.BoundStruct` covers two ownership contracts: `NonFrozen` (C# *adopts* the handle → Swift must not free) and `FrozenWithMemory`/ClassWithBufferStruct (C# *copies* via `NativeMemory.Alloc` + `InitializeWithCopy`, orphaning the handle → Swift *must* deinitialize + deallocate). `MapDatabaseType` (InitAnalyzer.cs:492-515) returns `BoundStruct` for both; the closure trampoline (3306-3318) and ResultClosure path (3854-3872) emit one no-defer "ownership transfers to C#" path for both. Generation + emit-ir/emit-silgen probes confirmed the frozen-ref struct has a non-trivial VWT and the bridge function returns the retaining-initialized buffer with no `destroy_addr`/release — a per-call buffer leak plus a `+1` on each ref field. The fix mirrors the reference: emit a Swift `defer { argiPtr.deinitialize(count:1); argiPtr.deallocate() }` only when `StructProjection == FrozenWithMemory`. `FrozenBlittable` returns null at InitAnalyzer.cs:501-502 and is unaffected; pure-template-fallback views never reach this path.

## Inconclusive / needs deeper probe

**`BuildViewInitArgsFromChain` auto-infer leaf-name coupling (`AsyncPattern.cs:611`, P1).** The two verifier votes split: one *refuted* (the auto-infer branch correctly routes leaf params through `FormatFlatParamSwiftValue`, so a BoundEnum leaf emits `{name}Enum` and `swiftc -typecheck` of the real output passes); one *confirmed-as-fragility* (the coupling between `FormatFlatParamSwiftValue` (864-873) and the eager-conversion locals (709/741/743/753/764) is enforced *only* by duplicated suffix string literals — `"Enum"`/`"Val"` — with no shared constant, assertion, or test). Both agree there is **no present-day codegen bug**: removing the BoundEnum branch produces non-compiling Swift, proving the coupling is load-bearing and currently correct. The residual is genuine maintainability risk: any future leaf kind whose converted-local name diverges from its ABI param name must be added in lockstep or the auto-infer rootView line silently emits a wrong identifier. **Recommendation:** treat as a hardening item (extract the `"Enum"`/`"Val"` suffixes to shared constants; add a regression test asserting the emitted rootView arg for a BoundEnum direct leaf in the auto-infer branch) — not a bug fix.

## Deferred (candidate, unverified)

These are real candidates not probed due to the per-track verification cap. Listed so nothing is silently dropped; each needs its own probe before being treated as confirmed or refuted.

1. **ResultClosure success/error BoundStruct frozen-with-ref-fields leak** (`SwiftUIBridgeEmitter.cs:3869`, P1) — same root cause as confirmed finding #4 but a separate emission site (Result decomposition). Heap-allocates + `initializeMemory` with no defer-deallocate; C# `NewFromPayload` copies for ClassWithBufferStruct.
2. **BoundEnum modifier-setter force-unwrap** (`SwiftUIBridgeEmitter.cs:2013`, P1) — already swept into confirmed finding #2's six-site family; listed separately in the source queue. Out-of-range C# value traps Swift at the Set site.
3. **Inferred async pattern never deduplicates flattened leaf params** (`AsyncPattern.cs:362`, P1) — duplicate param names across DAG branches emit colliding `_Create` parameters → Swift redeclaration + C# duplicate-parameter compile error.
4. **Async BoundEnum factory param cast to `nint` drops `IsSimpleEnum`** (`AsyncPattern.cs:1216`, P1) — complex (non-Simple) raw-value enums are emitted as C# classes; `(nint)reason` over a class reference is CS0030. The `IsSimpleEnum` bit is dropped in `BridgeParamToFlatParam` and absent from the `AsyncFlatParam` record. Sole outlier vs every sync BoundEnum path.
5. **TypedClosure return encoding ignores ObjC-bridgeable class types** (`SwiftUIBridgeEmitter.cs:3589`, P1) — unconditional `result.Payload + Arc.Retain` has no `IsObjCBridgeable` branch; ObjC-bridgeable class bindings use `.Handle` and ObjC retain. CS1061 (`.Payload` missing) or wrong refcount. The arg-decode at 3494 is similarly unconditional.
6. **TypedClosure BoundStruct argument heap-allocates raw bytes even for ObjC-bridgeable structs** (`SwiftUIBridgeEmitter.cs:3315`, P1) — no `IsObjCBridgeable` branch (unlike the ResultClosure path at 3856-3861), so a `(URL) -> Void` closure arg is heap-allocated as raw struct bytes while C# expects an ObjC object pointer → type confusion.
7. **Async BoundEnum Swift conversion force-unwraps `Type(rawValue:)!`** (`AsyncPattern.cs:753`, P1) — same crash class as confirmed #2 but at the distinct async-path emission site, not covered by the sync-path finding.
8. **SwiftUI bridge C# gate omits visionOS while Swift gate (`canImport(UIKit)`) emits there** (`SwiftUIBridgeEmitter.cs:2221`, P2) — `@_cdecl` symbols compile into the visionOS slice but the C# session/Create block (`#if __IOS__ || __TVOS__ || __MACCATALYST__`) compiles out → bridge silently unusable on visionOS. Latent (visionOS not a current TFM).
9. **`SwiftUIViewDetector` only detects DIRECT `View` conformance** (`SwiftUIViewDetector.cs:56`, P2) — transitive conformance (`protocol MyContent: View {}; struct Foo: MyContent`) and non-literal module names are missed; type emitted as ordinary with no bridge and no diagnostic.
10. **BoundType closure-callback arg uses owning `passRetained` + owning `MarshalFromSwift`** (`SwiftUIBridgeEmitter.cs:3346`, P2) — nets to zero (no leak), but release is GC-deferred → per-invocation retain pressure / retain-cliff for frequently-fired closures; fragile if anyone swaps in the borrowed marshal.
11. **`SwiftUIBridgeCollector` dedups views by unqualified `Name`** (`SwiftUIBridgeCollector.cs:25`, P2) — two same-named Views from different modules collapse to one bridge (first-collected wins, second dropped silently), while emission keys on `{module}_{View}`.
12. **Optional<BoundEnum>/Optional<Primitive> width/sentinel concern for wide/unsigned raw types** (`SwiftUIBridgeEmitter.cs:2961`, P2) — `: 0` literal sentinel and two-switch-table raw-type mapping for `UInt`/`UInt64` enums untested; lower-confidence width concern.
13. **Async result-monitor Task strong-retains the awaited source; cooperative cancel can't interrupt a never-completing await** (`AsyncPattern.cs:628`/`632`, P2) — leak (not UAF) if the awaited method never returns and the session is never Disposed; the use-after-free angle was separately *refuted* (see below).
14. **Non-frozen BoundStruct closure arg `UnsafeMutableRawPointer.allocate` vs C# `NativeMemory.Free` allocator dependency** (`SwiftUIBridgeEmitter.cs:3315`, P2) — undocumented cross-allocator assumption; probe on device under guard-malloc.
15. **BoundEnum closure args silently rejected though BoundEnum is a documented v2 type** (`InitAnalyzer.cs:231`, P2) — `MapClosureType` nulls any closure arg not BoundType/BoundStruct, so `(MyEnum) -> Void` demotes the whole View to template with no log.
16. **Async String factory params emitted as required/non-nullable yet encoded as nullable** (`AsyncPattern.cs:1107`, P2) — `string` (required) vs `?? ""` body, diverging from the simple-view `string?` + `= null`; NRT/optionality mismatch between sync and async views.
17. **`SelectBestConstructor` final tiebreak on ABI declaration order is non-deterministic** (`AsyncPattern.cs:182`, P2) — ties on param count + async depth fall through to positional order; can pick a semantically-wrong but compiling constructor.
18. **`AnalyzeView` classifies a whole View Unsupported if ANY (even unused) constructor has a generic/existential param** (`SwiftUIBridgeEmitter.cs:331`, P2) — a View with one bridgeable init + one generic init is demoted to template, losing coverage of the bridgeable init.
19. **Async `OnReadyTrampoline` dereferences userData GCHandle without the null/IsAllocated guard used by OnError/OnResult** (`AsyncPattern.cs:1005`, P2) — asymmetric guarding; a null/freed userData throws an unmanaged exception across the ABI boundary instead of a graceful no-op.
20. **`InferAsyncPattern` ignores `viewHint.PreferredInit`** (`SwiftUIBridgeEmitter.cs:311`, P2) — async chain built by `SelectBestConstructor` heuristic; a consumer-set `preferredInit` is silently overridden (unlike the simple/generic paths).
21. **`BuildViewInitArgsFromChain` chain-step leaf args keyed by `innerParam.Name` not bridge-param Name** (`AsyncPattern.cs:329`, P2) — divergent external/internal labels → lookup miss → raw ABI name emitted unsuffixed (Bool/BoundEnum loses `Val`/`Enum`). Lower confidence; depends on parser populating decl name vs bridge-param name.
22. **Simple-enum BridgeArray element cast widens/sign-extends vs Swift `Int` element width** (`SwiftUIBridgeEmitter.cs:2820`, P2) — C# enum underlying type vs mapped `nint`/`nuint` rawArrayType skew can corrupt elements or trap the force-unwrap. Lower confidence; hinges on the generator's chosen C# enum underlying type.

## Checked & refuted

Recorded briefly so future agents do not re-chase these.

- **BridgeArray `Count` 4-byte/8-byte ABI mismatch causing heap over-read** (`SwiftUIBridgeEmitter.cs:2360`, claimed P0). The `int` (C#) vs `Int` (Swift) inconsistency is real and cosmetic, but the claimed SIGSEGV mechanism is **physically impossible**: a 32-bit register write zero-extends the full 64-bit register on both arm64 (W-reg) and x86_64 (E-reg). SIL/assembly + real .NET CoreCLR P/Invoke probes confirmed `int count=3` round-trips clean; the count is always `array.Length` over a pinned buffer. Residual: normalize to `nint` for consistency and lock with a unit-test assertion — not a crash.
- **Non-frozen (resilient) BoundStruct via `assumingMemoryBound(to:).pointee` bypasses value witness** (`SwiftUIBridgeEmitter.cs:1316`, claimed P1). REFUTED: `.pointee` of a resilient (address-only) struct does **not** use a static binding-time layout — SIL shows it lowers to `copy_addr [init]` (the value-witness `initializeWithCopy`) + runtime field accessors + `destroy_addr`. The compiler has resilience info at bridge-compile time. Runtime probe read a resilient struct 1001× under MallocScribble/NSZombie with no crash. (Distinct from confirmed finding #1, which is the *ObjC-bridgeable* case where the incoming pointer is an object pointer, not a struct buffer.)
- **BoundType init param `takeUnretainedValue` over un-retained C# handle → dangling reference** (`SwiftUIBridgeEmitter.cs:1299`, claimed P1). REFUTED: `takeUnretainedValue()` lowers to `strong_copy_unmanaged_value` (a real `+1`); storing into the View's strong `@Published`/state property holds an independent ARC `+1` for the session lifetime. Runtime probe: object survives after the C# source is dropped+GC'd; a no-stored-property control deinits immediately. The proposed "fix" (`takeRetainedValue` without a C# `passRetained`) would *introduce* an over-release.
- **View-specific self-returning modifier `applyModifiers` helper fails to compile for non-Self-returning modifiers** (`SwiftUIBridgeEmitter.cs:1240`, claimed P1). REFUTED: the ABI records the *declared* return type, and Swift forces the body to conform. Opaque (`some View`) / wrapped (`ModifiedContent`) returns are recorded as `OpaqueTypeArchetype`/`SwiftUI.ModifiedContent` (a `ProtocolListTypeSpec`, never the parent name), so `IsSelfReturningMethod` correctly *excludes* them — they are dropped, not mis-emitted. Generated bridge compiled cleanly; modifiers with freshly-constructed bodies type-check.
- **Async result-monitor invokes user callback with a possibly-freed CreateState GCHandle** (`AsyncPattern.cs:620`, claimed P1). REFUTED: the `_Free` release closure runs synchronously on the MainActor in one turn (`remove → cancelResultMonitor → release → postReleaseFreeFn`), strictly downstream of handle removal; the monitor body has no suspension point between the `handlesVar.contains` guard and `cb?(...)`. 25,000-interleaving probe: 0 UAF; an artificially-inserted `await` between guard and cb produced ~2940 UAF, proving safety is *because* there is no suspension point. C# probe: `GCHandle.FromIntPtr` on a freed raw handle does not throw; the trampoline's `IsAllocated`/`Target is CreateState` guards suppress it.
- **PreferredInit constructor analyzed but Swift init args built from `Constructors[0]`** (`SwiftUIBridgeEmitter.cs:1218`, claimed P1). REFUTED: for non-generic views `synthesizedArgs` is always null, so `BuildMergedInitArgs` early-returns `viewInitArgs` verbatim and **never consumes** the `Constructors[...??0]` argument. `viewInitArgs` come from `bridgeParams`, whose names derive from the `preferredInit`-selected constructor. Two probes (label-divergent and arity-mismatch inits with `preferredInit:1`) emitted the correct selected-ctor labels. The line-1218 expression is dead code for the non-generic path (latent cruft worth tidying, not a bug). Existing test `BridgeHints_PreferredInitHint_SelectsCorrectConstructor` already covers this.

## Coverage gaps (what this track did NOT reach)

- **Async path force-unwraps and casts** — the deferred queue items #4 (`AsyncPattern.cs:1216` complex-enum `nint` cast) and #7 (`AsyncPattern.cs:753` BoundEnum `rawValue!`) are the async-path twins of confirmed sync-path defects and were not probe-verified here. The async Create / factory / construction-chain surface (`EmitDataDrivenAsyncCreate`, `BuildConstructionChain`, dedup) is largely unprobed.
- **TypedClosure ObjC-bridgeable handling** — deferred #5 (return encoding) and #6 (arg heap-alloc) follow the *same* asymmetry as confirmed finding #1 (missing `IsObjCBridgeable` branch) but at the closure arg/return sites; not independently verified.
- **Detection / collection layer** — `SwiftUIViewDetector` indirect-conformance (deferred #9) and `SwiftUIBridgeCollector` name-only dedup (deferred #11) were read but not exercised through generation.
- **Platform gating** — visionOS gate asymmetry (deferred #8/#15-source) is latent and was not compiled against a visionOS TFM (none exists today).
- **Runtime behavior on device** — every probe ran on host macOS Swift 6.2.4. The NativeAOT (device) path, where allocator and refcount bugs diverge from Mono, was not exercised; deferred #14 (allocator mismatch) specifically wants a device guard-malloc run.
- **No `nuke binding-tests` / `nuke validate` runs** — this was a static + standalone-probe audit; the confirmed defects are not yet locked by any in-repo end-to-end gate.

## Recommended BindingTests fixtures

Swift shapes that would lock down each confirmed defect (fixtures only — no fixes proposed). Add Swift source to `BindingTests/Sources/SwiftBindingsTestLib/SwiftUI/` and C# drivers to the matching `BindingTests/RuntimeTestsApp/SwiftUIBridge/` domain file. None of these shapes exists today.

1. **ObjC-bridgeable struct init param (confirmed #1).** A View with a `Foundation.URL` (and, separately, a `Foundation.Data`) init param:
   `public struct UrlParamView: View { public let target: URL; public init(target: URL) { ... } }`. C# driver: `Create` with a real URL, then read a property derived from it on the Swift side. Today this should crash (URL) or read garbage (a trivial bridgeable struct) at the `assumingMemoryBound(to:).pointee` conversion. Also add an *Update* variant and an *Optional<URL>* variant to cover the parallel sites (837/1333/1550/1566).

2. **Out-of-range BoundEnum across all six sites (confirmed #2/root).** Reuse `enum AlertStyle: Int32 { case info=0, warning=1, error=2 }`. Drive each path with `(AlertStyle)99`: a scalar-init view, an *updatable* enum view (`UpdateStyle((AlertStyle)99)`), a modifier-`Set` enum view, an `Optional<AlertStyle>` view with a present out-of-range value, and an `[AlertStyle]` array view containing `99`. Each should currently trap; the fixture is the permanent gate that the eventual graceful-handling fix is applied uniformly.

3. **ResultClosure ObjC-bridgeable struct branch (confirmed #3).** A View taking a `(Result<Data, MyError>) -> Void` closure (use `Data`, **not** `URL` — URL is incidentally safe). Fire `.success(someData)` and have the C# `Action<NSData>` read `.Length`/bytes. Should currently use-after-free. Add a `.failure` branch with an ObjC-bridgeable error struct to cover the symmetric path.

4. **Frozen-with-ref-fields closure-arg leak (confirmed #4).** `@frozen public struct FrozenRefArg { public let s: String; public init(s: String) }` used as a closure arg: `init(onEvent: @escaping (FrozenRefArg) -> Void)`. Fire the closure N times from Swift and assert via `LifetimeTracker` / RSS that the struct's `String` payload count and heap usage stay flat per call. Pair with a non-frozen-struct closure-arg control that must *not* leak. A ResultClosure twin (`(Result<Int, FrozenRefError>) -> Void`) covers deferred candidate #1.
