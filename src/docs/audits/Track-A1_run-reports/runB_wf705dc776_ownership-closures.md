# Track A1 — P/Invoke ABI Contract + x64/arm64 Thunks

**Scope:** Audited the generator's native-thunk decision pipeline, struct/return register lowering, @convention(c) closure callback emission, parameter-ownership modeling, and the ARM64/SysV thunk assembly targets — i.e. the path that decides whether a Swift symbol is reached via a bare tail-call thunk vs an `@_cdecl` wrapper, and whether the emitted C# P/Invoke signature matches the swiftcc register layout.

**Overall risk rating: 5 / 5 (high confidence).** Seven findings confirmed by probe, including one P0 memory-safety defect (double-destroy of a `consuming` non-copyable value) and three P1 ABI/compile defects. Two of the confirmed findings are silent wrong-value miscompiles on the SIMD/small-struct return path that are masked today only by coincidental layout matches in the existing fixtures. Confidence is high because every confirmed item was verified twice independently — source read + a `/tmp` probe that either compiled the generated C# (CS150x) or disassembled the swiftcc vs C-ABI register convention and round-tripped a value.

### 1 — P0: `consuming` non-copyable struct double-destroy
`UniqueResource` is `~Copyable` (`frozen=false`), so `TypeLowering.LowerStruct` (`TypeLowering.cs:171-178`) returns `Slots=[]`, `IsIndirect=true`, `TotalByteSize=0`. The thunk gate `AreAllParametersLowerable` keys only on `Slots.Count <= 1` (`NativeThunkEmitter.cs:614`, comment "Single-slot param — safe for thunk register shifting") and admits the 0-slot result. The only non-copyable guard in `ShouldEmitThunk` is `IsNonCopyableStructParent(env.ParentDecl)` at `:84`, which gates the *self* type, not a *parameter*. `transferOwnership(_ resource: consuming UniqueResource)` is therefore reached by a bare `jmp/b _$s...transferOwn. ...UniqueResourceVnF` (the trailing `Vn…` = `__owned`/consuming mangling), forwarding the C# `SafeHandle` pointer at +0. The Swift callee destroys (runs `deinit`) through that pointer; the C# wrapper does NOT `Dispose`/`SetHandleAsInvalid`, so `SwiftSafeHandle.ReleaseHandle` later runs VWT `Destroy` + `NativeMemory.Free` on the already-consumed buffer. Probe: a resilient `~Copyable` struct with an observable `deinit` counted **2** destroys for the consuming case (vs **1** for the borrowing contrast); a heap-owning variant SIGABRT'd inside the second destroy. Silent today only because the real `UniqueResource.deinit` is empty with an `Int32` payload — any non-trivial `deinit` or refcounted field is a live use-after-consume / double-free. (Note the related inconclusive item below: the *borrow* sibling has a separately-disputed value-vs-pointer concern, but the consuming double-destroy here is independently confirmed.)

### 2 — P1: divergence guard bypassed on null lowering
`SmallStructReturnDivergesFromCAbi` (`:315`) is meant to decline thunking for small struct returns whose swiftcc field-wise layout diverges from the C-ABI aggregate return. But `:321-323` returns `false` when `LowerReturnType` is null — and `LowerStruct` returns null exactly for a frozen struct with nonzero `InlineSize` and empty `AbiFieldLayout` (`TypeLowering.cs:181-192`, comment "route to @_cdecl instead"). That routing never happens: the null short-circuits the guard, `IsReturnTypeLowerable` falls through to `!NeedsReturnBridging`, and `NeedsReturnBridging` returns false for any frozen `InlineSize<=8` struct (`:700-702`). A mixed int/float ≤8-byte frozen struct in that null-layout state is mis-thunked as a by-value return. Reached today via hand-authored XML (simd) or any cross-module / unclassifiable-field frozen struct (the explicit "Frozen struct without layout info" branch). The contrasting sibling `makeMixedSmall` ({Int32,Float} *with* `abiLayout="i4,f4"`) is correctly routed to an `@_cdecl` `IntPtr resultPtr` wrapper, proving the guard works only when `abiLayout` is present. Probe corrupted the float field to 0 on both arm64 and x86_64.

### 3 — P1: ownership not modeled in the parser/model
`ArgumentDecl` (verified in source) carries `IsInOut` (`:25`) but has no `Consuming`/`Borrowing`/`Ownership` member. `SwiftABIParser.cs` declares `paramValueOwnership` (`:61`) and reads it at exactly one site — `:2167` `IsInOut = childNode.paramValueOwnership == "InOut"` — so `Owned` (consuming) and `Shared` (borrowing) both collapse to `IsInOut=false` and the distinction is discarded. This is the upstream enabler of finding #1: no code path can branch on +1-vs-+0 because the data was never threaded into the model. Any fix to #1 must first add an ownership field to `ArgumentDecl` populated from `paramValueOwnership`.

### 4 & 5 — P1: `@convention(c)` closure Bool/enum parameter forwarded raw
For a non-optional `@convention(c)` closure parameter, `EmitConventionCCallback` declares the `[UnmanagedCallersOnly]` callback param at the P/Invoke type (`TranslateTypeSpecToPInvokeType`: `Swift.Bool→byte`, simple enum→underlying int) and forwards it verbatim (`paramCalls.Add($"arg{argIdx}")`, `:985`) into a `[ThreadStatic]` delegate typed at the idiomatic C# type (`GetCSharpDelegateType`→`TranslateTypeSpecToCSharp`: `Bool→bool`, enum→the C# enum type). The comment at `:984` ("P/Invoke type matches delegate type") is false for these cases. The **return** direction IS bridged (`byte` + `? 1 : 0` at `:1011-1013`), and the **optional** parameter path bridges via `EmitConventionCBoolBridge` (`byte` + `argN != 0`) — only the non-optional parameter direction is broken. Both votes compiled the generated bodies and got `CS1503` (`byte→bool`; `long/int→EnumType`); the int-param and bool-return baselines compiled clean. Findings #4 and #5 are the same root defect at the same line (the orchestrator surfaced two overlapping claims); they should be fixed once, by reusing the existing per-arg bridge (`byte argN` + `argN != 0` for Bool, `(EnumType)argN` for simple enums). Latent only because no BindingTests fixture exercises a Bool/enum **parameter** in a non-optional `@convention(c)` closure.

### 6 — P2: asymmetric SIMD return routing (and a real `simd_float2` miscompile)
`CdeclParamMapper.IsSimdVectorType` forces every SIMD **parameter** through an indirect `UnsafeRawPointer`, and SIMD returns of width >8 bytes (`simd_float3/4`, `double2`) go through `@_cdecl` `IntPtr resultPtr` wrappers. `simd_float2` returns escape both: the thunk return decision never consults `IsSimdVectorType`, relying on the generic frozen-struct gate (`NeedsReturnBridging` `InlineSize<=8`, `:700-702`), which admits `simd_float2` because `SimdDatabase.xml` records it `frozen=true inlineSize=8` with no `abiLayout`. Both votes found this is not merely an organizational inconsistency: on arm64 Swift returns `simd_float2` packed in `d0` while .NET marshals the projected `System.Numerics.Vector2` as an HFA in `s0/s1` (`Y` read from a register Swift never wrote). The existing green test `TestMakeFloat2ReturnsVector2` uses the trivial body `MakeFloat2(3,4)` where `y` coincidentally survives in `s1`; any non-trivial body loses the second lane (`doubleFloat2(3,7)→Y=7` un-doubled; `MakeFloat2Scaled(3,4)→(10,1)` vs expected `(10,22)`). x86_64 mismatches in the opposite direction. Fix direction: route ALL SIMD vector returns (including `simd_float2`) through the same indirect `@_cdecl resultPtr` path the param side and `simd_float3/4` already use.

### 7 — P2: contradictory ARM64 self/error comment (maintenance trap)
Verified in source: `Arm64ThunkTarget.cs:59-60` states the cdecl order is `[self?,] param0, ...` with "self is x0, params start at x1" (self-first), while `:106-108` states/implements `[Arguments][Metadata][Self][ErrorOut]` with `mov x20, x{ParameterCount}` (self-after-args). `CdeclSignatureContract.cs:129-143` and `MethodSignature.cs:948-972` confirm self-after-args is the real order. The numeric `errorOutRegIndex = baseIndex(1) + ParameterCount` happens to equal the correct self-after-args value, and the thunk path rejects generic methods (so the Metadata phase adds 0 cdecl params and self genuinely sits at `x{ParameterCount}`), so this is latent — but a future edit trusting the self-first comment would mis-place self/error by one register. Fix: correct the `:59-61` comment to match the contract. `SysVThunkTarget.cs:51-57,160-165` mirror the same self-after-args layout correctly.

## Inconclusive / needs deeper probe

These had split or non-decisive verdicts and warrant a dedicated register-level probe before action.

- **`borrowing` non-copyable struct param thunked as +0 pointer** (`NativeThunkEmitter.cs:614`). One vote built a same-module probe where the small `~Copyable` struct lowers *loadable* (passed by value in a register) and concluded the binding passes a pointer where Swift expects the scalar → wrong value (returned the low 32 bits of the pointer). The opposing vote disassembled the **actual library-evolution (resilient) build** of `SwiftBindingsTestLib`, found `borrowResource` does `ldr w8,[x0]` (dereferences x0 as a pointer-to-value), confirmed the binding passes exactly that, and showed the existing tests `ClassMarshallingTests.TestBorrowResource` and `OwnershipTests.TestBorrowResourcePreservesOwnership` pass. **Resolution hinge:** whether the shipped framework is built resilient (pointer-at-+0 correct) or same-module/loadable (value-in-register, binding wrong). The resilient-build vote is the stronger evidence for the production artifact, suggesting *borrowing is correct* — but the consuming sibling (#1) is independently confirmed broken regardless. Probe: round-trip `BorrowResource(UniqueResource(id:N))`, assert `==N` AND that `r` is still usable + exactly one `deinit`, on the actual resilient dylib.

- **0-slot/`IsIndirect` lowering conflated with single-register params in thunk admission** (`NativeThunkEmitter.cs:614`). The structural premise (the `Slots.Count <= 1` branch never inspects `IsIndirect`, so a direct single-register param and a 0-slot indirect param share one path) is confirmed by both votes. They split on whether it is a defect: one says the convergence is ABI-correct for `@in_guaranteed` borrows (cdecl-x0 == swiftcc-x0 for a pointer/first-int arg, 101 unit tests pass, behavior-neutral), the other says the *consuming* (`@owned`) case routed through the same branch is genuinely unsafe (same root as #1). Net: the **defense-in-depth smell is real**; whether it is a standalone bug beyond #1 depends on the ownership distinction (#3), which is orthogonal to `IsIndirect`. Recommended: split the predicate to require `!IsIndirect` for the fast path AND derive consuming/borrowing from `paramValueOwnership`.

- **`MaxDirectSlots=4` treated as a COMBINED int+float budget** (`TypeLowering.cs:228`). Direct, sharp disagreement. One vote disassembled `@frozen {Int32×3, Float×2}` (20 bytes, 5 combined slots, fits per-class) and showed swiftcc returns it **directly** in `x0/w1/s0/s1` while the generator marks it `IsIndirect` and ships an x8-sret C# signature → corrupt return; built the full generator end-to-end to confirm the bare tail-call + by-value C# struct. The opposing vote disassembled `{Int×3, Double×2}` (40 bytes) and `{Int×3, Double×3}` (48 bytes) and found swiftcc returns those **indirectly** via x8, concluding the combined-4 limit is correct. **Resolution hinge:** the two probes used different field *widths* — the 20-byte 3i+2f case (≤16 register-return budget per the size interaction) vs the 40/48-byte cases (genuinely over budget). The 20-byte small-and-per-class-fitting case is the unverified gap; the disagreement is likely a size-vs-slot-count interaction, not a flat refutation. A definitive probe must hold total size ≤ the swiftcc register-return budget while exceeding 4 combined slots (e.g. 4-byte fields). Treat as a live candidate.

## Deferred (candidate, unverified)

Real candidates not probed due to the per-track cap — listed so none is silently dropped:

1. **>256-case frozen simple enum with null `InlineSize` truncated to low byte on x86_64** (`NativeThunkEmitter.cs:525`). `ComputeReturnZeroExtension` maps `null/0/1 → 1` byte; `EnumHandler.Marshalling.cs:778,858` default the same null `InlineSize` to 1 byte. Both sides agree on the truncation (so not a thunk-vs-managed mismatch) but a >256-case frozen enum loaded via the XML/cross-module path (`SimpleEnum|Frozen` flags, `InlineSize==null`) would alias `tag → tag & 0xFF` = silent wrong case. Exotic, hence P2.

2. **`TypeLowering.LowerOptional` enum-tag slot placed at integer-register index = count of integer slots, inconsistent with `ReturnBufferSlots` byte-offset model** (`TypeLowering.cs:299`). For `Optional<float-payload>` the tag's register-index view (integer index 0) and its flattened buffer-offset view (after the payload) disagree; any path consuming both would mis-place the tag byte. Latent — `ShouldEmitThunk` rejects Optional returns and multi-slot Optional params today; flagged for the next feature that lifts the Optional-return gate.

3. **`ThunkDescriptor.SelfLowering` computed and stored but never read by any thunk target** (`NativeThunkEmitter.cs:740`). Both `SysVThunkTarget` and `Arm64ThunkTarget` hard-code self into the integer self register (`r13`/`x20`) as a single pointer; `IsSelfTypeLowerable` is the only line of defense. A future multi-register value-type self would silently diverge from the stored lowering. Dead ABI input.

4. **SysV `EmitMetatypeSetup` offsets integer arg spill/restore by `sretOffset` but uses a fixed xmm base for floats** (`SysVThunkTarget.cs:284`). Correct today (sret hidden pointer is integer-class, never shifts FP arg registers) but the asymmetric invariant has no assertion; a future float-classed hidden return arg would silently swap the float restore base.

5. **`ComputeReturnZeroExtension` folds `null/0/1 → 1` byte zero-extend** (`NativeThunkEmitter.cs:525`). Distinct input class from (1): conflates unknown-size and zero/Void-like returns with a genuine 1-byte return → spurious/truncating `movzbl`. P2.

6. **Verified-clean note (no action — re-flag avoidance):** the orchestrator recorded that Optional-tag-on-float-payload, multi-register by-value frozen struct params, ARM64/SysV self placement, SysV register overflow gating, and the synchronous throwing error-pointer path (`MethodMarshalPlanBuilder.BuildSwiftErrorSetup`, `:1046-1227`) were each traced and found correctly guarded. Listed here so future agents don't re-chase; the suggested hardening is to add BindingTests fixtures (Optional<Double> return, 16-byte struct-by-value param, throwing mixed int/float method) that would have tripped each path.

## Checked & refuted

- **ARM64 thunk has no `CanEmit` register cap; only SysV's ≤6-GPR gate protects the 8-GPR path** (`Arm64ThunkTarget.cs:111`). The ABI mechanism is real and a reflection probe reproduced the predicted corruption (`mov x20, x8` reading the AAPCS64 indirect-result register for an 8-int-param self bridge) — **but only on the `x64AsmBuilder == null` path, which does not exist in production.** `ModuleEmissionContext._x64AssemblyBuilder` is a `readonly` field initialized `= new()`, never null; all four production callers pass it, so the SysV ≤6 cap always runs and conservatively covers the ≤8 ARM64 budget. The "arm64-only build" the comment contemplates has no implementing code path. This is latent fragility / missing defense-in-depth (Arm64ThunkTarget should have its own `CanEmit` cap), **not** a live wrong-ABI/SIGSEGV defect. Do not re-file as a live defect; consider only the hardening (add an ARM64 `CanEmit` ≥8-GPR/>8-FP cap).

## Coverage gaps (what this track did NOT reach)

- **Async / throwing-async thunk paths.** Only the synchronous throwing error-pointer path was spot-checked (and found sound). The async Start-thunk closure dispatch, continuation marshalling, and async error propagation were not probed for ABI correctness.
- **`@_cdecl` wrapper-side ABI** beyond the SIMD/struct-return and consuming-param interaction — e.g. inout parameter buffer lifetimes, indirect-return `resultPtr` alignment for >16-byte structs, and existential/protocol-witness P/Invoke signatures.
- **`StringEmitter` UTF-8 slice marshalling** (`SBW_Utf8Slice`) ABI was not exercised; only referenced in passing.
- **x86_64 runtime confirmation.** All x86_64 evidence is from disassembly + Rosetta; no native x64 device run. The `simd_float2` x86_64 divergence (finding #6) and the mixed-struct x86_64 corruption (finding #2) are disassembly-proven but not executed on a true x64 host.
- **The three inconclusive items** (borrowing-param ABI, 0-slot conflation as a standalone bug, combined-4-slot small-struct return) each need one focused register-level probe to settle.
- **`generated BindingTests/output/*.cs + *.swift`** were inspected as evidence for the confirmed findings but not exhaustively diffed for other emitter regressions.

## Recommended BindingTests fixtures

Swift shapes that would lock down each confirmed defect (shapes only — no fix proposed):

1. **(#1, P0)** `public struct R: ~Copyable { let id: Int32; deinit { /* increment an observable global counter or os_log */ } }` plus `public func take(_ r: consuming R) -> Int32` and a contrast `public func borrow(_ r: borrowing R) -> Int32`. Runtime test: create `R` in C#, call `Take(r)`, let `r` Dispose/finalize; assert `deinit` runs **exactly once** (today: 2). Add a variant whose `deinit` frees a `malloc`'d pointer (or owns a class ref) to force a hard crash on the double-free. Run on `--sim` and `--device`.

2. **(#2, P1)** A frozen `{Int32, Float}` struct that reaches the null-`AbiFieldLayout` state — either a cross-module frozen struct whose fields the parser can't classify, or an XML-DB entry with `InlineSize=8` and empty `abiLayout`. Free function `makeMixedTiny(a:Int32, b:Float) -> MixedTiny`. Round-trip on arm64 AND x86_64, assert `b` survives (e.g. `a=0x41424344, b=3.5`).

3. **(#3, P1)** Covered by the #1 fixtures plus a unit assertion that the parsed `ArgumentDecl` for the `consuming` param carries an ownership flag (after the model field is added) distinct from the `borrowing` param.

4. **(#4/#5, P1)** Add to `BindingTests/Sources/SwiftBindingsTestLib/Closures/ConventionC.swift`: `public func callCBoolConsumer(_ fn: @convention(c) (Bool) -> Void)`, `public func callCBoolBinary(_ fn: @convention(c) (Bool, Int32) -> Int32) -> Int32`, and an `@objc` simple-enum variant `@convention(c) (Direction) -> Void`. 5. **(#6, P2)** `public func makeFloat2NonTrivial(_ x: Float, _ y: Float) -> simd_float2 { return simd_float2(x, y) * 2 }` (a body that clobbers the input registers so the HFA-coincidence can't mask the loss). 6. **(#7, P2)** A throwing frozen-struct instance method `func f(_ a: Int) throws -> Int`; assert (via the thunk unit test, `ThunkAssemblyEmitterTests`) the ARM64 asm reads self from `x{ParameterCount}` and error_out last — codifying the self-after-args layout the `:59-61` comment contradicts.
