# Track A1 — P/Invoke ABI Contract + x64/ARM64 Thunks

**Scope:** Audit of the cdecl ↔ swiftcc bridge contract: the `@_cdecl`/native-thunk parameter-ordering contract (`CdeclSignatureContract`), the C# P/Invoke signature builder, the per-arch thunk emitters (`Arm64ThunkTarget`, `SysVThunkTarget`, `ThunkAssemblyEmitter`, `TypeLowering`), the cdecl parameter mapper, and the generic protocol-witness-table (PWT) ordering — verified against generated `BindingTests/output/*.cs`/`*.swift` and compile/disassembly probes.

**Overall risk rating: 5 / 5 (critical).** *Confidence: high.* Two independent P0 memory-corruption defects (throwing-class-constructor error-register placement on **both** arches; ARM64 x8 sret-register loss on the static-method metatype path) generate silently-wrong, crashing ABI for any third-party Swift library that uses those shapes. They escape the test suite only because no BindingTests fixture exercises them. Both were demonstrated by end-to-end generator + assembly probes, not just code reading. Two further P1 ABI mismatches (Foundation.Data two-word asymmetry; generic-PWT culture-sensitive ordering) are latent today and trigger under register pressure / specific protocol-name pairs.

### Per-item detail

**Throwing class-constructor error-register placement (P0, both arches).** `CdeclSignatureContract.DetermineParameterOrder` puts a *class* constructor's phases in order `[ErrorOut][Arguments][Metadata]` (`CdeclSignatureContract.cs:100-114`; `needsResultPtr = !isClass` drops ResultPtr for classes), so the generated C# P/Invoke and the thunk's entry contract both place the error-out pointer in the **first** integer register (x0 / %rdi). But both thunk targets compute the error register as if it were **trailing**: `errorOutRegIndex = (needsSelf?1:0) + ParameterCount` (`Arm64ThunkTarget.cs:62-67`) and `errorCdeclIndex = ParameterCount + (needsSelf?1:0) + sretOffset` (`SysVThunkTarget.cs:163-165`). For a 1-arg ctor that yields x1/%rsi — the *value* register. The thunk then (a) feeds the error-out pointer into the Swift init as its integer argument and (b) writes the captured swifterror through the integer value reinterpreted as an address. Throw path → wild store / SIGSEGV; success path → x21/%r12 (=0) written to the bogus address. `NativeThunkEmitter.ShouldEmitThunk` only gates `HasTypedThrows` for the throws dimension (line 67), so a plain `throws` non-failable, non-actor-isolated, value-arg **class** ctor passes every gate and IS thunked (`NativeThunkEmitter.cs:461` sets `IsInstanceMethod=false` for ctors). The fix must drive the thunk's register math from the contract's phase order (errorOut first for class ctors), not the trailing-error formula that is only correct for regular/instance methods. The SysV metatype spill cascade (`SysVThunkTarget.cs:277-280`) is the same root cause: `EmitMetatypeSetup` spills `IntArgReg(sretOffset + i)` starting at %rdi, capturing the leading errorOut as "arg0."

**ARM64 x8 sret-register loss on the static metatype path (P0, ARM64-only).** For a `static func` returning a `ReturnLowering.IsIndirect` struct (a >32-byte / >4-slot frozen all-scalar struct, `TypeLowering.cs:227-237`), the cdecl indirect-result buffer arrives in x8 (AAPCS64 hidden sret). `Arm64ThunkTarget.cs:88-89` saves x8 → x19 **only when `needsReturnBridge`**, and `ThunkAssemblyEmitter.NeedsReturnBridge` returns false for `IsIndirect` (`ThunkAssemblyEmitter.cs:163-165`). `EmitMetatypeSetup` (`Arm64ThunkTarget.cs:164-218`) spills/restores only x0..x{n}/d0..d{n} around the accessor `bl` — never x8. Since x8 is caller-saved and the accessor clobbers it (verified: it calls `objc_opt_self`), the subsequent `bl <make>` writes the return struct through a corrupt pointer. The SysV target handles the identical descriptor correctly via the `cdeclUsesSret`/`swiftIndirect` pair (`SysVThunkTarget.cs:64-65,183-184,215-216`), which is *independent* of `needsReturnBridge`. ARM64 has no equivalent — a genuine arch asymmetry. Constructors are excluded from struct thunking (`NativeThunkEmitter.cs:102`) and class ctors return a class pointer in x0, so the metatype+IsIndirect combination is reachable only by a static method; no fixture exercises it (the comment at `NativeThunkEmitter.cs:246-250` claims the bridge exists — on ARM64 it does not). *Note on one factual slip in the source finding:* its claim that the corpus has zero `...Ma` thunks is wrong (there are ~40), but every one is a constructor (x0 return) or a non-IsIndirect static getter — none hit the hazard. Verdict unaffected.

**Generic PWT culture-sensitive ordering (P1).** Three sort sites order a generic parameter's conformances by `ConformanceTarget.ModuleQualifiedName`. `PInvokeEmitter.cs:839` (P/Invoke param decl) and `MethodMarshalPlanBuilder.cs:162` (call-site PWT var decls) use the bare `OrderBy(...)` (current-culture comparer); `PInvokeHelperEmitter.cs:235` uses `StringComparer.Ordinal`. Swift's swiftcc witness-table ABI order is the canonical generic-requirement order, which is **Ordinal/ASCII byte comparison of the qualified protocol name** (confirmed via SIL/IR/demangle — Swift re-canonicalizes independent of source order). Culture vs Ordinal diverge for underscore-prefixed names (`_Internal` vs `View2`, very common in stdlib/SwiftUI) — *in every culture, including invariant* — and for case-adjacent names; the Turkish-locale dotted/dotless-I also flips letter-only names on a non-invariant host. Because the method-level-generic P/Invoke binds the raw swiftcc symbol directly (no `@_cdecl` wrapper to re-canonicalize), the C# positional PWT order **is** the swiftcc order; a divergent pair swaps witness tables → wrong witness. The fix is `StringComparer.Ordinal` at both `:839` and `:162` (they must move together to keep decl/call-site slot order consistent), matching the already-correct `:235`. *Adjudication note:* the headline "generic constructor on generic parent via `PInvoke_getMetadata`" scenario one verifier flagged as *masked* (the class init/getter take no trailing PWT ABI args; the metatype carries them via the Ordinal-correct `_sbw_meta` helper), while another verifier showed the same `_sbw_meta` path IS reached with default order at the C# call site. Either way the root-cause defect and fix are identical; the surfacing shape is method-level-generic dispatch and possibly the constructor-on-generic-parent path. Confirmed.

**Foundation.Data two-word asymmetry (P1, ARM64).** `CdeclParamMapper.cs:284-289` emits a Data `@_cdecl` param as `_dW0_<name>: Int, _dW1_<name>: Int` (reconstructed via `unsafeBitCast`). The C# side has no matching branch — `ShouldDecomposeStringForCdecl` (`MarshallingHelpers.cs:64-66`) gates two-word emission on `IsSwiftString` only, and `PInvokeEmitter.cs:758-763` is the String-only consumer; Data falls through to the FrozenBuffer/struct path (`:765-768`), passing a single 16-byte `Swift.Foundation.Data` by value. These coincide only when the struct lands in two consecutive GP registers. Under AAPCS64 register pressure (7+ leading integer-class args, odd remaining-register count) a 16-byte composite goes wholly to the stack while two scalars fill the last register + spill — the two callees read different bytes. Demonstrated as silent corruption (not a crash) in an e2e arm64 probe. All in-repo fixtures put Data first (x0/x1), masking it. x86_64 did not diverge at the tested 7-arg boundary; the ARM64 defect alone is sufficient. Fix: generalize the two-word decomposition to also cover `Foundation.Data` on the C# side, mirroring the String precedent (both sides agree).

**Thunk throwing-ctor / static-throwing coverage gap (P1).** Confirmed empirically: `grep -c KcfC` (throwing-constructor mangling) on both generated `.s` files = 0; the only error-bridge thunk combining metatype-setup + x21/%r12 store is `safeDivide` (a throwing *static* method, distinct register layout). The throwing-class-ctor register model is exercised only without the error bridge, and the error bridge only for instance/static/free shapes — their intersection is never produced. This is exactly why the two P0 ctor defects ship silently.

## 3. Deferred (candidate, unverified)

These are real candidates not reached due to the per-track probe cap — listed so none are silently dropped:

1. **Contradictory cdecl self/errorOut comments masking the ctor bug (`Arm64ThunkTarget.cs:59`, mirrored `SysVThunkTarget.cs:161`).** P2 documentation/contract-consistency. The two in-file comment blocks model self at opposite ends; neither enumerates the constructor `[ErrorOut]`-first order. Probe idea: a unit test asserting that for every `(IsConstructor, IsStaticMethod, IsInstanceMethod, Throws)` combination the thunk's computed errorOut/self register index equals the index the contract's phase list yields — the constructor row will fail, pinning the divergence. (Closely tied to the confirmed P0; same code, different file/line lens.)

2. **Bool `@_cdecl [MarshalAs(U1)]` relies on exact `"bool"` string match (`MethodSignature.cs:401`, `MarshallingHelpers.cs:578`).** P2 fragility. Correct today (sampled P/Invokes route through `PInvokeSignatureString`→`[MarshalAs(U1)]`), but `IsBoolType(string) => type == "bool"` and a divergent `SignatureString` path (no attribute) mean a future fully-qualified `System.Boolean` name silently drops U1 → 1-vs-4-byte mismatch vs Swift `Int8`. Harden by routing through `IsBoolType(TypeSpec)`.

3. **Two more fragile bool-string sites in `CdeclParamMapper.cs:72,836` (`IsBoolType(x) || x == "Bool"`).** P2 fragility, second file. The redundant `|| == "Bool"` disjunct signals distrust of `IsBoolType` over rendered strings; a sugared/module-qualified Bool render would emit a full-width Swift `Bool` against the C# `[MarshalAs(U1)]` byte.

4. **3-byte no-payload-enum tag never zero-extended on x86_64 (`NativeThunkEmitter.cs:525`, `_ => 0` arm).** P2. `InlineSize == 3` (65537–16,777,216 cases) → `ReturnZeroExtendFromBytes == 0` → `EmitReturnZeroExtension` emits nothing, leaving the 4th byte of %eax dirty. Opposite corner of the confirmed P2 truncation. Exotic enums; gate is asymmetric with the documented "4+ bytes fills %eax" intent. **Verified present** by code read during this audit (the `_ => 0` switch arm at line 525).

5. **`LowerOptional` value-type tag-slot model (`TypeLowering.cs:297`).** P2 latent/likely-dead. Appends a 1-byte integer tag slot at `slots.Count(Integer)`; any non-trivial value-type Optional yields `Slots.Count >= 2` → rejected by `AreAllParametersLowerable` (`NativeThunkEmitter.cs:620-621`), and Optional returns are rejected. Either dead-but-misleading code or an untested single-slot corner. Also flagged separately as a possible divergence from Swift's spare-bit/payload tag placement for `Optional<Float>` / frozen-payload types — a future direct consumer trusting these slots would emit a wrong-ABI thunk.

6. **`NeedsReturnBridge` conflates "needs repacking bridge" with "needs indirect pointer preserved across a call" (`ThunkAssemblyEmitter.cs:163`).** P2 — the *structural* root cause of the ARM64 x8 P0. SysV uses two predicates (`needsReturnBridge` vs `cdeclUsesSret`/`swiftIndirect`); ARM64 uses one. A clean fix introduces an IsIndirect-aware ARM64 predicate.

## 4. Checked & refuted (do not re-chase)

| file:line | claim | why refuted |
|---|---|---|
| `Emitter/StringEmitter/CdeclParamMapper.cs:799` + `EnumHandler.SimpleEnum.cs:28-29` | Tag-only (no-raw-value) simple enum: Swift declares 8-byte `Int`, C# declares 4-byte `int` → register-width ABI violation / latent crash | **Refuted by two independent probes.** The width inconsistency is real *cosmetically* but is **not** an ABI violation: (1) a 300-case (2-byte-tag) enum round-trips all 0–299 cases through the generated pattern; (2) .NET *deterministically zero-extends* the 32-bit arg into the upper 32 bits of x0/%rax on both Mono JIT and NativeAOT (passing `int -1` → Swift sees `0x00000000FFFFFFFF`, not garbage); (3) the Swift body reads exactly the tag bytes via `load(as:)` (single `ldrb`), so the high bytes never matter; (4) enum case indices are 0..N-1, so the `(int)` cast cannot truncate a real tag. Cosmetic cleanup only — not a defect. |

## 5. Coverage gaps (what this track did NOT reach)

- **Runtime execution on real hardware.** All probes were standalone compile/disassembly/emit probes in `/tmp` (the source findings ran the actual generator + `swiftc`/`clang` + `otool`, and linked/ran emitted thunks natively). No probe ran the full `nuke binding-tests --device` (NativeAOT/ARM64) or `--sim` pipeline. The P0s are demonstrated at the assembly/ABI level but not yet inside the app harness — which is precisely the missing durable gate.
- **The x86_64 Data boundary** was only characterized at the 7-leading-arg point (no divergence there). Other odd remaining-register configurations on x86_64 were not exhaustively swept; the confirmed corruption is ARM64-only as tested.
- **Closure/inout/generic-method P/Invoke ABI** beyond the PWT ordering question was out of scope here (these are gated out of thunking and routed to `@_cdecl` wrappers; their wrapper-side ABI was not separately audited).
- **The protocol-extension cdecl ordering** (`CdeclSignatureContract` 4th branch, `[ResultPtr?][Self?][Arguments?][Metadata][ErrorOut?]`) was read but not probed against the thunk register model — the thunk targets only enumerate the regular/constructor shapes; a throwing protocol-extension method through a thunk was not exercised.
- **Async / swifttailcc** thunking is excluded by `ShouldEmitThunk` and not in scope.
- **Whether `MethodMarshalPlanBuilder.cs:162` independently mis-binds** (vs being inert because consumed by name) is unresolved (see §2).

## 6. Recommended BindingTests fixtures (Swift shapes, no fixes)

1. **Throwing non-failable final-class init with value args (locks the two P0 ctor defects + the coverage gap).** Add a non-actor-isolated `public final class ValidatedBox { public let v: Int32; public init(value: Int32) throws { guard value >= 0 else { throw SomeError.bad }; self.v = value } }`. It passes every `ShouldEmitThunk` gate → thunked. Add RuntimeTestsApp tests calling it with a value that throws and one that succeeds, on **both** `--device` (NativeAOT/ARM64) and `--sim` (x86_64 via Mono / arm64 sim). Today: SIGSEGV / corrupted `v` / uninitialized `errorPtr` read. Include a 2-arg variant to exercise the argument-shift cascade.

2. **Static factory returning a >32-byte frozen all-scalar struct (locks the ARM64 x8 P0).** Add `public struct Big40 { let a,b,c,d,e: Int64 }` (40 bytes → `ReturnLowering.IsIndirect`) with `public static func make() -> Big40` on a class *and* a struct namespace (so the metatype accessor is invoked). The static method is not excluded from thunking. Run on a physical iOS device — today: SIGBUS/SIGSEGV. Contrast with the same as an *instance* method (self in x20, no accessor) which already works.

3. **Generic method whose one type param conforms to two protocols whose qualified names diverge under culture vs Ordinal (locks the PWT ordering P1).** Use an underscore-prefixed pair, e.g. `protocol _Aux {}` + `protocol View2 {}` with `func combine<T: _Aux & View2>(_ x: T) -> Int32` where each witness returns a distinct value. Call methods that dispatch through each witness and assert the values are not transposed. (Diverges in every culture, so no special build host is needed.) A unit test asserting `HandleProtocolConformance`, `MethodMarshalPlanBuilder`'s witness emission, and `FlattenConformances` all produce identical orderings for a deliberately-divergent set is a cheaper companion gate.

4. **`Foundation.Data` param after 7 leading `Int` params (locks the Data two-word P1).** `public func packed(a: Int, b: Int, c: Int, d: Int, e: Int, f: Int, g: Int, payload: Data) -> Int` reconstructing a checksum from `payload`. Round-trip a known `Data` value and assert byte survival on `--sim` and `--device`. Fails on device today (16-byte struct on stack vs two `Int` words). Also dump the wrapper SIL/asm to confirm x0..x7 vs stack placement.

5. **>256-case `@frozen` no-payload enum returned by value through a thunk, registered via the XML/cross-module path that drops `inlineSize` (locks the P2 truncation).** A `@frozen enum BigTag { case c0, …, c300 }` returned from a thunk-routed value-return method; assert a case with raw value ≥ 256 round-trips on x86_64 (SysV / Rosetta / x86_64 simulator slice). Today the high byte is dropped (`movzbl`), collapsing the case to `(rawValue & 0xFF)`. Optionally a 3-byte-tag variant for the deferred `InlineSize == 3 → 0` corner.

(No fixture is proposed for the comment-only P2s — those want a unit test cross-reading `CdeclSignatureContract.DetermineParameterOrder` against both thunk targets, per §3 item 1.)
