# Track A1 — P/Invoke ABI Contract + x64/arm64 Thunks

**Scope:** Audit of the cdecl→swiftcc thunk emitters (ARM64 / SysV x86_64), `TypeLowering`, the `NativeThunkEmitter` decision gates, the `@_cdecl` wrapper marshalling/return path, `CdeclParamMapper`, and the generated BindingTests artifacts — verifying that the generated C# P/Invoke, the Swift wrapper, and the native thunk all agree on calling convention, register/buffer placement, sret/error modeling, and value widths.

**Overall risk rating: 4 / 5** (confidence: high). Five distinct ABI-contract defects were probe-confirmed against the real Swift 6.2.4 toolchain. All five are *silent wrong-value or crash* hazards (no compile-time signal), and three (the struct-offset/register defects and the small-float gate bypass) corrupt return values on fully supported, tested platform paths. The rating is not 5 because every defect is gated behind a specific reachable-but-uncommon type shape (nested frozen struct, packed same-register-file fields, missing `AbiFieldLayout`, >256-case enum, static method returning a large struct), so the *common* binding corpus is unaffected — and the broad "30+ wrapper sample" mechanical sweep found no defect in the ordinary path.

### Nested-struct offset + same-register packing (`TypeLowering.LowerStruct` / `ReturnBufferSlots`) — P1
Two independent probes converged on the same root: the flat `AbiFieldLayout` comma-string carries register-file + field-width but **not** byte offsets or inner-struct alignment, and `LowerStruct` assigns registers positionally (`intIndex++/floatIndex++`, `TypeLowering.cs:215-218`). Both votes corrected the claim's "Swift reorders fields" premise — Swift does *not* reorder — but confirmed the defect via two real mechanisms: (a) `ModuleProcessor.ClassifyFieldType` (`:627-628`) inlines a nested frozen struct's layout string, dropping its alignment, so `ReturnBufferSlots`' `AlignUp` accumulator (`ThunkAssemblyEmitter.cs:188-198`) reconstructs wrong offsets across the nested boundary; and (b) swiftcc coalesces multiple same-register-file sub-eightbyte fields into one return register, which the per-field slot model never models. Both reach the buffer-store via `Arm64ThunkTarget.EmitReturnStore` (`:228`) and `SysVThunkTarget.EmitReturnStore` (`:321`), so x86_64 is corrupted too. Manifests when `InlineSize` resolves from live metadata (>16B return on a host-loadable slice, e.g. `nuke binding-tests --macos`). On the cross-compiled iOS-sim slice `InlineSize` stays null and the case degenerates to a (separately latent) plain tail-call. The existing `MixedWide`/`WidePair` fixtures pass only because each field owns a full eightbyte or splits int/float across register files.

### Small ≤8B float struct gate bypass — three findings, one root (`NativeThunkEmitter.cs:321` + `:700`) — P1
Three confirmed votes (two probing the same defect from the lowered-vs-fallback angle, one from the shipping-SIMD2 angle) establish: when `TypeLowering.LowerReturnType` returns null (frozen struct, `InlineSize≤8`, absent/unparseable `AbiFieldLayout` — `TypeLowering.cs:181-192`), `SmallStructReturnDivergesFromCAbi` early-returns false at `:322` (the divergence gate never fires) **and** `NeedsReturnBridging` waves the struct through at `:700-702`, so `ShouldEmitThunk=true` and a bare tail-call thunk is emitted with no return repacking. swiftcc returns a mixed `{Int16,Float}`/`{Float,Float}`/SIMD2 field-wise across two register files; the C ABI / CLR reads it from a single GPR/SSE register → the second field is corrupt on x86_64. The premise is realistic, not a stripped-XML hypothetical: `ComputeAbiFieldLayout` returns null for a frozen struct whose stored field is a tuple/closure/protocol-composition/nested-struct (`ModuleProcessor.cs:502-507,627-633`), and the XML round-trip writes `inlineSize` but omits `abiLayout` when null (`ModuleDatabaseEmitter.cs:217`, `TypeDatabase.cs:406`). One vote demonstrated end-to-end that the **shipping** `simd_float2`→`Vector2` is itself corrupted on CoreCLR x86_64 (Y=0), refuting the long-standing comment that SIMD2 is packed into a single xmm0. Single-`Float` structs are genuinely safe (swiftcc s0 == C-ABI s0), so the corrupting domain is the multi-field/mixed/two-packed-float ≤8B case.

### Enum return zero-extension truncation (`NativeThunkEmitter.cs:525`) — P2
`ComputeReturnZeroExtension` only emits a 2-byte `movzwl` when `InlineSize==2` explicitly; a null `InlineSize` (every XML/cross-module enum record — `inlineSize` is persisted only from live metadata, `ModuleProcessor.cs:749-755`, and `ModuleDatabaseEmitter.cs:213` writes it only `when HasValue`) falls to the 1-byte `movzbl` arm regardless of case count. A >256-case `@frozen` no-payload enum has a 2-byte tag (`movw $299,%ax`), so the high byte is discarded: case 256→0, 299→43 (verified vs `SysVThunkTarget.cs:344-355` which maps width 1→`movzbl`, 2→`movzwl`). x86_64-only (AArch64 callee widens). One vote noted the in-code comment understates the gap — `inlineSize` is absent for *all* generated enum records, not just cross-module ones. Latent: requires the rare >256-case enum + null `InlineSize` + x86_64 target intersection. `NeedsReturnBridging:695-697` admits a frozen simple enum unconditionally (no `InlineSize` guard), so it is never diverted to `@_cdecl`.

### ARM64 x8 not preserved across metadata accessor (`Arm64ThunkTarget.cs` EmitMetatypeSetup) — P2
`EmitFullFrame` gates the x8→x19 save solely on `needsReturnBridge` (`:88`), which `NeedsReturnBridge` returns false for an indirect (>32B) return (`ThunkAssemblyEmitter.cs:164`). `EmitMetatypeSetup` (`Arm64ThunkTarget.cs:164-218`) then saves only x0..x{N-1}+d-regs around the accessor `bl` (`:183-197`), never x8. A static method on a plain class returning a large frozen struct reaches this (the `MethodRequiresIndirectResult` gate returns false for a frozen struct on the non-cdecl thunk path — `MarshallingHelpers.cs:380` — and `NativeThunkEmitter.cs:246-250` explicitly documents that such a return "IS thunked"). The real `objc_opt_self` reached via every ObjC-interop class accessor `*CMa` clobbers x8 (`ldr x8,[x0]`), so the cdecl sret pointer is destroyed before the Swift call reads it. The x86_64 target stashes %rdi→%rbx for exactly this reason (`SysVThunkTarget.cs:183-184,215`); ARM64 lacks the equivalent. Trivial cached-metadata accessors leave x8 intact, so the bug is latent for those but a guaranteed SIGSEGV for any accessor whose body/callee touches x8. *Note:* the cited line 164 is the `EmitMetatypeSetup` signature / the `IsIndirect` early-return in `NeedsReturnBridge` — the defect spans both; both EVIDENCE references resolve correctly.

### ARM64 missing `CanEmit` overflow guard (`Arm64ThunkTarget.cs:111`) — P2
`Arm64ThunkTarget` never overrides `ThunkTargetArch.CanEmit` (base returns true, `ThunkTargetArch.cs:60`), so nothing caps the integer-register count. Self is read from `x{ParameterCount}` (`:111`) and error from `x{ParameterCount+1}` (`:66,:95`); AAPCS64 passes only x0-x7 as args (x8 = indirect-result, 9th+ spill to stack), so high-arity instance/throwing signatures read self/error from x8/x9/x10 → garbage self pointer. Latent today because all four production call sites pass a never-null `X64AssemblyBuilder` (`ModuleEmissionContext.cs:1317`), and the stricter SysV `CanEmit` (≤6 integer regs, `SysVThunkTarget.cs:76`) at `NativeThunkEmitter.cs:477` declines these shapes before ARM64 would mis-emit. Becomes P0 on the arm64-only emission path the comment at `NativeThunkEmitter.cs:476` contemplates as supported but no caller exercises today. The fix is to mirror SysV with a `CanEmit` override that caps cdecl integer-register consumption at 8.

## Deferred (candidate, unverified)

These are real candidates not yet probed due to the per-track cap. Listed so they are not silently dropped.

1. **Constructor-only thunk guard is narrower than the stated Mono-AOT hazard** (`NativeThunkEmitter.cs:102`, P2). `ShouldEmitThunk` rejects struct-returning `LibraryImport` only for struct *constructors*, but free/static functions returning a >16B frozen struct by value (e.g. `makeMixedWide`→`MixedWide`) emit the structurally identical struct-returning `LibraryImport` and are not rejected. Either the constructor guard is over-broad (the shape is fine and the rejection is dead) or under-broad (free/static functions should be gated too). Probe: run `nuke binding-tests --device` and check `TestMixedWideFactoryRoundTrip` / `TestWidePairFactoryRoundTrip`.

2. **`TypeLowering.LowerOptional` over-counts extra-inhabitant Optionals** (`TypeLowering.cs:300`, P2). Appends a phantom 1-byte tag slot for every value-type inner, but `Optional<Bool>` and small no-payload enums reuse a spare bit pattern (size == inner size, no tag). Reports `Optional<Bool>` as 2 slots / 2 bytes vs the real 1 slot / 1 byte. Latent — Optional params with >1 slot are rejected by `AreAllParametersLowerable` and Optional returns are gated out — but the primitive itself reports a wrong shape that a future relaxed gate or recursive aggregate would trust. (Confirmed in source: `:297-302` appends the tag unconditionally for any non-class value-type inner; the class case is special-cased at `:286-290`, the extra-inhabitant case is not.)

3. **Stale/self-contradictory self-parameter ABI comment** (`Arm64ThunkTarget.cs:60`, P2). The header comment says "self is x0, params start at x1," but the code (`:111`) and the adjacent correct comment (`:104-106`) put self LAST at `x{ParameterCount}`; emitted asm agrees with the code. Pure documentation hazard, but under the AI-maintainability constraint an agent trusting line 60 could "correct" the working `mov x20,x{ParameterCount}` to `mov x20,x0`, producing a self/arg register swap (SIGSEGV) on every thunked instance method with ≥1 parameter.

4. **Vector2/SIMD2 single-xmm assumption never verified** (`TypeLowering.cs:192`, P2). The `makeFloat2`→`Vector2` path lowers to null and tail-calls without ever asserting the packed-vector property; this is the same null-lowering outcome a non-vector two-float aggregate gets (overlaps the confirmed `:321` finding). Recommend an explicit single-SSE-slot lowering for SIMD types so the safe outcome is reasoned and a non-SIMD lookalike is provably declined. (Note: the confirmed `:321` finding already shows the shipping `Vector2` path is *not* actually safe on x86_64 CoreCLR.)

## Checked & refuted

Briefly, so future agents don't re-chase:

- **ARM64 enum return lacks defensive `uxtb` widening** (`Arm64ThunkTarget.cs:51`, P1 claimed) — REFUTED. Across ~25 inputs (incl. 2-byte-tag and adversarial 64-bit-derived enums) a C trampoline reading the full x0/x64 found 0 dirty bits; Swift's no-payload enum tag is always materialized by a 32-bit write (zeroes x[63:32]) or a zero-extending `ldrb`/`ldrh`. The code is safe. The justifying comment ("AArch64 mandates sub-word widening") is factually wrong (the IR has no `zeroext`; a `UInt8` *value* return is NOT clean) — a documentation nit, not a defect. A defensive `uxtb` would be cheap hardening but fixes no active bug.
- **SysV return-store indexes past 4 integer return registers** (`SysVThunkTarget.cs:328`, P1 claimed) — REFUTED. The mechanism is real (no bounds guard on `IntRetSubRegs[index]`, throws if fed index ≥4) but unreachable: integer slots are a subset of total slots, and `slots.Count > MaxDirectSlots(4)` forces `IsIndirect` (no bridge), so any bridged return has ≤4 total slots → max integer index ≤3 (r8). The claim's own probe shapes (`i4,i4,i4,i4,i4`, `Optional<4-int struct>`) all flip to indirect. A defensive assert would document the invariant; not a defect.
- **x86_64 zero-extend tail-call frame misaligns the stack** (`SysVThunkTarget.cs:110`, P1 claimed) — REFUTED. Empirically the callee's entry %rsp measured `8 mod 16` (i.e. 16-aligned at `callq`, exactly SysV-correct); a negative control with a stray push flipped it and the probe reported FAIL, proving sensitivity. The single `pushq %rbp` realigns correctly; aligned-SSE callees are safe.
- **SysV swiftIndirect+metatype %rbx assumption** (`SysVThunkTarget.cs:215`, P2 claimed) — REFUTED. The co-occurrence IS reachable, but %rbx is callee-saved in SysV and every metadata accessor flavor (struct/class/`objc_opt_self`/generic/`swift_getGenericMetadata`) preserves it; end-to-end run returned correct values. Only an ABI-violating accessor (impossible with standard Swift) crashes it. A unit test for the combination is missing (documentation gap), but codegen is correct.
- **Bool round-trip width mismatch** (`CdeclParamMapper.cs:72`, P2 claimed) — REFUTED. Every Bool P/Invoke param is emitted as `[MarshalAs(UnmanagedType.U1)]` (1 byte) via the single path `MethodSignature.cs:70`; the assembly-wide `DisableRuntimeMarshalling` makes an unattributed `bool` a hard compile error (SYSLIB1051), not a silent 4-byte BOOL. The Swift `!= 0` reconstruction masks to the low byte (`ands w8,w0,#0xff`), so even a non-canonical 0xFF reads correctly. inout write-back lands in the byte C# reads.
- **30+ wrapper mechanical sweep** (`SwiftBindingsTestLib.cs`) — REFUTED (i.e. no defect in the ordinary path). All sampled P/Invoke ↔ Swift `@_cdecl` ↔ thunk-asm triples agree on calling convention, param count/type, self placement, sret/error modeling, bool marshalling, and metadata ordering. `SmallStructReturnDivergesFromCAbi` is correctly applied for *layout-present* records, and protocol-extension methods (self-before-args order) never reach the thunk emitter. (The confirmed `:321` finding is the *layout-absent* hole this sweep did not stress.)

## Coverage gaps (what this track did NOT reach)

- **Runtime confirmation on Mono-JIT iOS-simulator x64** for the small-float/SIMD2 corruption — probes used CoreCLR x86_64 under Rosetta and host arm64; Mono's `Vector2` marshalling on the x64 simulator was not exercised, so the shipping `simd_float2` behavior on the *default* `nuke binding-tests --sim` path is unverified.
- **Parameter-side struct lowering** — the nested-struct/packed-field offset analysis focused on the return-buffer path (`ReturnBufferSlots`/`EmitReturnStore`). Whether the same flat-layout encoding mis-places *inbound* struct arguments was not separately probed.
- **The `@_cdecl` wrapper marshalling/return path** (`WrapperEmitter.Marshalling.cs`, `WrapperEmitter.Return.cs`, `MethodMarshalPlanBuilder.cs`) was read for the bool/optional contract but not exhaustively cross-checked against every projection; only the thunk path received deep probing.
- **The four deferred candidates** above are unprobed.
- **tvOS / Mac Catalyst thunk slices** were not separately inspected; analysis assumed arm64 + x86_64 (SysV) cover the register-model space.

## Recommended BindingTests fixtures

Each locks down one confirmed defect by round-tripping field values on both `--sim` and `--device` (and ideally an x86_64/Rosetta or x64-simulator path where the defect is arch-specific). No code fixes proposed — these are the Swift shapes that would make each defect a permanent in-repo gate.

1. **Nested frozen struct return** (locks `LowerStruct`/`ReturnBufferSlots` offset bug): `@frozen struct Inner { var a: Int8; var b: Int64 }` (alignment 8) inside `@frozen struct Outer { var p: Int8; var x: Inner; var q: Int8 }`, returned by value from a free function and a static method. Assert all four leaf fields round-trip. Must run on a host-loadable slice (`--macos`) so `InlineSize` is non-null and the >16B return path is taken.
2. **Packed same-register-file struct return** (locks the positional-slot register bug): `@frozen struct PackedRet { let a: Int8; let b: Int8; let c: Int64; let d: Int64 }` (24B) and an all-Int32 variant `{Int32,Int32,Int64}` (16B), returned by value. Assert every field; the first field after the packed pair is the canary.
3. **≤8B mixed/float struct with absent layout** (locks the `:321`/`:700` gate bypass): a `@frozen struct` whose stored field is a tuple, e.g. `@frozen struct TupleHolder { var pair: (Int16, Float) }` (so `ComputeAbiFieldLayout` yields null while `InlineSize=8`), returned by value. Assert the float field round-trips (not 0.0). Add a non-SIMD `@frozen struct TwoFloats { var a: Float; var b: Float }` registered without `abiLayout`, and exercise `MakeFloat2`→`Vector2` explicitly on an x86_64 path.
4. **>256-case frozen enum return** (locks the enum zero-extension truncation): a `@frozen` no-payload enum with ≥300 cases in a separate module (so its `InlineSize` is null), returned from a free function selecting case 256 and case 299. Assert the C# value equals 256/299 on an x86_64 run (not 0/43).
5. **Static method returning a large frozen struct** (locks the ARM64 x8-preservation bug): a non-generic class with `static func make() -> Big40` where `@frozen struct Big40` is ≥40 bytes (address-only, `IsIndirect`). Assert all fields round-trip on `--device` (NativeAOT, arm64) — the metadata accessor's x8 clobber is the trigger.
6. **High-arity throwing instance method** (locks the ARM64 `CanEmit` overflow — defense-in-depth): an instance method with ≥7 integer parameters that `throws`, asserting correct self/argument values. Today shadowed by the SysV gate; the fixture documents the invariant and would catch any future arm64-only emission path.
