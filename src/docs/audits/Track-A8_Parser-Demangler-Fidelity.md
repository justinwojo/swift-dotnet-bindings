# Track A8 — Parser / ABI-ingestion / Demangler Fidelity Audit

**Scope:** Fidelity of the front-end that turns compiled Swift artifacts (ABI JSON, `.swiftinterface`, mangled symbols) into the binding Model — `Parser/SwiftABIParser.cs`, `Parser/SwiftInterfaceAccessParser.cs` (esp. `CollectPublicMember` + `IsModuleInternal` negative-space detection), `Demangler/Swift5Demangler.cs`, `Parser/GenericSignatureParser.cs`, plus `tests/UnitTests/ParserTests/*` and `DemanglerTests/*`.

**Overall risk rating: 3 / 5 (moderate).** Confidence: high on the per-finding verdicts (every confirmed item was probe-demonstrated against real `swiftc` output and the freshly-built generator DLL; cited line numbers were re-read directly during this audit and match verbatim). The rating is held to 3 rather than 4 because the most alarming confirmed defects are either **latent** (corrupt Model data that no current emitter consumes, e.g. typed-throws-error and operator/protocol-requirement `IsModuleInternal`) or **shadowed on the default macOS path** (the SwiftSyntax host producer hides several regex-fallback defects). The two findings with live, observable consequences today are the demangler `Y`-modifier gap (broad — `@Sendable` is pervasive) and the unbalanced-paren continuation EOF-swallow (a single poison line can silently drop the rest of a parser pass).

### Typed-throws error type mis-extracted (regex first-match) — `SwiftInterfaceAccessParser.cs:3561/3774`
`TypedThrowsRegex = throws\(([^)]+)\)` with `.Match(line)` returns the **leftmost** occurrence. `swiftc` prints a closure parameter's typed-throws clause **before** the function's own trailing clause on the same interface line, so a function carrying a typed-throwing closure parameter records the parameter's error type as its own. The consumer `SwiftABIParser.cs:2046` builds `{parentDecl.Name}.{printedName}`, matches the corrupted entry exactly, and (because ABI `throwing=true`) sets `methodDecl.ThrownErrorType` to the wrong `TypeSpec`. **Caveat (verified):** for the only signature shape that triggers this — a parameter-position typed-throwing closure — the method is currently *pruned* before emission (unsupported parameter type), so the wrong `ThrownErrorType` does not reach generated C# today. This is a genuine parser logic defect and an untested latent landmine: it becomes a live wire-format bug the moment typed-throwing-closure parameters become emittable, or for any other multi-`throws(` line shape. Fix: select the **last** match (the function's own trailing clause), or anchor past the parameter-list close paren.

### Demangler `Y`-modifier gap (`@Sendable`/typed-throws) — `Swift5Demangler.cs:552/1095`
The `case 'Y'` switch recognizes only `'a'`; everything else does `PushBack();PushBack();DemangleIdentifier()`, and `PopFunctionType` pops only `ThrowsAnnotation` + `AsyncAnnotation`. `Yb` (@Sendable) yields a `ReductionError`; `YK` (typed throws) yields a `TypeSpecReduction`. `SwiftABIParser.CreateMethodDecl` does `reduction as FunctionReduction` → null for both, disabling the demangle-based variadic-detection tier and the demangle-based async signal. `@Sendable` closure parameters are pervasive in modern Swift concurrency APIs, so this is the broadest live fidelity gap in the track. **Two secondary-detail corrections (do not affect the defect):** async detection is *not* fully lost — `DetectAsyncFromMangledName` string-scans for `"Ya"` as a fallback; and the `Yb` failure here is *silent* (returns a `ReductionError`, not a thrown exception, so the `CreateMethodDecl` catch-and-warn does not fire). No demangler unit test covers `Yb`/`YK`/`Yc`/`Yi`.

### `where ... : AnyObject` throws and drops the whole decl — `GenericSignatureParser.cs:124`
`ParseConstraint` only short-circuits constructed-generic (`<`) targets before calling `SwiftTypeName.FromModuleQualifiedName`, which requires a dotted `module.Type` and throws `ArgumentException` on the dot-less keyword `AnyObject`/`Any`. The throw is not caught by `ExtractConstraints`' lazy `.OfType<>()`; it propagates through `ParseGenericSignature` into `SwiftABIParser.HandleNode`'s catch-all (`:888`), which logs a `LogWarning` and returns null, so `CollectDeclarations` silently omits the entire `Func`/`Constructor`/`Subscript`. Real `swift-api-digester` emits `<O, R where O : AnyObject>` for the common `<U: AnyObject>` idiom (RxSwift, observer/delegate registration), and the end-to-end probe confirmed the function vanished from generated C# with only a warning. Fix: special-case bare `AnyObject`/`Any`/`Sendable`/etc. (mirroring the keyword set already at `SwiftABIParser.cs:1887-1888`) or return null like the `<` case, so one bad constraint is dropped rather than the whole decl.

### Public protocol requirements flagged module-internal (parser layer) — `SwiftInterfaceAccessParser.cs:2795`
The negative-space heuristic is structurally unsound for protocol requirements: requirements carry no `public`/`open` keyword in a `.swiftinterface`, the `Bare*Regex` set that exists precisely for them is **not** used by `CollectPublicMember` (only the `Broad*Regex` that require `public`/`open`), and `ProtocolDecl : TypeDecl` so `IsInternalFromPublicMemberNames` runs the `TypeDecl` branch with no `IsProtocolRequirement` exemption. Confirmed at the Model layer on both producers. The in-tree comments at `EveryProtocolEmitter.cs:1588-1593` and `KeyPathBagWalker.cs:206` acknowledge the root cause and work around it locally. **Important scope note:** see the Inconclusive section — the *protocol-interface emission path* (`ProtocolHandler` → `MemberGateEvaluator`) does **not** consult `IsModuleInternal`, so `IDrawable.Draw`/`Area` still emit; the defect is a real Model-flag corruption (a maintainability landmine for any future `IsModuleInternal` consumer, e.g. `MemberEmissionValidator`) rather than a demonstrated dropped-binding today.

### `HasUnmatchedOpenParen` paren miscount inside string literals — `SwiftInterfaceAccessParser.cs:3816`
The helper has no `inString`/escape tracking, so a string default value containing an unbalanced paren makes a complete one-line declaration look like an unfinished signature. Because the lone `(` lives in a string and is never closed by a real `)`, the continuation buffer **never re-balances and swallows every following line to EOF** — more severe than "swallows the next member". This poisons `GetParameterNames`, `GetTypedThrowsErrors`, and (via the same idiom) ~15 other extraction sites (`GetActorIsolatedMembers`, `GetNonisolatedMembers`, `GetSubscriptLabels`, `GetInternalMembers`, …). The reverse `")"`-default underflow case is a latent code property that did not reproduce from real `swiftc` output (Swift 6.2 normalizes multi-line signatures to one line). Fix: give `HasUnmatchedOpenParen` the same `inString`/escape state machine that `CountBraces` (`:2916`) already has.

## Inconclusive / needs deeper probe

These had a **split verdict** (one voter confirmed the mechanism + Model corruption; another refuted the *observable* downstream impact). In every case the parser/Model-level defect is real and reproduced, but the claimed user-visible symptom (dropped binding / wrong-ABI wrapper) did **not** materialize on the path tested, because the relevant emitter happens not to consult the corrupted flag. They are genuine fidelity/hygiene defects and future landmines, but not demonstrably behavior-changing today.

- **Public protocol requirements `IsModuleInternal=true` — observable drop?** (`SwiftABIParser.cs:2024/2572`). Confirmed the flag is set wrong on both producers; refuted that requirements are dropped — `ProtocolHandler`/`MemberGateEvaluator` gate on `IsSpiProtected`, not `IsModuleInternal`, and the regex-producer output was byte-identical to SwiftSyntax. The drop lives only in `MemberEmissionValidator.CanEmitProperty:84` / count loop `:1319`, which the protocol-interface path bypasses. **Deeper probe wanted:** route a `ProtocolDecl` (which *is* a `TypeDecl`) through `MemberEmissionValidator` and confirm its public-API member counts are mis-deflated.

- **Public operator methods (`==`, `+`, …) flagged module-internal** (`SwiftInterfaceAccessParser.cs:147`). Confirmed: `BroadPublicFuncRegex` captures only `func\s+(\w+)` and cannot match operator characters; sibling `PublicFuncRegex:86` *does* (`(\w+|[/=\-+!*%<>&|^~?.]+)`). Full pipeline showed `Operator '=='/'+'/'<' UnderlyingMethod.IsModuleInternal=TRUE`. Refuted impact: the struct operator-emission path (`FrozenStructHandler`/`OperatorHandler.ValidateAndEmitPairs`) does **not** gate on `UnderlyingMethod.IsModuleInternal` (`grep` finds **zero** readers of that field), so all operators + the `Equatable` witness still emit. Latent inert misclassification. **Fix is still defensible as model-hygiene:** add the operator branch to `BroadPublicFuncRegex:148`.

- **Public `consuming`/`borrowing func` flagged module-internal** (`SwiftInterfaceAccessParser.cs:147`). Confirmed mechanism: the self-modifier alternation omits `consuming`/`borrowing`, so `public consuming func drain()` is absent from `publicMemberNames` → `IsModuleInternal=true` (verbose log: `module_internal`). Refuted the "silently suppressed" symptom, but found a **different real adverse effect**: with `-s` the method is *not dropped* — it is denied the safe `@_cdecl`/native-thunk wrapper and degraded to an `[Obsolete(...SB0001)]` raw `CallConvSwift` P/Invoke against the mangled symbol (a calling-convention-mismatch risk for an owned-`self` method). Gap exists on **both** producers (the SwiftSyntax host shares the access-modifier gate), so a fix must cover both. This is arguably closer to *confirmed-P2* than inconclusive: the consequence is real (wrapper denial), just not the visibility-removal the claim asserted.

## Checked & refuted

- **`nonmutating` extension funcs dropped by `ExtensionFuncRegex`** (`SwiftInterfaceAccessParser.cs:1239`) — REFUTED. The regex gap is real in isolation, but **Swift never emits `nonmutating func` into a `.swiftinterface`** (`nonmutating` is the default for funcs; only `mutating` is printed). A `public nonmutating func` source decl prints as `public func`, which matches. SDK survey of ~3000 `.swiftinterface` files found **zero** `nonmutating func` occurrences (`nonmutating` appears only on property accessors). The defect is unreachable from real compiler output. (Adding the alternation is harmless defense-in-depth.)
- **Public `indirect enum`/`distributed actor` dropped** (`SwiftInterfaceAccessParser.cs:60`) — REFUTED. The regexes are **unanchored** and the claim assumed the wrong token order. `swiftc` normalizes the interface to `indirect public enum Tree` / `distributed public actor Worker` (modifier **before** `public`), so the unanchored regex still matches the `public enum Tree` substring and captures `Tree` (and correctly scopes `Tree.Inner`). End-to-end generation emitted `Tree`, `depth()`, the distributed actor, and `Tree.Inner` correctly. The parity tests at `InterfaceFactsProducerParityTests.cs:322/397/428` feed hand-authored `public indirect enum` (access-first) text the toolchain never produces — they parity-lock producer divergence for a non-real input, not a real-world correctness claim.

## Coverage gaps (what this track did NOT reach)

- **Marshaler/Emitter consumption of the corrupted Model flags was only spot-checked.** The inconclusive items were resolved at the parser/Model layer plus the *one* emitter path each voter tested. A systematic sweep of every reader of `IsModuleInternal` / `ThrownErrorType` / `IsMutating` / `ProtocolListTypeSpec` (especially `MemberEmissionValidator`, `ConformanceValidator`, public-API shape counters) was not done; that is the gating question for whether the "latent" P1s are actually behavior-changing.
- **The default macOS SwiftSyntax host producer (`tools/SwiftInterfaceParser`) was not audited as a track.** Several findings note it *shares* the regex producer's gaps via a documented byte-equal parity contract, but its Swift-side walkers (`MemberCollectionWalker.swift`, `ThrowsWalker.swift`) were only read where they corroborated a C#-side finding — they were not independently fuzzed.
- **No live ABI-JSON corpus diff.** Probes used minimal hand-built modules + a few real `swift-api-digester` dumps. The deferred candidates with "latent given current ABI shape" caveats (#10, #24) were not validated against a Swift-6.x emission corpus to confirm reachability.
- **The deferred candidates (#1–#28) were not probe-demonstrated.** Line numbers were verified for #13, #14, #21, #10 this pass; the rest carry only the original finder's evidence.
- **Round-trip / reducer behavior of the demangler** (`Swift5Reducer.cs` MatchRules) was not exercised beyond the `Yb`/`YK` cases.
