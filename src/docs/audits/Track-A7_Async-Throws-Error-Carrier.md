# Track A7 — Async / throws / error-carrier paths

Scope: the C# + Swift async wrapper emission (`AsyncHarnessEmitter`, `AsyncMethodGenericBridgeEmitter`, `WrapperEmitter.Async`), the cancellation task registry (`CancellationTaskEmitter`), and the runtime async-closure / result-carrier helpers (`AsyncClosureHelper`, `SwiftResult`). Focus: what happens to result/error marshalling, cancellation identity, and GCHandle/buffer lifetime when the happy path is perturbed.

**Overall risk rating: 5/5 (high confidence).** The single dominant pattern — managed exceptions escaping `[UnmanagedCallersOnly]` async callbacks into native Swift — is confirmed by probe at the runtime/ABI level (SIGABRT exit 134) across multiple independent emitters, and is genuinely reachable on real metadata/marshal-failure paths. It is a process-crash + Task-hang + resource-leak class, present in every async result/error callback the generator emits except the one (`Array<String>`) that was hardened. Two additional P1 defects (GCHandle-integer task identity recycling; per-call async-closure GCHandle leak) are also probe-confirmed.

### Per-item notes

**#1 — Async success-callback marshal throw escapes UCO (the headline defect).** In `AsyncHarnessEmitter.EmitAsyncWrapperForComplexType` (`AsyncHarnessEmitter.cs:906-933`), the result materialisation (`{{marshalResultCode}}` at line 915) runs inside `try` *before* `BuildHolderCleanupCode` (`AsyncHarnessEmitter.cs:1687-1706`) and *before* `TrySetResult`, with only `finally { SBW_Free; handle.Free(); }` and no `catch`. `MarshalFromSwift<T>` genuinely throws (`SwiftMarshal.cs:920,981`, plus the reflection `NewFromPayload` and metadata-resolution paths), and the existential branch also constructs a proxy whose ctor can throw. On a throw, three failures co-occur: (1) the exception unwinds out of the `[UnmanagedCallersOnly]` Cdecl callback into the native Swift continuation thread → process abort (probe: exit 134 / SIGABRT); (2) `BuildHolderCleanupCode` never runs, leaking `RetainedSelfPtr` (Arc retain), `DeferredSafeHandleRelease`, every `CopyBufferWithType` buffer, `ExistentialContainerHeap`, and the `AsyncDeferredDisposeList`; (3) the TCS is never completed, so the awaiting Task hangs forever. The only path that defends is `EmitAsyncWrapperForArrayString` (catch → `deserializationError` → `TrySetException`), and the asymmetry proves the other paths were not deliberately exempted.

**#2 / #4 / #6 — Same crash class in the method-generic bridge.** `AsyncMethodGenericBridgeEmitter.EmitCallbackBody` (`AsyncMethodGenericBridgeEmitter.cs:824-926`) emits the success callback for class-bound method-level generics (e.g. StoreKit2 `Product.purchase<S>`-style APIs) as `try{...}finally{SBW_Free;handle.Free}` with no catch. The throwing surfaces inside the `try`: `SwiftObjectHelper<T>.GetTypeMetadata()` (875), `ValueWitnessTable->InitializeWithCopy/Destroy` (877/879/890), `MarshalFromSwift<T>` (878/888/897), the `SwiftClass` ctor (863), and the hard casts `(object[])handle.Target!` / `holder[0]` (902). This is a *separate live emitter* (registered at `MethodHandler.cs:760` via `AsyncMethodGenericBridgeAdapter`) that prior findings did not name. Probes invoking the emitted shape through a native (Swift `@_cdecl`) frame produce SIGABRT exit 134 on a throwing marshal; the `catch→TrySetException` control exits 0 with a faulted Task. The throw is conditional (only fires on metadata/marshal/trimming failure), so it is an error-path crash, not a guaranteed-on-every-call crash — but any such throw is a hard native abort plus a permanently-hung Task.

**#3 / #10 — Typed-throws error-callback rethrow.** In `AsyncHarnessEmitter.cs:1288-1291`, the class-direct and ownership-transfer typed-error free blocks are `catch { ...Arc.Release/SBW_Free...; throw; }`. The `throw;` re-raises any `MarshalFromSwift<TError>` / force-cast failure, and the surrounding error-callback method (`AsyncHarnessEmitter.cs:1376-1402`) has only `try{}finally{handle.Free();}` — no outer catch — so the rethrow escapes the UCO error callback into Swift's `} catch {` site (probe: SIGABRT exit 134). It also skips `BuildHolderCleanupCode` (leak) and `holderTcs.TrySetException` (hang). **Scope note for the fixer:** the verifiers found this same error-callback shape is ALSO present in `WrapperEmitter.Async.cs:2399-2402/2487-2513`, and one verifier flagged that file as the *active* emit path for async wrappers while `AsyncHarnessEmitter` is the parallel/secondary copy. The reporter should confirm which BuildErrorCallbackBlock actually runs for a given method and fix both. The `finally { SBW_Free }` branches (VWT-destroy / frozen-enum shapes) also let a marshal exception escape — `finally` does not swallow — so the uncovered-escape surface is broader than the two cited `catch{...;throw;}` branches.

**#5 — Three more live success callbacks.** The primitive/class (`AsyncHarnessEmitter.cs:410-436`), tuple (497-520), and String (539-572) callbacks share the identical unguarded `try{marshal;TrySetResult} finally{...handle.Free()}` shape. The String path is notable: `Marshal.PtrToStringUTF8(slicePtr, (int)sliceLen)` (line 552) casts a `nint` length to `int`, so a Swift-supplied length ≥ 2³¹ wraps negative → `ArgumentOutOfRangeException`, and an oversized positive length → `AccessViolationException`; the `sliceLen == 0` guard at line 546 does not protect either. Counting #1, #5, there are five unguarded success callbacks total (410, 497, 539, 912, 1187); only `Array<String>` (585-688) is remediated.

**#7 — Diverged dead duplicate.** `WrapperEmitter.Async.cs` carries a full second copy of the async emitters (`EmitAsyncWrapper` at 1330, the `For*` variants, and a 3-param `TryGetOptionalMarshalType` at 2189). The only live caller is `WrapperEmitter.cs:529` `_asyncHarness.EmitAsyncWrapper`, dispatching to the extracted `AsyncHarnessEmitter` instance; `WrapperEmitter.cs:67-68` self-labels the copies as pending-cleanup dead code. The dead copy has *already* diverged: its `TryGetOptionalMarshalType` lacks the 4th `valueContainerInnerConversion` out-param and the `ArrayProjection/SetProjection/DictionaryProjection` branch (`AsyncHarnessEmitter.cs:1102-1111`) that the live version uses for `Optional<[String]>`-style returns. Dynamic proof: live output for `Optional<[String]>` emits the `_rawCol.AsProjected(...)` branch + carrier VWT-Destroy; the dead copy's fall-through `else` would emit a wrong-shaped, element-unconverted, leaking result. Latent today (genuinely unreachable), but a copy-edit or an accidental rewire of line 529 to call `this.EmitAsyncWrapper` would silently regress Optional-collection async returns and re-introduce a +1 carrier leak. This is exactly the "multiple async emitter paths diverging" hazard.

**#8 — GCHandle-integer task identity recycling.** The async cancellation registry (`CancellationTaskEmitter.cs:43` `_sbwActiveTasks: [Int64: _SBWTaskEntry]`) is keyed on `taskId = (long)(IntPtr)handle` (`WrapperEmitter.Async.cs:413`, mirrored at `AsyncMethodGenericBridgeEmitter.cs:1244`), the integer value of a `GCHandleType.Normal` handle. A .NET probe showed free+realloc returns the identical integer 100% of the time. The C# callback's `finally { handle.Free(); }` recycles the integer *before* the Swift `Task` body's `defer { _sbwUnregisterTask(_sbwTask) }` runs (`AsyncHarnessEmitter.cs:1586-1600`). A Swift probe reproducing this ordering showed a live in-flight call#2 that obtains the recycled integer is silently evicted from `_sbwActiveTasks` by call#1's stale deferred unregister → call#2 becomes permanently uncancellable. The symmetric hazard (a late `SBW_CancelTask(recycledId)` cancelling an unrelated task) follows from the same root cause. This is OUR generator/runtime bug, not a Mono/NativeAOT bug. Fix direction: a monotonic per-call token (`Interlocked.Increment`) stored in the holder and used as the registry key / `_sbwTask` / cancel id, decoupled from GCHandle memory reuse.

**#9 — Per-call async-closure GCHandle leak.** Every `RunAsync*`/`RunVoidAsync*` overload in `AsyncClosureHelper.cs` (and the `StringAsyncClosureHelper.cs` family) accepts a `GCHandle handle` it never references — documented "intentionally NOT freed" (lines 26-33). The generated Start thunk allocates it as a strong `GCHandleType.Normal` handle (`ClosureEmitter.Async.cs:343-344`), and the Swift `_success`/`_error` `@_cdecl` callbacks only balance the Swift continuation BOX, never the C# context handle — there is no Swift-side release callback. A finalizer probe at N=200 one-shot calls showed 200/200 state objects survive full GC (control with `.Free()` collects all 200). For the common one-shot `() async throws -> T` case the "Swift may invoke more than once" rationale does not apply (the adapter uses `withCheckedThrowingContinuation`, single-resume), yet the handle still leaks one strong GCHandle + the whole captured-delegate graph per call, unbounded under looped/per-frame invocation. Correctly self-documented as a post-1.0 TODO, but it is a live resource defect today.

## Inconclusive / needs deeper probe

**`AsyncClosureHelper.CompleteWithResult` double-resume if `result.Dispose()` throws after `successAction`** (`AsyncClosureHelper.cs:438`, claimed P0). The two verifiers SPLIT — this is the one item where the verdict is genuinely unresolved and a reporter/owner should adjudicate:

- The control-flow MECHANISM is confirmed by both: if `result.Dispose()` in the outer `finally` (line 440) throws after `successAction` already consumed the Swift box + resumed the continuation (line 430), the exception propagates to `RunAsync`'s `catch` (lines 48-50) → `ReportError` → `errorAction`, which does a SECOND `takeRetainedValue()` on the already-consumed box (double-free/UAF) AND a second `cont.resume` (Swift `SWIFT TASK CONTINUATION MISUSE` fatalError). Standalone Swift probes reproduced both an exit-133 continuation-misuse trap and an exit-139 UAF.
- The DISAGREEMENT is reachability. Verifier A: `ISwiftObject : IDisposable` (`ISwiftObject.cs:13`), so any async closure returning a Swift class type takes the generic `CompleteWithResult<T>` path and `Dispose()` calls native release which can throw → CONFIRMED. Verifier B: `IsBaselineAsyncThrowingClosure` → `IsBlittablePrimitiveSwiftType` (`ClosureHandler.cs:877-911`, `CdeclParamMapper.cs:738-750`) restricts the throwing-async-closure return type to blittable PRIMITIVES, which can never implement `IDisposable`, so `(result as IDisposable)` is always null; Data/String returns route to separate helpers that have no `(result as IDisposable)?.Dispose()` (grep: the pattern exists at exactly one site, `AsyncClosureHelper.cs:440`) → REFUTED as currently gated.

Net: the code is a real latent double-resume/UAF hazard that is currently dormant *if* the return-type gate is as Verifier B describes. The split turns on whether a Swift-class return can actually reach the generic `CompleteWithResult<T>` — that single reachability question decides between P0-live and P2-latent. **Recommend the owner resolve this directly** (and regardless, the defensive fix is cheap: wrap the `finally` `Dispose()` in try/catch, or dispose before `successAction`, so a future gate relaxation cannot turn it into a double-resume crash).

## Deferred (candidate, unverified)

These were not probed this pass (per-track cap). Listed so none are silently dropped. Most are the same crash/leak/identity classes confirmed above, in additional sites — they are strong candidates, not yet decisively demonstrated.

- **AsyncClosureHelper per-call GCHandle leak (restatements).** Two further write-ups of finding #9 (`AsyncClosureHelper.cs:34`) — already CONFIRMED above; deferred copies are redundant.
- **Non-throwing async has no error/cancel channel → silent hang.** `AsyncHarnessEmitter.cs:1605` (and `AsyncMethodGenericBridgeEmitter.cs:761` for the generic bridge): non-throwing async wrappers emit only the success callback. A system-cancelled or non-returning underlying Swift function leaves `_tcs` never completed and the holder (copy buffers, RetainedSelfPtr, AsyncDeferredDisposeList) + GCHandle leaked. Probe idea: `func slow() async -> Int` that `try? Task.sleep`s for an hour; cancel the token and assert the Task completes within seconds (expect hang).
- **Generic-bridge `cbTakesOwnership` `__resultBuf` leak on marshal throw.** `AsyncMethodGenericBridgeEmitter.cs:874` — `__resultBuf = NativeMemory.Alloc(...)` + `InitializeWithCopy` then `MarshalFromSwift`; the `finally` frees only the carrier, never `__resultBuf`, and skips the carrier `Destroy` on throw → native buffer + carrier +1 leak (rides on the #2/#4 escape).
- **AsyncHarness `newFromPayloadTakesOwnership` `_vwtBuf` leak on marshal throw.** `AsyncHarnessEmitter.cs:879` — same allocation-outside-cleanup shape; `_vwtBuf` is never freed if `MarshalFromSwift` throws.
- **Swift `defer { _sbwUnregisterTask }` after `handle.Free()` evicts a concurrent live entry.** `AsyncHarnessEmitter.cs:1589` and `CancellationTaskEmitter.cs:55` — the registry-eviction direction of finding #8 (CONFIRMED). Deferred copies refine the same race.
- **Generic-bridge async ERROR callback marshal/CreateException with no catch.** `AsyncMethodGenericBridgeEmitter.cs:928` (`EmitErrorCallbackBody`) — `CreateException`, the `(object[])` cast, and `PtrToStringUTF8` can throw out of the no-catch UCO error callback (same class as #3, error side of the generic bridge).
- **Fast-cancel post-launch leak: cancel completes TCS but never disposes registration / frees GCHandle.** `WrapperEmitter.Async.cs:414` — cleanup lives only in the success/error callbacks; a Task cancelled before its body runs fires `defer` but no callback, leaving GCHandle + holder + self +1 leaked.
- **Generic-bridge hard cast `(object[])handle.Target!` with no `is`-guard / directTcs fallback.** `AsyncMethodGenericBridgeEmitter.cs:902/939` — null/recycled handle → NRE/InvalidCast escapes UCO (unlike `AsyncHarnessEmitter`'s `is object[]` guard).
- **taskId recycling duplicated in the generic bridge.** `AsyncMethodGenericBridgeEmitter.cs:1244` — the second instance of finding #8; must be fixed in lockstep.
- **Registry unregister has no value-identity guard.** `CancellationTaskEmitter.cs:55` `removeValue(forKey:)` with no `===` check — the Swift-side enabler of the #8 eviction.
- **SwiftClass generic-bridge return leaks +1 if the wrapper ctor throws.** `AsyncMethodGenericBridgeEmitter.cs:862` — `passRetained` pointer consumed by `new {Class}(new SwiftHandle(rawResult))`; no `Arc.Release` in finally for the class path if the ctor throws before the SafeHandle adopts.
- **Typed-throws direct (non-holder) error path marshals an uninitialized buffer on cancellation.** `AsyncHarnessEmitter.cs:1307` — `directErrorBody` has no `isCancellation` guard; Swift leaves `_errPtr` uninitialized on cancel (`1469-1471`). Currently dead (always-`object[]` holder) but uniquely dangerous because it reads uninitialized Swift memory rather than merely failing to complete. (Closely related to the refuted directTcs finding — same dead branch, different hazard framing.)
- **Async-closure result buffer freed with `NativeMemory.Free` but never VWT-Destroyed.** `AsyncClosureHelper.cs:434` — for any reference-bearing `T`, `MarshalToSwift` does `InitializeWithCopy` (+1) but the `finally` only `NativeMemory.Free`s without `Destroy` → +1 leak per successful completion. Distinct from #9.
- **`any Error` existential metadata built with `classConstraint=0` (Class).** `SwiftResult.cs:536` — `_getExistentialTypeMetadata(0, ..., 1, ...)` vs the Any=1 contract documented at `TypeMetadata.cs:747`; possible mis-sized metadata vs the 5-word `ExistentialContainer1` carrier. May be coincidentally correct due to Swift's special compact `any Error` box — needs a struct-error round-trip probe. (Three overlapping write-ups.)
- **`GetAnyErrorExistentialMetadata` `Unsafe.As<ProtocolDescriptor, IntPtr>` type-unsafe reinterpret.** `SwiftResult.cs:534` — correct today (single-IntPtr struct) but silently corrupts if `ProtocolDescriptor` layout ever changes; wants a `SizeOf == IntPtr.Size` unit gate.
- **Foreground async try/catch can double-free the GCHandle.** `WrapperEmitter.Return.cs:135` — the foreground `catch { ...; handle.Free(); throw; }` frees the same handle the launched Swift Task will free in its callback, if a post-P/Invoke emitter throws. Usually an empty window (those emitters are no-ops for pure async), but no "task launched" flag guards it.
- **ReportError UTF-8 message pin lifetime / type-fidelity loss.** `AsyncClosureHelper.cs:444/446` — pins the message only for the synchronous `errorAction` (safe today because the Swift `_error` thunk does `String(cString:)` eagerly); surfaces only `ex.Message` (loses exception type / typed-error identity). Multiple overlapping P2 write-ups.
- **Typed-throws cancellation allocates+frees an uninitialized buffer every cancelled call.** `AsyncHarnessEmitter.cs:1240/1466` — wasteful and a brittle split invariant between the Swift init-skip and the C# bare-`SBW_Free`-on-cancel; a future change initializing the buffer on cancel would leak/crash.
- **Two live hand-maintained halves of the async wire ABI.** `WrapperEmitter.Async.cs:2546` `BuildSwiftCatchBody` (Swift, live) vs `AsyncHarnessEmitter` `BuildErrorCallbackBlock` (C#, live) — the 6-param error wire is split across two classes with only mirror-comment enforcement; a one-sided edit silently produces a wrong-ABI decode. (Note: this and finding #3's scope note both point at the WrapperEmitter.Async vs AsyncHarnessEmitter split being live for the Swift side — the live/dead boundary between these two files is itself worth a dedicated pass.)
- **Generic-bridge pre-launch cancel race.** `AsyncMethodGenericBridgeEmitter.cs:1241` — cancellation `Register` precedes the P/Invoke launch; a cancel in the window hits an empty registry while the Swift Task still spawns and runs. Mirror of the WrapperEmitter pre-launch window.

## Checked & refuted

- **Typed/cascade async error callback: `directTcs` branch never handles cancellation, marshals an uninitialized buffer** (`AsyncHarnessEmitter.cs:1393`, claimed P1). REFUTED by both verifiers. The structural reading is accurate — the `isCancellation` check + cancellation `SBW_Free` live only in the `object[] holder` arm, and `directErrorBody` (1307-1316) has no cancellation guard. BUT the `directTcs` branch is provably dead: every async GCHandle is allocated as an `object[]` holder (`WrapperEmitter.Async.cs:320/342/361/374/392` all alloc `_asyncCallHolder`; the only bare-TCS `GCHandle.Alloc` in the tree, `ProtocolProxyEmitter.ClosureThunks.cs:173`, has its own completion thunk and never routes through `BuildErrorCallbackBlock`). Empirical generate-probe for the exact no-param static `async throws(MyError)` shape confirmed `handle.Target is object[]` always matches and the cancellation path (`TrySetCanceled` + `SBW_Free`) runs first; the `directTcs` arm is unreachable. Correct severity: P2 dead-code / latent-trap smell, not a live runtime defect — matching the claim's own downgrade fallback. (The uninitialized-buffer hazard is preserved in the deferred list as a forward-looking note since it would become live if a bare-TCS handle were ever wired in.)

## Coverage gaps (what this track did NOT reach)

- **Live runtime reproduction in BindingTests.** All confirmations are `/tmp` probes that faithfully model the emitted UCO shape across a real native frame (clang/swiftc dylib) — decisive for the ABI/crash semantics, but none drive an *actual generated binding* into a marshal failure on simulator/device. Whether a real generated type can be coerced into the `MarshalFromSwift` throw depends on `TypeDatabase` completeness; the existential branch (documented at `AsyncHarnessEmitter.cs:730-737`) is one historically-confirmed concrete trigger.
- **Live vs dead boundary between `WrapperEmitter.Async.cs` and `AsyncHarnessEmitter.cs`.** Finding #7 confirms the C# `EmitAsyncWrapper` copy in `WrapperEmitter.Async.cs` is dead, but finding #3's scope note and a deferred item both claim the *Swift-side* `EmitAsync`/`BuildSwiftCatchBody` half of `WrapperEmitter.Async.cs` is LIVE and shares the error wire with `AsyncHarnessEmitter`. The precise call graph (which `BuildErrorCallbackBlock` and which `BuildSwiftCatchBody` actually run per method shape) was not pinned down and should be the first thing the fixer establishes — it determines which file(s) the #1/#3/#5 fixes must land in.
- **`SwiftResult` / `any Error` carrier sizing.** The `classConstraint=0` and `Unsafe.As` concerns are flagged but unprobed; no struct-error `Result<Int, any Error>` round-trip was run.
- **NativeAOT vs Mono divergence for the escape paths.** Probes ran on CoreCLR; the Track-A4 audit already empirically confirmed the same no-catch UCO shape aborts at exit 134 on BOTH CoreCLR JIT and NativeAOT for closures, so the async escape is very likely identical — but it was not directly re-run for the async emitters here.
- **Stress/concurrency reproduction of #8 in a real generated binding.** The recycling race was reproduced in isolated Swift/.NET probes, not under a real async-heavy library workload; real-world frequency is timing-dependent.

Today it grows unbounded.
