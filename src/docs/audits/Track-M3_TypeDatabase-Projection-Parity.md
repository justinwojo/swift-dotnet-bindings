# Track M3 — TypeDatabase / Projection Parity Audit

**Scope:** The Apple-framework type classification + projection pipeline — `apple-frameworks.json`, `AppleFrameworkRegistry`, the per-module XML databases (`*Database.xml`), `TypeDatabase`/`TypeDatabaseExtensions`, and `TypeProjectionFactory` + the `ITypeProjection` implementations it dispatches to. The recurring failure shape across this track: **a type's *classification* (value vs ObjC-class, enum width, blittable vs ref-counted) disagrees with its real Swift/ObjC ABI, so the projection layer emits the wrong marshalling.**

**Overall risk rating: 4 / 5 (high).** Confidence: high. Seven distinct defects were probe-confirmed against the compiled generator (reflection probes against the real embedded `apple-frameworks.json` and live `Swift.Bindings.dll`, plus end-to-end Swift→C# generation against real SDKs and SIL/`_isPOD`/MemoryLayout ABI probes). All are classification/data-table defects in the Apple-framework heuristic layer; none is a generator control-flow crash. Several are latent (small enum values, XML-rescued types) but every one represents a wrong-ABI or silent-drop path for a public Apple API surface, with no unit coverage pinning the correct answer.

### 1. CoreNFC `objcPrefixes: ["NK"]` — wrong prefix drops `Optional<NFCTag>` (P1)
`apple-frameworks.json:226` declares CoreNFC's ObjC prefix as `"NK"`, but every CoreNFC class is `NFC*` (`NFCTag`, `NFCNDEFTag`, `NFCReaderSession`, `NFCISO7816Tag`, …). `AppleFrameworkRegistry.HasObjCClassPrefix` (`AppleFrameworkRegistry.cs:422-441`) iterates the global `_objcPrefixes` union and requires `typeName.StartsWith(prefix)` + an uppercase next char; `"NFCTag".StartsWith("NK")` is false, so all six canonical names return `False`. Because CoreNFC is an `optionalFallback` module, the `Optional<T>` ObjC-bridged fallback at `TypeProjectionFactory.cs:206-207` and the parity-locked `MarshallingHelpers.IsOptionalObjCBridged` (`MarshallingHelpers.cs:143-146`) both gate on `IsOptionalFallbackModule(module) && HasObjCClassPrefix(name)` — the conjunction fails, the ObjC-bridged nullable-pointer projection never fires, and `Optional<NFCTag>` degrades to `Swift.SwiftOptional<IntPtr>`. `"NK"` is declared by exactly one module and matches zero types, so it is also dead noise in the longest-first-sorted global set. **Correction noted by verifiers:** the `[NFCTag]` *array* sub-claim does not follow from this — array-element bridging gates on `IsKnownModuleForElements`, which is `False` for CoreNFC regardless of prefix (a separate missing flag). Fix: change the prefix to `"NFC"`.

### 2. `UIKeyboardType` / `AVCaptureVideoOrientation` missing `rawValueType` — 4-vs-8-byte enum width (P1)
`UIKitDatabase.xml:11` and `AVFoundationDatabase.xml:11` are the **only two** `simpleEnum="true"` entries across all XML databases that omit `rawValueType`; every sibling NSInteger enum carries `rawValueType="Int"` (e.g. `UIViewContentMode` at `UIKitDatabase.xml:23`). Both Swift enums are `NS_ENUM(NSInteger)` (8 bytes). With a null `rawValueType`, `EnumHandler.GetCSharpEnumUnderlyingType(null)` returns `"int"` (4B) while the Swift `@_cdecl` wrapper side (`CdeclParamMapper`/`CdeclReturnMapping`, default `_ => "Int"`) emits an 8-byte slot — a genuine declared-width mismatch that diverges from the codebase's own NSInteger convention. A runtime AArch64 probe confirmed the return path drops the high 32 bits (`0x3_0000_002A` read back as `0x2A` via the `int` P/Invoke; the `long` path preserved it). **Severity nuance:** both enums' defined cases are small (UIKeyboardType 0-12, AVCaptureVideoOrientation 1-4), so .NET zero-extends and observed values survive in practice — this is a latent correctness/ABI-consistency bug, not an active corruption crash. Fix: add `rawValueType="Int"` to both lines (matching every sibling and commit `8dbb8f72`, which added the attribute to siblings and missed these two).

### 3. optionalFallback modules with no declared prefix (CM/CT/CS/PDF/WC absent from the global union) (P1)
CoreMedia, CoreMotion, CoreTelephony, CoreSpotlight, PDFKit, and WatchConnectivity are `optionalFallback:true` with **no** `objcPrefixes`, so `HasObjCClassPrefix` falls back to the 44-entry global union — which contains none of `CM`/`CT`/`CS`/`PDF`/`WC`. Same gate as #1, six different modules whose correct prefix is wholly absent (not merely mistyped). End-to-end generation reproduced the defect: `CMFormatDescription?` / `CMMotionManager?` / `CTCarrier?` members were fully **dropped** ("unsupported placeholder type"), while `CSSearchableItem?` and `PDFDocument?` emitted `Swift.SwiftOptional<IntPtr>` (opaque); the control `UIImage?` resolved to `UIKit.UIImage?`. **Two verifier corrections:** (a) `Optional<CMSampleBuffer>` is **refuted** as broken — a hand-authored `CoreMediaDatabase.xml` ships an `objcBridged` record that rescues it via `TryGetTypeRecord` (`→ CoreMedia.CMSampleBuffer?`); CoreMedia is only *partially* affected (non-XML types like `CMFormatDescription` still drop). (b) CoreSpotlight and PDFKit **are** `autoBridge:true` — the claim's "NOT autoBridge" reasoning is wrong, but the conclusion holds because the Optional inner projection uses `TryGetTypeRecord` (`TypeProjectionFactory.cs:362`), which never mints synthetic ObjC records. Fix shape mirrors #1: backfill the real prefixes, scoping carefully (CM also belongs to CoreMotion; CT-prefixed CoreText types exist).

### 4 & 7. NSString-typedef RawRepresentable structs registered blittable `kind="struct"` (P1)
(Findings #4 and #7 are the same defect family — #7 broadens the set to AVFoundation/NaturalLanguage.) `QuartzCoreDatabase.xml:22-38` registers `CAGradientLayerType`, `CAContentsFormat`, `CACornerCurve`, `CATextLayerAlignmentMode`, `CATextLayerTruncationMode`, `CAScroll`, `CADynamicRange`, `CAToneMapMode` as `kind="struct" frozen="true" requiresMemoryManagement="false"` with empty `mangledName` and no `objcBridged`. These are `typedef NSString * X NS_TYPED_ENUM` ObjC typedefs — the Swift importer makes each a `_SwiftNewtypeWrapper`/`_ObjectiveCBridgeable`(NSString) struct that **stores a retained NSString pointer** (`_isPOD=false`, `MemoryLayout.size == 8`, SIL shows `retain_value` / `objc_autoreleaseReturnValue`). `TypeProjectionFactory.CreateProjectionForTypeRecord` routes them to `BlittableProjection` (`TypeProjectionFactory.cs:455-456`), which is pure `MarshalPlan.PassThrough` — a bitwise by-value copy with no ARC and no NSString bridging → under-retain / dangling-pointer (use-after-free once the autorelease pool drains). Their byte-identical sibling typedefs (`CALayerContentsGravity`, `CAMediaTimingFunctionName`, `CATransitionType`, `CATransitionSubtype`, `QuartzCoreDatabase.xml:40-50`) are correctly registered `kind="class" objcBridged="true"` → `ObjCBridgedProjection`, proving the maintainers knew the shape and the struct-registered set was missed. The same misclassification appears in `AVFoundationDatabase.xml` (`AVMediaType`, `AVFileType`, `AVLayerVideoGravity`, `AVCaptureDevice.DeviceType`) and `NaturalLanguageDatabase.xml` (`NLLanguage`, `NLTagScheme`), and is mirrored in `apple-frameworks.json` `valueTypes` (lines ~745-777). The genuine integer OptionSets in the same file (`CACornerMask`/`CAEdgeAntialiasingMask`/`CAAutoresizingMask`) are real `NS_OPTIONS` (`_isPOD=true`) and **correctly** blittable. **Correction:** the claim's "16-byte Swift.String" is wrong — the wrapper is an 8-byte single NSString object pointer; the hazard is an ObjC-object ARC/refcount bug, not native-String bitwise corruption. One verifier also observed that for the C# enum target type the no-retain pass-through can dereference an integer ordinal as a raw pointer → SIGSEGV. Fix: re-register these as `kind="class" managedTypeName="NSString" objcBridged="true"` (matching the siblings) and remove from `valueTypes`.

### 5. `Foundation.Date` tuple element — DateProjection vs raw `double` divergence (P1)
`FoundationDatabase.xml:10-11` maps `Foundation.Date` to the bare keyword `double` (`managedNameSpace="" managedTypeName="double"`), while `TypeProjectionFactory.ProjectNamedType` short-circuits the name `Foundation.Date` to `DateProjection` (System.DateTimeOffset + 2001-01-01 epoch offset, `TypeProjectionFactory.cs:331-332`). The two paths disagree on both public type and epoch math. **Important verifier correction to the mechanism:** the divergent consumer is **not** `CreateProjectionForTypeRecord`/`BlittableProjection` as the claim states — the name short-circuit fires for *every* `NamedTypeSpec` named `Foundation.Date`, including inside `ProjectTuple`, so a Date array element (`[Date]`) correctly projects to `DateTimeOffset` (refuting the collection/bound-generic limbs). The real root cause is the **tuple emitter** (`WrapperEmitter.Return.cs` `GetCSharpTypeForTupleElement`/`GetTupleElementMarshalCode`), which reads `typeRecord.CSharpTypeName == "double"` directly and emits `MarshalFromSwift<double>` with no epoch conversion. Empirically: `(Date,Int)` **return** → declared `(System.DateTimeOffset, nint)` but body returns raw double → **CS0029 hard compile failure**; `(Date,Int)` **parameter** → public surface is raw `(double, nint)` with no DateTimeOffset/epoch surface. So the defect is real and direction-dependent (compile error on return, silent raw-double on parameter), but the original "resolves via TypeRecord → BlittableProjection" framing is refuted. No `(Date,Int)` tuple fixture exists in `BindingTests/.../Foundation/Date.swift`.

### 6. `typeRemaps` forces ObjC-class classification on value struct `_LocationEssentials.CLLocationCoordinate2D` (P1)
`IsObjCBridgedTypeName("_LocationEssentials","_LocationEssentials.CLLocationCoordinate2D")` returns `True` (reflection-confirmed) for a plain 16-byte two-double value struct, because `_LocationEssentials` (an SPI module, `apple-frameworks.json:1050-1058`) has a `typeRemaps` entry for `CLLocationCoordinate2D` but **no** `valueTypes` list. The `valueTypes` exclusion at `AppleFrameworkRegistry.cs:496` is keyed `CoreLocation.CLLocationCoordinate2D` (per the `{Module}.{vt}` format) and so misses the SPI-qualified name; the `typeRemaps` gate at `:502` then unconditionally returns `True` for any remapped name. **Broader than the claim's single line:** the struct is also misclassified by `TypeDatabaseExtensions.IsObjCModuleType` (`IsAutoBridgeModule && !IsKnownValueType`), which never consults `typeRemaps` at all — so fixing only line 502 would not fully fix it; the missing `valueTypes` entry is the real root cause. Reachability is real: `RewriteSpiModulePrefix` only rewrites the rendered string at specific emitter sites (e.g. `ExistentialBypassEmitter.cs:1341`), never mutating the `NamedTypeSpec.Module`, so classifiers see the raw `_LocationEssentials` qualifier (the generator's own `ModuleHandlerTests.cs:366` fixture proves SPI-qualified specs flow through). `CLLocation` (a real class) correctly → `True`. SIL confirms `CLLocationCoordinate2D` is a by-value struct, so the NSObject-pointer ABI is wrong. Fix options: give `_LocationEssentials` a `valueTypes` list mirroring CoreLocation's, or make the line-496/502 gates SPI-aware, or have line 502 not return true when the remap target is a known value type.

## Checked & refuted

So future agents don't re-chase these:

- **Vision.VNConfidence (Float typealias) → ObjC-bridged class** (`apple-frameworks.json:1002`). **Refuted.** `VNConfidence` is a C `typedef float` (`VNTypes.h`), not a Swift `public typealias`; the Clang importer flattens it to `Swift.Float` everywhere. The name never reaches the resolver (0 occurrences in swiftinterface / swift-api-digester ABI JSON); end-to-end generation emits `public float`. The cited code path is accurate *in isolation* but the triggering input is never produced. (Narrow residual: a third-party lib that explicitly writes `VNConfidence` in its own signatures could preserve the alias — not the Vision framework's own surface.)
- **NSString-typedef *class*-form siblings (`CALayerContentsGravity` et al) round-trip broken via `as AnyObject`** (`AppleFrameworkRegistry.cs:502` / `QuartzCoreDatabase.xml:40-51`). **Refuted.** The structural half is accurate (Kind=Class bypasses the struct-gated NSString guard), but these `NS_TYPED_ENUM` types are genuinely `_ObjectiveCBridgeable`, so `value as AnyObject` yields a real NSString and the end-to-end round-trip preserves the value with no crash. The WrapperValidation/unit-test comments asserting "boxed Swift struct, not NSString" are themselves empirically wrong for these types. (Real residual: the guarding unit test covers Kind=Struct, not the production Kind=Class — a test-coverage gap, not a runtime defect.)
- **`OptionalProjection` routes ObjCRooted through nullable-IntPtr ABI, contradicting `SwiftOptional<T>` contract** (`OptionalProjection.cs:140/344`). **Refuted (two independent submissions).** SIL/MemoryLayout probes prove `Optional<NSObject-subclass>` is nil-pointer-optimized to a single 8-byte pointer (nil = all-zero = `IntPtr.Zero`, some = object pointer = `.Handle`); the Swift wrapper signature is a bare `UnsafeMutableRawPointer?`. The IntPtr path is **correct**; a `SwiftOptional<T>` tagged buffer would itself be the ABI mismatch. The `constraints.md` "ObjCRooted uses SwiftOptional<T>" note governs the *unresolved-Apple-framework fallback predicate*, not the resolved projection, and is misleading as worded. Real residual flagged by a verifier: the property **setter** conversion (`AccessorConversionVisitors.cs:389-390`) does route through `SwiftOptional<T>` against a bare-nullable-pointer wrapper — an inverse asymmetry worth a runtime probe, but NOT the claimed site.
- **`OptionalProjection` ObjCRooted signature/body divergence → CS0029** (`OptionalProjection.cs:140/344`). **Refuted.** End-to-end generation of all four `Optional<ObjCRooted>` shapes compiled cleanly (0 warnings under `TreatWarningsAsErrors`). `PublicType` is always `inner + "?"` = `T?`; `SwiftOptional<T>` appears only on private accessor signatures, never as the public type the body must match. No member where declared type and body diverge.
- **`Foundation.Data` factory short-circuit (`DataProjection`) vs TypeRecord `NativeRemappedProjection(NSData)` — incompatible ABIs** (`TypeProjectionFactory.cs:322`). **Refuted (two submissions).** The name short-circuit dominates every reachable path (including tuple/array element recursion via `Project`), so no real consumer reaches `CreateProjectionForTypeRecord` for `Foundation.Data`. Even if reached, `Data` is `frozen=true`, so `NativeRemappedProjection.PInvokeType` = the by-value wrapper struct (NOT a SafeHandle/pointer) — ABI-identical to `DataProjection` at the `@_cdecl` boundary. The only divergence is the C# `PublicType` (`NSData` vs `byte[]`), and that path is unreachable.

## Recommended BindingTests fixtures

Swift shapes that would lock down each confirmed defect (descriptions only — no fixes proposed):

- **#1 CoreNFC prefix**: a Swift func returning `CoreNFC.NFCNDEFTag?` (and a property of that type). Assert the emitted C# uses `NFCNDEFTag?` / nullable-pointer ABI, not `Swift.SwiftOptional<IntPtr>`. Cheapest lock is a unit `[InlineData("CoreNFC.NFCNDEFTag", true)]` on the `HasObjCClassPrefix` theory (RED today).
- **#2 enum width**: a func taking and returning `UIKeyboardType` and `AVCaptureVideoOrientation`. Assert the P/Invoke declares `long` (8B), not `int`. A round-trip of a value whose ordinal lives above bit 31 (constructed via the `@_cdecl` wrapper) demonstrates the truncation directly; a SIL dump confirms the 8-byte slot.
- **#3 missing-prefix modules**: funcs returning `CMFormatDescription?`, `CMMotionManager?`, `CTCarrier?`, `CSSearchableItem?`, `PDFDocument?`, `WCSession?`. Assert each resolves to `<Module>.<Type>?` (not dropped, not `SwiftOptional<IntPtr>`); include a `UIImage?` control. Use the already-XML-rescued `CMSampleBuffer?` as the negative control.
- **#4/#7 NSString-typedef structs**: a property/param of `CAGradientLayerType` (and `AVMediaType`, `NLLanguage`). Round-trip a value through the binding and assert it survives the autorelease-pool drain (allocate, force a pool cycle, re-read) — a blittable pass-through would dangle. Contrast against `CALayerContentsGravity` (correct class form).
- **#5 Date-in-tuple**: a func returning `(Date, Int)` and one taking `(Date, Int)`. Assert the return compiles (no CS0029) and the epoch offset is applied to the Date element; assert the parameter's public surface is `DateTimeOffset`, not raw `double`. This is the missing fixture next to `BindingTests/.../Foundation/Date.swift`.
- **#6 `_LocationEssentials` value struct**: hardest to express in BindingTests (SPI module). A unit `[InlineData("_LocationEssentials","_LocationEssentials.CLLocationCoordinate2D", false)]` alongside `[InlineData("_LocationEssentials","_LocationEssentials.CLLocation", true)]` on the `IsObjCBridgedTypeName` theory pins the classifier; an end-to-end shape would need a Swift API exposing the SPI-qualified coordinate type marshalled by value.
