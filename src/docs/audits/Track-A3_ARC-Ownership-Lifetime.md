# Track A3 — ARC / Ownership / Lifetime / Memory Safety Audit

**Scope:** ARC retain/release correctness, ownership transfer, finalizer/Dispose safety, and existential/closure lifetime across `Swift.Runtime` (`Arc.cs`, `SwiftHandle.cs`, `ProxyLifetimeTracker.cs`, `ExistentialContainer.cs`, `InteropServices/SwiftMarshal.cs`), the proxy/closure emitters (`ClosureEmitter.cs`, `EveryProtocolEmitter.cs`, `ProtocolProxyEmitter.*`), the BindingTests `Lifetime/` and `MemoryManagement/` suites, and `src/docs/Design/memory-management.md`.

**Overall risk rating: 5 / 5 (high).** Confidence: high. Six distinct memory-safety defects were probe-confirmed, including two P0/P1 ARC-corruption bugs that reproduce as deterministic SIGSEGV under native probes (`swift_retain` on ObjC-backed classes; double-free of borrowed wrappers on explicit `Dispose`) and three P1 leaks on the outbound existential boxing/inline paths. The corruption findings are the headline: they silently mis-handle reference counts on real, reachable type shapes and crash under load rather than failing loudly.

> **Independent code-level verification — 2026-06-01 (Claude).** All **6 confirmed findings (§1)** were re-verified by reading the exact cited code plus a targeted grep (no live harness run). **Result: zero false positives; every line citation precise; every claimed mechanism matches the code.** Spot-confirmed facts:
> - **`ExtractCopiedValue` (`SwiftMarshal.cs:466`) + `ExtractCopiedElement` twin (`:1466`)** — both take `Arc.Retain` (= `swift_retain`, `Arc.cs:33-38`) gated purely on `Kind == TypeMetadataKind.Class`, with no unknown-object discrimination. (`swift_retain` no-ops on ObjC-backed instances — textbook runtime fact.)
> - **Opaque-proxy finalizer (P0)** — `DestroyWireBufferRetains` (`SwiftMarshal.cs:189`) is a **direct** `ValueWitnessTable->Destroy(...)` calli, *not* a trampoline; both `Dispose()` (`SwiftObject.cs:108`) and `~Proxy()` (`:128`) reach it; the class-bound twin (`:81`) correctly uses the finalizer-safe `Arc.UnknownObjectReleaseFinalizerSafe`. **The comment at `:71` ("the opaque path routes through SBW_VWTDestroy") is confirmed FALSE.** Crash *tier* genuinely disputed — the audit's own §2 negative simulator probe is sound (the VWT Destroy slot is Cdecl, not CallConvSwift).
> - **`MarshalBorrowedFromSwift` (`:825-843`)** — builds an owning wrapper and only `GC.SuppressFinalize`s it; never sets the handle non-owning / `SetHandleAsInvalid`. The comment at `:831-833` names the finalizer hazard but misses that explicit `Dispose()` also runs `ReleaseHandle`.
> - **Non-inline box leak (`ExistentialContainer.cs:964`)** — `swift_allocBox` (+1) stored in `Payload0`, never released. **Grep confirms zero `swift_deallocBox` anywhere in `Swift.Runtime`** and `boxPair.HeapObject` is stored once (`:971`) and never released.
> - **Inline ref-backed leak (`:938`)** — `value.MarshalToSwift(ref span)` (= InitializeWithCopy, +1) copied verbatim into `Payload0..2` with no `using`/destroy.
>
> **Only soft spot:** the opaque-proxy *crash tier* (P0 vs lower) — a documented dispute, flagged by the audit in §2. **Not verified:** the §2 inconclusive and §3 deferred candidates (unconfirmed in the audit too), and — the audit's own §5 gap — **no live Mono/NativeAOT binding run was performed for any finding.**

### `ExtractCopiedValue` / `ExtractCopiedElement` — `swift_retain` on ObjC-backed classes (P1, two sites)

The class fast path in both `ExtractCopiedValue<T>` (`SwiftMarshal.cs:458-467`) and its tuple-element twin `ExtractCopiedElement` (`SwiftMarshal.cs:1459-1468`) takes an independent +1 via `Arc.Retain(classPointer)` (= `swift_retain`, native-Swift-only, `Arc.cs:33-39`) gated purely on `elementMetadata.Kind == TypeMetadataKind.Class`. A Swift class subclassing `NSObject`/`UIView` has metadata `Kind == Class` (its first metadata word is an isa pointer > `kMaxDiscriminator`, so the C# `Kind` getter returns `Class`), but it is an ObjC object whose refcount must be incremented via `objc_retain`. Probes resolving the real `libswiftCore` entry points via `dlsym` showed `swift_retain` is a **no-op** on such an instance (`CFGetRetainCount` unchanged), while `swift_unknownObjectRetain` correctly dispatches to `objc_retain`. The full-lifecycle probe reproduced premature `deinit` and a SIGSEGV when the carrier was dropped after the no-op retain. The release side of the wrapper already balances via ObjC ARC (the wrapper is an NSObject-derived `ISwiftObject`, or `SwiftClassHandle.ReleaseHandle` routes through `SBW_SwiftRelease`/`Unmanaged.release` which DOES decrement the ObjC count), so this is an **inbound-retain twin** of the round-1 release finding — the retain never landed but the release will, dropping the count one too far. The existing NSObject defense lives in a *different* method (`MarshalFromSwift`, `SwiftMarshal.cs:933-942`) and runs *after* the damaging `Arc.Retain` already executed; `ExtractCopiedElement` has no such guard at all. **Fix both sites by replacing `Arc.Retain(classPointer)` with `Arc.UnknownObjectRetain(classPointer)`.** Reachability: `ExtractCopiedValue`/`ExtractCopiedElement` are called from inside `Swift.Runtime` (`SwiftOptional.Some`, `SwiftResult` payload, `SwiftAsyncStream` elements, tuple-element marshalling), so `SwiftOptional<WidgetObjC>.Some`, a `Result`/async-stream/tuple carrying an ObjC-rooted class hits the bug. Note: a *top-level* tuple return `(NSObjectSubclass, Int)` does NOT exercise `ExtractCopiedElement` (lifted element-by-element via `MarshalFromSwiftObject`); the bug needs the tuple to be the **element of a carrier** (`Optional<(NSObjectSubclass, Int)>`, etc.).

### Opaque adopted-existential proxy finalizer — direct VWT Destroy on the finalizer thread (P0)

For owned (`ownsContainer:true`), OPAQUE-layout `any P` proxies, the generated `~Proxy()` finalizer (`ProtocolProxyEmitter.SwiftObject.cs:124-129`) calls `ReleaseAdoptedSwiftContainer()`, whose opaque branch (`SwiftObject.cs:84-100`) calls `SwiftMarshal.DestroyWireBufferRetains((IntPtr)containerPtr, existentialMetadata)` → `metadata.ValueWitnessTable->Destroy(...)` (`SwiftMarshal.cs:189`), a raw `delegate* unmanaged<void*,TypeMetadata,void>` VWT calli into Swift (`ValueWitnessTable.cs:44`). The owning ctor (`ProtocolProxyEmitter.Receivers.cs:1858-1870`) does **not** `GC.SuppressFinalize` when `ownsContainer` is true, so the finalizer is armed and this direct VWT release runs on the GC finalizer thread. This is precisely the call that `SwiftSafeHandle.HandleFinalizerRelease` (`SwiftHandle.cs:226-247`, via `VwtDestroyTrampoline.Destroy` = `SBW_VWTDestroy` Cdecl), the class-bound proxy twin (`SwiftObject.cs:81`, `Arc.UnknownObjectReleaseFinalizerSafe`), `ProxyCleanup`, and `SwiftEscapingClosure.Dispose(false)` all deliberately AVOID — commit `b912a9c1` reworked SwiftSafeHandle's finalizer to the Cdecl trampoline specifically to fix the Mono `jit-info.c:918 !ji->async` crash from a direct VWT/CallConvSwift release on the finalizer thread. The adjacent comment at `SwiftObject.cs:71` and `Arc.cs:158-159` both assert "the opaque path routes through SBW_VWTDestroy" — it does NOT. The try/catch at `SwiftObject.cs:87-100` swallows only managed exceptions; a native Mono abort bypasses it. Verifier note: this finding is **confirmed at the static/ABI/contract level** but its severity tier carries a documented disagreement — see §3, where a direct Mono-simulator finalizer-drop probe did NOT reproduce the crash (the VWT `Destroy` slot is `unmanaged`/Cdecl, not CallConvSwift, and the metadata fetch for N≥1 uses a Cdecl `[DllImport]`). The real, undisputed defects are the contract violation, the false comment, and zero finalizer coverage. **Fix:** route the opaque finalizer release through `SBW_VWTDestroy` (`VwtDestroyTrampoline.Destroy`), mirroring SwiftSafeHandle; Dispose (user thread) may keep the direct calli.

### `MarshalBorrowedFromSwift` — owning SafeHandle over a borrowed handle (P1)

`MarshalBorrowedFromSwift<T>` (`SwiftMarshal.cs:825-843`) constructs a normal owning wrapper (its `SwiftClassHandle`/`SwiftSafeHandle` is built with `base(ownsHandle:true)`, `SwiftClassHandle.cs:56-60`) over a BORROWED native handle (the Swift `@_cdecl` closure wrapper passes `Unmanaged.passUnretained(p0).toOpaque()` — +0, no retain, `ClosureEmitter.SwiftWrapper.cs:557-558`), then only `GC.SuppressFinalize`s the wrapper and its `Payload`. It never marks the handle not-owning, never calls `SetHandleAsInvalid`, and sets no `_disposed` flag. The wrapper is `IDisposable` and is handed to user delegate code in closure callbacks (`ClosureEmitter.cs:760` Optional<class>, `:848` plain class). If the user calls `Dispose()`/`using` on the borrowed wrapper, `SwiftClassHandle.Dispose()` → `ReleaseHandle()` → `Arc.Release(handle)` → `swift_release` on a reference Swift still owns. A native probe (`/tmp/borrow-probe`) showed entry refcount 1, the release fired `deinit` immediately, the subsequent field read returned freed memory (UAF), and Swift's natural ARC release at scope exit double-freed → SIGSEGV (exit 139). A .NET-level probe deterministically ran `ReleaseHandle` twice (wrapper + `Payload`). Real exposed surface: `DatabaseReader` (a Swift class) is received borrowed in generated closure callbacks. The String/Data borrowed sites immediately convert and never expose the wrapper; the defect is specifically the class and Optional<class> callback parameters. **Fix:** construct the borrowed `Payload` SafeHandle with `ownsHandle:false` (or neutralize via `SetHandleAsInvalid`) so explicit `Dispose` is a native no-op.

### `MarshalPayload` non-inline box — `swift_allocBox` +1 never released (P1)

`MarshalPayload`'s non-inline branch (`ExistentialContainer.cs:958-974`) allocates a Swift heap box via `swift_allocBox(metadata)` (+1) for any value-type conformer whose value-witness `Size > 24` (or `IsNonInline`), `InitializeWithCopy`s the value into the box (giving the box owning +1 refs on its payload), and stores `boxPair.HeapObject` in `Payload0`. Nothing in the runtime ever releases that box — `swift_deallocBox`/`swift_release` of a box pointer appears nowhere in source. ABI ground truth (verified by SIL): a by-value `any P` parameter is `@in_guaranteed` (borrowed); the CALLER must run the existential value-witness destroy after the call. In the .NET binding C# IS the caller, and the generated call site (e.g. `AcceptsAnyDescribable`, all 82 existential-arg sites in `BindingTests/output/SwiftBindingsTestLib.cs`) does only `NativeMemory.Free(itemHeap)` — it frees the 5 container words but never runs the value-witness destroy. The generated `@_cdecl` wrapper uses `item.load(as:)`, a non-consuming copy that takes and releases its own +1 only. A runtime probe leaked all 4 tracked fields per call; the control with a VWT-destroy before free leaked 0. **Important scope nuance:** the common inline-class **proxy** path (`GetOrCreate` → `proxy.GetExistentialContainer`, where the proxy owns the +1 via the strong registry / `ProxyLifetimeTracker`) correctly omits the destroy and does NOT leak — destroying there would be a double-decrement. **The double-free alternative in the original claim is refuted** (the callee never releases under `@in_guaranteed`). **Fix:** run the existential value-witness destroy (`SwiftMarshal.DestroyWireBufferRetains` over the existential metadata) at the boxed-payload argument call sites only — NOT a blanket destroy of every existential argument.

### `MarshalPayload` inline ref-backed — `InitializeWithCopy` +1 leaks (P1)

The inline branch (`ExistentialContainer.cs:938-957`, `size <= 24 && !IsNonInline`) calls `value.MarshalToSwift(ref span)` (a value-witness `InitializeWithCopy` = +1 on the embedded reference for a reference-backed payload) and copies the words verbatim into `Payload0..2` with no `using` and no post-copy/post-call value-witness `Destroy`. `ExistentialContainer1` is a plain struct with no Dispose/finalizer, so nothing releases that +1. The generated consumer does `NativeMemory.Alloc` → `Unsafe.Copy` → `NativeMemory.Free`, which frees the heap block but not the embedded reference. An ARC repro yielded final `liveCount=1` (leak); the control adding a VWT-destroy yielded 0. **Reachability correction (does not change the verdict):** the flagship example `Swift.String passed via Create<T,TProtocol>` is NOT reachable — `SwiftString` does not implement `IExistentialBoxable`, so a bare `String: P` goes through `ExistentialContainer0.Box` (which is correctly balanced via `using var swiftStr`). The genuine trigger is a **frozen-with-ref struct conformer** (a `@frozen` struct with a String/class field, ≤24 bytes, stored inline) — which the emitter does emit `IExistentialBoxable` for (`FrozenStructHandler.cs:393`). **Fix:** a blanket Destroy after every existential-param call is WRONG (the EveryProtocol/proxy path marshals a raw class pointer with no +1, so destroying it would over-release); the fix must be conditional on the conformer being a value-witness-copy type, mirroring the type-aware Destroy in `ClosureEmitter.StructParams.cs:360-363` and `WrapperEmitter.Marshalling.cs:1212`.

> Note on the three boxing/inline leak entries: the confirmed findings JSON contains two near-duplicate confirmations of the non-inline box leak (`ExistentialContainer.cs:964`). They describe the same defect — one leak, two independent confirmations — and are merged into the single "non-inline box" row above.

## 2. Inconclusive / needs deeper probe

These have a real defect somewhere but the *claimed* failure mode did not cleanly reproduce, or the votes split.

- **Opaque proxy finalizer `!ji->async` crash tier (P0 candidate, votes split confirmed/refuted).** `ProtocolProxyEmitter.SwiftObject.cs:92`. The structural facts are confirmed (direct VWT calli on the finalizer thread, false comment, zero coverage — see §1). What is *inconclusive* is whether it actually crashes Mono: one verifier built a `/tmp` RuntimeTestsApp copy, dropped 300 owned `any Renderable` proxies without `Dispose` (both after heavy CallConvSwift contamination and cold-JIT), forced `GC.WaitForPendingFinalizers` on the iPhone 17 Pro Max simulator, and observed **no crash** (`{"done":true,"passed":2}`, 299/300 payloads released on the finalizer thread). Their argument: the VWT `Destroy` slot is `unmanaged` (Cdecl), not CallConvSwift, so it is not async-classified, and the metadata fetch for N≥1 uses a Cdecl `[DllImport]`, not the CallConvSwift accessor — per `src/docs/Future/upstream-issue-01`, `!ji->async` fires only on a signal-handler unwind through a CallConvSwift frame. **Resolution path:** keep the fix (route through `SBW_VWTDestroy`) on contract/consistency grounds; the *crash* claim needs a sustained finalizer-drop probe that also drives the opaque value-witness Destroy across many GC cycles under a future runtime regression. The contract violation and false comment are real regardless.

- **`MarshalToSwift` raw `GetFunctionPointerForDelegate` with no keep-alive (P1, premise true / defect narrow).** `SwiftMarshal.cs:605`. `CreateConventionCClosure` (the UNPINNED variant) writes a fn-ptr with no `GCHandle`; a `/tmp` probe confirmed a delegate on that exact path is GC-collectible and crashes (`A callback was made on a garbage collected delegate`, SIGABRT). BUT: in the generated bindings (1448 `MarshalToSwift` calls), **zero** pass a delegate — escaping closures use the emitter's `[UnmanagedCallersOnly]` static thunk + `GCHandle.Alloc`-rooted `ClosureHandle`. The branch is only reachable by marshalling a delegate-TYPED element into a runtime container (`SwiftArray<TDelegate>.Add`, etc.), a rare untested shape. So the bug is real-if-reached but currently latent. **Hardening:** use `CreatePinnedConventionCClosure` and surface the `GCHandle`, or throw `NotSupportedException` for delegate elements.

- **Adopted-proxy `_disposed` double-release race (P1, votes split refuted/confirmed).** `ProtocolProxyEmitter.StaticInit.cs:65` (`private bool _disposed;`, non-volatile) + bare check-then-set in both `Dispose()` and `~Proxy()`. The claim's *primary* mechanism (Dispose-vs-finalizer race) is **refuted**: a thread inside `Dispose()` roots `this`, so the GC cannot have queued the finalizer (probe: 0 double-releases across 300k-1M iterations of the Dispose-vs-GC scenarios; `GC.SuppressFinalize` also de-queues). What IS real: **two concurrent `Dispose()` calls on the same instance** double-release (~0.7-0.02% in 1M-instance runs). This violates the (not-thread-safe) `IDisposable` contract — caller misuse, not normal-disposal corruption. The runtime already uses the correct `Interlocked.Exchange(ref entry.Released, 1)` pattern in `ProxyLifetimeTracker.cs:281`; the proxies do not. **Hardening (defense-in-depth, not a live-bug fix):** change `_disposed` to `int` + `Interlocked.Exchange` claims-the-release in both `ProtocolProxyEmitter.SwiftObject.cs` and the composition-proxy duplicate at `ModuleHandler.cs:1904-1922`.

## 4. Checked & refuted

Do not re-chase these — verified and the code is correct (or the claimed mechanism is impossible).

- **`MarshalBorrowedFromSwift` reflective `GetProperty("Payload")` silently no-ops → double-release of borrowed handle.** `SwiftMarshal.cs:825`. REFUTED: no generated wrapper shape simultaneously (a) lacks a public `Payload` AND (b) holds a finalizer-bearing SafeHandle. The flagship example (protocol proxy) lacks `Payload` but its backing is a VALUE-TYPE `ExistentialContainer1` field — no SafeHandle to leak — and proxies never route through `MarshalBorrowedFromSwift` anyway (existential closure args emit `new {Proxy}(arg)`, grep-confirmed zero `MarshalBorrowedFromSwift<...Proxy>` in real output). Every concrete type that DOES flow through it exposes a public `Payload` (class `SwiftClassHandle Payload`, opaque-payload `SwiftSafeHandle Payload`, frozen-struct value types, runtime `SwiftResult`/`SwiftString`). The `?.`-swallows-null design is correct by construction. (The *separate* owns-handle defect on this same method IS confirmed — see §1.)
- **`swift_allocBox` box writes value bytes via raw `MarshalToSwift` instead of `initializeWithCopy` (raw byte copy of a ref-bearing type).** `ExistentialContainer.cs:964`. REFUTED: `value.MarshalToSwift` IS the `InitializeWithCopy` call for every reference-containing value type (non-frozen struct `TypeHandlerHelpers.cs:406`, frozen-as-class `:345`, enum `EnumISwiftObjectMethodWriter.cs:293`, class `ClassHandler.cs:1026/1056`, runtime `SwiftString.cs:141`/`SwiftArray.cs:143`). Only POD/blittable types take the raw-byte path, and those never reach the box branch. A `/tmp` probe driving the exact box sequence (allocBox + VWT InitializeWithCopy + release) on a 32-byte 4-ref struct was perfectly balanced (no over-release, no leak, source survived); a counter-probe doing the alleged raw `memcpy` SIGSEGV'd, confirming the failure mode is real *only* for raw copy — which the code does not do. (The box +1 *not being released* is a separate, confirmed leak — see §1.)

## 5. Coverage gaps

What this track did NOT reach or fully resolve:

- **No live Mono-simulator / NativeAOT-device runtime reproduction for most findings.** The ARC-corruption confirmations rest on native `swiftc` `dlsym` probes (which faithfully mirror the C# `[DllImport]` Cdecl calls and the wrapper lifecycle) plus generated-output inspection, not a running `.NET` binding under Mono/NativeAOT. The opaque-proxy `!ji->async` *crash tier* specifically remains unresolved (one negative simulator probe — see §2). Mono and NativeAOT have different ARC/JIT exposure; device runs are needed to close calibration.
- **22 deferred candidates (§3) were not probed at all** due to the per-track cap — the async-continuation UAF (#13, #14), the closure-getter `GCHandle` sim leak (#2), and the `Arc.Release` TOCTOU (#7) are the highest-value unprobed items.
- **Apple-supplement boxed-error proxy** (a likely *third* instance of the non-atomic `_disposed` double-release shape, in a separate assembly referenced by `SwiftBindings.Apple.xml`) was not opened.
- **`ProxyLifetimeTracker` race semantics under genuine multi-threaded Swift release threads** (the deinit-vs-finalizer claim window) were only modeled with managed probes, not driven by real Swift release threads calling `OnEveryProtocolDeinit`.
- **`memory-management.md`** was read for the ownership contract (`@in_guaranteed` borrowed-parameter rule, InitializeWithCopy requirement at `:177-181`) but not audited for staleness against the confirmed leaks — the doc states the rule the box/inline paths violate.

## 6. Recommended BindingTests fixtures

Swift shapes that would lock down each confirmed defect (descriptions only — no code-fix proposals). New fixtures go in `BindingTests/Sources/SwiftBindingsTestLib/` with C# in the matching `RuntimeTestsApp/MemoryManagement/` or `Lifetime/` domain file.

1. **ObjC-backed class extracted via copied-value/element paths (covers `ExtractCopiedValue` + `ExtractCopiedElement`).** Swift: `class Holder: NSObject {}` plus APIs returning `Optional<Holder>`, `Result<Holder, E>`, and a tuple carried inside a carrier — `Optional<(Holder, Int)>` (a *top-level* `(Holder, Int)` does NOT hit `ExtractCopiedElement`; it must be a carrier element). C#: extract via `.Some`/`.Item` in a loop, assert liveness/`CFGetRetainCount` balance over many iterations on simulator AND device. Today's `LeakDetection.swift:559` exercises this path only with a pure-Swift `TrackedRef`, for which `swift_retain` is correct — so the ObjC case is genuinely uncovered.
2. **Owned opaque `any P` proxy dropped WITHOUT Dispose (covers opaque finalizer path + closes the §2 crash-tier question).** Swift: an API returning an owned `any Renderable` (opaque, non-class-bound protocol) whose conformer is a boxed value type. C#: in a CallConvSwift-heavy sim test class, obtain the returned proxy, drop the reference without `Dispose()`, force `GC.Collect()/WaitForPendingFinalizers()` over many cycles. Existing `ExistentialReturnLeakProbeTests` always `Dispose()`s (suppressing the finalizer), so the `~Proxy()` path has zero coverage.
3. **Borrowed class closure callback with user `Dispose` (covers `MarshalBorrowedFromSwift` owns-handle).** Swift: a closure parameter `(SomeClass) -> Void` (non-escaping, borrowed), where `SomeClass` is a Swift class (mirroring `DatabaseReader`). C#: pass a delegate that does `using (arg) {}` or `arg.Dispose()`; on the next GC/Swift release, assert no double-free SIGSEGV / no `swift_isDeallocating` throw. Also cover the Optional<class> variant.
4. **>24-byte value-type conformer passed as `any P` (covers non-inline box leak).** Swift: `protocol P {}` and a value type larger than 24 bytes whose stored field is a `LifetimeTracker`-counted class; API `func acceptP(_ x: any P)` (and `func acceptAny(_ x: Any)`). C#: loop N times with `[MethodImpl(NoInlining)]`, then `DrainFinalizers` + `LifetimeTracker.AssertNoLeaks`. Assert specifically on the boxed-value-type path — the inline-class proxy path is correctly non-leaking and would muddy the signal.
5. **Frozen-with-ref struct conformer ≤24 bytes passed as `any P` (covers inline ref-backed leak).** Swift: a `@frozen struct` with a single `String` or class-ref field conforming to a non-class-bound protocol `P`; API `func acceptP(_ x: any P)`. C#: loop with `LifetimeTracker`, `AssertNoLeaks` after draining. Compare against passing the same value as bare `Any` (through `ExistentialContainer0.Box`), which should NOT leak.
