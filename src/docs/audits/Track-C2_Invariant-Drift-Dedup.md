# Track C2 — Invariant Drift / Dedup / Key Consistency

Scope: the `.claude/rules/*.md` "trap" invariants vs. live code, the 23 `WasEmitted` emission sites and their ancestor-resolution readers, and the family of projected-C#-method-key generators (`IHandler.GetProjectedCSharpMethodKey`, `DefaultParameterOverloadEmitter.GetProjectedOverloadKey`, `ProtocolSignatureHelper.GetProjectedCSharpMethodKey`) plus the EveryProtocol subscript/property dedup keys.

Overall risk rating: **4 / 5** (high). Confidence: **high** for the confirmed defects (each is probe-demonstrated to produce a hard `CS0111` or a silent override mis-binding); medium for the breadth of the deferred set (real candidates in the same key-divergence family, not yet probed under the per-track cap).

The headline is a single root cause with multiple manifestations: the **authoritative emitted C# method name applies a property-collision rename (`Foo`→`FooMethod` / `WithFoo`) and a numeric collision suffix (`Foo2`) that the dedup keys and the same-module override verifier do NOT see.** Emitted name and dedup key disagree, so genuine C# overload collisions slip past dedup (`CS0111`) and overrides bind to the wrong slot. The `constraints.md` invariants that exist precisely to prevent this drift are themselves stale (WasEmitted: doc 13/6 vs actual 23/12; overload-key: doc ~26/15 vs actual 35/16; GetPublicMethodName: doc ~22/15 vs actual 27/14).

### IHandler.cs:528 — `GetProjectedCSharpMethodKey` drops the property-collision rename

`BaseHandler.GetProjectedCSharpMethodKey` populates the shared `EmittedProjectedSignatures` set used by the main pass and by every post-processor (`NativeIntOverloadEmitter.BuildOverloadKey`, `ThrowingClosureSimplificationEmitter.BuildOverloadKey`, the completion-handler async wrapper). Its method-name component is built by `NameProvider.GetPublicMethodName(...)` with `parentTypeName` but **no `propertyNames` argument** (`IHandler.cs:528`). Step 4 of `GetPublicMethodName` (`NameProvider.cs:1409-1415`) — the `Foo`→`FooMethod` / `WithFoo` rename when a sibling property collides — therefore never fires inside the key. But the real emitted member name, `MethodEnvironment.CSharpMethodName` (`IEnvironment.cs:149-156`), passes `SiblingPropertyNames` and *does* rename. Two writers of one set disagree on the namespace. Probe-confirmed `CS0111` (two independent reproductions). The contrast point is unambiguous: `ProtocolSignatureHelper.GetProjectedCSharpMethodKey` (`ProtocolSignatureHelper.cs:114/122`) *does* accept and pass `propertyNames`, so the two same-named key functions already disagree on this dimension. Per `constraints.md:16`, `GetProjectedOverloadKey` (`DefaultParameterOverloadEmitter.cs:664`) must match this function exactly — it carries the same omission, so any fix must thread the sibling-property set into both static builders in lockstep (they currently receive only `MethodDecl` + `ITypeDatabase`, no sibling-property context).

### IEnvironment.cs:149 — single source of truth diverges from all dedup keys

This is the same defect viewed from the name producer. `CSharpMethodName` is the authoritative emitted name and is the only key participant that passes `SiblingPropertyNames`. All three dedup-key generators (`IHandler.cs:528`, `DefaultParameterOverloadEmitter.cs:664`, and the concrete-path use of `ProtocolSignatureHelper`) withhold it. The decisive end-to-end trigger found by the probes is the **completion-handler async overload vs the native-async main-pass key**: both project to the same `(CancellationToken)` parameter list, so the method-name divergence alone yields two identical `DataMethodAsync(CancellationToken)` members → `CS0111`. A single nint-narrowing method colliding with a property compiles cleanly; the defect needs a sibling whose native emission lands on the same `Name(int)` signature the convenience overload synthesizes. The fix site is `IHandler.cs:528`; `IEnvironment.cs:149` documents why the divergence matters.

### WrapperEmitter.Signature.cs:570 — override verifier ignores `EmittedCSharpName`

`HasMethodInResolvedAncestors` (line 462) passes `derivedCSharpName = _env.CSharpMethodName` (which includes the `+(CollisionIndex+1)` suffix) and compares it via `AncestorCSharpNameMatches` → `ComputeMethodCSharpName(ancestorMethod, ...)` (lines 570-571, 587-624). `ComputeMethodCSharpName` recomputes only the `NameProvider` base name with **no collision suffix and no read of `ancestorMethod.EmittedCSharpName`**. When an ancestor's overload set was disambiguated into `Process` / `Process2`, the verifier returns the unsuffixed `Process` for both, so a derived override of the *second* overload is emitted as `override Process(...)` and binds to the first base slot. Both probes confirmed this; one demonstrated the silent runtime mis-binding via CLR metadata (`Derived.Process` is a REUSESLOT override of `Base.Process` overload #1, while overload #2's slot is left un-overridden). The cross-module populator `ClassHandler.cs:582-583` prefers `EmittedCSharpName` for exactly this reason; the same-module verifier has the bug that path was written to avoid. Suggested fix shape: `AncestorCSharpNameMatches` should prefer `ancestorMethod.EmittedCSharpName` when non-null before falling back to `ComputeMethodCSharpName`.

The readers (`WrapperEmitter.Signature.cs:473`, `:664`, with the in-code comment at 489-495 stating this "prevents silent CS0115") make the stale checklist load-bearing: a future emission path that emits a base member but forgets the flag will make a derived override drop `override` or yield `CS0115`, and the doc that should enumerate the mirror-set no longer reflects the live sites.

## 2. Inconclusive / needs deeper probe

### ProtocolExtensionEmitter manual dedup key bypasses the normalizations of the key it compares against (`ProtocolExtensionEmitter.cs:314`, gate at `:327`) — P1

The injected-extension collision gate hand-builds its key (`$"{csMethodName}({...projParamTypes})"`, line 314) where `csMethodName` is `GetPublicMethodName` with **no `isSelfReturning`, no `parentTypeName`, no `propertyNames`, raw `parameters.Count`**, and each param type is `projection?.PublicType ?? paramTypeSpec.ToString()` (line 312) — skipping `StripOptionalClassLikeForOverloadIdentity` and `NormalizeParamTypeForOverloadIdentity`. It compares against `existingProjectedKeys` built by the canonical `BaseHandler.GetProjectedCSharpMethodKey` (line 323), which applies all of those. Code-level divergence verified (read both sides; `OptionalProjection.PublicType` appends `?` so an extension `combine(_:Widget?)` keys `Combine(...Widget?)` while the canonical existing-method key normalizes to `Combine(...Widget)`).

The two votes split on consequence:
- **Confirmed (isolated driver):** a probe driving the real `ProtocolExtensionEmitter.InjectExtensionMethods` showed the gate misses the collision and injects a duplicate (method count 1→2) instead of dropping it.
- **Refuted (end-to-end):** a full generator run showed the duplicate is *repaired downstream* by the authoritative "B15" secondary dedup in `HandleBaseDecl` (`IHandler.cs:442`), which re-keys every injected method via the canonical (`parentTypeName`-aware) key and numeric-suffixes the collision (`Verify` / `Verify2`). Net generated output compiled with 0 errors.

Resolution: the manual key is a **redundant early/advisory filter whose correctness is already guaranteed by the downstream B15 pass** — so it is a genuine `constraints.md:16` consistency violation (a fourth, hand-rolled key construction outside the canonical helpers) but not, on current evidence, a `CS0111`-producing defect in shipped output. It warrants a deeper probe to determine whether any shape exists where B15 does *not* backstop it (e.g. an injection path that doesn't flow through the normal `HandleBaseDecl` member loop, or the self-returning/`parentTypeName` axis combined with a path B15 skips). Recommended tidy regardless: have the gate compute the synthetic key through the canonical path rather than hand-rolling it.

## 3. Deferred (candidate, unverified)

These are real key-divergence candidates in the same family, not probed under the per-track cap. Listed so none is silently dropped.

1. **Protocol interface-declaration dedup omits `propertyNames` while the proxy that implements it includes them** — `ProtocolHandler.cs:371` builds the interface-method dedup key via `ProtocolSignatureHelper.GetProjectedCSharpMethodKey(..., propertyNames defaulting to null)`, but the proxy dedups the same methods *with* `emittedCSharpPropertyNames` (`ProtocolProxyEmitter.InterfaceImpl.cs:117/125`). Interface and proxy can disagree about which overloads survive → `CS0535` (proxy doesn't implement a declared member) or `CS0111`. Fix appears to be a one-line pass-through. (P1)

2. **Protocol DIM nint-overload key uses the property-renamed name into the same set the primary registered un-renamed** — `ProtocolHandler.cs:1449` builds `dimKey` from a `propertyNames`-aware name and adds it to the `emittedCSharpKeys` set that the primary loop (`:372`) populated without `propertyNames`. Two naming rules feeding one set. (P1)

3. **ProtocolExtensionEmitter projected key omits `isSelfReturning` + `parentTypeName`** (a distinct axis from the parameter-normalization bypass in §2, same `ProtocolExtensionEmitter.cs:301`). Self-returning or type-name-equal extension methods get `Get`/`With` from the real emit path but the bare name in the gate key. (P1)

6. **`ProtocolSignatureHelper.GetProjectedCSharpMethodKey` diverges from the other two**: omits `parentTypeName` (CS0542 `Get` prefix) AND omits the async `CancellationToken` param (`ProtocolSignatureHelper.cs:114/121-143` — confirmed absent vs `IHandler.cs:615-618` / `DefaultParameterOverloadEmitter.cs:717-721`). When this helper's key is cross-pool-compared with the other two, async methods and self-named methods produce mismatched keys. (P2)

7. **`constraints.md:16` overload-key count stale and omits the hand-rolled bypass** — doc says "~26 call sites across 15 files"; verified **35 call sites across 16 files**, and the count does not flag the inline `ProtocolExtensionEmitter.cs:314` construction. (P2)

10. **Three overload-key generators feed `GetPublicMethodName` with mutually-exclusive optional args** (`propertyNames` vs `parentTypeName`) — cross-pool key comparison (e.g. concrete-vs-witness specialization matching) is unsound for a method that emits `Foo` in one context and `FooMethod`/`GetFoo` in another. `ProtocolConformanceValidator.cs:447-459` already works around this by computing both ways — evidence the divergence is known to bite. (P2)

11. **`constraints.md:27` GetPublicMethodName count stale** — doc "~22 call sites across 15 files"; verified **27 across 14 files**. The trap mentions only `parameterCount` consistency, not the `propertyNames`/`parentTypeName` divergences that actually bite. (P2)

Producer/consumer coupling is unenforced; any key-format change silently breaks the lookup → empty-buffer/no-op subscript dispatch with no compile error. (P2)

13. **`GetProjectedOverloadKey` trim-variant `Get`-prefix flip** — the trim variant computes `parameterCount` on the *trimmed* signature; a method that trims to zero non-default params gains a `Get` prefix the full-signature primary key never had (`Data(double)` primary vs `GetData()` trim), so the divergent name can clash with an unrelated `GetData` getter undetected. Sugar differences (`[Int]` vs `Array<Int>`, `Optional<X>` vs `X?`, typealias resolution, module qualification) between base and override break the override modifier → degrades to `virtual`/`new`. (P2)

15. **Cross-protocol subscript global-dedup embeds per-protocol position index** (`EveryProtocolEmitter.cs:1150`, `GetSubscriptKey(sub, subscriptIndex)` with index reset per protocol) — position-dependent identity. Lower confidence (subscripts may never emit as C# `override`). (P2)

17. **`NormalizeParamTypeForOverloadIdentity` trailing-`?` trim only covers literal `"string"`/`"object"`** (`ProtocolSignatureHelper.cs:409/420-421`), narrower than the structural `StripOptionalClassLikeForOverloadIdentity` reference-like predicate — frozen-struct-as-class or bridged ObjC reference types projected to other C# names keep `?` in the post-projection trim path, so `T?` and `T` keys can diverge across the mirror generators. (P2)

18. **`ProtocolExtensionEmitter` fast-path key uses parser-escaped `arg.Name` vs raw swiftinterface `p.label`** (`BuildOverloadAwareMethodKey` :2518 vs `BuildOverloadAwareExtensionKey` :2539) — keyword labels (`for`→`_for`) make `name(_for:Int)` vs `name(for:Int)` mismatch, so a real ABI-method collision slips the fast gate (backstopped by the projected gate, which itself carries the §2/§3 divergences). (P2)

19. **`ProtocolSignatureHelper` key generator lacks the closure-tombstone `object?`-collapse** present in `BaseHandler` — two protocol overloads with different unsupported closure shapes get distinct protocol-side keys while emitting the same `object?` signature → potential `CS0111` in the interface/proxy. (P2)

## 4. Checked & refuted

Brief, so future agents don't re-chase. Each was probe-tested and the predicted defect did not manifest.

- **EveryProtocol subscript cross-protocol dedup omits return type → dropped witness** (`EveryProtocolEmitter.cs:1150`). REFUTED: `ComputeSubscriptEmissionPlans` records a plan entry for *every* non-static subscript (no single-member guard), and `ModuleHandler.cs:1255` always passes `subscriptPlans` non-null, so the line-1141 plan lookup always succeeds and the return-type-blind `else if` global branch is **unreachable in production**. Probe emitted both subscript bodies; wrapper typechecked.
- **Two divergent subscript-identity keys disagree on labels/return → dropped witness** (`EveryProtocolEmitter.cs:4753`). REFUTED for the same reason — the plan-map key is the tuple `(protoQName, subscriptKey)`, so the bare-key collision is harmless; both protocols emit. The `GetSubscriptKey` vs `GetSubscriptSiblingKey` divergence is benign by design (subscript overloading is legal within a protocol, properties are not).
- **ProtocolExtensionEmitter projected-collision csMethodName omits `parentTypeName`/`isSelfReturning` → CS0542** (`ProtocolExtensionEmitter.cs:301`). REFUTED: the asymmetry is real, but the emitted name comes from `MethodEnvironment.CSharpMethodName` (which *does* pass `parentTypeName`, so rule 4c renames `foo`→`GetFoo`), and the downstream B15 dedup (`IHandler.cs:442-476`) numeric-suffixes any residual collision. Probe of the exact `func foo` on type `Foo` scenario emitted `GetFoo` and compiled clean.
- **EveryProtocol sibling-property fallback keyed by name only → wrong vtable dispatch** (`EveryProtocolEmitter.cs:800`). REFUTED: the precondition (one `ProtocolDecl` owning two same-named different-typed properties) is **impossible in Swift** (`invalid redeclaration`), and the cross-protocol same-name/different-type case is dropped upstream by `ModuleHandler.cs` conflict filtering before the map is built. The property-path key correctly omits the type because `(proto, name)` is already unique; the subscript-path asymmetry is justified (subscripts overload, properties don't).
- **WasEmitted ancestor checks scan only `ancestor.Methods/Properties`; synthesized bridge decls bypass them → CS0114/CS0506** (`WrapperEmitter.Signature.cs:472`). REFUTED (functional). Every WasEmitted setter targets the canonical class-member decl that lives in `ClassDecl.Methods` (the `synthesized` clone in `…Async.cs:78` is a throwaway whose *original* also gets the bit at :77; CSM/keypath emitters emit `static` extension methods that never reach the `override` decision). Probe with a generic-bridge-routed base method overridden by a derived class emitted `override` correctly. (The doc-staleness sub-claim is the separately-confirmed §1 item.) Two *unrelated* real bugs surfaced incidentally — `CS0460` (redundant `where` on a generic override) and `CS0108` (CSM concrete overloads missing `new`) — worth separate tickets, opposite in direction (they prove `override` IS emitted).
- **`GetProjectedOverloadKey` lacks the closure-tombstone `object?`-collapse → CS0111** (`DefaultParameterOverloadEmitter.cs:687`). REFUTED. A tombstoned method's `Emit` returns early (`MethodHandler.cs:106-116/821-831`) *before* the default-overload post-processor runs, and `BuildOverloadDecl` does not copy `IsClosureParamTombstone`, so the trim path never sees a tombstone. Probes (single tombstone, and tombstone + supported sibling) emitted exactly one tombstone declaration each and compiled with 0 errors. The IHandler `object?` branch guards a different scenario (two tombstoned overloads differing only in closure shape). (This is listed as deferred §3.5 only as the documented-invariant-violation framing — it is not a live output defect.)

## 5. Coverage gaps

What this track did NOT reach:

- **The 19 deferred candidates in §3 were not probe-verified.** Several (especially the interface-vs-proxy `propertyNames` mismatch §3.1, the DIM nint-overload key §3.2, and the `ProtocolSignatureHelper` async-`CancellationToken` omission §3.6) are structurally identical to the confirmed P1s and are strong candidates for `CS0535`/`CS0111` under the right Swift shape. The per-track cap stopped probing after the four confirmed defects + the one inconclusive split.
- **The `ProtocolExtensionEmitter` manual-key (§2) was not exhaustively swept** for a shape where the downstream B15 dedup fails to backstop it (e.g. an injection path bypassing the normal `HandleBaseDecl` loop, or the self-returning/`parentTypeName` axis crossed with a B15-skip case such as constructors). Only the Optional<class>-param axis was driven; the other four named axes (`isSelfReturning`, `parentTypeName`, raw `parameterCount`, `propertyNames`) remain unconfirmed end-to-end.
- **Property-side dedup** (PropertyHandler emission keys, `CS0102` member-name collisions between a renamed method and an auto-property/getter) was only touched tangentially via the `GetData` getter scenario in §3.13; no dedicated property-vs-method cross-namespace probe was run.
- **The cross-module override path** (`ClassHandler.PopulateEmittedClassMethods` → persisted `EmittedClassMethods` → `CrossModuleAncestorHasMethod`) was read but not probed; it correctly prefers `EmittedCSharpName` for methods but the raw-`ToString()` parameter compare (§3.14) was not exercised cross-module.
- **`swiftui-bridge.md` and `bindingtests.md` rule files** were in scope by name but contained no key-consistency invariants of the drift class; no findings.

## 6. Recommended BindingTests fixtures

Swift shapes that would permanently lock down each confirmed defect (no fix code proposed — fixtures only). Add Swift to `BindingTests/Sources/SwiftBindingsTestLib/` and the C# assertions to the matching domain file in `BindingTests/RuntimeTestsApp/`. Because the defects are compile-time (`CS0111`) or silent-mis-dispatch, the durable gate is `nuke binding-tests --compile-only` (compile must succeed) plus a runtime dispatch assertion for the override case.

1. **Property-collision dedup (`IHandler.cs:528` / `IEnvironment.cs:149`).** A class with a stored property whose PascalCase name (`var conflict: Int`) collides with two methods: `func conflict(_ x: Int) -> Int` and a naturally-named `func conflictMethod(_ x: Int) -> Int`. Both project to `ConflictMethod(nint)`. Fixture asserts the binding compiles (no `CS0111`) and that calling each surfaces its distinct Swift behavior (e.g. different return values), proving they were disambiguated rather than collapsed. Include a control sibling without the property to confirm the property is the trigger.

2. **Completion-handler async vs native async collision (`IEnvironment.cs:149`).** A class with `var data: Int`, `func data() async -> Int`, and `func data(completion: @escaping (Int) -> Void)`. The property forces the `DataMethod` rename; the async + completion overloads both project to `DataMethodAsync(CancellationToken)`. Fixture asserts compile success and that both async entry points return correctly.

3. **Same-module override with collision-suffixed base (`WrapperEmitter.Signature.cs:570`).** A same-module base class with two overloads that project to a colliding C# key (cleanest trigger: `func process(_ x: Widget) -> Int` and `func process(_ x: Widget?) -> Int`, exercising nullable-ref erasure), emitting `Process` / `Process2`; a derived class overriding only the optional variant. Runtime assertion: instantiate `Derived`, hold as `Base`, call the member backing the *second* (optional) overload, and assert the Swift `Derived` override actually runs — i.e. that the override attached to the correct slot (`Process2`), not `Process`. This is the decisive check because the bug compiles cleanly and only manifests as wrong virtual dispatch. Existing same-module override tests (`ClassInheritanceEmissionTests.cs:814-870`) only use Int-vs-String overloads that produce distinct keys (no suffix) — this fixture fills that gap.

4. **WasEmitted-checklist guard (`constraints.md:18`).** Not a Swift fixture — a generator-side unit/architecture test asserting that the count of `WasEmitted = true;` assignment statements under `src/Swift.Bindings/src/Emitter/StringEmitter/Handler` equals the number documented in `constraints.md:18` (and that every emitter that contributes a class instance method/property to the override chain sets the flag on the live `ClassDecl.Methods`/`.Properties` decl). This converts the stale-doc hazard into a failing test the moment a new emission path forgets the flag or the doc count drifts.
