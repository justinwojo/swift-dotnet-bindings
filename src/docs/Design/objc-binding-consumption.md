# Pure-ObjC binding consumption model

How the native payload of a **pure-ObjC** binding package (`$(SwiftFrameworkType) == 'ObjC'` with an `@(SwiftFramework)` xcframework source) reaches a consumer app, why that lane deliberately emits no consumer `.targets`, and which guard covers which lane. As-built against SDK 0.18.0 (verified 2026-07-30; lane membership and package measurements re-verified 2026-07-31).

Lane membership is narrower than it looks. In this repo's consumer monorepo exactly three projects are on it — **MapLibre**, **Stripe3DS2**, and **FBSDKCoreKit_Basics** — plus **Intercom** externally. In particular *not* "the Facebook kits": of the five Facebook projects only `FBSDKCoreKit_Basics` is pure ObjC (`_SwiftBindingFrameworkType=ObjC`, `HasWrapperXCFramework=False` in its generated `binding-metadata.props`). `FBAEMKit` and `FBSDKLoginKit` are Swift lane; `FBSDKCoreKit` and `FBSDKShareKit` are mixed lane. All four pack a real wrapper plus `buildTransitive` targets whose `runtimes/` **is** the referenced carrier — gate off the lane, never off "the Facebook library".

Scope note: `SwiftFrameworkType == 'ObjC'` means **pure** ObjC — a framework with no Swift half. A mixed (ObjC + Swift) framework does *not* set it (that's why `Sdk.props` suppresses the Runtime/Apple `PackageReference`s with `!= 'ObjC'`), so mixed bindings ride the Swift lane described below, plus a managed-only ObjC companion assembly in the same `lib/`.

Second scope note, load-bearing for any gate: the type flag **alone does not identify this lane**. The lane is ObjC-type *and* xcframework-sourced — `'$(SwiftFrameworkType)' == 'ObjC'` **and** `'@(SwiftFramework)' != ''`. `apple-frameworks/Matter` also sets `SwiftFrameworkType=ObjC`, but it is on the *Apple-direct* lane (`<SwiftAppleFrameworkTarget Include="Matter"/>`), where `_SynthesizeAppleFrameworkConsumerTargets` does emit consumer `.targets` that `NativeReference` into `runtimes/` — there the `runtimes/` payload is load-bearing and must never be dropped. Every condition described in this document (the `runtimes/` drop and SWIFTBIND074 alike) requires `'@(SwiftFramework)' != ''`, and **SWIFTBIND011** (`Sdk.targets:125-127`) hard-errors if `SwiftAppleFrameworkTarget` and `SwiftFramework` are both set, so the two lanes cannot overlap. Concretely: `_ValidateObjCBindingPackShape` is conditioned `'@(SwiftFramework)' != '' AND '$(SwiftFrameworkType)' == 'ObjC'` (`:3680`), and the dropped source-xcframework pack item is conditioned `'@(SwiftFramework)' != '' AND '$(SwiftFrameworkType)' != 'ObjC'` (`:4076-4078`) — an Apple-direct project matches neither, so Matter's `runtimes/` is untouched by both.

## Two lanes, two carriers

| | Swift / mixed lane | Pure-ObjC lane |
|---|---|---|
| Native payload location in the nupkg | `runtimes/<rid>/native/<Name>.xcframework/**` | `lib/<tfm>/<Assembly>.resources[.zip]` (the classic binding sidecar — directory *or* zip, see step 2 below) |
| What points the consumer at it | `buildTransitive/<tfm>/<PackageId>.targets`, emitted by `ConsumerTargetsEmitter`, containing `<NativeReference Include="…/runtimes/…">` | Nothing in our SDK — Microsoft.iOS's own `_ExpandNativeReferences` / `ResolveNativeReferences` find and extract the sidecar |
| Pack-shape guards | SWIFTBIND030/031/032 (`_ValidateSwiftBindingPackSlices` — slice/RID validation) and SWIFTBIND038 (empty-native pack, inside `_ConfigureSwiftBindingPack`) | SWIFTBIND074 (`_ValidateObjCBindingPackShape`) |

## Why no consumer `.targets` on the ObjC lane

`ConsumerTargetsEmitter.Emit` is the only writer of `<PackageId>.targets`, and it is called from exactly two places in `BindingsGeneratorCommand` — the Swift/mixed xcframework path and the Apple-direct path. The pure-ObjC branch runs `ObjCPipeline.Run` and **returns** before either call site (`BindingsGeneratorCommand.cs`, the `ObjCPipeline.Run` branch and the auto-detect fallback branch both return immediately after reporting). The SDK's own synthesizer, `_SynthesizeAppleFrameworkConsumerTargets`, is gated on `@(SwiftAppleFrameworkTarget)` and so covers only Apple frameworks.

This is **intentional, and correct**: a pure-ObjC binding is a real Microsoft.iOS binding project (`IsBindingProject=true`), so the workload already produces and packs the native payload through the platform's own long-standing mechanism. Emitting our own `NativeReference` on top would embed the same frameworks twice.

## The sidecar mechanism (as-built, Microsoft.iOS)

Producer side (`Xamarin.Shared.targets` in the installed Microsoft.iOS SDK):

1. `_CreateBindingResourcePackage` runs when `'$(_DisableBindingProjectBuild)' != 'true' And '$(NoBindingEmbedding)' == 'true'` and writes `$(OutputPath)$(AssemblyName).resources`, containing every `@(NativeReference)` xcframework.
2. `$(CompressBindingResourcePackage)` defaults to `auto`, so the result is **either** a `.resources` directory **or** a `.resources.zip`. Both shapes are normal; anything reading the sidecar must handle both.
3. `Xamarin.Shared.Sdk.targets` packs `$(TargetDir)$(TargetName).resources` into `lib/<tfm>/` of the nupkg. Note the naming shift between steps 1 and 3: creation is keyed off `$(AssemblyName)`, packing off `$(TargetName)`. They are the same string in every normal project; SWIFTBIND074 deliberately keys off **`$(TargetName)`**, matching the pack step — i.e. it validates the file that actually ships.

Consumer side, when an app `PackageReference`s the package:

4. `_ExpandNativeReferences` selects reference paths for which `%(RelativeDir)%(Filename).resources.zip` (or `.resources`) exists — i.e. it discovers the sidecar purely from the assembly's neighbours in `lib/`.
5. The `ResolveNativeReferences` task extracts it, embeds the frameworks into the app bundle, and re-signs them. It runs only when `IsBindingProject != 'true'`, i.e. in the app, not in another binding project.

Empirical proof outside this repo: **`Plugin.Maui.Intercom.iOS.Binding` 0.7.1** on nuget.org was produced by this SDK with `SwiftFrameworkType=ObjC`, ships zero `buildTransitive` entries, and is consumed by a published MAUI plugin via `PackageReference` — working in the wild.

Empirical proof from our own catalog: **`SwiftBindings.Stripe.ThreeDS2` 26.4.1** is live on nuget.org today, built by this same SDK on this same lane — 2.1 MB, `lib/net10.0-ios26.0/{dll,xml,resources.zip}`, 172 `runtimes/` entries, **0 `buildTransitive`** — and has been consumed in the wild since the Stripe wave. Same shape, same conclusion, but on a package we ship and can re-measure at will.

## Consequences

- **`runtimes/` is not packed on this lane.** Before 0.18.x the source xcframework was staged into `runtimes/<rid>/native/` for ObjC packs too, but nothing ever referenced it (no consumer `.targets` exists to name it), so it was a byte-for-byte duplicate of the sidecar — roughly doubling the package size. Measured on a locally packed `SwiftBindings.MapLibre` 6.27.0 (that package is built in the consumer repo but has never been published): `runtimes/` accounts for 10.3 MB of the 20.6 MB package (compressed, i.e. the download-size share; the extracted duplicate is 24.3 MiB), and 270 of its 271 files are CRC-identical to their sidecar copy (the sidecar's only extra entry is its own `manifest`). Both the pack item and `_SliceSourceXcframework` now carry `AND '$(SwiftFrameworkType)' != 'ObjC'`. Swift/mixed packs keep `runtimes/`: their packed consumer `.targets` `NativeReference`s into exactly that path.
  Resulting pure-ObjC package shape: `lib/<tfm>/{Assembly}.dll`, `{Assembly}.xml`, `{Assembly}.resources[.zip]`, plus README/icon. Nothing else.
  This applies retroactively to already-shipped packages on the next release: `SwiftBindings.Stripe.ThreeDS2` 26.4.1 carries 172 dead `runtimes/` entries, so the next Stripe wave shrinks it automatically — **~27 % off the 2.16 MB download** (0.58 MB of compressed payload) and **~half the extracted size** (1.9 MB `runtimes/` beside 2.0 MB `lib/`). The download saving is smaller than the on-disk saving because the sidecar ships as an already-compressed `.resources.zip` while `runtimes/` holds raw Mach-O that deflates well; quote whichever number matches the axis you mean. No consumer action required — nothing on this lane ever named that path.
  **Neither package's number is a rule.** MapLibre halves on *download* (raw Mach-O deflating 24.3 → 9.8 MiB against a sidecar that stores ~as-is, leaving the two carriers roughly equal halves of the archive) while ThreeDS2 sheds only ~27 % of its download, because the saving is governed by the package's native-to-managed ratio and by how much its native deflates. Expect ~27–50 % off the download across this lane, and measure the specific package before quoting a figure in a release note.
  **Consumer-visible change (theoretical, release-note it):** the supported way to consume a pure-ObjC package is and always was the sidecar, which the platform wires up automatically. Anyone who hand-wrote custom `.targets` reaching into a pure-ObjC package's `runtimes/<rid>/native/…` path was relying on an off-spec artifact — no such consumer is known, and the path was never named by anything we ship — but such a consumer would now find the directory gone and must stop. There is no replacement path to point at: remove the hand-written `NativeReference` and let `ResolveNativeReferences` extract the sidecar. Swift/mixed packages are unaffected; their `runtimes/` layout is unchanged and is still the referenced carrier.
- **`ProjectReference` consumers must hand-wire the `NativeReference`.** Step 5 above only runs for an app that *references the assembly*; a `NativeReference` does not propagate through a `ProjectReference`. A repo-local test app that project-references a pure-ObjC binding therefore has to name the vendor xcframework itself — see the comment in `swift-dotnet-packages` `libraries/MapLibre/tests/SwiftBindings.MapLibre.Tests.csproj` ("The native MapLibre framework must be referenced directly (NativeReference does not propagate through ProjectReference)"). This is platform behaviour, not something the SDK can fix from the producer side.
- **The sidecar is load-bearing and invisible.** Nothing in our own build ever reads it, so a missing or half-sliced sidecar produces a nupkg that restores clean and only fails at the *consumer's* link/dyld with missing ObjC symbols — the issue-#39 silent-broken-nupkg shape, in the one lane #39's guard cannot see. Hence SWIFTBIND074.

## Guard-coverage boundary

Two *distinct* Swift-lane guards cover the `runtimes/` carrier — they are easy to conflate, and neither can see the ObjC lane:

- `_ValidateSwiftBindingPackSlices` (**SWIFTBIND030 / 031 / 032**) validates wrapper slice/RID coverage. Its condition is `IsPackable` + TFM + framework items + `'$(SwiftFrameworkType)' != 'ObjC'` — the `!= 'ObjC'` alone excludes the pure-ObjC lane.
- **SWIFTBIND038** is a *different* guard, inside `_ConfigureSwiftBindingPack`: it fails a pack that produced no `TfmSpecificPackageFile` while `_SwiftBindingHasWrapperXCFramework == 'True'`. That flag is never `True` for a pure-ObjC binding (no Swift wrapper is compiled), so 038 is structurally unreachable here — the ObjC lane could not "already be covered" by it.

- `_ValidateObjCBindingPackShape` (**SWIFTBIND074**) is the ObjC-lane counterpart, `BeforeTargets="_ConfigureSwiftBindingPack"`. For each xcframework that lands in this sidecar it asserts the sidecar exists (zip *or* directory) and that **every slice directory the source xcframework has is still present in the sidecar copy**, failing the pack otherwise. Two failure texts: *missing its native payload* (no sidecar, or one carrying no xcframework at all) and *does not match the xcframeworks it was built from*, with per-framework causes `<Name>:absent` (that xcframework is not in the sidecar at all) and `<Name>/<slice>:missing-from-sidecar` (the source had that slice, the packed copy lost it).

Five shape details the guard has to respect, all regression-tested in `SdkTargetsBehaviorTests`:

- **The assertion is a match against the source, never a fixed minimum.** An earlier draft demanded a device *and* a simulator slice; that is wrong. A vendor legitimately shipping a device-only (or otherwise partial) xcframework packs faithfully and must not be failed — the defect being caught is a *copy step that dropped a slice the source had*. This also makes the guard correct on macOS / Mac Catalyst for free: there is no simulator slice in the source, so none is demanded.
- **Slice ids are compared verbatim, with no id shape assumed.** Vendor xcframeworks spell the simulator slice `ios-arm64_x86_64-simulator`, which never equals `$(_SwiftBindingSimulatorSliceId)` (`ios-arm64-simulator`, our wrapper convention). Because both sides of the comparison come from real directories, nothing here needs to know which slice is which — and `$(_SwiftBindingHasSimulatorSlice)` (platform-derived in the `Sdk.targets` early property block, not user-settable) is deliberately *not* consulted.
- **An unreadable source degrades to presence-only.** If a source path is not on disk at pack time there is nothing to match against, so the per-slice comparison is skipped for that framework rather than guessed. Sidecar presence and `absent` still apply.
- **The checked set is everything that lands in the sidecar, not just the primary.** `_CreateBindingResourcePackage` packs *every* `@(NativeReference)`, and `_ResolveSwiftNativeReferences` promotes each existing `@(SwiftFrameworkDependency)` to one — so the guard iterates `@(SwiftFramework)` ∪ existing `@(SwiftFrameworkDependency)` ∪ existing `@(NativeReference)`, filtered to `.xcframework` and de-duplicated by full path. Checking only the primary would let a multi-native pack silently drop a dependency framework. (Dependency-derived entries are filtered on `Exists()` — precisely the condition under which they become `NativeReference`s; the primary is checked unconditionally so a vanished source is still caught.)
- **Both sidecar shapes are read and unioned, and names are matched literally.** A compress-mode flip can leave a stale/empty `.resources.zip` beside a healthy `.resources/`; preferring the zip would fail a good pack, so both listings are read and combined, then filtered to xcframework entries (which also means an empty archive — `unzip -Z1` prints `Empty zipfile.` on stdout for one — reports missing-payload rather than being mistaken for content). Framework names are compared with `awk index()==1` / string equality, never as grep regexes: a name like `Foo.Bar` must not be satisfied by `FooXBar`, and paths or slice ids containing spaces must not word-split.
