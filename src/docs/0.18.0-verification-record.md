## 2. The four defects the loop caught, and their fixes

Each was implemented by an Opus subagent in an isolated worktree, paired-reviewed
(Codex + Grok per /coding-rules), and merged into `main` by the orchestrator only after
gates were green. Review artifacts live under `/private/tmp/{codex,grok}-swift-bindings-*`
with resume session IDs recorded in the session transcript — note `/private/tmp` is
volatile; the durable review outcome is recorded here and in the pre-release changelog.

### Fix 1 — generator artifact writes unsafe under concurrent invocations

- **Symptom**: `Stripe/ios-device` ERROR (`dotnet publish` NativeAOT exit 1) in run 1
  (`20260726-230515Z` artifact). Two concurrent generator invocations raced on shared
  artifact writes; the manifest store was the observed casualty.
- **Fix**: `1760a9f5` — new `AtomicArtifactWriter` (write-to-temp + atomic rename) applied
  to the manifest store and failure reporting; new `GeneratorScratchDirectory` rerouting
  scratch writes to Guid-scoped OS-temp-root dirs. Category sweep performed: two
  `WriteAtomic` copies fixed; examined-and-deliberately-unchanged: wrapper staging dirs
  (already mutex-serialized), props direct-writes (different defect class, flagged),
  `AppleTypesCsCommand` wipe.
- **Tests**: 346 lines across `BindingArtifactManifestTests`,
  `GeneratorScratchDirectoryTests`, `BindingFailureReportTests`.
- **Review**: Codex 1 Medium + 3 Lows; Grok 1 Medium + 5 Lows — all addressed
  (`*-mrace-r1.md` artifacts).
- **Verified by**: Stripe/ios-device PASS in runs 2b–4.

### Fix 2 — internal-binding-testing csprojs missing the split-file Types compile glob

- **Symptom**: Step 4 `validate.sh` 30/30 BUILD_FAILED (CS0246/CS0234) — the generator
  now emits `{Module}.Types.*.cs` split files and the 35 IBT test csprojs compiled only
  the monolithic `{Module}.cs`.
- **Fix**: one `{Module}.Types.*.cs` Compile glob per test csproj in the
  internal-binding-testing repo. **Uncommitted there by design** — the packages-repo hold
  keeps both downstream repos uncommitted until 0.18.0 is on NuGet.
- **Review**: Codex clean; Grok 0 High / 1 Medium (fixed by deletion) / 3 Lows.
- **Verified by**: 30/30 green builds immediately after; run 4 Step 4 fully green.
- **Note**: this is harness scaffolding in a temporary repo (see memory:
  internal-binding-testing is throwaway; BindingTests is the durable gate). No
  swift-bindings change was needed.

### Fix 3 — SDK sibling prep-build double-builds binding projects (torn `.g.cs`)

- **Symptom**: `Stripe/ios-sim` ERROR — CS1513 in a bgen-generated `.g.cs`: the file was
  torn mid-write because the same binding project built twice concurrently.
- **Root cause**: `_BuildSiblingSwiftBindingDeps` (and `_BuildMixedObjCCompanion`'s three
  calls) invoked nested builds with a global-property set that diverged from the
  authoritative `ResolveProjectReferences` graph request — MSBuild keyed them as a
  *different project configuration*, so the same csproj built twice in parallel and the
  two instances raced on `obj/`.
- **Fix**: `96772622` + `e30918d1` — forward/remove exactly the property axes the graph
  request uses (SetConfiguration/SetPlatform/SetTargetFramework forwarded; `NoBuild`,
  `RuntimeIdentifier`, `SelfContained`, per-item `%(GlobalPropertiesToRemove)` removed),
  coalescing the prep-builds onto the one authoritative configuration.
- **Review**: round 1 — 0 Highs, 4 Mediums (residual property-fork axes); all four fixed
  with red-first theory coverage (8 axis cases) before merge.
- **Verified by**: Stripe both platforms PASS in runs 3–4. Floor ratchet `4624e4c6`.

### Fix 4 — mixed-companion reference injection lost under request interleaving

- **Symptom**: `Facebook/ios-sim` + `ios-device` ERROR in run 3 (`20260729-100716Z`) —
  ~70× CS0234 (`FBSDKAccessToken` etc. missing from `FBSDKCoreKit`): the binding compiled
  without its ObjC companion assembly reference; the companion built *after* the compile
  had already failed.
- **Root cause**: `_ReferenceMixedObjCCompanion` reached `ResolveProjectReferences` via
  its own `BeforeTargets` trigger in a build request where its producer
  `_BuildMixedObjCCompanion` had not run — `AfterTargets` is a soft edge ("if X runs, run
  me after"), not "ensure X ran". Under fix 3's coalesced graph, a second request against
  the same configuration could interleave during the producer's `<MSBuild>` yield, run
  the injection target with an empty capture, and MSBuild's once-per-configuration target
  caching then poisoned every subsequent request. Fix 3 *exposed* this latent hole: the
  old divergent serial prep-build had accidentally closed the interleave window. Silent
  because the SWIFTBIND041 guard is deliberately scoped to non-packable projects.
- **Fix**: `b58bd94a` — `DependsOnTargets="_BuildMixedObjCCompanion"` on the injection
  target (the hard edge; `AfterTargets` retained only for bare `-t:_BuildMixedObjCCompanion`
  entry, which the unit-test harness uses), plus a red-first behavioral regression test
  (`ReferenceMixedObjCCompanion_ProducerHookDidNotFire_StillInjectsCompanionReference`)
  that severs the producer's hook chain and drives `-t:ResolveProjectReferences`.
- **Review**: Codex zero findings (independently re-ran unit tests, 16313/0); Grok 0 High
  / 0 Medium / 4 Lows — two fixed in the amended commit (stale SWIFTBIND041 comment edge
  attribution; test-harness Directory.Build placement), two accepted residuals, both
  documented in-code/in-test: (a) producer→generation remains a soft edge, unreachable
  with current target names; (b) the test models the precondition, not the multi-request
  cache race.
- **Verified by**: Facebook both platforms PASS in run 4; standalone Facebook repro
  against the packed SDK passed before merge.
