# 1.0 Tier + claims alignment proposal

**Status:** PROPOSAL — owner decides. This document assigns no tier and edits no public claim.
It converts the tier/claims call (audit §10 row 8; decision-record **D3**/**D4**) into a
~30-minute review: per-package evidence already checked, a recommended tier per package with
its open blocker, and a claims-change list with drafted replacement wording. The owner's calls
get appended to `1.0-decision-record.md` per that record's appendix rule; sessions 06/07 carry
the actual README/wiki edits.

**Decision tags** used below: **D3** = package-tier call (Verified / Preview / Community / Parked);
**D4** = certified platform/architecture matrix; **wording** = a pure copy pick the owner makes.

**Tier definitions (from D3, verbatim):**
- **Verified** — at least one headline functional round-trip test in the harness; known-dark
  paths documented; regressions here block releases.
- **Preview** — compile- and load-proven; documented dark/untested paths; issues triaged
  best-effort.
- **Community** — published as-generated; no functional claim; issues welcome, no SLA.
- **Parked** — not regenerated/republished until demand appears.

## 1. Evidence: does a real functional round-trip exist?

Every "Verified" recommendation gates on one fact — does at least one test assertion exercise a
real functional round-trip (download / render / scan / charge-shaped, whose *result* is asserted),
or is the coverage construction-only (object created, not null) / metadata-only (a constant, enum,
or version string)? The audit already found test depth is construction-heavy everywhere; this
section grades the five packages whose README claims a "dedicated end-to-end test app" (Nuke,
Lottie, BlinkID, BlinkIDUX, Stripe) and confirms the four Apple smokes' recorded status.

### 1a. The five packaged third-party test apps

Graded from `swift-dotnet-packages/libraries/<Lib>/tests/Program.cs`.

| Package | Strongest assertion (file:line) | What it proves | Grade |
|---|---|---|---|
| **Nuke** | `await pipeline.ImageAsync(request)` on a **bundled `file://` image** routed through Nuke's **"full async + cache + decode binding round-trip"** (`Program.UIKit.cs:141-148`); gates `results.Pass`/`results.Fail` on `image != null` (`:1303-1324`). *(The separate `DataCache` `StoreData`+`ContainsData` test at `:805-820` is presence-only and weaker.)* | The library's headline flow — an async image load through the real pipeline — actually runs and its result is asserted (decoded image non-null). **Weak in one dimension:** it asserts load-success (non-null), not image content/size | **functional round-trip** *(weak — asserts the load result, not image content)* |
| **Lottie** | `view.Play()` then check `IsAnimationPlaying`, and `Play()`→`Stop()`→assert `!IsAnimationPlaying` (`Program.cs:1106-1160`); plus a duration self-consistency check on a real-loaded `PlaneAnimation.json` (`:607-611`) | The playback API **is** exercised (`Play`/`Stop` called). But the `Play` gate passes even when `IsAnimationPlaying` stays `false` ("no display context" → `Pass("Play() did not throw")`, `:1127-1131`), so in the headless test context it does not verify a render actually occurred | **playback API exercised; assertions soft/headless** *(no verified render)* |
| **BlinkID** | `Country.Germany → RawValue → Country.FromRawValue(raw)` tag equals `Germany` (`Program.cs:1969`) | An enum's raw-value string echoes back to itself; no `InputImage`, no `RecognizerRunner` scan, no extracted field asserted | construction/metadata only |
| **BlinkIDUX** | `DocumentSide.Passport(PassportOrientation.Left90).TryGetPassport(out o) && o == Left90` (`Program.cs:765-766`) | FFI marshalling round-trips a value the same test synthesized one line earlier; no scan/capture session | construction/metadata only |
| **Stripe** | `STPCardValidator.Brand("4242…")==Visa`, `…("5555…")==Mastercard`, `…("378…")==Amex` (`Program.cs:~3717-3726`) | Real local BIN-prefix classification on three card numbers — but pure local compute; grepping the 6418-line file found no `await`/`ConfirmPayment`/network payment flow at all | construction/metadata only |

**Finding (the evidence gap is closed — the picture is mixed, and the real question is *how strong the
bar is*):** the earlier grading pass under-described Nuke and Lottie; corrected against the source:
- **Nuke has a real functional image-load round-trip today** — its headline flow (`ImageAsync` through the
  full async/cache/decode pipeline) runs and its result is asserted (`image != null`, gated Pass/Fail).
  Under the §1 bar ("download … whose *result* is asserted") **this qualifies** — the only weakness is that
  the assertion checks load-success (non-null), not image content/size.
- **Lottie** exercises the playback API (`Play`/`Stop`) but with **soft, headless gates** — `Play` passes
  even when the animation isn't playing — so it stops short of a verified render.
- **BlinkID, BlinkIDUX, Stripe** are genuinely **construction/metadata only** (enum round-trips, a
  self-constructed value's marshalling, local card-brand compute) — none exercises the scan/charge flow the
  library exists for.

So it is **not** true that "no functional round-trip exists anywhere." The honest consequence for tiering
is a **D3 sub-question the owner should settle: how strong must a "headline functional round-trip" be?**
D3's text ("at least one headline functional round-trip test in the harness",
`1.0-decision-record.md:59-60`) is underspecified on strength. Under a **result-shape** bar (the headline
operation runs and returns a non-null / expected-shaped result), **Nuke already qualifies for Verified**;
under a **content-assertion** bar (assert a decoded pixel/size, an extracted field, a charge value), **none
of the five qualifies yet** and each needs its assertion strengthened (Verified-tier-only work, allowed
pre-1.0 by D3). This still matches the audit's repo-wide "universal test-depth finding"
(`BindingAudit/_SUMMARY.md:167-181`): *"Every binding audited proves construction / metadata / enum
ordinals but not the end-to-end functional flow the library exists for."* §2 recommends the content bar and
tiers accordingly; the README's current "end-to-end runtime validation" claim for all five (§3.1) overstates
what four of the five assert.

### 1b. Apple framework smokes (confirmation spot-check)

Confirmed against `BindingTests/RuntimeTestsApp/SmokeTests/`. The recorded status —
"pipeline check, not API coverage" (memory `project_smoke_tests_narrow_purpose`) — **still holds
for all four**. Every substantive assertion is either pure C# reflection over the generated
binding's shape/attributes, or a call into a deterministic, hermetic, metadata-only surface; each
file's own doc comment enumerates the real functional APIs it deliberately excludes (network- or
entitlement-gated). None is a functional round-trip against the framework's actual purpose.

|---|---|---|

| WeatherKit | `WeatherError.PermissionDenied.GetErrorDescription()` non-empty (`WeatherKitSmokeTests.cs:65-71`); an `[SupportedOSPlatform]` reflection check (`:108-126`) — no forecast fetched (doc excludes `WeatherService` at `:29-34`) | pipeline check |
| TipKit | 3 of 4 tests are reflection-only; the 4th dispatches a PWT call through an existential container on a synthetic in-repo fixture `TipKitSmokeMinimalTip` (`TipKitSmokeTests.cs:210-222`), not a real Tips-datastore registration (doc excludes `Tips.configure` at `:88-93`) | pipeline check |
| MusicKit | `MusicItemID("…").RawValue` string round-trip (`MusicKitSmokeTests.cs:72-77`); an availability reflection check (`:119-133`) — no catalog query (doc excludes `MusicCatalog.search` etc. at `:34-39`) | pipeline check |

**Conclusion:** the four Apple smokes cannot support a Verified tier for their frameworks —

The CryptoKit / MusicKit / TipKit / WeatherKit tier calls therefore rest on `swift-dotnet-packages`
coverage and open findings, not these smokes.

## 2. Tier proposal table

Per-package recommendation with a one-line evidence basis and the open blocker that caps it.
Starting points are from scope item 2; each is verified against the audit `_SUMMARY`, the
EveryProtocol fail-closed impact report, and the test grades above. **Demand signals are
undocumented** — the roadmap references WorkoutKit / ProximityReader only as *capability* limits
(RC-PAT app-defined conformers; `Measurement<T>` projection), never as demand evidence. Where a
call hinges on demand, it is flagged as an owner call, not invented.

**Headline result up front (and a D3 sub-question for the owner):** §1 found the "functional round-trip"
bar is **underspecified in D3** and the answer decides the whole Verified column. Under a **result-shape**
bar (the library's headline operation runs and returns a non-null/expected-shaped result), **Nuke already
qualifies for Verified today** (its `ImageAsync` pipeline load is asserted non-null); Lottie's `Play` gate is
too soft to qualify even here (it passes even when `IsAnimationPlaying` stays false, §1a).
Under a **content-assertion** bar (assert a decoded size/pixel, an extracted field, a charge value), **none
of the five graded test apps qualifies yet.** (MapLibre's packaged sim consumer *does* assert content-level
evidence — a `fullyRendered` map-render callback and ObjC→C# delegate delivery, hard-fail if absent, 11/0/0
on the Simulator, §2a — but MapLibre is SPIKE-status with a pending device leg, so it is capped below
Verified regardless of its test strength.) This proposal **recommends the content bar** — it is the one that
makes "Verified" mean the flow actually works, not merely returns non-null — under which **the Verified tier
is empty at proposal time by policy**: not because no round-trip exists, nor because no test asserts content
(MapLibre's does), but because no package is *both* content-bar-passing *and* release-grade today. Every row below is therefore **Preview
or lower**, with the top candidates flagged **Verified-eligible** — one named, small,
headless-where-possible assertion-strengthening away from Verified (Verified-tier-only work, explicitly
allowed pre-1.0 by D3). **If the owner instead picks the result-shape bar, Nuke moves to Verified now.**

### 3.1 README "65+ libraries validated" — **D3 / wording**

**Current** (`README.md:205,207,218`):

>

> ## Real-World Validation

> generator **breadth gate** — it proves the generator produces **compiling** C# bindings across a

> functionally exercised is stated by their **support tier** (see the package tables).
>
> *(…category table…)*
>

> depth varies: some exercise a functional round-trip (e.g. Nuke's image-load), others only construction

**Note:** §1a found Nuke performs a weak (non-null) functional image-load round-trip and Lottie exercises
playback with soft gates, while BlinkID, BlinkID UX, and Stripe are construction/metadata only — so
"end-to-end runtime validation" overstates what four of the five assert. The replacement above deliberately

### 3.4 tvOS-device wording → D4's best-effort — **D4**

## 4. Facebook Known-Limitations wiki drafts (paste-ready)

Two paste-ready entries for the wiki `Known-Limitations.md`. Source wording:
`next-release-remaining-work.md:265-275` ("Known limitations to document"). Cleaned for a public

### 4.1 — Facebook App Links deep-linking (unsupported)

> **Facebook App Links deep-linking is not supported.** `AppLink.targets`,
> `AppLink.init(sourceURL:targets:webURL:)`, `AppLink.appLink(…)`, `AppLinkFactory.createAppLink`,
> and `AppLinkNavigation.navigationType` do not bind. `AppLinkTargetProtocol` is an Objective-C
> (`@objc`) protocol, so a collection typed `[any AppLinkTargetProtocol]` is the heavyweight
> `@objc`-container-existential case, which the generator deliberately declines rather than
> mis-marshal. **Facebook Login and Share are unaffected** — this limitation is confined to the App
> Links deep-linking surface.

### 4.2 — Facebook `[String: Any]` dictionary parameters (dropped)

> **Facebook `[String: Any]` dictionary parameters are dropped by design.**
> `Share*Content.addParameters(_:options:)` and the `AppLinkNavigation` extras / `appLinkData`
> parameters take a Swift `[String: Any]` dictionary. An `Any`-valued dictionary is an
> untyped-in-container position the generator cannot marshal without type information, so these
> parameters are omitted from the generated surface. Structured, strongly-typed Share content
> (`ShareLinkContent`, `SharePhotoContent`, `ShareVideoContent`, `ShareMediaContent`) is fully
> supported; only the free-form dictionary overloads are affected.
