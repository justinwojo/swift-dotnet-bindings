## B. Confirmed defects — OPEN, need a fix

| B1 | PKG | **Auto-detected `ProjectReference` injector deletes correct references.** `ApplyProjectRefs` strips the existing block — including hand-authored sibling refs — *before* deciding whether to re-emit, and `BuildPrBlock` returns `""` on a zero-hit scan. The scan is a literal `\bModule\.` token grep over generated wrapper C#, so any reference not surfacing as that exact text reads as zero hits and the ref is dropped, never replaced. **This is the root cause of the 25 missing managed references SWIFTBIND081 caught during the 0.18.0 run** — the generator was right, the fixtures were mis-wired. | `build/Helpers/CsprojRewriter.cs` (`ApplyProjectRefs`, `BuildPrBlock`, `MigrateSiblingProjectRefs`, `StripPrAutoBlock`); `GeneratedCsScanner.ContainsModuleReference`. Proven by commit `eb1b24cd`, which deleted StripeConnect's and StripeIdentity's `../StripeCore/…` refs with no replacement. **Still live**: untracked `libraries/Facebook/FBSDKCoreKit` and `FBAEMKit` already show SFD-without-PR. |
| B2 | PKG | **PR injection is all-or-nothing on freshness; SFD injection is not.** `InjectProjectRefsForLibrary` freshness-checks *every* product before any write, so one stale product silently aborts `ProjectReference` injection library-wide, while `InjectFrameworkDepsForLibrary` writes per-product regardless. That asymmetry is how the two marker blocks drift apart unnoticed. | `build/Build.Dependencies.cs` (freshness pass ~L194–203); contrast `InjectFrameworkDepsForLibrary` ~L72–153. |
| B4 | SB | **`nuke validate` never supplied dependency xcframeworks to the generator — FIXED 2026-07-26.** `GenerateTarget` (xcframework mode) invoked the generator with a bare `--xcframework` and no `--framework-dependency`, so the compile-import graph was never closed for any multi-module SDK. | B5 | SB | **`nuke validate` LINE DRIFT measured one arbitrary file — FIXED 2026-07-26.** `FindMainCsFile` returned `Directory.GetFiles(outdir, "*.cs").FirstOrDefault()` — **filesystem order, unsorted, not stable across runs**. That was ~accurate when the emitter produced a single monolithic `{Module}.cs`, but it now splits output per type (`{Module}.Types.{X}.cs`), so the metric measured a random fraction of the binding. Result: phantom 95–100% "drift" across essentially the whole corpus while emission was actually flat or *up* — **Alamofire reported `59665 -> 362` when it really emitted 62,284 lines across 97 files (an increase)**; `362` is literally `Alamofire.Types.RetryResult.cs`. `Quick: 137 -> 328 (139%)` is the same bug pointing the other way. This is worse than noise: it would equally well have hidden a genuine emission collapse. Fix: `CountEmittedCsLines` sums every emitted file; `EmittedCsFiles` sorts ordinally so the metric is deterministic. **Baseline `Lines` values are now incomparable to the old ones (per-file → total), so a re-baseline is mandatory once the run is green.** | `build/Build.Validation.cs` — `FindMainCsFile` / `EmittedCsFiles` / `CountEmittedCsLines` (was L2321). |
| B6 | SB | **The dependency-tier compile gate only ever compiled ONE file per binding — FIXED 2026-07-26.** `WriteDependencyCsproj` emitted `<Compile Include="{single filename}" />`, taking that filename from `FindMainCsFile` (see B5, arbitrary). Since the emitter splits output per type, every dependency-gate "OK" was reached with the compiler having seen a small fraction of the binding. Fix: mirror the generated csproj's real item set — `EnableDefaultCompileItems=false` plus `{Module}.cs`, `{Module}.Types.*.cs`, and the conditional `.Wrappers.cs` / `.SwiftUIBridge.cs`. Effect was immediate and large: the dependency gate went from `1/8 tested, 7 failed` to `13/13 tested, passed` once it was compiling whole bindings against real DLLs. | `build/Build.Validation.cs` — `WriteDependencyCsproj`. |
| B7 | SB | **Dependency DLL resolution was blind to pure-ObjC bindings — FIXED 2026-07-26.** `FindDependencyDll` searched only `<outdir>/bin` for `{Module}.dll` / `{Module}.Swift.{Platform}.dll`. A pure-ObjC binding emits `{Module}.ObjC.{Platform}.csproj` and builds to **`bin.objc/`**, so any Swift module depending on one (FirebaseAuth → FirebaseCore, FirebaseRemoteConfig → FirebaseCore) resolved nothing and the dependency gate parked it as `skipped (dependencies not resolved)` forever. 26 of the corpus's targets build this way. Fix: search `bin` and `bin.objc`, and add `{Module}.ObjC.{Platform}.dll` to the candidate names. | `build/Build.Validation.cs` — `FindDependencyDll`. |
| B8 | SB | **Import parser dropped dependencies to an attached comment — FIXED 2026-07-26.** The derived-dependency walk read module names by cutting the text after `import ` at the first `.`.
