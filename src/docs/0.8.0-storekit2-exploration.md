# StoreKit 2 — Phase 1 Exploration Findings

**Date**: 2026-04-07
**Scope**: First exploration session for the 0.8.0 Apple-frameworks pivot. Goal was narrow — build a StoreKit 2 wrapper Swift package, run our existing generator against it, capture observations. Not strategy, not implementation, not generator changes.

**Sibling**: `0.8.0-plan.md` (the broader release plan; this is exploration input that feeds the future `Future/apple-framework-binding-strategy.md` deliverable).

---

## TL;DR

The wrapper-package strategy in `0.8.0-plan.md` § "Working assumption" **does not work as written**. Two distinct blockers, both architectural rather than cosmetic:

1. **`@_exported import StoreKit` does not inline the imported module's API surface into the wrapper's `.swiftinterface` or `.abi.json`.** The wrapper xcframework's abi.json contains exactly one entry — the `Import` declaration itself — and zero StoreKit type declarations. Generator runs cleanly on it and produces 0 types / 0 members. Wrapper packaging by itself is empty.
2. **Even bypassing the wrapper and feeding the generator an abi.json produced directly from Apple's SDK (via `swift-api-digester`), the generator skips StoreKit entirely.** Reason: `Program.cs:65` pre-loads `StoreKitDatabase.xml` as a built-in dependency database, which registers the "StoreKit" module in the type database. When the generator parses an abi.json whose module name is also "StoreKit", `IsModuleProcessed("StoreKit")` returns `true` and emission is skipped (warning: `"Bindings generation already completed"`). No `.cs` files are written.

Neither blocker is a generator bug — they're consequences of design assumptions that pre-date the Apple-frameworks pivot. The generator was built around "Apple frameworks are dependencies provided by Microsoft.iOS, never targets." The Phase 1 pivot inverts that.

**Independent review** (Codex + Grok, same day): Both claims confirmed. No P0 contradictions. Codex ran two hands-on validations the original session did not — (a) a fresh Swift 6.2.3 build of a one-line `@_exported import StoreKit` module with and without library evolution, both producing only the bare `@_exported import` line in the swiftinterface (no inlined declarations); (b) the rename probe for Claim 2 — renamed the `swift-api-digester` dump's module from `StoreKit` to `StoreKit2`, re-ran the generator, got real `.cs` output (`StoreKit2.cs`, `StoreKit2.Wrapper.swift`). That rules out a `swift-api-digester` format mismatch as a confounder. **Codex also surfaced a real new constraint about how the fix must be shaped — see "The generator treats Apple frameworks as dependencies" below.**

## What this means

### The wrapper package is the wrong shape

The `0.8.0-plan.md` working assumption — *"the xcframework's `.swiftinterface` describes the Apple framework's Swift API surface"* — is wrong. `@_exported import` is a re-export *for downstream consumers of the wrapper module*, not an inlining of declarations into the wrapper's own interface file. The wrapper's `.swiftinterface` lists the import; consumers of the wrapper see StoreKit symbols by transitive resolution at compile time. **Nothing about that helps a tool like our generator that reads the wrapper's interface in isolation.**

This is current Swift compiler / module-interface emission behavior, not a hard language guarantee — but it's been stable across the toolchain and is consistent with how [SE-0409](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0409-access-level-on-imports.md) frames re-export as visibility semantics rather than declaration cloning. Codex independently rebuilt the same one-line wrapper on Swift 6.2.3 with and without `-enable-library-evolution`; both produced the same bare `@_exported import StoreKit` line in the swiftinterface with no inlined declarations. Codex also checked `swiftc -help-hidden` and `PackageDescription.SwiftSetting` and found no flag, package setting, or experimental feature that changes this behavior. The wrapper-as-metadata-source approach is therefore not salvageable on the current toolchain.

There may still be a role for a wrapper Swift package — e.g., to emit hand-written `@_cdecl` thunks bridging StoreKit calls into a C ABI we can P/Invoke against, the way our generator already does for third-party libraries. But that role is *additive Swift code we author*, not "hosting StoreKit's surface for reflection." The naming `StoreKit2Wrapper` is also misleading if its only job becomes thunk hosting; something like `StoreKit2Bridge` or `StoreKit2Thunks` would scan more honestly. **Decision deferred** — Phase 1 strategy doc territory.

### The generator treats Apple frameworks as dependencies, not targets

The Apple framework registry (`apple-frameworks.json` + the `*Database.xml` files in `Swift.Runtime/src/Swift/`) was built for the world where:
- Generator output (third-party Swift libs) **references** Apple framework types, and
- Microsoft.iOS already provides the C# binding for those types as ObjC bindings, and
- The generator just needs a stub database to do type resolution + name remapping when emitting references to those types.

That model has zero room for "this Apple framework IS the generation target." The pre-load conflict isn't a switch we can flip; the generator's whole orchestration assumes Apple framework module names are read-only dependency entries.

To make StoreKit 2 (or any Apple Swift-first framework) generatable, the generator needs at minimum:
- A way to declare "the abi.json I'm parsing replaces (rather than collides with) the pre-loaded database for module X" — possibly a `--apple-framework-target StoreKit` flag, or detection that the input module name matches a pre-loaded database and unloading it.
- A way to suppress the type-stub side of the registry for the target module so the generator doesn't accidentally treat real declarations as "use the existing ObjC binding instead."
- Possibly a way to declare the runtime library path so the emitted DllImport library name is `/System/Library/Frameworks/StoreKit.framework/StoreKit` rather than a wrapper dylib name. (The `-l` flag accepts arbitrary library names, so this may already be sufficient — needs validation once the pre-load conflict is past.)

These are real generator changes. They are not large changes — the pre-load logic is a single block in `Program.cs:65–79` and the gate is a single `IsModuleProcessed` call — but they need to be designed deliberately because they crack open an assumption that's been load-bearing since the project started.

#### Constraint surfaced by review (added 2026-04-07): the fix must keep the module name as `StoreKit`

Codex ran the rename probe — modified the `swift-api-digester` dump's module name from `StoreKit` to `StoreKit2` and re-ran the generator. It bypassed the `IsModuleProcessed` gate cleanly and emitted real `.cs` and `.swift` files. That validates the diagnosis: the pre-loaded `StoreKitDatabase.xml` is the sole reason manual mode produced no output, and renaming around it works at the parse-and-emit layer.

**But renaming is NOT a viable fix.** Codex flagged a downstream constraint: metadata/conformance resolution keys in `DemanglingResults.cs:107` and `DemanglingResults.cs:133` are joined on module-qualified names. The TBD's exported symbols are mangled with `_$s8StoreKit...` (the leading `8StoreKit` is the module-name length-prefix in Swift mangling). If we generate with module name `StoreKit2`, the bindings will look for `_$s9StoreKit2...` symbols and find nothing — the resulting C# would compile but the P/Invokes would fail to bind at runtime. The Swift module name is load-bearing across the abi.json, the swiftinterface, the TBD, and the demangling-key joins; it cannot be changed in isolation.

So the actual fix must:
- **Keep the module name as `StoreKit`** in the abi.json fed to the generator (no rename workaround).
- **Drop or replace the pre-loaded `StoreKitDatabase.xml` entry** before the parse-and-emit branch is gated, so `_modules` no longer contains "StoreKit" when the generator checks.
- **Preserve the dependency-database semantics for OTHER libraries that reference the legacy SK* enums** until they migrate to the real generated bindings (or until those libraries are validation-only, in which case the migration is a non-issue).

#### Architectural framing: `IsModuleLoaded` and `IsModuleProcessed` should be different predicates

Today, both `TypeDatabase.IsModuleLoaded` (line 71) and `TypeDatabase.IsModuleProcessed` (line 298) are literally the same expression: `_modules.ContainsKey(moduleName)`. They are aliased because the project never needed to distinguish "we have a stub for this module from a dependency database" from "we have actually parsed and emitted bindings for this module." The Apple-frameworks pivot makes that distinction load-bearing for the first time.

The minimal narrow-spike fix can stay as "drop the matching entry from `_modules` before parsing the target abi.json" — implementable in a few lines of `Program.cs`. The correct long-term refactor (per Codex's read) is to split the predicates: a module can be `Loaded` (we have a dependency database) without being `Processed` (we have generated real bindings for it as a target). The gate at `Program.cs:344` should be checking `Processed`, not `Loaded`, and they should be tracked separately in `TypeDatabase`.

Both can land in the same change, but the spike should not block on the predicate split — get the Apple-framework target mode working first, then tighten the type-database semantics in a follow-up.

### The system framework runtime-loading question is still unanswered

Per `0.8.0-plan.md` strategy question #3 (`SystemFrameworkResolver`), we don't yet know whether the existing `SwiftFrameworkResolver` correctly `dlopen`s system frameworks via the `/System/Library/Frameworks/<X>.framework/<X>` path. **We did not get far enough in this session to test this.** The blocker chain is: fix generator → produce real bindings → install on a device or simulator → see if P/Invokes resolve. Each link is a separate piece of work.

### Plan section that needs revision

`0.8.0-plan.md` § "Working assumption" steps 1–3 should be rewritten. The current text reads:

> 1. Wrapper Swift package does `@_exported import <SystemFramework>` and ships an xcframework via `spm-to-xcframework`
> 2. The xcframework's `.swiftinterface` describes the Apple framework's Swift API surface
> 3. Our existing bindings generator consumes that xcframework like any other

Step 2 is false. Step 3 cannot work for any Apple framework currently in `apple-frameworks.json` (which is most of them). Suggested replacement direction:

1. ABI source comes from `swift-api-digester -dump-sdk -module <X> -sdk <iphoneos sdk>`, not from a wrapper xcframework.
2. The generator gains an "Apple framework target mode" that removes the target module from the pre-loaded dependency set before parsing.
3. P/Invokes are emitted with the system framework's on-device path as the library name; runtime loading uses the existing resolver if it already handles that path, or a small extension if not (TBD).
4. A wrapper Swift package may still be useful for hand-written thunks (e.g., bridging async/await or AsyncSequence into something P/Invokeable), but it is not the source of binding metadata.

That's a strategy refinement, not a strategy doc — the strategy doc still has to answer all 12 questions in `0.8.0-plan.md` § "Strategy questions". This exploration just rules out one branch and points at a different one.

## What the StoreKit 2 surface looks like through the generator

We never got to a real binding pass, but the swiftinterface load gives us a count-only view:

- **78 public types** in StoreKit (Swift surface). For comparison, Nuke is ~30 types; Lottie is ~50. StoreKit 2 is meaningfully larger than the third-party libs we currently ship, but well within the order of magnitude the generator handles.
- **452 public member names** — this is the "method/property names that need underscore-suppression" set, not the total method count. Order-of-magnitude indicator only.
- **359 availability annotations** is striking. StoreKit 2 has dense `@available(iOS 15, *)`, `@available(iOS 16, *)`, etc. annotations across its surface. This makes strategy question #6 (iOS-version availability) **very real** — the surface has version gates everywhere, and how we surface them in C# (TFM, `[SupportedOSPlatform]`, runtime guards) will affect every consumer.
- **9 `@MainActor` member entries** under **1 `@MainActor` type** — one of `AppStore`, `Storefront`, etc. is main-actor-isolated. We already handle `@MainActor` types in the generator, so this is observation, not blocker.
- **5 marker protocol conformances** — `Sendable` and friends. Already handled.
- **0 typed throws entries** — interesting, given StoreKit 2's `Result<Transaction, VerificationError>` is famous. Either typed throws aren't used in StoreKit 2 (it uses `Result` types instead), or `swift-api-digester` doesn't surface them in the same way `swiftinterface` ABI parsing does.

Notable surprises:
- **Apple's StoreKit `.swiftinterface` is shipped at `arm64e-apple-ios.swiftinterface`, not `arm64-apple-ios.swiftinterface`.** Our generator's `--xcframework` mode auto-resolves the swiftinterface based on the slice path. For Apple SDK frameworks, the only available slice is `arm64e` on device (no simulator slice exists in the system framework — the simulator uses the simulator SDK's separate framework copy). This will matter when wiring xcframework-mode auto-resolution against system framework paths.
- **The TBD's exported symbol list is the most complete inventory of the Swift surface.** It contains every mangled Swift symbol with `_$s8StoreKit` prefix. Cross-referencing this against the abi.json after generator parsing would let us measure real coverage rather than relying on the swift-api-digester dump alone.

## Side observations worth keeping

- **`spm-to-xcframework` works against local paths cleanly.** It accepts a local directory as a positional arg and produces a working xcframework. Good news for any future wrapper-package work.
- **The generator's CLI `-o /tmp/foo/` (with trailing slash) is rejected as "Valid output directory is required" if the directory does not pre-exist.** Without trailing slash and with `mkdir -p` first, it works. Minor papercut, not a bug worth filing — reproduces only on first-run cleanup paths.
- **The generator's `--xcframework` mode silently succeeds on an empty wrapper xcframework**, producing the resolver scaffold and a `.csproj` for an empty module. There is no warning that the abi.json contained zero declarations. Adding a warning ("Module X has 0 type declarations — likely indicates an incorrect ABI source") would have caught this exploration's first blocker in seconds. Cheap quality-of-life improvement; flag for future grooming.
- **`apple-frameworks.json:583` already lists StoreKit with `objcPrefixes: ["SK"]` and four enum value-type entries.** That's the StoreKit 1 surface. When the registry is reworked for Apple-framework targets, the StoreKit entry will need to either grow to cover the StoreKit 2 surface OR be split into `StoreKit` (legacy SK*) and `StoreKit2` (Product, Transaction, etc.) entries. This is open design space.

## Open questions this exploration created

These are NEW questions, distinct from the 12 in `0.8.0-plan.md`:

A. **Do we replace the wrapper-package strategy with an `swift-api-digester`-driven approach, or do we keep the wrapper as a host for hand-written thunks?** Both are compatible — the wrapper just stops being the binding-source. Decision affects how `apple-frameworks/StoreKit2Wrapper/` evolves.

B. **What's the right shape for the generator's "Apple framework target mode"?** Options:
   - A new CLI flag (`--apple-framework-target StoreKit`) that drops the matching pre-loaded database before parsing.
   - Auto-detection: if the parsed abi.json's module name matches a pre-loaded database, replace it.
   - A separate code path entirely (`apple-framework-mode` in `Program.cs` that bypasses the registry pre-load + uses different emission defaults).

   I lean toward auto-detection with an opt-out — least surprising for callers, smallest CLI surface — but this is design space.

C. **Is `StoreKitDatabase.xml`'s existing four-enum stub still correct after StoreKit 2 generation?** When we ship a real StoreKit 2 binding, the pre-loaded database is no longer a stub — it's the binding itself. Other libraries that today reference `SKError.Code` or `SKPaymentTransactionState` (validation libs etc.) would presumably switch to referencing the generated bindings. That's a migration question, not a blocker.

D. **Does our generator's existing async/AsyncSequence handling cover StoreKit 2 cleanly?** We never got far enough to find out. Once the pre-load gate is past, this becomes the next thing to discover.

E. **The `arm64e` swiftinterface slice issue** (above) — does our `--xcframework` mode know how to find it when the xcframework points at a system framework? Probably needs a smaller patch than the database pre-load issue.

F. **Will Apple's `iPhoneOS26.2` SDK be the right thing to dump from for a StoreKit 2 binding targeting iOS 15+ deployment?** The dump captures the API surface as of the SDK version, which includes everything added in iOS 16/17/18/26. Availability annotations distinguish them, so a binding compiled against the SDK is forward-compatible with older deployment targets — but this needs verification, and it's a model we haven't used before.

#### Session 1 outcome (2026-04-08, commit `ae44d0b8`)

**What landed** (4 src files, +224/-37):
- **Apple-framework target mode** (`Program.cs`, `CliOptions.cs`, `BindingsGeneratorCommand.cs`): auto-skip a built-in `*Database.xml` whose `moduleName` matches the input abi.json's module name, via `PeekModuleNameFromXml` before parse-and-emit. This is the original narrow spike — it's the smallest possible diff that lets the generator target a Swift framework whose name is also a pre-loaded dependency-database stub.
- **Parameter-position opaque type lowering** (`Parser/SwiftABIParser.cs`): swift-api-digester emits `some P` parameters as `TypeNominal/GenericTypeParam` with `printedName="some Foo"` and no children. The existing `OpaqueTypeArchetype` branch only caught return-position opaques. New `_opaqueParamCapture` list installed around `CreateMethodDecl`'s param loop; matching nodes are routed through `SynthesizeOpaqueParameter`, which produces a `τ_opaque_N` synthetic `TypeName` + `GenericArgumentDecl` with the constraint protocol attached. The capture is merged into `MethodDecl.GenericParameters` after the loop, mirroring Swift's own `some P` → `<T: P>` desugaring. The `τ_` prefix routes the emitted name through `NameProvider`'s positional `T{i}` branch, so the synthetic param's emitted C# name is `T<position>` and pre-existing generics keep their sugared names. **This is a real Swift language feature, not a defensive skip.**
- **`\@` CLI escape strip** (`BindingsGeneratorCommand.StripCliAtEscape`): the documented `\@rpath/...` escape (which bypasses System.CommandLine's response-file handling) was flowing through into the C# string literal emitted in `DllImport`, producing `CS1009: Unrecognized escape sequence`. Strip applied to `--library` and `--async-library` after CLI parsing.

### Why this order

The dominant uncertainty in Phase 1 is **feasibility**, not design elegance. Writing the strategy doc before the generator spike risks producing a document full of assumptions that the spike will falsify in minutes — exactly the way this exploration session falsified the wrapper assumption in 30 seconds. The spike is a small, scoped, high-leverage piece of work that unblocks every Apple framework simultaneously. Front-loading it means the strategy doc gets written against real evidence rather than speculation, and the time spent on the strategy doc is time spent capturing what we know rather than guessing what might work.

Sessions 1–2 confirmed that the basic chain works (parse → emit Swift wrapper → compile wrapper) and surfaced the next layer of generator bugs that affect every Apple framework, not just StoreKit. The follow-up bug fixes are also high-leverage: each one generalizes beyond StoreKit. The strategy doc benefits from waiting until those land too.

The dead-end branch (forcing `@_exported import` to inline declarations via some Swift toolchain trick) was previously listed as a session candidate. After review, both Codex and Grok independently confirmed there is no such trick on the current toolchain. **Removed from the next-session list.** Don't spend time here unless a future Swift compiler release surfaces something new.
