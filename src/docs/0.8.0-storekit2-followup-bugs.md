**Created**: 2026-04-08
**Parent docs**: `0.8.0-plan.md` (Phase 1 release plan), `0.8.0-storekit2-exploration.md` (exploration history)

This is the cold-start brief for the next session(s) on StoreKit 2. Sessions 1–2 unblocked the parser and the Swift wrapper compile chain. Four unrelated C# emit bugs now block compiling the generated `StoreKit.cs` into a `.dll`. Each bug is its own session; each generalizes beyond StoreKit.

## What's already in place (do not redo)

- **Parser-side**:
  - `some P` parameter-position opaque types lower to `τ_opaque_N` synthetic generic params.
  - Pre-loaded `*Database.xml` whose `moduleName` matches the input `abi.json` is auto-skipped (Apple-framework target mode), opt-out via `--keep-builtin-database`.
  - Per-case enum `@available` annotations propagate from the swiftinterface (`SwiftInterfaceContextTracker` recognizes `case` lines, `SwiftABIParser.ApplyMemberAvailability` is called on enum cases).

- **Wrapper-emitter side**:
  - `WrapperEmitterHelpers.MergeAvailabilityFromAncestors` walks parent decls and merges per-platform `@available` constraints. Wired through `MetadataWrapperEmitter`, `WrapperEmitter.Async.cs`'s async wrapper templates, `PropertyHandler`'s async-property accessor, `ClassHandler.cs`'s `==` operator wrapper, and `EnumCaseWrapperEmitter.cs`.
  - `Unmanaged<value-type>` foreign extension bug fixed (`ForeignTypeExtensionEmitter` no longer emits `Unmanaged<StoreKit.Struct>` — uses the legitimate `Unmanaged<AnyObject>` form).

- **CLI side**:
  - Direct/manual mode without `--async-library` defaults `AsyncLibraryName` to `{Module}SwiftBindings` (e.g. `StoreKitSwiftBindings`).
  - `\@` CLI escape (used to bypass System.CommandLine response-file handling for `@rpath/...` library names) is stripped from `--library` and `--async-library` after parsing.

- **Validation gates** (all green at HEAD `eafe252d`):
  - `nuke test` 9441/0/1
  - `nuke validate` 95/95
  - `nuke binding-tests` pass
  - `nuke runtime-tests-simulator --skip-regen` 1312/0/23

- **Concrete result**: `StoreKit.Wrapper.swift` compiles to `StoreKitSwiftBindings.dylib` (486 KB) cleanly. The Swift wrapper side of the StoreKit 2 binding is fully working.

## What is broken

`dotnet build /tmp/storekit2-direct-fresh/StoreKit.Swift.iOS.csproj` originally produced **215 errors / 118 unique CS codes**, traceable to bug families #1–#4 below. After Bugs #1–#4 landed, two latent `CS1503` errors in the async `Optional<Collection<…>>` marshalling path surfaced (Bug #5 — they were previously masked by Bug #4's cascading `CS0234`). The Swift wrapper side compiles cleanly throughout; only the C# side is broken.

## Recommended attack order

1. **Bug #2 first** — highest leverage. Constrained-extension dedup generalizes to any library that uses `extension X where Self == ConcreteType`. This is a common Swift idiom; fixing it prevents similar regressions in every Apple framework that follows StoreKit.
2. **Bug #1 second** — every modern Apple framework uses nested AsyncSequences. Fixing nested type qualification unblocks WeatherKit, App Intents, and more.
3. **Bug #3** — narrow but easy. Reuse the existing instance/static name-collision suffix pass.
4. **Bug #4** — narrowest. Pure data fix in `AppleFrameworkRegistry` / Foundation XML.
5. **Bug #5** — async `Optional<Collection<…>>` marshalling. Surfaced once Bug #4 cleared the cascading `CS0234` errors that were hiding it. Required before the StoreKit reproduction can compile cleanly.

After bugs #1–#5 all land: re-run the reproduction command in step 3 above; it should produce a clean compile. Then return to the deferred Session 2 work (wire wrapper compilation into direct mode, verify `SwiftFrameworkResolver` against system framework paths, simulator smoke test).

## Bug #2: Constrained-extension member duplication (CS0102 × 34)

**Symptom**: Three specialized extensions on `VerificationResult<TSignedType>` collapse into a single C# class and re-emit the same members three times.

```swift
// StoreKit declares (paraphrased):
public struct VerificationResult<SignedType> { ... }

extension VerificationResult where SignedType == AppTransaction {
    public var signatureData: Data { ... }
    public var signedData: Data { ... }
    // ... more
}

extension VerificationResult where SignedType == Transaction {
    public var signatureData: Data { ... }   // SAME signature
    public var signedData: Data { ... }
    // ... more
}

extension VerificationResult where SignedType == Product.SubscriptionInfo.RenewalInfo {
    public var signatureData: Data { ... }   // SAME signature again
    // ... more
}
```

**Generator output**: All three extensions are merged into the single C# `VerificationResult<TSignedType>` class declaration. Each extension's members are re-emitted, producing three copies of `SignatureData`, `SignedData`, `SignedDate`, `DeviceVerification`, `DeviceVerificationNonce`, `JwsRepresentation`, `HeaderData`, `PayloadData` (and their `_Get` companion accessors). Result: 34× `CS0102: type already defines a member called X with the same parameter types`.

**Root cause** (worker's read, unverified — confirm during fix): the generator's extension-merging step keys members by the constrained type witness (`AppTransaction`, `Transaction`, etc.) when assembling the parent `TypeDecl`. Members from different specializations look distinct because their parent extension is distinct, even though their final emitted signature (no generic constraint visible in C#) is identical.

**Fix direction**: extension dedup needs to key on the **emitted member identity** (name + parameter types as projected to C#), not on the source extension or the constrained witness. Where: probably in the part of `TypeDecl` assembly that walks extensions and merges members. Look at how non-constrained extensions are deduped today and extend that pass to cover the constrained case.

**Files to investigate** (start here, expand as needed):
- `src/Swift.Bindings/src/Parser/SwiftABIParser.cs` — where extensions are attached to their parent type. Look for "extension" handling in `CreateTypeDecl` or its callees.
- `src/Swift.Bindings/src/TypeDatabase/TypeDecl.cs` — the `TypeDecl` itself, especially how `Members` is populated.
- `src/Swift.Bindings/src/Emitter/StringEmitter/Handler/PropertyHandler.cs` — where the duplicates are ultimately emitted.

**Tests to add**: a unit test that constructs a `TypeDecl` with two specialized extensions on the same generic parent emitting the same property name; assert that the merged `Members` collection contains exactly one entry per emitted name.

**Done criteria**: the 34 CS0102 errors in the StoreKit reproduction disappear; `nuke validate` and `nuke test` baselines hold.

## Bug #1: Nested type qualification stripped (CS0234 × 52) — FIXED

**Status**: Fixed. Root cause was upstream of "name normalization" — nested types were never even reaching the type database. `HandleConformance` in `SwiftABIParser.cs` called the demangler unguarded; an `IndexOutOfRangeException` on the `$sSci` substitution (Swift `_Concurrency.AsyncSequence`) propagated up through `node.Conformances.Select(...)` in `CreateStructDecl`/`CreateClassDecl` and was swallowed by `HandleNode`'s catch-all, silently dropping the entire enclosing type. After the fix, demangler crashes degrade gracefully to a printedName-derived fallback protocol identity, and the type stays in the database. Regression coverage: `HandleConformanceRobustnessTests`.



**Symptom**: AsyncSequence-style nested types resolve to the wrong containing type. Generator emits `StoreKit.PurchaseIntents` instead of `StoreKit.PurchaseIntent.PurchaseIntents`.

Affected types observed in StoreKit:
- `StoreKit.PurchaseIntents` (should be `StoreKit.PurchaseIntent.PurchaseIntents`)
- `StoreKit.Transactions` (should be `StoreKit.Transaction.Transactions`)
- `StoreKit.Storefronts`
- `StoreKit.Messages`
- `StoreKit.ProductSubscriptionInfoStatuses`
- `Foundation.DateComponentsFormatStyle` (overlap with bug #4)
- `Foundation.DecimalFormatStyleCurrency` (overlap with bug #4)

These are all nested types — typically `AsyncSequence` conformances declared as `public struct Transactions: AsyncSequence` inside the parent type.

**Worker observation**: The generated `intents_Get` accessor routes through `ObjCRuntime.Runtime.GetNSObject<>` for what is a Swift type. That's not just a name-mangling problem — it's a **type misclassification**. Somewhere in the type resolution path the nested struct is being tagged as an ObjC type, then the emitter falls back to the ObjC runtime helper.

**Fix direction** (untested hypothesis — verify before implementing):
1. Find where the type is parsed from the ABI JSON. The `printedName` should already include the parent qualification (e.g. `Transaction.Transactions`).
2. Trace where that qualification is dropped. Likely in name normalization or in the `TypeProjection` step.
3. The ObjC misclassification is downstream of the name corruption — once the emitted name resolves to a real Swift nested type, it should not enter the ObjC fallback path.

**Files to investigate**:
- `src/Swift.Bindings/src/Parser/SwiftABIParser.cs` — `CreateTypeSpec`, `CreateTypeDecl`, and any `printedName` parsing.
- `src/Swift.Bindings/src/TypeDatabase/TypeProjection.cs` (or wherever type projection lives) — how nested types are projected to C# names.
- `src/Swift.Bindings/src/Emitter/StringEmitter/Handler/PropertyHandler.cs` — the `_Get` accessor emission path that's routing through `Runtime.GetNSObject<>`.

**Concrete repro to use during the fix**: search the generated `StoreKit.cs` for `intents_Get` and see what it currently emits; the emitted method should reference the type as `global::StoreKit.PurchaseIntent.PurchaseIntents`, not `global::StoreKit.PurchaseIntents`, and should NOT call `Runtime.GetNSObject<>`.

**Done criteria**: the 52 CS0234 errors disappear; nested AsyncSequence types in StoreKit project to their correct nested C# names; `nuke validate` and `nuke test` baselines hold.

## Bug #3: Property / nested-type name collision (`Transaction.OfferType`) — FIXED

**Status**: Fixed. The existing nested-type rename pass (`NameProvider.ApplyNestedTypeRenames`) added a `Type` suffix when a property collided with a sibling nested type, but didn't check whether the new leaf name itself collided with another sibling that was still in the queue. For `Transaction`, the `Offer`/`offer` pair renamed to `OfferType` and clashed with the pre-existing `Transaction.OfferType` struct that was itself the rename target of the `offerType` property — yielding CS0102/CS0542. Fix: build a `takenNames` set (properties + nested types) and loop appending `Type` until the new leaf name is unique, then reserve it so a subsequent rename in the same loop sees it. Regression coverage: `NameProviderRenameTests.ComputePropertyRenames_TwoCollisions_AvoidsSecondaryRenameClash`.



**Symptom**: `Transaction` declares both:
- An instance property `OfferType` (line 4581 of generated `StoreKit.cs`)
- A nested class `OfferType` (line 7144 of generated `StoreKit.cs`)

C# does not allow a member and a nested type to share a name within the same enclosing type. CS0102 / CS0542.

**Source Swift** (paraphrased):
```swift
public struct Transaction {
    public var offerType: OfferType { get }   // property of type OfferType
    public enum OfferType { case introductory, promotional, code }  // nested type
}
```

**Fix direction**: the generator already has a suffix-disambiguation pass for instance/static name collisions (search for tests or helpers with names like `Disambiguate`, `SuffixCollision`, `MemberNameCollision`). Extend that pass to also disambiguate property↔nested-type collisions. Convention: rename the **nested type** with a suffix (e.g. `OfferTypeKind` or `OfferTypeEnum`) rather than the property — properties are part of the public API surface and have stronger naming expectations than nested types. Or rename the property — preference is up to the implementer; pick whichever causes less consumer surprise. Document the choice.

**Files to investigate**:
- `src/Swift.Bindings/src/Emitter/StringEmitter/Handler/TypeHandlerHelpers.cs` — likely contains the existing disambiguation helpers.
- `src/Swift.Bindings/src/Emitter/StringEmitter/Handler/PropertyHandler.cs` and the type handler that emits nested types — both need to be aware of the collision and apply the suffix consistently.

**Tests to add**: a unit test with a Swift type declaring both a property and a nested type of the same name; assert that one of them is renamed and the other isn't, and that all references to the renamed one are updated.

**Done criteria**: `Transaction.OfferType` collision resolved; if any other StoreKit types hit the same pattern they're auto-fixed; `nuke validate` and `nuke test` hold.

## Bug #4: Foundation projection gaps — FIXED

**Status**: Fixed. Root cause: `IsObjCModuleType` over-bridges *any* unknown nested type in an auto-bridge module (Foundation, UIKit, etc.) by routing it through `CreateObjCBridgedTypeRecord`, which flattens nested parts (`Foundation.Decimal.FormatStyle.Currency` → `Foundation.DecimalFormatStyleCurrency`) and tags the result as an ObjC class. For the two Swift-only Foundation FormatStyle structs that StoreKit references, the flattened name is invented — there is no matching `Foundation.DecimalFormatStyleCurrency` / `Foundation.DateComponentsFormatStyle` type in Microsoft.iOS — and `CreateObjCBridgedTypeRecord` then steers property emission through `ObjCRuntime.Runtime.GetNSObject<…>`, producing CS0234 on the bogus type name.

Fix: add `Decimal.FormatStyle.Currency`, `Date.ComponentsFormatStyle`, and `Locale.Currency` to `Foundation.valueTypes` in `apple-frameworks.json`. `IsKnownValueType` now returns true for the full module-qualified names, `IsObjCModuleType` returns false, and `TryGetTypeRecord` falls through to `null`. Regression coverage: new `[InlineData]` rows in `AppleFrameworkRegistryTests.IsKnownValueType_ReturnsExpected` and `TypeDatabaseExtensionsTests.GetTypeRecordOrAnyType_FoundationValueType_ReturnsAnyType`.

**Two distinct skip paths kick in after the data fix** — confirmed in `binding-report.json` against the regenerated StoreKit:

1. `Product.priceFormatStyle` and `Product.subscriptionPeriodFormatStyle` (bare `Foundation.Decimal.FormatStyle.Currency` / `Foundation.Date.ComponentsFormatStyle`, not wrapped in Optional) skip via `PropertyHandler`'s **`UnsupportedType`** path — `processed = TryGetTypeRecord(...)` returns `false`, the property isn't a bound generic / existential / closure, so the early skip at `PropertyHandler.cs:197` fires with `Type resolution failed for property type 'Foundation.…'`.

2. `Transaction.currency`, `Storefront.currency`, and `Product.SubscriptionInfo.RenewalInfo.currency` (all `Optional<Foundation.Locale.Currency>`) skip via the **`AnyTypeFallback`** path. Optional IS a bound generic, so PropertyHandler takes the bound-generic branch and `BoundGenericsHandler.TranslateBoundGenericTypeToCSharp` produces `Swift.SwiftOptional<Swift.AnyType>` because the inner now resolves to `AnyType`. The `csTypeName.Contains("AnyType")` guard at `PropertyHandler.cs:343` then skips the property.

**Important nuance about `Foundation.Locale.Currency`** (the second pass added this — the original Bug #4 fix missed it): the original `Bug #4` patch left this entry out, so the inner did *not* fall back to `AnyType`. Instead `IsObjCBridgedType` returned true via the synthetic ObjC bridge record, and `BoundGenericsHandler.TranslateBoundGenericTypeToCSharp` collapsed the Optional inner to `IntPtr` (the stdlib-container ObjC fallback at `BoundGenericsHandler.cs:604-612`). The result was a public property `Swift.SwiftOptional<IntPtr> Currency` on `Transaction`, `Storefront`, and `RenewalInfo` — it compiled (via the implicit `IntPtr → IntPtr? → SwiftOptional<IntPtr>` conversion in the runtime) but exposed an opaque pointer type to consumers instead of a real C# type. Cleared by adding the entry; the property is now recorded as `AnyTypeFallback` in `binding-report.json` instead of being emitted.

Cross-check from the ABI dump (search for `Foundation.*` references in `/tmp/storekit-dump.json`): the only remaining Foundation types referenced from StoreKit are `Foundation.DateComponents.ReferenceType` / `Foundation.NSDateComponents`, both inside a `ReferenceConvertible` typealias that never reaches C# emission. No additional `valueTypes` entries needed.

**Note**: Removing the four `CS0234` errors exposed two latent `CS1503` errors in the async marshalling path for `Optional<Array<Foundation.URL>>` returns (`StoreKit.ExternalPurchaseLink.getEligibleURLs`). These were previously masked by cascading effects of the `CS0234` failures. Tracked separately as Bug #5 below — the StoreKit reproduction does *not* compile cleanly until that bug is fixed too.



**Symptom**: StoreKit references `DateComponentsFormatStyle` and `DecimalFormatStyleCurrency` (both Foundation types) in formatter APIs. Neither is in `AppleFrameworkRegistry` (`apple-frameworks.json`) or in the Foundation database XML. The generator falls back to emitting `Foundation.DateComponentsFormatStyle` as an unresolved type, producing CS0234 (overlaps with bug #1's count).

**Fix direction (historical)**: add the missing types to the Foundation XML database (`src/Swift.Runtime/src/Swift/FoundationDatabase.xml` or wherever Foundation types are catalogued — find the existing entries for `Date`, `Data`, etc. and follow the same pattern). Confirm the C# projection target — these are SwiftUI-style format styles that may already have a Microsoft.iOS analog or may need to project as `ISwiftObject`-rooted Swift types.

**Files to investigate**:
- `src/Swift.Runtime/src/Swift/FoundationDatabase.xml` (or similar — confirm path with Glob)
- `apple-frameworks.json` — Foundation entry, see what's already listed there
- The existing entries for analogous types like `Date`, `Data`, `Decimal`, `URL`

**Cross-check**: search the StoreKit ABI dump for every distinct Foundation type that's referenced, not just the two surfaced by the compile errors. There may be more in the same gap class (`AttributedString`, `Locale.Region`, etc.) that didn't trip a compile error because no method on the StoreKit C# surface uses them yet.

**Done criteria**: `Foundation.DateComponentsFormatStyle` and `Foundation.DecimalFormatStyleCurrency` (and any other newly-discovered gaps) resolve to a real C# type; CS0234 count drops to zero (combined with bug #1's fix); `nuke validate` and `nuke test` hold.

## Bug #5: Async `Optional<Array<ObjCBridgeable>>` return — wrong runtime/public type in TCS

**Status**: Open. Newly exposed once Bug #4 unblocked the four `CS0234` errors that were masking it.

**Symptom**: After Bug #4, compiling the StoreKit reproduction reports two `CS1503` errors on `StoreKit.ExternalPurchaseLink.getEligibleURLs` (both at the `holderTcs.TrySetResult(result)` and `directTcs.TrySetResult(result)` lines of the generated async-success callback):

```
error CS1503: Argument 1: cannot convert from 'Swift.SwiftArray<nint>'
              to 'System.Collections.Generic.IReadOnlyList<Foundation.NSUrl>?'
```

The Swift method's return type is `Optional<Array<URL>>`. The generated async callback emits:

```csharp
var result = SwiftMarshal.MarshalFromSwift<SwiftOptional<SwiftArray<IntPtr>>>(resultPtr).ToNullable();
// ...
holderTcs.TrySetResult(result);   // TCS<IReadOnlyList<Foundation.NSUrl>?>
```

`result` is `SwiftArray<IntPtr>?` (the runtime type), but the `TaskCompletionSource` is parameterised on the *public* type `IReadOnlyList<Foundation.NSUrl>?`. The async callback never converts the runtime container into the public projection.

**Root cause**: `WrapperEmitter.Async.cs` → `TryGetOptionalMarshalType` resolves the optional's inner spec via the projection factory and returns `SwiftOptional<SwiftArray<IntPtr>>` as `marshalType`. The success branch then emits a flat `…ToNullable()` that drops directly into the TCS without applying the inner-container conversion. The synchronous path already handles this case correctly: `OptionalProjection.GetReturnPlan` calls `_innerProjection.GetReturnContainerConversion("swiftResult.Some")` for collection inners and emits a discriminant check + container conversion (see `OptionalProjection.cs:258`). The async path needs the equivalent.

The same pattern likely affects `Optional<Array<T>>`, `Optional<Set<T>>`, `Optional<Dictionary<K,V>>` whenever the element conversion is non-identity (Swift→ObjC bridge or value-type projection). It only escaped notice until now because Bug #4's `CS0234` errors stopped C# semantic analysis before it reached these lines.

**Fix direction** (untested):
1. In `TryGetOptionalMarshalType`, recognise when the inner spec is `Swift.Array` / `Swift.Set` / `Swift.Dictionary` and grab the projection's `GetReturnContainerConversion("_rawResult.Some")` — exactly mirroring the existing `objcBridgeConversion` branch for `Optional<ObjCBridgeable>`.
2. Extend the `marshalResultCode` branch at `WrapperEmitter.Async.cs:1413-1418` to handle the new `containerBridgeConversion`, producing:
   ```csharp
   var _rawResult = SwiftMarshal.MarshalFromSwift<{optionalMarshalType}>(resultPtr);
   var result = _rawResult.Case == SwiftOptionalCases.Some ? {containerConv} : null;
   ```
3. Add a regression test under `BindingTests/Sources/SwiftBindingsTestLib/Async/` covering an async function returning `[Foundation.URL]?` (or any `Optional<Array<ObjCBridgeable>>`) and verifying the awaited result projects to `IReadOnlyList<Foundation.NSUrl>?`.

**Files to investigate**:
- `src/Swift.Bindings/src/Emitter/StringEmitter/Handler/WrapperEmitter.Async.cs` — `TryGetOptionalMarshalType`, `EmitAsyncWrapperForOptional` (around line 1413).
- `src/Swift.Bindings/src/Marshaler/Projection/OptionalProjection.cs` — `GetReturnPlan` shows the synchronous discriminant + container conversion pattern.
- `src/Swift.Bindings/src/Marshaler/Projection/ArrayProjection.cs` — `GetReturnContainerConversion` is reusable for `_rawResult.Some`.

**Done criteria**: `getEligibleURLs` (and any other `Optional<Collection<…>>` async returns) compile cleanly in the StoreKit reproduction; the new BindingTests case awaits a non-null result with the projected element type; `nuke validate`, `nuke test`, `nuke binding-tests` baselines hold.
