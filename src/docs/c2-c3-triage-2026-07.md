### 1.2 Headline result: 22 of the 53 rows are misclassified — the surface is reachable

The brief asked me to be skeptical of the premise. The `@_spi` sibling precedent repeats
here, three separate times. **22 of 53 rows (42%) name surface that a consumer can actually
call.**

**(a) 8 rows — `SuppressedProxyMemberDegraded` (StripePayments).** The enum is documented at
`src/Swift.Bindings/src/Reporting/BindingReport.cs:~231` as "emitted **but degraded**". All
eight named methods are present as public C# API in
`.../StripePayments/StripePayments.Types.STPPaymentHandler.cs` at lines
**352, 412, 484, 543, 639, 696, 753, 824** (`ConfirmPaymentIntent`, `HandleNextAction`,
`ConfirmSetupIntent`, `HandleNextAction`, `ConfirmPayment`, `ConfirmSetupIntent2`,
`HandleNextAction2`, `HandleNextAction2`), each taking `ISTPAuthenticationContext`. The
report itself corroborates this: `DegradedConsumeCount: 8`
(`SkipTriage.cs:53`, populated at `:113-126`). The real loss is one direction only — a
**C#-authored** `ISTPAuthenticationContext` cannot be marshalled *in*; Swift-vended
conformers round-trip.

**(b) 9 rows — `EveryProtocolConformanceSkipped` naming `{P}Proxy` types.** These rows are

#### Bug (3 rows) — a catalogued Apple value type that cannot be resolved

`PaymentSheet.ApplePayConfiguration.buttonType: PassKit.PKPaymentButtonType`
(`.swiftinterface:725`) is skipped with "Type resolution failed for property type
'PassKit.PKPaymentButtonType'" — yet **that exact name is registered** in
`src/Swift.Bindings/src/Data/apple-frameworks.json:677`, inside PassKit's `valueTypes`
(module entry at `:670-675`, `autoBridge: true`, `objcPrefixes: ["PK"]`).

Root cause, pinned at `src/Swift.Bindings/src/TypeDatabase/TypeDatabaseExtensions.cs:833-834`:

```csharp
return AppleFrameworkRegistry.IsAutoBridgeModule(typeSpec.Module)
    && !AppleFrameworkRegistry.IsKnownValueType(typeSpec.Name);
```

A type from an auto-bridge Apple module gets a synthetic ObjCBridged **class** record
*unless* it is listed in `valueTypes`. Listing is therefore what makes these names fail
closed rather than mis-bind as opaque classes — correct as far as it goes — but **nothing
supplies a value-type record in its place**. The asymmetry is visible in the output:
`PassKit.PKPaymentSummaryItem` (not listed → gets the synthetic class record) resolves and
appears three times in the emitted C#, while `PKPaymentButtonType` (listed) appears only
inside an "Unsupported:" comment at
`.../StripePaymentSheet/StripePaymentSheet.Types.PaymentSheet.cs:8848`.
`PKPaymentButtonType` is an `NS_ENUM(NSInteger)` — trivially bindable if a record existed.

Three of the 53 rows trace to this one gap:

1. `ApplePayConfiguration.buttonType` (`UnsupportedType`, StripePaymentSheet).
2. `ApplePayConfiguration.init` (`UnsupportedSignature`, "Constructor signature contains

3. `StripeCore.StripeAPI.additionalEnabledApplePayNetworks` (`AnyTypeFallback`, "Property type
   resolved to AnyType (`Swift.SwiftArray<Swift.AnyType>`)") — the Swift declaration is
   `[PassKit.PKPaymentNetwork]` (`StripeCore` `.swiftinterface:61`), and `PKPaymentNetwork` is
   registered at `apple-frameworks.json:679`. Same gap, surfacing as element-type collapse
   inside an array.

**This is not a Stripe-local defect.** Scanning `SkippedItems` across all 132 corpus reports
for `Reason == "UnsupportedType"` with a "Type resolution failed" detail yields 61 rows over

### 1.5 Recommended reporting fix (out of scope for this pass, worth recording)

`PublicSurfaceLost` overstates by 42% on this corpus because it counts (a) emitted-but-degraded
members, (b) proxy *types* whose interface is emitted, and (c) SwiftUI views that the bridge
generated. `DegradedConsumeCount` already exists as an additive callout
(`SkipTriage.cs:53`) but is not subtracted. Subtracting degraded-but-emitted rows, and
cross-checking `EveryProtocolConformanceSkipped`/`SwiftUIView` rows against emitted interfaces
and `BridgedViews` before counting them as lost, would make the metric mean what its name says.

## Part 2 — C3: which shipped packages carry dangling P/Invokes?

### 2.1 The defect and its trigger

`EnumHandler.cs:74-89` replaces the Swift writer with a discarding one for module-internal
enums:

```csharp
var wrapperPlaneDiscarded = WrapperValidation.IsTypeOrEnclosingModuleInternal(enumDecl);
if (wrapperPlaneDiscarded)
    swiftWriter = new SwiftWriter(new System.IO.StringWriter()) { IsDiscarding = true };
```

Pre-fix, `EmitRawRepresentableSupport` still ran on that path and emitted `LibraryImport`
declarations naming `SBW_{Module}_{Enum}_InitWithRawValue` /
`SBW_{Module}_{Enum}_CaseByIndex`
(`EnumHandler.RawRepresentable.cs:122`, `:130`, `:141`; `LibraryImport` sites at `:183-186`,
`:352-355`, `:360-368`, `:446-450`) while the Swift side was thrown away — an
`EntryPointNotFoundException` on first call. The fix at `EnumHandler.cs:424-446` routes that
combination to `TombstoneRawRepresentableSurface`
(`EnumHandler.RawRepresentable.cs:19-52`).

**The briefed trigger shape is narrower than the code.** Symbol emission is gated on
`isStringRawType` **or** `(!enumDecl.IsFrozen && WrapperValidation.IsXCFrameworkMode(...))`
(`EnumHandler.RawRepresentable.cs:122`, `:130`, `:141`). So the trigger is a module-internal
raw-representable enum that is either `String`-backed **or** non-`@frozen` in XCFramework
mode — not only `enum X: String`.

2. **All 16 carry a real native payload** (`.xcframework` + Mach-O under
   `runtimes/ios-arm64/native/`). None is a managed-only artifact, so the CI-package caveat
   in §2.3a does not apply to any of them.
3. **`Stripe.ThreeDS2` is structurally immune, not merely lucky.** It ships **no**
   `*SwiftBindings.framework` companion at all — only the vendor `Stripe3DS2.xcframework` —
   and its managed DLL declares zero `SBW_` strings of any kind. It cannot exhibit this
   defect by construction.
4. **Exported counts run ~2× declared, and that direction cannot manufacture a false clean.**
   Dangling is the set difference `declared \ exported`, so extra names on the export side can
   only shrink it — and only if an extra *exactly equalled* a declared symbol. The extras are
   mangled twins of the real symbols, roughly one per symbol, with the name prefix replaced by
   a short digit-bearing token: `SBW_StripeConnect_EmbeddedComponentError_ErrorType_CaseByIndex`
   has the twin `SBW_ab24_EmbeddedComponentError_H16Type_CaseByIndex`, and BlinkIDUX's
   `SBW_BlinkIDUX_MicroblinkColor_CaseByIndex` has `SBW_A32IDUX_MicroblinkColor_CaseByIndex`.
   Because no twin is byte-identical to a declared name, none can mask a real dangling symbol.
   Verified directly: `comm -23 declared exported` returns **0 rows** for
   Stripe.Connect (6/12), Stripe.CardScan (2/4), Mappedin (84/168), BlinkID 7.8.4 (50/97) and
   BlinkIDUX (4/8) — i.e. `declared ⊆ exported` by exact string comparison in every case, so
   the zero is a genuine subset result and not an empty-`declared` artifact.

*Cross-validation between the two independent methods.* The audit's `declared.txt` for
`Stripe.Connect` (6 names) and `Stripe.CardScan` (2 names) match **exactly**, name for name,
the sets found by the source-level scan in §2.3b. Two different extraction paths — shipped
managed binary vs freshly generated `.cs` — over two different generator builds, same result.

### 2.7 The library-name axis: 16/16 clean on CC-003, one adjacent exposure

Part 2 up to §2.6 compares *entry-point symbols*, which cannot see a library-name mismatch.
This section closes that axis for the same 16 published packages.

**Method.** The library name of a P/Invoke is not a string-heap literal you can `strings` for;
in ECMA-335 it lives in the **ImplMap** table, whose `ImportScope` points at a **ModuleRef**
row carrying the name. A throwaway `System.Reflection.Metadata` reader was built in a scratch
directory (outside both repos) that walks `MetadataReader.MethodDefinitions`, keeps rows with
`MethodAttributes.PinvokeImpl`, and resolves `MethodDefinition.GetImport().Module` →
`GetModuleReference(...).Name`. That is the authoritative library name the CLR will hand to
the resolver. An earlier `strings`-based pass on `swiftbindings.stripe.core` produced four
apparent bare `SwiftBindings` hits which were, in context, 2× the assembly name
`SwiftBindings.Stripe.Core`, 1× the `.dll` name and 1× a `.pdb` path — which is precisely why
this audit reads metadata instead.

**Coverage.** 18 managed assemblies across all 16 packages. Every one had readable metadata —
no `<NO-METADATA>` row, no read error — so there is no unchecked package hiding inside the
"16/16". Counts below are P/Invokes bound to each library name.

#### Adjacent exposure: `SwiftBindings.Mappedin` 6.4.2 binds 403 P/Invokes to a library it does not ship

This is **not** CC-003 — the wrapper name is correct. It is the same defect *class* (P/Invoke
library name names no shipped library) on the **vendor-module-name** axis.

1. `SwiftBindings.Mappedin.dll` declares **403 P/Invokes whose ModuleRef name is `Mappedin`**:
   354 `…Ma` type-metadata accessors, 29 `…tF` methods, 14 `…FZ` statics, 3 `…vg` getters,
   2 `…Tj` dispatch thunks — e.g. `$s8Mappedin10CoordinateC2eeoiySbAC_ACtFZ` (`Coordinate ==`)
   and `$s8Mappedin10AnnotationCMa`. These are ordinary-API entry points, not exotic ones.
2. The package ships **only** `MappedinSwiftBindings.xcframework`. `unzip -l` finds no
   `Mappedin.xcframework`, no `Mappedin.framework`, no `libMappedin.dylib`. Mappedin is the
   **only one of the 16** that does not ship its vendor framework alongside the wrapper.
3. Its nuspec dependencies are only `SwiftBindings.Apple 26.2.8` and
   `SwiftBindings.Runtime [0.16.0, 0.17.0)` — nothing supplies `Mappedin` transitively.
4. The vendor SDK is **statically merged into the wrapper**: all 403 wanted symbols are
   *defined* in `MappedinSwiftBindings.framework/MappedinSwiftBindings` (403/403 matched;
   0 undefined; 0 absent), and `otool -L` on the wrapper lists only itself plus system
   libraries — no `Mappedin.framework` dependency. The code is present, under the other name.
5. `buildTransitive/net10.0-ios26.0/SwiftBindings.Mappedin.targets:55-58` `NativeReference`s
   `Mappedin.xcframework` **only when `MappedinSwiftBindings.xcframework` does not exist**, so
   the vendor framework is deliberately dropped once the wrapper is present. Nothing aliases
   or renames the library.
6. There is no rescue path in resolution. `SwiftFrameworkResolver.GetSearchPaths("Mappedin")`
   yields `@rpath/Mappedin.framework/Mappedin`, `@rpath/libMappedin.dylib`,
   `@rpath/Mappedin.dylib`, four `@executable_path` variants, and
   `/System/Library/Frameworks/Mappedin.framework/Mappedin` — none of which can exist for this
   package. `ExtractFrameworkName("Mappedin")` is identity, so `TryLoadByBareFrameworkName`
   walks the same dead list. The resolver holds no library-name alias table.
7. **The vendor slice is a static archive, so no dynamic `Mappedin` image can exist at all.**
   The xcframework the package was built from —
   `swift-dotnet-packages/libraries/Mappedin/Mappedin.xcframework/ios-arm64/Mappedin.framework/Mappedin`
   — is reported by `file` as `current ar archive random library` (15,441,768 bytes, 7,467
   `$s8Mappedin` symbols defined). It is a **static** library wearing a framework layout, not a
   dylib. `library.json` pins vendor 6.4.0 from `github.com/MappedIn/ios` via the release-zip
   path. This closes the one remaining escape: a consumer *cannot* supply the missing
   `Mappedin` library, because there is no loadable image to supply — packaging omitting it is
   correct. (A stale dynamic 6.x build at `Misc/Libraries/Mappedin.xcframework`, 1,388,896
   bytes, dated May 2025, is **not** the build source; it is noted only so it is not mistaken
   for one.)

**Verdict: exposed on static evidence; the runtime throw was NOT observed.** The expected
symptom is `DllNotFoundException` on first use of any of those 403 entry points.

*What is established:* the 403 ModuleRef names, the absence of any `Mappedin` payload in the
nupkg, the absence of a transitive supplier, the symbols' presence in the wrapper, the targets
file dropping the vendor xcframework, the resolver's dead candidate list and lack of an alias
table, and the vendor slice being static.

*What is NOT established:* that a consumer actually hits it. Nobody has watched the exception
throw. No simulator or device run was performed — this pass is read-only and holds no build
lock, and the sim leg is deliberately owned elsewhere. Nor is reachability quantified: 354 of
the 403 are lazily-invoked type-metadata accessors, and no attempt was made to determine which
managed API surfaces reach them first.
*What would settle it:* one simulator run of a consumer app on `SwiftBindings.Mappedin` 6.4.2
calling any of those members.

**Mechanism: UNTRACED HYPOTHESIS — do not treat as known.** The shape *suggested* by the
artifacts is that when a vendor slice is static and its symbols land in the wrapper, the emitter
still names direct vendor-module P/Invokes after the vendor module rather than the wrapper.
Evidence point 7 is consistent with that story but does not establish it: **no emitter source
site was traced in this pass.** A trace may well contradict this reading, and the shipped-artifact
facts above stand independently of whatever cause it finds. Nothing downstream should be built
on the hypothesis.

### 2.8 Two published packages have no bound surface at all — a product question, not a defect

**This is not a generator bug. Do not open a generator investigation on it.** It is recorded
here because the fact is product-level and easy to misread as a regression.

`SwiftBindings.Stripe.UICore` 26.0.0 and `SwiftBindings.Stripe.CameraCore` 26.0.0 each ship a
full native payload — vendor xcframework *and* `{Module}SwiftBindings.xcframework` wrapper — yet
their shipped managed assemblies contain **zero P/Invokes** (§2.7 table). We published binding
packages with nothing bound.

The cause is upstream and the generator is behaving correctly. The vendor's **public**
`.swiftinterface` for both modules contains no declarations whatsoever — only the format header
and `import` lines:

| Module | Published? | public `.swiftinterface` | declarations in it | `.private.swiftinterface` | `@_spi` lines in private |
|---|---|---:|---:|---:|---:|
| `StripeUICore` | yes — 26.0.0 | 15 lines | **0** | 1,906 lines | 1,265 |
| `StripeCameraCore` | yes — 26.0.0 | 19 lines | **0** | 166 lines | 108 |
| `StripeCryptoOnramp` | **no** — corpus only | 21 lines | **0** | 255 lines | 180 |

`StripeCryptoOnramp` shares the identical cause and is listed here so the explanation lives in
one place, but it is **not** a published package — there is no `SwiftBindings.Stripe.CryptoOnramp`
in `~/.nuget/packages` and none under `swift-dotnet-packages/libraries/`, so it carries no
consumer impact and is not part of the "we published an empty package" product question. Only
the two Stripe packages above are live in that state.

Read from
`swift-dotnet-packages/libraries/Stripe/{Module}/{Module}.xcframework/ios-arm64/{Module}.framework/Modules/{Module}.swiftmodule/arm64-apple-ios{,.private}.swiftinterface`.
Stripe ships these modules' entire API as `@_spi(STP)`, so it appears only in the private
interface. With zero public declarations there is nothing to bind, and emitting zero members is
the correct outcome. This confirms independently what the release lane concluded from the same
source.

This resolves **three** of the four §1.7 zero-emission rows. The fourth, `AlertToast`, has a
**different** cause and is explained separately below — the "zero public surface" reading does
not apply to it and must not be extended to it.

**The open question is a product one, for the owner, not an engineering fix:** should a binding
whose module has zero public surface publish at all, or should generation fail loudly rather
than emit an empty package? Both `Stripe.UICore` and `Stripe.CameraCore` are currently live on
nuget.org in that state. A related reporting gap is genuine and separable: the members are
counted in `TotalTypes` / `TotalMembers` but recorded as neither emitted nor skipped, so
`PublicSurfaceLost` cannot see them (§1.5, §1.7).

#### `AlertToast` — a different cause: SwiftUI suppression of the parent type

**Also not a generator bug, but not for the §2.8 reason.** `AlertToast` is a corpus module, not
a published package (nothing under `swift-dotnet-packages/libraries/`, nothing in
`~/.nuget/packages`), so it carries no consumer impact.

Its public `.swiftinterface` has **15 real public declarations and zero `@_spi`** — so the
zero-public-surface explanation is factually false for it. Anyone checking §2.8's claim against
this module would find public declarations and reasonably conclude the doc was unreliable; hence
the separate heading.

It is nonetheless correct-by-design. The entire public surface is SwiftUI `View` conformance
machinery: four enums (`BannerAnimation`, `DisplayMode`, `AlertType`, `AlertStyle`) nested inside
`AlertToast.AlertToast`, which is itself a SwiftUI `View`; their compiler-synthesized
`Equatable`/`Hashable` members; and the typealiases `Body`, `UIViewType`
(= `UIKit.UIVisualEffectView`) and `Coordinator` — one `Body` being literally
`@_opaqueReturnTypeOf("$s10AlertToastAAV4bodyQrvp", 0)`. 22 lines of the interface reference
SwiftUI / `View` / `ViewModifier`.

SwiftUI types are suppressed by design under the generator's two-path SwiftUI gate (Path A in
`TypeDatabaseExtensions`, Path B in `MemberEmissionValidator`), and members whose **parent** type
is suppressed are never enumerated at all. That is precisely why its recorded skips — 2
`SwiftUIView`, 2 `SwiftUIConstraint`, 1 `EveryProtocolConformanceSkipped` — account for only 5
of its 20 members: the other 15 were never reached to be skipped.

`AlertToast` is therefore the cleanest illustration of the separable **reporting-fidelity** gap:
20 total members, 0 emitted, 5 skips recorded, **15 unaccounted**, and `PublicSurfaceLost`
consequently blind to all 15 (§1.5). That is a reporting defect, not a binding defect, and it is
distinct from the product question above.
