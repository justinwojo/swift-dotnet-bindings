## 1. Where we are

SDK 0.8.0 ships Apple framework bindings (StoreKit 2, WeatherKit, TipKit,
CryptoKit, …) as NuGet packages for .NET iOS / MAUI apps. `Microsoft.iOS`
is an ObjC binding generator with no Swift-first story; that gap is what
this release fills.

**Phase 1 (generator + closeouts): done.** Stripe suite, BlinkID/BlinkIDUX,
HealthKit scheduler, StoreKit2 + MusicKit CSM, defensive co-gater for
throwing-closure facades. Baseline 95/95 validation-gate pass (90 clean +
5 `known_errors` whitelist entries — `FirebaseCoreExtension`, `CodeScanner`,
`RichTextKit`, `WhatsNewKit`, `YouTubePlayerKit` — which are allowed to
report nonzero C# compile errors without failing the gate). 61/61 Swift
wrapper compile.

**Phase 2 (`SwiftBindings.Apple` supplement): done** (commits
`41d00b1e` → `4f2ae4ae`). All 7 target frameworks — Translation,
ProximityReader, LiveCommunicationKit, FamilyControls, WeatherKit, TipKit,
CryptoKit — at their permanent-skip floor with Swift-only-type references
routed to the supplement. Architectural machinery (`TypeOwnerRegistry`,
manifest pipeline, VWT-backed storage, cross-module identity test,
live-SDK validation, blast-radius smoke) all in place. Design doc:
[`apple-swift-types-architecture.md`](apple-swift-types-architecture.md).

**Phase 3 (pack + publish): the remaining work.** See §7.

## 2. 1.0 thesis

**Bridge .NET MAUI to Apple's Swift-first platform APIs, plus select
third-party Swift SDKs that fill real gaps.** Measured by shipping
packages and where they run, not by skip percentages. Skip rate at 15.1%
is diminishing returns — headline is Apple framework coverage and
multi-platform proof.

## 3. Locked-in decisions

Inputs, not options to revisit.

### 3.1 Versioning

- **Apple-framework packages:** `{SDK-major}.{SDK-minor}.{binding-rev}[-preview.N]`.
  Major.Minor mirrors iPhoneOS SDK version (not Xcode). Patch is our binding
  revision lane. Example: `SwiftBindings.StoreKit2 26.2.0` → `26.2.1` (fix) →
  `26.3.0` (iOS 26.3 SDK) → `27.0.0-preview.1` (Xcode 27 beta).
- **Third-party packages:** mirror upstream (`SwiftBindings.Nuke 12.8.x` = Nuke 12.8.x).
- **`SwiftBindings.Apple` supplement:** per Apple SDK train major. Cross-major
  additive-only; breaking changes ship as a new package name
  (`SwiftBindings.Apple.v2`), not a breaking major.

### 3.2 `SwiftBindings.Runtime` pinning

Bounded `[0.8.0,0.9.0)` — patch releases must be ABI-compatible (no struct
layout changes, no P/Invoke signature changes). Avoids republish tax across
every Apple-framework package on every runtime patch.

### 3.3 TFM in generator-emitted csprojs

Explicit `--platform-version` CLI flag (e.g., `--platform-version 26.2` →
`net10.0-ios26.2` in both `<TargetFramework>` and `buildTransitive/`). Dynamic
`$(TargetPlatformVersion)` resolution was rejected — .NET 10 library projects
default to the oldest installed TPV, producing stale TFMs on multi-workload
machines.

### 3.4 Package layout (multi-TFM)

```
lib/net10.0-ios26.2/SwiftBindings.StoreKit2.dll
lib/net10.0-macos26.2/SwiftBindings.StoreKit2.dll
lib/net10.0-maccatalyst26.2/SwiftBindings.StoreKit2.dll
lib/net10.0-tvos26.2/SwiftBindings.StoreKit2.dll
buildTransitive/net10.0-ios26.2/SwiftBindings.StoreKit2.targets
...
runtimes/ios-arm64/native/StoreKitSwiftBindings.xcframework/...
runtimes/osx-arm64/native/StoreKitSwiftBindings.xcframework/...
...
```

### 3.5 Forward compatibility

Old nupkgs work on newer Apple workloads. Swift ABI stability since 5.0 + .NET 10
TFM precedence rules select older-versioned `lib/` entries; `runtimes/` is
RID-based not TFM-based. Verified with a `26.0 → 26.2` consumer repro.

### 3.6 Naming — framework packages vs. supplement

Two distinct lanes. Do NOT conflate.

- **Framework packages** keep current names: `SwiftBindings.StoreKit2`,
  `SwiftBindings.WeatherKit`, etc. One package per Apple framework.
  Namespace e.g. `StoreKit2` (NOT `StoreKit`, to avoid collision with
  Microsoft.iOS ObjC types).
- **Swift-only types supplement** is a separate package: `SwiftBindings.Apple`.
  Hosts newly-generated Apple Swift-only value types (`Foundation.Locale.Language`,
  `ManagedSettings.Application`, `CryptoKit.P256.Signing.ECDSASignature`, …).
- **`SwiftBindings.Runtime`** stays SDK-agnostic. Existing legacy canonical
  types (`Foundation.Date`, `.URL`, `.Decimal`, `.Measurement<T>`,
  `ManagedSettings.Token<T>`, `SwiftUI.Text`) stay in Runtime indefinitely.
  Supplement does NOT re-emit them.
- Framework packages reference the supplement via `TypeOwnerRegistry`-driven
  transitive `PackageReference`, pulled only when a consumer actually
  references a supplement-owned Swift identity.

## 7. Phase 3 — Ship & publish

**This is the active work.**

### 7.1 Steps

1. **Wire `apple-frameworks/` into swift-dotnet-packages Nuke pipeline.**
   (Out of this repo; in `swift-dotnet-packages`.) Extend
   `Build.Xcframework.cs:DiscoverLibraries` to handle SDK-sourced
   multi-TFM projects. `BuildLibrary`, `Pack`, `PackValidate`,
   `BuildAndPackRelease`, `ListChangedLibraries` must all see
   apple-framework packages.
2. **Stripe hardening.** NativeAOT validation across all Stripe
   sub-products, sample-app polish, residual test-coverage gaps.
   Primarily swift-dotnet-packages work.
3. **Pack all packages.** `nuke pack --version 0.8.0 --apple-version 26.0.0`
   (or `0.9.0` — see §7.2) → `SwiftBindings.Sdk`, `.Runtime`,
   `.Templates`, `.Apple`, plus every framework package.
4. **Pre-publish licensing checklist.** Execute the 10-item checklist
   in [`licensing-analysis.md`](licensing-analysis.md) before the
   first `SwiftBindings.Apple 26.0.0` publish.
5. **Local-feed regression validation.** Drop nupkgs into
   `swift-dotnet-packages/local-packages/`, clear NuGet caches,
   rebuild on both sim and device. Run the `regression-validation`
   skill (end-to-end Mono JIT simulator + NativeAOT device).
6. **Publish to nuget.org.** All packages.
7. **Commit swift-dotnet-packages.** Only AFTER nuget.org publish
   succeeds (external Claude memory: `feedback_no_commit_packages.md`
   lives in the assistant's project memory, not this repo; the rule is
   simply "don't commit the consumer repo until the referenced SDK
   version is live on nuget.org").

### 7.2 Version-number review

At end of Phase 3, decide 0.8.0 vs 0.9.0:

- **Stay at 0.8.0** if cumulative changes are compatible with 0.8.0's
  already-published lane (runtime ABI unchanged, no framework-package
  breaking changes).
- **Bump to 0.9.0** if cumulative churn is large: a new
  `SwiftBindings.Apple` package shipping for the first time, generator
  internals significantly refactored (`TypeOwnerRegistry`, supplement
  emission), runtime ABI touched. Note 0.8.0's `SwiftBindings.Runtime`
  pinning `[0.8.0,0.9.0)` means any runtime ABI change forces 0.9.0
  anyway.

Default bias: **bump to 0.9.0**. Supplement is a genuinely new artifact
and Runtime picked up non-ABI-trivial changes in Phase 2.

## 8a. Post-ship operations (supplement)

If `SwiftBindings.Apple` ships with a bad manifest, wrong metadata
accessor, or over-broad framework linkage, the mitigation path is:

1. **Yank or deprecate a bad package.** `nuget.org` lists the package →
   **Manage Package** → **Listed: No** removes it from search and new
   restores (existing restores still resolve). If a version must be
   pulled entirely, contact nuget.org support — the registry does not
   let authors hard-delete a version. For broadcasts, attach a
   deprecation message: "Use `SwiftBindings.Apple 26.0.1`; 26.0.0 had
   an invalid VWT for X."
2. **Ship the fixed patch.** Increment the binding-revision digit
   (`26.0.0` → `26.0.1` — NOT a major bump, the Apple SDK train is
   unchanged). Cross-major additive-only still applies. Keep the old
   package listed-but-deprecated long enough for transitive consumers
   to upgrade.
3. **Local manifest / prototype override.** Consumers who need a patch
   before the NuGet fix lands can set the `SwiftAppleSupplementPrototypeDir`
   SDK property (see §3) to emit a prototype `SwiftBindings.Apple.Prototype.csproj`
   into their `obj/` and patch supplement sources locally. Canonical
   identity is preserved via matching `AssemblyName=SwiftBindings.Apple`
   + `RootNamespace=Swift` in the prototype project — consumer code is
   unchanged.
4. **Field diagnostics — "type resolved to supplement but package
   reference / method symbol is missing."**
   - Confirm the consumer csproj has a `<PackageReference
     Include="SwiftBindings.Apple" Version="..." />` *or* the prototype
     `ProjectReference` (check the generated `binding-metadata.props` /
     `apple-supplement.props` under `obj/`).
   - If the reference exists but the method symbol is missing, dump the
     supplement's metadata accessor with `nm -gU <dylib> | grep
     <mangled>` against the on-device framework to confirm the symbol
     exists in the platform SDK version the consumer targets.
   - For VWT-opaque types, verify the accessor's `library` matches the
     runtime framework path — a mis-mapped `library` surfaces as
     `DllNotFoundException` at load, not at resolve.

- **Kingfisher (102 SB0001)** — fluent builder chains on generic wrapper
  types (`KF.Builder`, `KingfisherWrapper<UIImageView>`). Architectural;
  not tractable without generator redesign. Unsupported for 1.0;
  revisit post-ship.
- **TipKit 6b Predicate-init demangler** — see §5 deferred.
- **ActivityKit `Activity<T>.request/update/end`** — permanent
  (app-defined `ActivityAttributes`).
- **Swift variadic parameter packs** (12 WeatherKit methods) —
  permanent, no C# equivalent.
- **SynthesizedCodable pruning** (~178 items) — compiler-internal, by
  design.
- **Result-builder DSL** (9 TipKit items) — `@_alwaysEmitIntoClient`,
  no binary symbol.
- **Framework-package renaming to `SwiftBindings.Apple.*`** — only at
  a deliberate major-version cleanup.

## Appendix — Testing layers (required per session)

Every session that touches generator output must produce evidence at
all three layers before sign-off.

1. **Unit tests** (`nuke test`, ~2 min). Exercise the exact code path
   changed.
2. **BindingTests** (`nuke runtime-tests-simulator`, ~3 min;
   `nuke runtime-tests-device` when calling conventions / marshalling
   change, ~5 min). Swift fixture in
   `BindingTests/Sources/SwiftBindingsTestLib/` (domain-organized, not
   "phase-N" files) + C# runtime test in `BindingTests/RuntimeTestsApp/`.
   Only layer that catches ABI / calling-convention / marshalling bugs
   unit tests can't.
3. **Generator regeneration against real libraries.** Primary
   end-to-end gate: rebuild SDK in place via
   `/Users/wojo/Dev/build-and-validate.sh` (external Claude memory
   `reference_build_validate_script.md` records the path; the script
   itself is outside this repo), drop into
   `swift-dotnet-packages/local-packages/`, clear NuGet caches,
   rebuild all of swift-dotnet-packages.

Zero-regression policy: `.validation-baseline.json` pass counts,
BindingTests runtime pass count, and unit test pass count must all be
equal-or-better than baseline BEFORE committing.

Keep SDK patch at 0.8.0 during iteration (external Claude memory
`feedback_sdk_version_stable.md`; in-repo rule: never bump the SDK
patch version during iterative 0.8.x work, rebuild 0.8.0 in place and
wipe old same-version nupkgs before redeploying).
