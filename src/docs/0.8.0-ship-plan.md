# SDK 0.8.0 Ship Plan

**SDK under work:** 0.8.x (rebuild in place, don't bump patch; revisit final
version at end of Phase 3)

Companion doc: [`apple-swift-types-architecture.md`](apple-swift-types-architecture.md)
— authoritative design for the Swift-only-types supplement package implemented in
Phase 2.

---

## 1. Where we are

SDK 0.8.0 delivers Apple framework bindings (StoreKit 2, WeatherKit, TipKit,
CryptoKit, …) as NuGet packages for .NET iOS / MAUI apps. `Microsoft.iOS` is an
ObjC binding generator with no Swift-first story; that gap is what this release
fills.

**Phase 1 is done.** Every closeout session shipped:

- Generator regressions cleared (cross-module imports, `Self.AssocType` in
  `@_cdecl`, `@available` propagation, async multi-return overload scope, nested
  non-`ISwiftObject` structs).
- Stripe suite — all 11 products at SHIP (18 SB0001 → 0 across StripePayments,
  StripePaymentSheet, StripeIssuing).
- Actor-isolated instance methods — BlinkID 10 → 1, BlinkIDUX 11 → 0.
- HealthKit scheduler-write blocker cleared; Nuke / Lottie / Mappedin verified
  already at 0 SB0001.
- `AsyncHarnessEmitter` extracted; PurchaseOption overload-disambiguation parser
  fix.
- CSM async/multi-param gate-lift + Phase 4a intercept — **StoreKit2 10 → 0,
  MusicKit 5 → 0** on fresh downstream build (verified 2026-04-16). StoreKit2
  gets concrete CSM overloads for `Product.products(for:)` +
  `PromotionInfo.updateAll<T>`; MusicKit writes route through the regular async
  cdecl path with generic TypeMetadata (concrete-overload follow-up noted in
  §5).
- Defensive co-gater pass for throwing-closure facades
  (`CSharpWrapperCoGater` Step G). Strips orphaned
  `ThrowingClosureSimplificationEmitter` facades when every same-name overload
  the facade could forward to has been removed by the base pipeline. Matches
  facade→base by scope, arity, delegate-type (positional per wrapped variable),
  and pass-through parameter type (exact match with `@verbatim` normalization,
  no substring collisions). Prevents dangling self-calls that would emit
  CS1501/CS1503 on the emitted C#.

**Phase 2 (Apple Swift-only types supplement)** is designed but not yet
implemented. Full SHIP for Translation / ProximityReader / LiveCommunicationKit /
FamilyControls / WeatherKit / TipKit / CryptoKit depends on it — they currently
compile with Swift-only-type members *skipped*.

**Phase 3** is the pack + publish closeout.

## 2. 1.0 thesis

**Bridge .NET MAUI to Apple's Swift-first platform APIs, plus select third-party
Swift SDKs that fill real gaps.** Measured by what shipping packages exist and
where they run, not by skip percentages. Skip-rate reduction is over-indexed at
the 15.4% range — diminishing returns. The headline is Apple framework coverage
and multi-platform proof.

## 3. Locked-in decisions

Inputs, not options to revisit.

### 3.1 Versioning

- **Apple-framework packages:** `{SDK-major}.{SDK-minor}.{binding-rev}[-preview.N]`.
  Major.Minor mirrors the iPhoneOS SDK version (not Xcode). Patch is our binding
  revision lane. Example: `SwiftBindings.StoreKit2 26.2.0` → `26.2.1` (fix) →
  `26.3.0` (iOS 26.3 SDK) → `27.0.0-preview.1` (Xcode 27 beta).
- **Third-party packages:** mirror upstream (`SwiftBindings.Nuke 12.8.x` = Nuke 12.8.x).
- **`SwiftBindings.Apple` supplement:** per Apple SDK train major. Cross-major
  additive-only; breaking changes ship as a new package name
  (`SwiftBindings.Apple.v2`), not a breaking major.

### 3.2 `SwiftBindings.Runtime` pinning

Bounded `[0.8.0,0.9.0)` — patch releases must be ABI-compatible (no struct
layout changes, no P/Invoke signature changes). Avoids republish tax across
every Apple-framework package on every runtime patch.

### 3.3 TFM in generator-emitted csprojs

Explicit `--platform-version` CLI flag (e.g., `--platform-version 26.2` →
`net10.0-ios26.2` in both `<TargetFramework>` and `buildTransitive/`). Dynamic
`$(TargetPlatformVersion)` resolution was rejected — .NET 10 library projects
default to the oldest installed TPV, producing stale TFMs on multi-workload
machines.

### 3.4 Package layout (multi-TFM)

```
lib/net10.0-ios26.2/SwiftBindings.StoreKit2.dll
lib/net10.0-macos26.2/SwiftBindings.StoreKit2.dll
lib/net10.0-maccatalyst26.2/SwiftBindings.StoreKit2.dll
lib/net10.0-tvos26.2/SwiftBindings.StoreKit2.dll
buildTransitive/net10.0-ios26.2/SwiftBindings.StoreKit2.targets
...
runtimes/ios-arm64/native/StoreKitSwiftBindings.xcframework/...
runtimes/osx-arm64/native/StoreKitSwiftBindings.xcframework/...
...
```

### 3.5 Forward compatibility

Old nupkgs work on newer Apple workloads. Swift ABI stability since 5.0 + .NET 10
TFM precedence rules select older-versioned `lib/` entries; `runtimes/` is
RID-based not TFM-based. Verified with a `26.0 → 26.2` consumer repro.

### 3.6 Naming — framework packages vs. supplement

Two distinct lanes. Do NOT conflate.

- **Framework packages** keep their current names: `SwiftBindings.StoreKit2`,
  `SwiftBindings.WeatherKit`, `SwiftBindings.TipKit`, `SwiftBindings.CryptoKit`,
  etc. One package per Apple framework. Namespace e.g. `StoreKit2` (NOT `StoreKit`,
  to avoid collision with Microsoft.iOS's ObjC types).
- **Swift-only types supplement** is a separate package: `SwiftBindings.Apple`.
  Hosts newly-generated Apple Swift-only value types that multiple framework
  packages consume (`Foundation.Locale.Language`, `ManagedSettings.Application`,
  `CryptoKit.P256.Signing.ECDSASignature`, etc.). See companion architecture doc.
- **`SwiftBindings.Runtime`** stays SDK-agnostic. Existing legacy canonical types
  (`Foundation.Date`, `Foundation.URL`, `Foundation.Decimal`,
  `Foundation.Measurement<T>`, `ManagedSettings.Token<T>`, `SwiftUI.Text`) stay
  in Runtime indefinitely. Supplement does NOT re-emit them.
- Framework packages reference the supplement via `TypeOwnerRegistry`-driven
  transitive `PackageReference`, pulled only when a consumer actually references
  a supplement-owned Swift identity.

### 4.4 Swift-only Apple type infrastructure

`SwiftBindings.Apple` package implemented per
[`apple-swift-types-architecture.md`](apple-swift-types-architecture.md):

- Metadata manifest embedded under `SwiftBindings.Sdk/tools/`.
- Monolithic single assembly first; multi-assembly deferred.
- `TypeOwnerRegistry` with per-type override precedence.
- VWT-backed opaque storage default; per-type sequential-layout whitelist after
  validation (frozen=true is necessary but not sufficient).
- Demand-driven prototyping mode via canonical project reference (not duplicate
  compile).

- CI validation against live SDK symbols (accessor exists, size/alignment match,
  VWT copy/destroy smoke, optional/container round-trip).
- Framework-linkage blast-radius smoke test (NativeAOT single-framework app).

## 5. Remaining small follow-ups from Phase 1

Not ship blockers, but tracked so they don't get lost:

- **MusicKit concrete CSM overloads — partial.** `AddAsync<T: MusicLibraryAddable>`
  on `MusicLibrary` now emits concrete per-conformer overloads (declarative hint
  in `specialization-hints.json`). `CreatePlaylistAsync<S,T>` / `EditAsync<S,T>` /
  `InsertAsync<S,T>` still emit through the generic-TypeMetadata async cdecl
  path because their `<S: Swift.Sequence, T: ... where S.Element == T>` shape
  requires `Swift.Array<MusicKit.X>` conformers under `Swift.Sequence`, which
  would cross-pollute non-MusicKit modules without additional module scoping
  in the hints registry. Runtime behavior is correct either way; the remaining
  three methods are UX-only follow-ups deferred until the hints registry gains
  module scoping.

## 6. Phase 2 — Apple Swift-only types supplement

**Goal:** Implement the supplement per
[`apple-swift-types-architecture.md`](apple-swift-types-architecture.md). After
Phase 2, the generator can emit references to `SwiftBindings.Apple` for Swift-only
Apple types that today force member skips.

No hard 0.8.0 deadline on this phase — pace for correctness. The design doc is
the authoritative spec; this section only enumerates the implementation milestones.

### 6.1 Implementation milestones

1. **Metadata manifest format.** Design the JSON/binary schema for the third
   artifact (accessor symbols, size/alignment, VWT pointers, conformance descriptor
   names, availability). Store under `src/Swift.Bindings.Sdk/tools/apple-types-manifest/`.
   Design schema so it can later migrate to a standalone
   `SwiftBindings.Apple.Metadata` data package without format changes.
2. **Manifest generator.** Build the Apple-SDK ABI-JSON → manifest pipeline.
   Driven by the same ABI JSON the generator already consumes for framework packages.
3. **`SwiftBindings.Apple` package skeleton.** New project under
   `src/Swift.Bindings.Apple/` emitting a monolithic assembly targeting all four
   Apple TFMs. CI builds the assembly from the manifest on every commit.
4. **VWT-backed opaque storage emission.** Extend the emitter to produce
   VWT-backed storage by default for supplement-owned types. Per-type
   sequential-layout whitelist behind a gated flag (requires size/alignment
   validated, copy/destroy trivial, runtime round-trip test passing).
5. **`TypeOwnerRegistry` with per-type override precedence.**
   1. Per-type owner override first (legacy canonical types pinned to
      `SwiftBindings.Runtime`).
   2. Module default second (Apple modules → `SwiftBindings.Apple`; third-party
      → their generated binding package).
   3. Same-module-being-generated → local.
6. **Generator integration.** Type DB resolver consults `TypeOwnerRegistry`.
   Consumer csprojs emit `PackageReference` to `SwiftBindings.Apple` when the
   registry resolves any referenced type to it.
7. **Demand-driven prototyping mode.** SDK MSBuild targets emit a supplement
   project into `obj/` for prototyping; referenced as a project dependency
   (NOT compiled as duplicate types into each consumer assembly — identity
   must stay canonical).
8. **Cross-module type identity test.** Permanent regression guardrail: two
   consumer assemblies reference the supplement, instantiate a Swift-only type
   in one, pass to the other, assert `typeof(T)` matches.
9. **Framework-linkage blast-radius smoke test.** NativeAOT single-framework
   app — does referencing one framework package pull in other framework binaries
   it doesn't use? If yes, mitigate (lazy P/Invoke, per-module conditional
   symbols, runtime probing) before Phase 3 ship.
10. **CI validation against live SDK.** Smoke test that supplement metadata
    accessor symbols exist on the current Apple SDK, size/alignment match,
    VWT copy/destroy works, optional/container round-trip works.
11. **Bootstrap supplement against the 7 target frameworks.** Discover every
    Swift-only type referenced by Translation, ProximityReader,
    LiveCommunicationKit, FamilyControls, WeatherKit, TipKit, CryptoKit.
    Populate the manifest. Regenerate all 7 — members that Phase 1 skipped
    should now bind.

### 6.2 Phase 2 deliverable

`SwiftBindings.Apple` package builds, passes CI gates, is referenced by the 7
target Apple framework packages. Generator's demand-driven prototyping mode works
for local iteration.

## 7. Phase 3 — Ship & publish

### 7.1 Steps

1. **Regenerate the 7 Apple frameworks** against the supplement-aware generator.
   Verify every previously-skipped Swift-only-type member now binds. `nuke validate`
   SB0001 counts for these frameworks should reach their floor (permanent-limit
   items only).
2. **Wire `apple-frameworks/` into swift-dotnet-packages Nuke pipeline.**
   Extend `Build.Xcframework.cs:DiscoverLibraries` to handle SDK-sourced
   multi-TFM projects. `BuildLibrary`, `Pack`, `PackValidate`, `BuildAndPackRelease`,
   `ListChangedLibraries` must all see apple-framework packages.
3. **Stripe hardening.** NativeAOT validation across all Stripe sub-products,
   sample app polish, any residual test-coverage gaps.
4. **Pack all packages.** `nuke pack --version 0.8.0` (or `0.9.0` — see §7.2) →
   `SwiftBindings.Sdk`, `SwiftBindings.Runtime`, `SwiftBindings.Templates`,
   `SwiftBindings.Apple`, plus every framework package.
5. **Local-feed regression validation.** Drop nupkgs into
   `swift-dotnet-packages/local-packages/`, clear NuGet caches, rebuild all of
   swift-dotnet-packages on both sim and device. Run the `regression-validation`
   skill (end-to-end Mono JIT simulator + NativeAOT device).
6. **Publish to nuget.org.** All packages.
7. **Commit swift-dotnet-packages.** Only AFTER nuget.org publish succeeds, per
   `feedback_no_commit_packages.md`.

### 7.2 Version-number review

At end of Phase 3, decide 0.8.0 vs 0.9.0:

- **Stay at 0.8.0** if cumulative changes are compatible with 0.8.0's already-
  published lane (runtime ABI unchanged, no framework-package breaking changes).
- **Bump to 0.9.0** if cumulative churn is large enough: a new
  `SwiftBindings.Apple` package shipping for the first time, generator internals
  significantly refactored (`TypeOwnerRegistry`, supplement emission),
  runtime ABI touched. Note that 0.8.0's `SwiftBindings.Runtime` pinning
  `[0.8.0,0.9.0)` means any runtime ABI change forces 0.9.0 anyway.

Default bias: **bump to 0.9.0**. The supplement is a genuinely new artifact and
`Runtime` may pick up non-ABI-trivial changes during Phase 2.

## 9. Deferred / post-ship

- **Kingfisher (102 SB0001)** — fluent builder chains on generic wrapper types
  (`KF.Builder`, `KingfisherWrapper<UIImageView>`). Architectural; not tractable
  without generator redesign. Document as unsupported for 1.0; revisit post-ship.
- **ActivityKit `Activity<T>.request/update/end`** — permanent (app-defined
  `ActivityAttributes`).
- **`ActorIsolatedAsyncStream`** — BlinkIDUX `BlinkIDEventStream.stream` (plain
  non-async getter on a Swift `actor` returning `AsyncStream<[UIEvent]>`).
  Actor-isolated stream properties need async-dispatch-through-executor
  property wrapping.
- **Swift variadic parameter packs** (12 WeatherKit methods) — permanent, no
  C# equivalent.
- **SynthesizedCodable pruning** (~159 items) — compiler-internal, by design.
- **Result-builder DSL** (9 TipKit items) — `@_alwaysEmitIntoClient`, no binary
  symbol.
- **MusicKit 3 indirect-buffer ABI types** (MusicLibrarySection, etc.).
- **Full `UnsafeRawBufferPointer` bridging** — split into pointer+length C params,
  bridge to `ReadOnlySpan<byte>`. CryptoKit currently skips these methods.
- **Framework-package renaming to `SwiftBindings.Apple.*`** — only at a
  deliberate major-version cleanup.

## Appendix — Testing layers (required per session)

Every session that touches generator output must produce evidence at all three
layers before sign-off.

1. **Unit tests** (`nuke test`, ~2 min). Exercise the exact code path changed.
2. **BindingTests** (`nuke runtime-tests-simulator`, ~3 min; `nuke runtime-tests-device`
   when calling conventions / marshalling change, ~5 min). Swift fixture in
   `BindingTests/Sources/SwiftBindingsTestLib/` (domain-organized, not "phase-N"
   files) + C# runtime test in `BindingTests/RuntimeTestsApp/`. Only layer that
   catches ABI / calling-convention / marshalling bugs unit tests can't.
3. **Generator regeneration against real libraries.** The generator CLI is the
   final arbiter. Primary end-to-end gate: rebuild SDK in place
   (`reference_build_validate_script.md`), drop into
   `swift-dotnet-packages/local-packages/`, clear NuGet caches, rebuild all of
   swift-dotnet-packages.

Zero-regression policy: `.validation-baseline.json` pass counts, BindingTests
runtime pass count, and unit test pass count must all be equal-or-better than
baseline BEFORE committing.

Keep SDK patch at 0.8.0 during Phase 1/2 iteration
(`feedback_sdk_version_stable.md`) — rebuild in place, wipe old same-version
nupkgs.
