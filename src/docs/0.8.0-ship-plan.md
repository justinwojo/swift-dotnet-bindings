## 1. Where we are

SDK 0.8.0 ships Apple framework bindings (StoreKit 2, WeatherKit, TipKit,
CryptoKit, …) as NuGet packages for .NET iOS / MAUI apps. `Microsoft.iOS`
is an ObjC binding generator with no Swift-first story; that gap is what
this release fills.

**Phase 1 (generator + closeouts): done.** Stripe suite, BlinkID/BlinkIDUX,
HealthKit scheduler, StoreKit2 + MusicKit CSM, defensive co-gater for

`RichTextKit`, `WhatsNewKit`, `YouTubePlayerKit` — which are allowed to
report nonzero C# compile errors without failing the gate). 61/61 Swift
wrapper compile.

**Phase 2 (`SwiftBindings.Apple` supplement): done** (commits
`41d00b1e` → `4f2ae4ae`). All 7 target frameworks — Translation,
ProximityReader, LiveCommunicationKit, FamilyControls, WeatherKit, TipKit,
CryptoKit — at their permanent-skip floor with Swift-only-type references
routed to the supplement. Architectural machinery (`TypeOwnerRegistry`,
manifest pipeline, VWT-backed storage, cross-module identity test,
live-SDK validation, blast-radius smoke) all in place. Design doc:
[`apple-swift-types-architecture.md`](apple-swift-types-architecture.md).

**Phase 3 (pack + publish): the remaining work.** See §7.

## 2. 1.0 thesis

**Bridge .NET MAUI to Apple's Swift-first platform APIs, plus select
third-party Swift SDKs that fill real gaps.** Measured by shipping
packages and where they run, not by skip percentages. Skip rate at 15.1%
is diminishing returns — headline is Apple framework coverage and
multi-platform proof.

## 3. Locked-in decisions

Inputs, not options to revisit.

### 3.1 Versioning

- **Apple-framework packages:** `{SDK-major}.{SDK-minor}.{binding-rev}[-preview.N]`.
  Major.Minor mirrors iPhoneOS SDK version (not Xcode). Patch is our binding
  revision lane. Example: `SwiftBindings.StoreKit2 26.2.0` → `26.2.1` (fix)
  → `26.3.0` (iOS 26.3 SDK) → `27.0.0-preview.1` (Xcode 27 beta).
- **Third-party packages:** mirror upstream (`SwiftBindings.Nuke 12.8.x` = Nuke 12.8.x).
- **`SwiftBindings.Apple` supplement:** per Apple SDK train major. Cross-major
  additive-only; breaking changes ship as a new package name
  (`SwiftBindings.Apple.v2`), not a breaking major.

### 3.2 `SwiftBindings.Runtime` pinning

Bounded `[0.8.0,0.9.0)` — patch releases must be ABI-compatible (no struct
layout changes, no P/Invoke signature changes). Avoids republish tax across
every Apple-framework package on every runtime patch.

### 3.3 TFM in generator-emitted csprojs

Explicit `--platform-version` CLI flag (e.g., `--platform-version 26.2` →
`net10.0-ios26.2` in both `<TargetFramework>` and `buildTransitive/`). Dynamic
`$(TargetPlatformVersion)` resolution was rejected — .NET 10 library projects
default to the oldest installed TPV, producing stale TFMs on multi-workload
machines.

### 3.4 Package layout (multi-TFM)

```
lib/net10.0-ios26.2/SwiftBindings.StoreKit2.dll
lib/net10.0-macos26.2/SwiftBindings.StoreKit2.dll
lib/net10.0-maccatalyst26.2/SwiftBindings.StoreKit2.dll
lib/net10.0-tvos26.2/SwiftBindings.StoreKit2.dll
buildTransitive/net10.0-ios26.2/SwiftBindings.StoreKit2.targets
...
runtimes/ios-arm64/native/StoreKitSwiftBindings.xcframework/...
runtimes/osx-arm64/native/StoreKitSwiftBindings.xcframework/...
...
```

### 3.5 Forward compatibility

Old nupkgs work on newer Apple workloads. Swift ABI stability since 5.0 + .NET 10
TFM precedence rules select older-versioned `lib/` entries; `runtimes/` is
RID-based not TFM-based. Verified with a `26.0 → 26.2` consumer repro.

### 3.6 Naming — framework packages vs. supplement

Two distinct lanes. Do NOT conflate.

- **Framework packages** ship under the flat `SwiftBindings.{Framework}`
  scheme: `SwiftBindings.StoreKit2`, `SwiftBindings.WeatherKit`, etc. One
  package per Apple framework. Matches the third-party convention
  (`SwiftBindings.Nuke`, `SwiftBindings.Lottie`) — Apple framework names
  (StoreKit2, WeatherKit, CryptoKit, …) are already unambiguous, so an
  `Apple.` qualifier would be informational, not disambiguating, and would
  introduce a two-tier convention. Namespace e.g. `StoreKit2` (NOT
  `StoreKit`, to avoid collision with Microsoft.iOS ObjC types).
- **Swift-only types supplement** is a separate package: `SwiftBindings.Apple`
  (singular). The `Apple` segment lives on the supplement because the
  supplement's role IS "Apple-platform Swift-only value types"; the framework
  packages don't repeat it.
  Hosts newly-generated Apple Swift-only value types (`Foundation.Locale.Language`,
  `ManagedSettings.Application`, `CryptoKit.P256.Signing.ECDSASignature`, …).
- **`SwiftBindings.Runtime`** stays SDK-agnostic. Existing legacy canonical
  types (`Foundation.Date`, `.URL`, `.Decimal`, `.Measurement<T>`,
  `ManagedSettings.Token<T>`, `SwiftUI.Text`) stay in Runtime indefinitely.
  Supplement does NOT re-emit them.
- Framework packages reference the supplement via `TypeOwnerRegistry`-driven
  transitive `PackageReference`, pulled only when a consumer actually
  references a supplement-owned Swift identity.

## 7. Phase 3 — Ship & publish

**This is the active work.**

### 7.1 Steps

1. **Wire `apple-frameworks/` into swift-dotnet-packages Nuke pipeline.**
   (Out of this repo; in `swift-dotnet-packages`.) Extend
   `Build.Xcframework.cs:DiscoverLibraries` to handle SDK-sourced
   multi-TFM projects. `BuildLibrary`, `Pack`, `PackValidate`,
   `BuildAndPackRelease`, `ListChangedLibraries` must all see
   apple-framework packages.
2. **Stripe hardening.** NativeAOT validation across all Stripe
   sub-products, sample-app polish, residual test-coverage gaps.
   Primarily swift-dotnet-packages work.
3. **Pack all packages.** `nuke pack --version 0.8.0 --apple-version 26.0.0`
   (or `0.9.0` — see §7.2) → `SwiftBindings.Sdk`, `.Runtime`,
   `.Templates`, `.Apple`, plus every framework package.
4. **Pre-publish licensing re-check.** Run the "Before each major
   publish" checklist in [`src/legal/RATIONALE.md`](../legal/RATIONALE.md)
   (three URLs) before the first `SwiftBindings.Apple 26.0.0` publish.
   The in-repo licensing artifacts (NOTICE, package metadata,
   CONTRIBUTING) are already in place.
5. **Local-feed regression validation.** Drop nupkgs into
   `swift-dotnet-packages/local-packages/`, clear NuGet caches,
   rebuild on both sim and device. Run the `regression-validation`
   skill (end-to-end Mono JIT simulator + NativeAOT device).
6. **Publish to nuget.org.** All packages.
7. **Commit swift-dotnet-packages.** Only AFTER nuget.org publish
   succeeds (external Claude memory: `feedback_no_commit_packages.md`
   lives in the assistant's project memory, not this repo; the rule is
   simply "don't commit the consumer repo until the referenced SDK
   version is live on nuget.org").

### 7.2 Version-number review

At end of Phase 3, decide 0.8.0 vs 0.9.0:

- **Stay at 0.8.0** if cumulative changes are compatible with 0.8.0's
  already-published lane (runtime ABI unchanged, no framework-package
  breaking changes).
- **Bump to 0.9.0** if cumulative churn is large: a new
  `SwiftBindings.Apple` package shipping for the first time, generator
  internals significantly refactored (`TypeOwnerRegistry`, supplement
  emission), runtime ABI touched. Note 0.8.0's `SwiftBindings.Runtime`
  pinning `[0.8.0,0.9.0)` means any runtime ABI change forces 0.9.0
  anyway.

Default bias: **bump to 0.9.0**. Supplement is a genuinely new artifact
and Runtime picked up non-ABI-trivial changes in Phase 2.

### 7.3 Release lanes

Version cadences of the four in-repo packages are formally decoupled
(§3.1, §3.6, architecture doc §Decoupling). Post-ship, this manifests
as two release lanes — identified by **tag prefix**, not by long-lived
branches.

**SDK lane** — `SwiftBindings.Sdk`, `SwiftBindings.Runtime`,
`SwiftBindings.Templates`.

- Tag: `sdk-v{version}` (e.g., `sdk-v0.8.1`)
- Triggers: generator bug fix, emitter improvement, Runtime non-ABI
  change.
- Runtime ABI must stay within `[0.8.0,0.9.0)`. Any ABI break forces
  the next minor (see §3.2).

**Apple lane** — `SwiftBindings.Apple`.

- Tag: `apple-v{version}` (e.g., `apple-v26.0.1`)
- Triggers: new Apple type added to manifest, iOS SDK train move,
  supplement bug fix, VWT drift correction.
- Pins Sdk/Runtime at their currently-published versions.
- Cross-major additive-only invariant applies (architecture doc §5).

**Framework packages** (`SwiftBindings.StoreKit2`, `SwiftBindings.WeatherKit`, …) live
in `swift-dotnet-packages` and release from that repo's own tags. They
pin a specific Sdk + Apple-train major at build time and float Apple
minor/patch via the open-ended `[26.0.0,)` range — an Apple supplement
patch does NOT cascade into framework-package republishes.

#### 7.3.1 Branching

Release from `main` when possible. Tags carry the durable release
identity — branches don't need to.

Create a short-lived `release/{lane}-{version}` branch **only** when:

- a last-minute release-note or version-stamp change needs isolation
  from ongoing `main` work;
- a hotfix must ship off an older commit (e.g., `apple-v26.0.1` off
  `apple-v26.0.0`'s SHA, bypassing unreleased `main` work);
- stabilization requires holding the release state while `main` moves.

Delete or archive a release branch after its tag is pushed. Avoid a
long-lived `release` branch — it becomes a second `main` with unclear
ownership, and ambiguity about whether a tag reflects `main` state or
branch state.

#### 7.3.2 Release manifest (CI allow-list)

Each release carries a `release-manifest.json` at repo root. Its job
is **release-intent enforcement**, not build orchestration.

```json
{
  "lane": "apple",
  "tag": "apple-v26.0.1",
  "packages": [
    {
      "id": "SwiftBindings.Apple",
      "version": "26.0.1",
      "summary": "Adds X and fixes Y."
    }
  ],
  "sdkRuntimeRange": "[0.8.0,0.9.0)",
  "builtAgainst": {
    "SwiftBindings.Sdk": "0.8.0",
    "SwiftBindings.Runtime": "0.8.0"
  }
}
```

CI fails the release job if any of the following hold:

- Apple-lane manifest contains `SwiftBindings.Sdk`, `.Runtime`, or
  `.Templates` in `packages` (or vice versa for SDK lane).
- The produced nupkg set differs from the manifest's `packages` list.
- Any emitted `PackageReference` dependency range differs from the
  manifest (e.g., supplement's Runtime range doesn't match
  `sdkRuntimeRange`).
- The pushed git tag doesn't match the manifest's `tag` field.

The manifest answers "was this package supposed to be part of this
release train?" Content-hash skip logic answers a different question
("did the artifact content change?") and is unsafe as a publish gate:
metadata-only changes (readme, dependency range, release notes) must
republish even when binary content is identical, and accidental NuGet
publishes are effectively permanent.

#### 7.3.3 Triggering a release

1. Author `release-manifest.json` on `main` (or short-lived branch if
   justified per §7.3.1).
2. Land lane-specific fixes; CI enforces zero-regression baselines per
   Appendix and the manifest allow-list per §7.3.2.
3. Push annotated tag: `git tag {lane}-v{version} && git push origin
   {lane}-v{version}`. CI tag-trigger runs `nuke pack
   --release-manifest release-manifest.json`, publishes declared
   packages to nuget.org, drafts the GitHub release (see §7.4).
4. Edit the drafted release to finalize notes, publish.
5. Commit `swift-dotnet-packages` only AFTER nuget.org publish
   succeeds (same rule as §7.1 step 7).
6. Delete the release branch if one was created.

#### 7.3.4 Coupled releases

SDK and Apple are **release lanes**, not development lanes. A
user-visible fix may require changes to both; ship them in order, not
simultaneously.

**Rule:** if an Apple supplement change requires a generator or runtime
change, publish the SDK lane first, then publish the Apple lane against
the newly-published Sdk/Runtime.

The Apple lane's promise is "pins Sdk/Runtime at their currently-
published versions." If a Runtime fix isn't yet on nuget.org, the
Apple lane can't honestly pin it. Landing the Runtime fix into both an
in-flight SDK release and an in-flight Apple release at once weakens
that boundary.

Expect coupled releases to be **common** for the first few cycles.
Adding a new Apple type often surfaces a generator projection case, a
metadata accessor gap, or a `TypeOwnerRegistry` assumption — each
requiring SDK changes before the supplement itself can ship. Once the
supplement manifest format, VWT machinery, and framework-package
patterns stabilize, the Apple lane should become more independent.

#### 7.3.5 Initial 0.8.0 ship

All four packages are new and must anchor at the same commit. One-time
shape:

- Release from `main` (or short-lived `release/0.8.0` branch for final
  stabilization if needed).
- Pack command: `nuke pack --version 0.8.0 --apple-version 26.0.0`
  (same as §7.1 step 3 — single-shot, no release manifest needed since
  every in-repo package ships).
- **Dual-tag the same commit:** `sdk-v0.8.0` AND `apple-v26.0.0`.
  Seeds both lanes with the same starting point for future `git diff`
  and compare URLs. Apply both tags at ship time, not retroactively.
- **One GitHub Release**, attached to `sdk-v0.8.0`, titled
  `[Initial Ship] SDK 0.8.0 + Apple 26.0.0`. Body explicitly enumerates
  all four packages and notes the companion `apple-v26.0.0` tag sits
  on the same commit. No separate Apple release object.

Future lane-specific compares still work: SDK's next release compares
from `sdk-v0.8.0`, Apple's next from `apple-v26.0.0`. Provenance lives
in the dual tags; the human-facing UX is one release body.

### 7.4 GitHub release conventions

One Releases stream, lane-prefixed for scannability. Discovery is
primarily via nuget.org — GitHub Releases serve repo-watchers and
provide the "what changed" narrative per version.

#### 7.4.1 Tag format

- `sdk-v{version}` — SDK lane
- `apple-v{version}` — Apple supplement lane
- 0.8.0 initial ship: dual-tagged `sdk-v0.8.0` + `apple-v26.0.0` on
  the same commit

#### 7.4.2 Release title format

```
[SDK 0.8.1] <one-line summary>
[Apple 26.0.1] <one-line summary>
[Initial Ship] SDK 0.8.0 + Apple 26.0.0
```

Prefix does the visual filtering work on the Releases page.

#### 7.4.3 Release body template

```markdown
**Lane:** <SDK | Apple | Initial ship>
**Packages published:** <list with versions>
**SDK/Runtime dependency:** <version range | "unchanged from prior release">
**Change type:** <Additive-only patch | Additive-only minor | Major>

### Added
- ...

### Fixed
- ...

### Changed
- ...

### Links
- NuGet: <per-package nuget.org links>
- Full diff: <GitHub compare URL>
- Companion tag: <for dual-tagged commits — e.g., initial ship>
```

The `SDK/Runtime dependency: unchanged` line on Apple-lane releases is
the key signal that tells SDK-lane watchers this release does not
affect them.

#### 7.4.4 "Latest" badge handling

GitHub flags only one release per repo as "Latest." The badge floats
to whichever lane most-recently shipped — accept this rather than
fight it.

Compensate with a README badge row showing both lane-latests pulled
live from nuget.org:

```markdown
[![SDK](https://img.shields.io/nuget/v/SwiftBindings.Sdk?label=SDK)](https://www.nuget.org/packages/SwiftBindings.Sdk)
[![Apple](https://img.shields.io/nuget/v/SwiftBindings.Apple?label=Apple)](https://www.nuget.org/packages/SwiftBindings.Apple)
[![Runtime](https://img.shields.io/nuget/v/SwiftBindings.Runtime?label=Runtime)](https://www.nuget.org/packages/SwiftBindings.Runtime)
```

Shields.io auto-polls NuGet, so these stay current without manual
maintenance.

#### 7.4.5 NuGet release notes (separate from GitHub)

Stamp `<PackageReleaseNotes>` into each nuspec at pack time — 1–3
lines per package, linking back to the GitHub release URL. Audience:
NuGet users browsing version history on nuget.org who never see the
GitHub side.

`Build.Pack.cs` is the natural place to template these from the
release manifest. Each package's release note entry composes as:

```
{lane} {version} — {one-line summary from manifest}
Full notes: https://github.com/justinwojo/swift-dotnet-bindings/releases/tag/{tag}
```

### 7.5 Pipeline implementation status

`.github/workflows/release.yml` is a working production release
pipeline, not a stub. It handles validation → pack → nuget.org push →
git tag → GitHub release → LLM-generated release notes. But it is
wired for the pre-0.8.0 three-package model and does not know
`SwiftBindings.Apple` exists. Both the 0.8.0 initial ship and the
post-ship two-lane strategy require concrete workflow edits.

#### 7.5.1 What's already wired

Trigger: push to `release/**` branch. Extracts `VERSION` from branch
name (e.g., `release/0.8.0` → `0.8.0`). Dry-run suffix `-dryrun.N`
supported. Prerelease detection via `-preview|alpha|beta|rc` suffix.

Flow:

1. Validation: `dotnet nuke test` + `dotnet nuke binding-tests
   --strict` + iOS Simulator tests.
2. Preflight nuget.org idempotency check (refuses inconsistent state
   where some packages at the target version already exist and others
   don't).
3. `dotnet nuke pack --version $VERSION --output-dir artifacts`.
4. `dotnet nuget push` to nuget.org with `--skip-duplicate`, using
   `NUGET_API_KEY` secret.
5. Create `v${VERSION}` git tag.
6. Generate release notes via Grok API (`XAI_API_KEY` secret; falls
   back to `gh release create --generate-notes` when unset).
7. `gh release create v${VERSION}` with `.nupkg` files attached.

Working infrastructure — extend, don't rewrite.

#### 7.5.2 Gaps for 0.8.0 initial ship

The workflow enumerates only `SwiftBindings.Runtime`, `.Sdk`, and
`.Templates`. Minimum edits for 0.8.0 to actually publish the Apple
supplement:

1. **Pack step** (`release.yml:201-205`). Add `--apple-version`:
   ```yaml
   dotnet nuke pack
     --version ${{ steps.version.outputs.version }}
     --apple-version 26.0.0
     --output-dir ${{ github.workspace }}/artifacts
   ```
   For 0.8.0 the Apple version can be hardcoded; post-ship it comes
   from the release manifest.
2. **Preflight step** (`release.yml:182`). Extend the package-ID loop
   to include `SwiftBindings.Apple` at its own version `26.0.0` (NOT
   the SDK version — the preflight must query two distinct versions).
3. **Publish step** (`release.yml:220-229`). Add
   `artifacts/SwiftBindings.Apple.${APPLE_VERSION}.nupkg` to the push
   loop. Needs a separate variable for the Apple version.
4. **Grok release-notes prompt** (`release.yml:319`). Update the
   "Packages" table instruction to list four packages with their two
   distinct versions (SDK version for three, Apple version for the
   supplement).
5. **Dual tag.** Simplest path: let the workflow push `v0.8.0` as
   today, then manually push `sdk-v0.8.0` and `apple-v26.0.0` tags on
   the same commit post-release. Alternative: extend the workflow's
   tag step to push all three. §7.3.5 accepts either path.

Estimated effort: ~1 hour of YAML edits. None of these are
speculative — each has a specific line number above.

#### 7.5.3 Gaps for post-ship two-lane releases

Shipping post-0.8.0 releases under the §7.3 lane model requires:

1. **Branch-name parsing** (`release.yml:152-174`). Current regex
   extracts `VERSION` from `release/${VERSION}`. Update to extract
   `LANE` and `VERSION` from `release/{lane}-{version}` (e.g.,
   `release/sdk-0.8.1` → `LANE=sdk`, `VERSION=0.8.1`). The §7.3.1
   guidance also allows release-from-main; in that case the workflow
   trigger needs a tag-push trigger variant.
2. **Lane-aware publish list.** SDK lane pushes
   `Runtime`/`Sdk`/`Templates`; Apple lane pushes only
   `SwiftBindings.Apple`. Switch on `LANE`.
3. **Lane-prefixed tag + title.** Push `{lane}-v{version}` instead of
   `v{version}`. Release title `[SDK {version}] …` or
   `[Apple {version}] …` per §7.4.2.
4. **Lane-aware Grok prompt.** Either fork the prompt template on
   `LANE`, or accept less-curated notes and fall back to
   `--generate-notes` for Apple-lane releases.
5. **`release-manifest.json` parsing + CI allow-list** (§7.3.2). New
   workflow step that reads the manifest at repo root and validates:
   - `lane` matches branch/tag-derived lane;
   - `tag` matches the tag about to be pushed;
   - `packages[]` matches the lane (SDK lane rejects Apple, and vice
     versa);
   - produced nupkg set matches `packages[]`;
   - emitted dependency ranges match `sdkRuntimeRange`.
   Fail the job on mismatch.
6. **Nuke `--release-manifest` flag.** `Build.Pack.cs` accepts a
   manifest path, parses it, stamps versions, and emits only declared
   packages. Can stay thin — the workflow may pre-parse and pass
   `--version` / `--apple-version` as CLI args derived from the
   manifest, leaving the Nuke side unchanged.
7. **NuGet `<PackageReleaseNotes>` stamping.** Pipe each package's
   manifest `summary` field into its nuspec at pack time (§7.4.5).

Estimated effort: ~2–4 hours across YAML + small C# additions.

**Non-blocking for 0.8.0.** Build this when the first post-ship lane
release is actually queued, not preemptively. By then the specific
corner cases (how coupled the first SDK/Apple patch pair is, what the
release notes actually need to say) will be concrete instead of
hypothetical.

## 8a. Post-ship operations (supplement)

If `SwiftBindings.Apple` ships with a bad manifest, wrong metadata
accessor, or over-broad framework linkage, the mitigation path is:

1. **Yank or deprecate a bad package.** `nuget.org` lists the package →
   **Manage Package** → **Listed: No** removes it from search and new
   restores (existing restores still resolve). If a version must be
   pulled entirely, contact nuget.org support — the registry does not
   let authors hard-delete a version. For broadcasts, attach a
   deprecation message: "Use `SwiftBindings.Apple 26.0.1`; 26.0.0 had
   an invalid VWT for X."
2. **Ship the fixed patch.** Increment the binding-revision digit
   (`26.0.0` → `26.0.1` — NOT a major bump, the Apple SDK train is
   unchanged). Cross-major additive-only still applies. Keep the old
   package listed-but-deprecated long enough for transitive consumers
   to upgrade.
3. **Local manifest / prototype override.** Consumers who need a patch
   before the NuGet fix lands can set the `SwiftAppleSupplementPrototypeDir`
   SDK property (see §3) to emit a prototype `SwiftBindings.Apple.Prototype.csproj`
   into their `obj/` and patch supplement sources locally. Canonical
   identity is preserved via matching `AssemblyName=SwiftBindings.Apple`
   + `RootNamespace=Swift` in the prototype project — consumer code is
   unchanged.
4. **Field diagnostics — "type resolved to supplement but package
   reference / method symbol is missing."**
   - Confirm the consumer csproj has a `<PackageReference
     Include="SwiftBindings.Apple" Version="..." />` *or* the prototype
     `ProjectReference` (check the generated `binding-metadata.props` /
     `apple-supplement.props` under `obj/`).
   - If the reference exists but the method symbol is missing, dump the
     supplement's metadata accessor with `nm -gU <dylib> | grep
     <mangled>` against the on-device framework to confirm the symbol
     exists in the platform SDK version the consumer targets.
   - For VWT-opaque types, verify the accessor's `library` matches the
     runtime framework path — a mis-mapped `library` surfaces as
     `DllNotFoundException` at load, not at resolve.

## Appendix — Testing layers (required per session)

Every session that touches generator output must produce evidence at
all three layers before sign-off.

1. **Unit tests** (`nuke test`, ~2 min). Exercise the exact code path
   changed.
2. **BindingTests** (`nuke runtime-tests-simulator`, ~3 min;
   `nuke runtime-tests-device` when calling conventions / marshalling
   change, ~5 min). Swift fixture in
   `BindingTests/Sources/SwiftBindingsTestLib/` (domain-organized, not
   "phase-N" files) + C# runtime test in `BindingTests/RuntimeTestsApp/`.
   Only layer that catches ABI / calling-convention / marshalling bugs
   unit tests can't.
3. **Generator regeneration against real libraries.** Primary
   end-to-end gate: rebuild SDK in place via
   `/Users/wojo/Dev/build-and-validate.sh` (external Claude memory
   `reference_build_validate_script.md` records the path; the script
   itself is outside this repo), drop into
   `swift-dotnet-packages/local-packages/`, clear NuGet caches,
   rebuild all of swift-dotnet-packages.

Zero-regression policy: `.validation-baseline.json` pass counts,
BindingTests runtime pass count, and unit test pass count must all be
equal-or-better than baseline BEFORE committing.

Keep SDK patch at 0.8.0 during iteration (external Claude memory
`feedback_sdk_version_stable.md`; in-repo rule: never bump the SDK
patch version during iterative 0.8.x work, rebuild 0.8.0 in place and
wipe old same-version nupkgs before redeploying).
