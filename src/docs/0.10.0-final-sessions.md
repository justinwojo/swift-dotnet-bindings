## How to run a session

1. Open a fresh Claude Code session in `/Users/wojo/Dev/swift-bindings` on `main`.
2. Hand it this doc + "do Session N."
3. Claude reads CLAUDE.md, this doc, and every in-scope per-bug doc in full.
4. Implement the fix plus BindingTests at the right layer (per CLAUDE.md "BindingTests are the real end-to-end gate").
5. Run the session-end gates listed below.
6. One codex-review pass — fix High / Medium inline, surface Low for accept-or-fix, commit. Do not loop codex-review.
7. `git mv` any newly-resolved docs to `src/docs/Resolved/` in the same commit.
8. Ratchet `.validation-baseline.json` if numbers improved; ratchet `runtime_pass_count_*` baselines if `--sim` / `--device` deltas are positive. Baseline bumps in a separate commit.

## Session 4 — EveryProtocol proxy forward dispatch

**Sizing:** Split into 4a + 4b after audit. The 4a/4b boundary is the closure-shape matrix, not "infra-vs-coverage": the audit found that **non-closure protocol methods already dispatch correctly** through `EmitMethodReceiver`. The open gap is closure-receiving protocol methods/properties, where both Swift (`fatalError`) and C# (`throw NotSupportedException`) emit stubs today.

### Background

**Doc:** `src/docs/Resolved/gap-0.10.0-everyprotocol-and-existentials.md`. Cases 1 and 2 (Swift→C# direction: `any Foo` existentials project to `IFoo`) are resolved. Case 3 (the proxy forward-dispatch path used when C# code passes an `IFoo` instance back to Swift) is the remaining open gap **for closure-bearing protocol members only** — every other member shape on the proxied protocol already forwards through the local vtable to the C# implementation.

When a closure-bearing method like `func onComplete(handler: @escaping () -> Void)` is invoked on a C#-implemented proxy, today's emit:

- Swift extension body: `fatalError("EveryProtocol: closure method '...' cannot be dispatched through vtable")` (`EveryProtocolEmitter.EmitClosureMethodStub`).
- C# proxy receiver: `[UnmanagedCallersOnly]` trampoline that throws `NotSupportedException` (`ProtocolProxyEmitter.EmitNotSupportedMethodReceiver`).
- Vtable shape: closure-bearing methods are excluded from vtable-field emission entirely (`EveryProtocolEmitter.cs:316`).

The retrospective (`src/docs/post-0.10.0-retrospective.md`) flagged this as a worse failure mode than most of the 46 bugs we just closed: it's a known runtime-throw on a common Swift API pattern (Starscream, RxSwift, Nuke, Stripe delegate protocols, Lottie value providers).

### Built on

- Session 2's wrapper-symbol contract — proxy emits one wrapper per protocol method.
- Session 3's `ClosureHandle` helper — proxy-method dispatch reuses the same closure-trampoline shape.
- Session B's existing `_SBClosureCtx` Swift-ARC box — proxy storage hooks into the same lifetime infrastructure.
- The existing `ClosureEmitter.InvokeThunk.cs` machinery — emits `@_cdecl` invoke thunks that reconstruct a Swift closure from `(fnPtr, ctx)` via typed memory binding. Session 4a reuses this pattern for the C#-side back-invocation path.

### What is already in place (audit findings)

- `ProtocolProxyEmitter.EmitMethodReceiver` for **non-closure** methods: working Swift→C# vtable dispatch with marshalled args/return.
- `_closureSkippedMethodKeys` set drives the NotSupported / fatalError stubs. Removing methods from this set is the gate that flips them to "real dispatch."
- `ClosureEmitter.EmitSwiftInvokeThunk` / `EmitCSharpInvokeThunkHelper` already emit per-shape cdecl thunks + nested invoker classes for the closure-return case. Same machinery can serve the closure-param-in-protocol-method case.

## Session 4a — Closure dispatch foundation + simplest shapes — **Done**

`() -> Void` closure-parameter dispatch through C#-implemented proxies ships end-to-end on 2026-05-12. `IsDispatchableClosureMethod` gates the new path (single `@escaping () -> Void` param, no other params, Void return, no throws/async, no generics); vtable-field emission expands each dispatchable closure param into two `UnsafeRawPointer` slots (fnPtr + ctx); `EmitClosureMethodImplementation` extracts the pair via `withUnsafeBytes(of: &localCopy, ...)` — using inout binding to dodge the Swift reabstraction-thunk dangling-pointer trap that surfaces when a concrete `Ieg_` closure is fed to a generic helper like `unsafeBitCast`. `ProtocolProxyEmitter.Receivers` wraps each (fnPtr, ctx) pair into a managed `Action` via a per-shape nested invoker class; the C#→Swift back-call routes through a Cdecl P/Invoke into a new `@_cdecl` invoke thunk emitted by `EveryProtocolEmitter.EmitProtocolClosureInvokeThunks` (entry-point + helper-name negotiated via `GetProtocolClosureInvokeThunkEntryPoint` / `GetProtocolClosureInvokeThunkHelperName`); the new `ProtocolProxyEmitter.ClosureThunks.cs` partial owns the C# helper side. Runtime addition: `SBW_SwiftReleaseRaw` resolves `swift_release` lazily via `dlsym(RTLD_DEFAULT, …)` (the symbol name is reserved by the Swift runtime, so `@_silgen_name` would warn / eventually error) so raw heap-object closure contexts can be released from the .NET finalizer thread without the Mono `!ji->async` JIT contamination that motivated `SBW_SwiftRelease`. Side fix discovered en route: when a protocol mixed non-dispatchable closure methods with a non-closure method, the C# vtable struct still declared the closure slots that the Swift vtable omitted, shifting every subsequent slot by one pointer-width and routing Swift's dispatch to the wrong fnPtr. Both sides now omit non-dispatchable closures consistently — regression locked in by `TestDataLoader_GetSourceId_NonClosureSlotReadsCorrectFunctionPointer_VtableSlotCollision`. Gates green on 2026-05-12: `nuke test` (11273 + 20 + 563 unit pass / 0 fail), `nuke binding-tests --sim` (1979 pass / 0 fail / 56 skip / 0 crash, auto-ratcheted from 1977), `nuke binding-tests --device` (1998 pass / 0 fail / 37 skip / 0 crash, auto-ratcheted from 1996). ## Session 4b — Closure-shape breadth (first cut) — **Done**

Three closure shapes landed end-to-end on 2026-05-12: multi-arg closures (`NumericDataDelegate` — `(Int32, Int32, Bool) -> Void`), return-typed closures (`IntFactoryDelegate` — `() -> Int32`), and `Optional<Closure>` (`CompletionDelegate` — `(() -> Void)?`). Each ships with the matching synthetic BindingTests fixture, runtime test, and Layer A unit coverage on `EveryProtocolEmitterTests`. The critical mid-session find was a SIGSEGV inside `$sIeg_ytIegr_TR` on the `Optional<Closure>` dispatch path: the prior `if var localVar = param { withUnsafeBytes(of: &localVar, …) }` unwrap pattern materialized a concrete `() -> Void` from the Optional's `Iegr_`-form payload, forcing Swift to insert a partial-application context whose storage was deallocated as soon as the unwrap scope exited — the captured `(fn, ctx)` bytes then dangled and the InvCR-thunk call SIGSEGV'd. The fix at `EveryProtocolEmitter.cs:2113-2150` reads raw bytes directly off the `Optional` value via inout binding (Optional<Closure> shares the closure's 2-word layout via the function-pointer extra-inhabitant; `.none` stores nil there). Vtable slot type is `UnsafeRawPointer?` so `.none` round-trips as `IntPtr.Zero` to the C# trampoline. The trap is captured in feedback memory `feedback_optional_closure_reabstraction.md` and protected by both a Layer A regression sentinel (`EmitProtocolExtension_OptionalClosureParam_UsesInoutBytesNotUnwrap`) and a Layer B post-return lifetime probe in `TestTaskRunner_FireExecute_WithNonNilCompletion_Session4b`. Side fix: `CompletionDelegate.taskName()` renamed to `taskLabel()` to break a Swift bare-name collision with `TaskDescriptor.taskName: String { get }` on the EveryProtocol conformance, which was masking witness-table getter emission. ### Scope

Implement the "Likely fix" from the gap doc: when the source argument
label is `_`, infer a parameter name from the declaration role.

- **Enum-case payload** (`case foo(_: Bar)`):
  `EnumHandler.CaseConstruction.cs:54` falls through to `value{i}` when
  `NameProvider.DeriveParameterNameFromType(typeSpec)` returns null or
  `"value"`. Prefer the payload-type name in camelCase as the synthesized
  name, or `value` for the single-payload case.
- **Free function** (`func foo(_: T)` → `Foo( T _)`): locate the
  free-function emit path (likely `MethodHandler` / `FunctionEmitter`)
  and apply the same role-based naming.

## Session 8 — SwiftUI bridge session GC-only finalizer crashes on Mono simulator — **Done**

Root cause: the SwiftUI bridge `_Free` emitted by `SwiftUIBridgeEmitter.cs` always routed through the shared `SBW_onMainThread` helper, whose body is `DispatchQueue.main.sync`. The Mono finalizer thread reaches `_Free` from the C# session's `Dispose(disposing: false)` while the test main thread is parked inside `GC.WaitForPendingFinalizers()`; the finalizer thread then blocks on `main.sync` waiting for a main queue that cannot drain, and the simulator runner kills the app on its no-output timeout. NativeAOT happens to pump the run loop while waiting for finalizers, which is why the device path passed all along. Fix splits `_Free` away from the helper: on-main callers (explicit `Dispose()` from `using` / SwiftUI teardown) run the release block inline, off-main callers (the finalizer thread, plus any future off-main caller) `DispatchQueue.main.async(execute:)` so the finalizer thread returns immediately and the queued block runs when the test pumps `NSRunLoop.Current.RunUntil(...)` between GC rounds. The rest of the bridge (`_Create`, `_GetViewController`, `_Update*`, modifier setters) keeps `SBW_onMainThread` — those callers require the block's return value and tolerate the sync wait, so the existing semantics are intentional. `BridgeSimpleViewTests.TestClassParamViewSessionFinalizerReleasesNativeHandle` is re-enabled (no `[SkipOnSimulator]`); it pre-flushes orphans, resets `deinitCount`, orphans a session via `[MethodImpl(NoInlining)]`, then loops up to six rounds of `GC.Collect()` + `GC.WaitForPendingFinalizers()` + a second `GC.Collect()` + `NSRunLoop.Current.RunUntil(0.1s)` (early-break on first observed `deinitCount >= 1`), and asserts `deinitCount >= 1`. The pump between GC rounds is load-bearing — without it the async-dispatched release block sits queued on main forever. The second `GC.Collect()` re-sweeps anything whose finalizer queued main-thread work that resurrected references. Contract pinned by a new emitter test `SwiftUIBridgeEmitterTests.EmitSimpleViewBridge_Free_DispatchesAsyncFromBackgroundCallers` (asserts the `_Free` body contains `Thread.isMainThread` + `DispatchQueue.main.async(execute:` and does not contain `SBW_onMainThread` or `DispatchQueue.main.sync`); the companion `EmitSimpleViewBridge_GeneratesOnMainThreadHelper` still asserts the helper exists for the rest of the bridge. Gates green on 2026-05-13: `nuke test` 11285 + 20 + 563; `nuke binding-tests --sim` 2007 → 2008 pass (auto-ratchet) / 0 fail / 0 crash; `nuke binding-tests --device` 2023 → 2027 pass (rolling Session 6/7/8 net gains) / 0 fail / 0 crash. `nuke validate` skipped — emitter change is narrow to the SwiftUI bridge `_Free` path, no cross-cutting regression plausible. Resolved doc: `src/docs/Resolved/bug-0.10.0-swiftui-bridge-free-deadlocks-finalizer-thread.md`.

**Follow-up — Codex round-1 + round-2 architectural fixes:** Codex round 1 flagged an ordering hazard against the async-dispatch fix above (Medium): with `release()` queued onto the main run loop, C# `Dispose` returned and freed every entry in `_lifecycleHandles` + `_closureHandles` immediately, while the Swift session state still referenced those GCHandles through its user-data pointers. The queued main-thread block (or any deferred SwiftUI cleanup that dereferenced a stale handle before the runtime serviced the release) would crash with a use-after-free. Fix transfers GCHandle ownership across the FFI boundary: `_Free` widens to `(handle, handleBuffer, handleCount, postReleaseFreeFn)` and the Swift wrapper calls the trampoline strictly *after* `Unmanaged.release` runs inside the dispatched block. C# `Dispose(bool)` packs the handles into a `NativeMemory.Alloc`'d buffer and passes the buffer plus a function-pointer-as-`IntPtr` to a `SwiftUIBridgePostReleaseHelpers.FreeGCHandles` `[UnmanagedCallersOnly(CallConvs = [typeof(CallConvCdecl)])]` trampoline emitted once per bridge file. Codex round 2 then surfaced (High) that async-view `_Free` had been left on the old single-arg / `SBW_onMainThread` shape — async-view sessions also own a GCHandle (`_stateHandle` wrapping `CreateState` + result-monitor userData), so the same finalizer-thread deadlock and the same UAF ordering hazard applied. Async-view `_Free` now mirrors simple-view: thread-aware dispatch + GCHandle ownership transfer; the post-release helper gate widened to `r.IsFunctional` (covering both shapes). Contract pinned by `SwiftUIBridgeEmitterTests.EmitSimpleViewBridge_Free_DelegatesGCHandleDisposalToSwift` and `EmitAsyncViewBridge_Free_DelegatesGCHandleDisposalToSwift`; runtime contract pinned by `BridgeSimpleViewTests.TestClassParamViewSessionWithLifecycleHandlesSurvivesAsyncFreeOrdering` (GC-only teardown smoke) and `TestClassParamViewFreeRunsPostReleaseTrampolineWithLiveHandle` (direct ordering: drives `_Free` with a sentinel GCHandle + test-controlled post-release trampoline, asserts the trampoline observed the sentinel as `IsAllocated == true` at trampoline time — would fail pre-architectural-fix because C# Dispose would have freed the handle locally before the queued release block ran). Async-view test scaffolding (`BridgeNativeMethods.AsyncServiceView_Free` / `DeepChainView_Free` / `MixedAsyncView_Free` DllImports + call sites in `AsyncViewBridgeTests.cs`) updated to the 4-arg signature. Gates green on 2026-05-13: `nuke test` 11288 + 20 + 563; `nuke binding-tests --sim` 2008 → 2010 pass (auto-ratchet); `nuke binding-tests --device` 2027 → 2029 pass (auto-ratchet across two runs — initial lifecycle-handle test + final ordering-contract test). Codex review through round 2 closed clean.
