## Goal

Make `/Users/wojo/Dev/swift-dotnet-packages` the home for Apple-framework binding packages (StoreKit 2 first, then WeatherKit, AuthenticationServices, etc.), consuming swift-bindings' **published** NuGet packages (`SwiftBindings.Sdk`, `SwiftBindings.Runtime`, `SwiftBindings.Templates`) as-is. Concrete end state: `apple-frameworks/StoreKit2/SwiftBindings.StoreKit2.csproj` in swift-dotnet-packages looks roughly like

```xml
<Project Sdk="SwiftBindings.Sdk/0.8.0">
  <PropertyGroup>
    <TargetFramework>net10.0-ios26.2</TargetFramework>
    <PackageId>SwiftBindings.StoreKit2</PackageId>
    <Version>26.2.0</Version>
  </PropertyGroup>
  <ItemGroup>
    <SwiftAppleFrameworkTarget Include="StoreKit" LibraryPath="@rpath/StoreKit.framework/StoreKit" />
  </ItemGroup>
</Project>
```

and `dotnet pack` produces a shipping nupkg with no manual steps.

## Where we are today (commit `2a747448`, 2026-04-09)

**Works** — proven end-to-end in Sessions 1–7 of `0.8.0-storekit2-exploration.md`:
- Direct-mode CLI generates a working `StoreKit.Swift.iOS.dll` + `StoreKitSwiftBindings.xcframework` from the iPhoneOS SDK
- `SwiftFrameworkResolver` correctly resolves `@rpath/StoreKit.framework/StoreKit` on Simulator
- A published `StoreKit.Swift.iOS.0.8.0-preview.1.nupkg` is consumed by a fresh `dotnet new ios` app that prints `[STOREKIT-SMOKE] PASS` on the Simulator

**Broken or missing** — gaps uncovered during the Codex review after Session 7:
- **`BindingProjectEmitter.cs:222`**: published path emits `<PackageReference Include="SwiftBindings.Runtime" Version="{runtimeVersion}" />` — unbounded, minimum-only. Any future runtime minor break silently hoses older bindings' consumers.
- **`PlatformInfo.cs:25`**: `DefaultPlatformVersion = "26.0"` hardcoded. The generator-emitted csproj has `<TargetFramework>net10.0-ios</TargetFramework>` (versionless) paired with `buildTransitive/net10.0-ios26.0/` (hardcoded). Session 7's pack flow produced an internally-consistent nupkg only by coincidence — the build machine had exactly one Apple workload installed. On a machine with multiple workloads, the library's versionless `net10.0-ios` resolves to the **oldest** installed TPV per .NET 10 library defaults (not "latest" — see strategy doc correction below), so `lib/` and `buildTransitive/` would mismatch.
- **`Future/apple-framework-binding-strategy.md:91`**: says "`<TargetFramework>net10.0-ios</TargetFramework>` stays versionless so `dotnet build` resolves the workload's current platform version automatically." This is factually wrong for .NET 10 library projects (apps float, libraries default to oldest unless `UseFloatingTargetPlatformVersion=true`). Decided-strategy doc needs a correction.
- **`SwiftBindings.Sdk/Sdk/Sdk.targets`**: hardwired to `--xcframework` mode (`Sdk.targets:242–248`). No code path for "this project targets an Apple system framework, run `swift-api-digester` against the SDK, invoke the generator in direct mode." Session 7's pack flow ran the generator CLI by hand — that won't port to swift-dotnet-packages' automated pack/publish harness.
- **`SwiftBindings.Sdk 0.8.0` is not published to NuGet.** swift-dotnet-packages currently consumes `Sdk="SwiftBindings.Sdk/0.7.0"`, which has none of the Apple-framework work.
- **Three StoreKit-surfaced generator bugs** (tracked in `roadmap.md`): foreign value-type metadata registration gap, orphan `[LibraryImport]` for `Transaction.updates`/`Storefront.updates`/`Product.SubscriptionInfo.Status.updates`, and dynamic pack-TFM resolution. All three would ship into every Apple-framework package if not fixed before cutting 0.8.0.

## Decisions locked in (from the Claude ↔ Codex pass on 2026-04-09)

### Versioning

- **Apple-framework packages**: `{iOS-SDK-major}.{iOS-SDK-minor}.{binding-rev}[-preview.N]`
  - Major.Minor mirrors the iPhoneOS SDK the binding was generated against (NOT Xcode — they usually match but SDK version is authoritative)
  - Patch is OUR binding revision lane (bug fixes, generator fixes, runtime ref bumps)
  - Skip SDK versions whose regeneration would produce an identical artifact — no noise bumps
  - Preview suffix for beta SDKs and for our own pre-release cuts
  - Example timeline: `26.2.0` → `26.2.1` (metadata fix) → `26.3.0` (iOS 26.3 SDK) → `27.0.0-preview.1` (Xcode 27 beta) → `27.0.0` (iOS 27 GA)
- **Third-party library packages**: unchanged — continue 1:1 with upstream (`SwiftBindings.Nuke 12.8.x` = Nuke 12.8.x)
- **Both schemes share the rule**: major.minor mirrors the thing being wrapped; patch is our revision lane.

### SwiftBindings.Runtime pinning in published bindings

- **Bounded** `[0.8.0,0.9.0)` for a binding built against `SwiftBindings.Runtime 0.8.x`
- Strict internal rule: `SwiftBindings.Runtime` patch releases must be ABI-compatible (no struct layout changes, no P/Invoke signature changes, no symbol renames — bug-fix implementations only)
- Rationale: exact pin creates a republish tax across every Apple-framework package on every runtime patch; bounded lets patch fixes flow to consumers without churning the entire Apple-framework matrix.

### TFM in the generator-emitted csproj

- **Explicit platform version driven by `--platform-version` CLI flag** (e.g. `--platform-version 26.2` → `<TargetFramework>net10.0-ios26.2</TargetFramework>` AND `buildTransitive/net10.0-ios26.2/`)
- **NOT dynamic `$(TargetPlatformVersion)` resolution** (the approach the SwiftBindings.Sdk pack target uses) — that collides with the .NET 10 "libraries default to oldest TPV" rule and would require `UseFloatingTargetPlatformVersion=true` contortions to work correctly.
- **NOT versionless `net10.0-ios`** — ambiguous, machine-dependent, can't be audited from the published nupkg.

### Package layout

Unchanged from what Session 7 shipped:
```
lib/net10.0-iosX.Y/<Module>.Swift.iOS.dll
buildTransitive/net10.0-iosX.Y/<Module>.Swift.iOS.targets
runtimes/ios-arm64/native/<Module>SwiftBindings.xcframework/...
```
Both TFM fragments come from `--platform-version`.

### Compat story for users

**Old nupkgs keep working on newer Apple workloads** — this is the committed position, pending one measured verification (see open questions). The reasoning:
- Swift ABI stability since Swift 5.0 (2019) — mangled symbols in `[LibraryImport]` declarations resolve against any newer iOS at runtime
- .NET 10 TFM precedence rules: a consumer targeting `net10.0-ios27.0` can restore a package that ships `lib/net10.0-ios26.0/` as long as Microsoft.iOS's 27.0 ref assemblies are additive over 26.0 (which is the pattern)
- `runtimes/ios-arm64/native/` is RID-based, not TFM-based, so it's orthogonal to the workload version
- Users only MUST update a binding package when they want new iOS APIs, or when they want a generator bug fix — never because their workload bumped

## Open questions

### Q1 — TFM cross-workload compatibility — **ANSWERED YES (Codex repro, 2026-04-09)**

**The question**: does a nupkg that ships `lib/net10.0-ios26.0/` + `buildTransitive/net10.0-ios26.0/` + `runtimes/ios-arm64/native/` restore and build cleanly when the consumer project targets a higher Apple TPV (e.g. `net10.0-ios26.2` or `net10.0-ios27.0`)?

**Measured answer (Codex repro at `/tmp/swiftbindings-q1-repro`)**: yes, for the `26.0 → 26.2` jump on a machine with both workloads installed.

What was measured:
- Producer package `Q1.Package` shipped `lib/net10.0-ios26.0/Q1.Package.dll` + `buildTransitive/net10.0-ios26.0/Q1.Package.targets` + `runtimes/ios-arm64/native/FakeNative.framework/Info.plist`
- Consumer targeted `net10.0-ios26.2`, referenced the package from a local feed, restore + build succeeded
- `project.assets.json` under target `net10.0-ios26.2` shows NuGet selecting `compile` / `runtime` / `build` / `runtimeTargets` entries from the `26.0` package assets
- `Q1.Consumer.csproj.nuget.g.targets` shows the actual import of the `26.0` buildTransitive target into the `26.2` consumer

Caveats:
- The `26.0 → 27.0` specific jump could not be measured (Codex's machine only has iOS workloads `26.0` and `26.2` installed). The repro proves the general NuGet/TFM selection shape but does not cover a major-version iOS jump.
- The repro validates asset selection, not runtime behavior under a future SDK. It's strong evidence the shape works, not proof that every native framework will run at runtime across a multi-year SDK jump.

**Verdict**: Session 3 is unblocked. The `{iOS-SDK-major}.{iOS-SDK-minor}.{binding-rev}` versioning scheme and the single-TFM publishing shape (one nupkg per iOS SDK cut, consumable by newer workloads) is the committed plan. If `26.0 → 27.0` ever turns out to behave differently in practice, the fallback is multi-TFM nupkgs — but the evidence points strongly toward this not being needed.

#### Part E — SwiftBindings.Sdk Apple-framework target mode

**Changes**:
1. **New MSBuild item**: `<SwiftAppleFrameworkTarget Include="StoreKit" Module="StoreKit" LibraryPath="@rpath/StoreKit.framework/StoreKit" />`. Module defaults to Include if unset. LibraryPath defaults to `@rpath/{Module}.framework/{Module}`.
2. **`Sdk.targets` branch detection**: `<SwiftBindingTargetKind>` property resolved as `AppleFramework` when `<SwiftAppleFrameworkTarget>` items are present and `<SwiftFramework>` items are absent. Conditional on that property, skip the xcframework-discovery target and enter a new Apple-framework chain.
3. **New target — `_SwiftBindingDumpAppleFrameworkAbi`**:
   - Runs `xcrun swift-api-digester -dump-sdk -module {Module} -target arm64-apple-ios{MinDeploymentVersion}[-simulator] -sdk $(XcodeSdkPath) -o $(IntermediateOutputPath)/{Module}.abi.json`. The `-target` value is a Swift/LLVM target triple (e.g. `arm64-apple-ios15.0` for device, `arm64-apple-ios15.0-simulator` for simulator), NOT a .NET TFM. The minimum deployment version comes from the `<SwiftAppleFrameworkTarget>` item or a sensible default. See `0.8.0-storekit2-exploration.md:45` for the exact form Session 1 used against StoreKit.
   - Discovers the swiftinterface at `$(XcodeSdkPath)/System/Library/Frameworks/{Module}.framework/Modules/{Module}.swiftmodule/{slice}.swiftinterface` and the TBD at `$(XcodeSdkPath)/System/Library/Frameworks/{Module}.framework/{Module}.tbd`
   - Handles the device-vs-simulator slice asymmetry noted in the exploration doc: device SDK ships `arm64e-apple-ios.swiftinterface` and simulator SDK ships `arm64-apple-ios-simulator.swiftinterface` (different `arm64` vs `arm64e` prefix AND different suffix).
   - **Fingerprints via content hashing** using the existing `_ComputeSwiftFingerprint` mechanism in `Sdk.targets:104–149` (shasum-a256 over file contents, not mtimes). The Apple-framework branch must hash: the produced abi.json, the discovered swiftinterface, the TBD, the resolved Xcode SDK version, and the `<SwiftAppleFrameworkTarget>` item metadata (Module, LibraryPath, min deployment version). Mtime-based detection would regress the existing xcframework-mode correctness guarantee — do NOT switch to mtimes. The abi.json is itself produced from Apple SDK inputs, so hashing the produced file captures the same signal a "hash the Apple SDK inputs" approach would, at lower cost.
4. **New target — `_SwiftBindingInvokeGeneratorAppleFramework`**:
   - Invokes the generator with direct-mode args: `-a {abi.json} -d {TBD} -t {TBD} -s {swiftinterface} -l '\@rpath/...' --platform-version {X.Y} --swift-runtime-version {pkg-version} -o {intermediate}`
   - Reuses the existing generator fingerprint gate so it doesn't re-run unnecessarily
5. **Wrapper compilation**: already works via the same Swift compile path used by direct mode. SDK mode should reuse it unchanged.
6. **New SDK-consumer test**: a MSBuild test project under `src/Swift.Bindings.Sdk/tests/` (or wherever SDK tests live) that consumes the Apple-framework target mode end-to-end against a small **Swift-first** Apple framework — candidates: `Observation` (iOS 17+, small, pure Swift, no ObjC bridge), `RegexBuilder` (small, Swift-first), or `_Concurrency` (runtime, Swift-first). **Do NOT use `Contacts` or `CoreLocation`** — they're ObjC-first with a thin Swift overlay, and would validate the MSBuild plumbing without exercising the Swift-first direct-mode path that's the whole point of the Apple-frameworks pivot. StoreKit is the right surface but too large for a test fixture; pick the smallest genuinely-Swift framework available. If none is small enough, synthesize a minimal pure-Swift system-framework-shaped test double instead of compromising the test signal.
7. **`Future/apple-framework-binding-strategy.md`**: update the framework-#2 checklist to reflect SDK-mode (not hand-rolled CLI) as the new baseline.

**Scope risks**:
- `swift-api-digester` is an `xcrun` tool — Xcode must be installed on the build machine. The SDK should fail with a clear error ("Install Xcode or set XcodeSdkPath") rather than a cryptic failure.
- Incremental-build discipline is critical — a 1.4 MB abi.json dump on every `dotnet build` would be a dealbreaker for developer ergonomics.
- Multi-platform expansion: SDK mode should handle `ios` / `macos` / `tvos` / `maccatalyst` the same way the existing xcframework mode does, but Session 7 of the exploration only exercised iOS. Defer non-iOS validation to a follow-up — the 0.8.0 release can ship iOS-only.
- **If Part E's scope expands beyond a single session** (e.g. the target chain surfaces unforeseen fingerprinting bugs or multi-target edge cases), land Part E and split Part F into its own follow-up. Publishing isn't worth rushing if the underlying SDK change is fragile.

## Success criteria for the whole 0.8.0 release

When all of this is done:
1. A user writes a one-file `SwiftBindings.{AppleFramework}.csproj` in swift-dotnet-packages, runs `dotnet pack`, and gets a shipping nupkg — no generator CLI invocations, no local-dev paths.
2. End consumers can `<PackageReference Include="SwiftBindings.{AppleFramework}" Version="X.Y.Z" />` and the binding Just Works on Simulator and Device against Apple's system framework.
3. When Apple ships a new iOS minor, the publishing flow is: bump `--platform-version`, regenerate, `dotnet pack`, publish. Consumers who want the new APIs bump their reference; consumers who don't, don't update.
4. When `SwiftBindings.Runtime` ships a patch release, every Apple-framework binding picks it up automatically via the bounded version range. No republish tax.
5. Adding a second Apple framework (WeatherKit, AuthenticationServices, etc.) is a 30-minute task per the framework-#2 checklist — not a multi-week generator deep-dive.
