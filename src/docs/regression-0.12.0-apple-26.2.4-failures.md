# Regression 0.12.0 / Apple 26.2.4 — Failures and Resolution

Scope: the failures seen in the downstream regression run using
SDK/Runtime/Templates `0.12.0` and Apple supplement `26.2.4`, with prior Apple
baseline `26.2.3` — three in `swift-dotnet-packages` (§1–3) and one in
`internal-binding-testing` (§4).

Repos involved:

- Generator: `/Users/wojo/Dev/swift-bindings`
- Downstream packages/tests: `/Users/wojo/Dev/swift-dotnet-packages`
- Third-party validation harness: `/Users/wojo/Dev/internal-binding-testing`

Two of the `swift-dotnet-packages` three were stale downstream test
expectations lagging behind deliberate, already-covered generator improvements;
the third was a release-process consistency bug (cross-framework Apple package
version skew) exposed by a generator API-shape change. The fourth
(`internal-binding-testing`, §4) is the same release-harness version-skew class
as §1, this time on the core Apple supplement. None required a generator
rollback.

## 1. RealityKit CS1739 — cross-framework Apple package version skew

**Root cause.** The RealityKit binding, regenerated by the 0.12.0 generator,
constructs a cross-module proxy with the owned-existential constructor:

```csharp
new RealityFoundation.SwiftInterop.SynchronizationPeerIDProxy(
    *(Swift.Runtime.ExistentialContainer1*)new IntPtr(swiftIndirectResult.Value),
    ownsContainer: true)
```

The `ownsContainer` parameter was added to existential proxy constructors to
adopt the `+1` on owned existential returns. But `RealityKit.csproj` pinned
`<PackageReference Include="SwiftBindings.Apple.RealityFoundation" Version="26.2.3" />`,
and the published `26.2.3` package predates that change — so it exposes only
the older one-argument proxy constructor. RealityKit calls a constructor the
referenced package does not have → CS1739.

The same shape exists for `MatterSupport → Matter` (also pinned `26.2.3`).

This is a release/harness integrity bug, not a generator bug. The generator
change is intentional and covered by BindingTests; reverting it would reopen
the owned-existential leak. The defect is that cross-framework Apple
`PackageReference` edges were not moving with the Apple supplement train, and
the regression harness had no way to resolve a coherent set of sibling
packages for a pre-release Apple version.

**Fix (build harness, `swift-dotnet-packages`).**

- `BumpAppleVersionInternal` now also rewrites cross-framework
  `<PackageReference Include="SwiftBindings.Apple.*" Version="…">` pins to the
  target Apple version, in lockstep with each csproj's own `<Version>`. A
  consumer regenerated by the current generator no longer compiles against an
  older published sibling.
- `RegressionValidate.Preflight` packs each distinct cross-framework
  dependency (RealityFoundation, Matter) at the target Apple version into
  `local-packages/` before the matrix runs, evicting any stale same-version
  extraction from the global NuGet cache first (NuGet won't re-expand a
  version folder that already exists). The pre-release Apple supplement isn't
  on nuget.org yet, so the bumped pins resolve to these fresh local packages.
- A coherence guard (`AssertCrossFrameworkCoherence`) fails pre-flight if any
  `SwiftBindings.Apple.*` cross-framework reference still lags the Apple train
  after the bump — the durable regression assertion: skew can no longer slip
  through to a published or validated mixed-ABI shape. The bump, the guard, and
  the dependency packer all match pins through one shared set of regexes
  (`AppleCrossRefTagPattern` / `…IncludePattern` / `…VersionPattern`), so the
  guard can never report "clean" on exactly the pin the bump touched. Those
  regexes accept either XML quote style (`"` or `'`) — the version pattern
  captures the quote char and backreferences it as the closing quote, preserving
  the original style on rewrite — so a single-quoted pin can't slip past the bump
  *and* the guard *and* packing discovery (a quote-style blind spot would reopen
  the exact silent-skew hole the single source of truth exists to close). The guard
  is deliberately stricter than discovery: it rejects any Apple cross-ref tag it
  can't read a `Version="…"` attribute from (e.g. a child-element `<Version>`
  pin), because the broad `<Version>` bump regex would rewrite such a pin's
  value while discovery and packing never see it — that unparseable form fails
  loudly rather than silently skewing the packed train. The dependency packer
  also hard-fails up front if any cross-framework dependency is itself a
  consumer (a multi-level chain alphabetical packing can't satisfy safely).

## 2. MusicKit `MusicItemCollection<Song>` Index/Distance surface

**Root cause.** The downstream smoke test used `Type.GetMethod` on
`MusicItemCollection<Song>` and expected instance methods
`Index(int, int)` / `Distance(int, int)`. Those two-argument members are
generic-parent `Collection` requirements; the generator emits them as
concrete-specialization (CSM) **extension** methods, one per conformer
(`MusicItemCollectionMusicKit_SongCsmExtensions.Index(this …, nint, nint)`).
`Type.GetMethod` cannot see extension methods, so the reflection probe failed
even though the API is callable as `collection.Index(i, n)`.

The CSM static-dispatch shape is deliberate — it avoids the Mono `!ji->async`
crash an open-generic instance method with 2+ type-metadata arguments trips —
and is exercised end-to-end by the generator's own `MusicItemBag` BindingTests
(`bag.Index(0, 2)`, `bag.Distance(0, 3)` pass on Mono-sim and NativeAOT-device).
`index(after:)` / `formIndex(after:)` remain instance methods with int
convenience overloads.

**Fix (downstream test).** The smoke test failed only on the NativeAOT device:
the `*CsmExtensions` static class was nothing-references-it dead code under
trimming, so `Assembly.GetTypes()` never returned it (it passed on Mono-sim,
which keeps full metadata). The test now proves the surface two complementary
ways:

- **Compile-time shape proof — all platforms, incl. device.** A never-invoked
  local function references every ergonomic member exactly as a consumer would
  (`collection.Index((int)0)` / `FormIndex((int)0)` instance overloads and the
  CSM extensions `collection.Index((nint)0,(nint)0)` /
  `Distance((nint)0,(nint)0)`). If the generator dropped or renamed any of them
  the test app would not *compile* for any TFM — a platform-invariant guarantee
  the callable surface exists — and the `ldftn` roots the `*CsmExtensions` class
  so the trimmer keeps it.
- **`[Obsolete]`/metadata probe — JIT/full-metadata runtimes only**
  (`RuntimeFeature.IsDynamicCodeSupported`). Verifies none of the members carry
  `[Obsolete]` (the SB0001 marker). `[Obsolete]` is a custom attribute; under
  NativeAOT trimming, custom-attribute and uncalled-member metadata are
  stripped, so this probe on device would pass *vacuously* (no attribute found ≠
  attribute absent) — false confidence, not coverage. The generated
  `MusicKit.cs` is byte-identical across TFMs, so verifying the non-stub
  property on the JIT runtime fully establishes it for the shipped code.

The generator-level behavior was already covered by `MusicItemBagTests` and
`GenericIndexableCollectionTests`, which call `bag.Index(0, 2)` /
`bag.Distance(0, 3)` / `coll.Index(0, 2)` *for real* on both Mono-sim and
NativeAOT-device — a stub regression would throw at the call, not silently pass.

## 3. Nuke `ImageRequest.Processors` — newly-bound existential-array property

**Root cause.** The downstream test expected `request.Processors` to throw
`NotSupportedException` — the old co-gated-stub behavior for a property
referencing a suppressed proxy. The existential-array binding work made the
property real:

```csharp
public IReadOnlyList<IImageProcessing> Processors
{
    get => Processors_Get().AsProjected(e => (IImageProcessing)new ImageProcessingProxy(e));
    set { … }
}
```

The getter now returns a projected `IReadOnlyList<IImageProcessing>`; for a
default request that's an empty list. The test asserting a throw was stale.

**Fix (downstream test + generator coverage).** The Nuke test now asserts the
capability: `Processors` is a non-null `IReadOnlyList<IImageProcessing>` and,
for a default request, an empty list.

The existential-array property **getter** projection (`[any Proto]` →
`IReadOnlyList<IProto>` of proxies, including the empty case) is the exact
shape that regressed, and it had no read-side BindingTests coverage — the
existing `ProcessingPipeline` tests only exercised the constructor +
`modeCount()`. Two runtime tests were added in
`BindingTests/RuntimeTestsApp/Collections/ConstructorCollectionTests.cs`:

- `TestProcessingPipelineModesGetterProjection` — reads the `Modes` getter,
  asserts order-preserving projection of 2 elements, and round-trips each
  projected proxy through the protocol witness (`ModeName`, `Validate`).
- `TestProcessingPipelineModesGetterEmpty` — asserts an empty backing array
  projects as an empty list, not null or a throw (the default-Nuke-request
  path).

Both pass on the iOS simulator (Mono JIT).

## 4. internal-binding-testing CS1739 — `AnyError` Apple-supplement version skew

**Root cause.** Five third-party libraries (Alamofire, Kingfisher, RxSwift,
Starscream, BonMot) that passed at the `0.11.2` baseline failed to compile at
`0.12.0` on both sim and device with, e.g.:

```
error CS1739: The best overload for 'AnyError' does not have a parameter named 'ownsContainer'
```

`AnyError` (the `any Swift.Error` wrapper, `Swift.Foundation.AnyError`) ships in
the core `SwiftBindings.Apple` supplement. Its owned-existential ctor —
`AnyError(ExistentialContainer1, bool ownsContainer)` — was added in the
`26.2.4` train. The `0.12.0` generator emits the owned form
(`new AnyError(_value_raw, ownsContainer: true)`) when extracting an `any Error`
enum payload at `+1`. But every test csproj references the supplement with an
open-ended floating range:

```xml
<PackageReference Include="SwiftBindings.Apple" Version="[26.0.0,)" />
```

NuGet resolves a version range to its *lowest* satisfying version, so the
restore pulled the oldest published supplement (`26.2.0`), which predates the
two-argument ctor → CS1739. At `0.11.2` the generator did not emit
`ownsContainer:`, so the one-argument ctor present in every published version
sufficed and the libraries compiled — the API-shape change exposed a skew that
was always latent in the floating pin.

This is the same release-harness integrity class as §1 (RealityKit), one level
down: there the skew was between sibling Apple-framework packages; here it is
between a new generated consumer and an older *published* core supplement. The
generator emission is correct and is covered end-to-end by BindingTests
(`CrossModulePayloadEnumTests.TestCrossModuleClassResult_Failed_ExtractsAnyErrorOnly`
and `ClassPayloadEnumTests`, which extract a `case failed(error: any Swift.Error)`
payload — emitting `new AnyError(…, ownsContainer: true)` and disposing it, so a
ctor regression fails the test app build). Reverting it would reopen the
`AnyError` owned-existential leak.

**Fix (validation harness, `internal-binding-testing/validate.sh`).**

- `validate.sh` now takes `--apple-version` and stamps every
  `SwiftBindings.Apple` reference to it — exactly as it already stamps
  `SwiftBindings.Runtime` — replacing the floating range with an exact pin so
  the supplement resolves the version under test from `local-packages/` rather
  than the oldest published version.
- Pre-flight verifies `SwiftBindings.Apple.<apple-version>.nupkg` exists in
  `local-packages/` (Step 1 of the regression skill drops it there), alongside
  the existing `SwiftBindings.Runtime` check.
- `--apple-version` is mandatory whenever any csproj references the supplement:
  the script fails closed rather than letting a silent stale-float through — a
  regression run can no longer mix a new generated consumer with an older
  published supplement.
- A shared post-stamp coherence guard (`assert_pinned`) fails the run if any
  core `SwiftBindings.Runtime` *or* `SwiftBindings.Apple` reference still lags
  the target version — catching any reference form the stamp regex didn't reach
  (reordered attributes, a child-element `<Version>`), and listing the
  offenders. It mirrors `swift-dotnet-packages`'s `AssertCrossFrameworkCoherence`
  and closes the same fail-open hole symmetrically on the Runtime side, not just
  Apple. The guard runs *inside* the stamp path (pre-regen): the binding-project
  csprojs the generator later resets to floating placeholders are still stamped
  at that point, so checking there is a true signal rather than a false-fail on
  the post-regen reset.
- Version arguments are validated as bare tokens before they reach the `sed`
  stamp and `grep` literals (rejecting a stray `|`, backtick, quote, space, or
  leading `-`), and the aggregator fails a `--filter` that matched no library
  rather than reporting a vacuous "0 cells, all green".
- The regression-validation skill's Step 3 now passes `--apple-version
  $APPLE_VERSION`.

## Cross-cutting note

The build harness now treats Apple-framework cross-package dependency pins as
part of the Apple train: a pre-release regression run can no longer mix a new
generated consumer with an older generated dependency. The two stale-test
failures drove no generator change — the underlying behaviors are covered by
BindingTests, and the downstream tests were corrected to assert the intended
shape.
