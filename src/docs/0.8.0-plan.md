# 0.8.0 Release Plan

**Drafted**: 2026-04-07
**Status**: Active focus doc for 0.8.0. `roadmap.md` is set aside — it accumulated too many small items to be useful as a planning surface. This doc is intentionally narrow.

---

## Focus Sequence

0.8.0 is **sequenced**, not parallel. Lock each phase down before starting the next. The Apple-frameworks work is the most uncertain and most strategically important — it gets undivided attention first.

### Phase 1 — Apple Swift-first frameworks → .NET MAUI

**Lock this down first. This is the headline of 0.8.0.** It is feasible — the question is the strategy and how best to support it. Effort budget is unbounded; this is the work that defines the next year of the project.

Bind Apple's Swift-first frameworks (StoreKit 2, WeatherKit, TipKit, App Intents, Foundation Models, etc.) and publish them as NuGet packages consumable by .NET MAUI / .NET iOS apps. None of these have any .NET binding today. They unlock the most strategically valuable surface area we've identified — these are the APIs every modern iOS app reaches for, and `Microsoft.iOS` (which is fundamentally an ObjC binding generator) has no story for them.

Deliverable: at least one published Apple-framework NuGet package (StoreKit 2 is the obvious first target), a fully documented binding+publish strategy that scales to the rest of the framework set, and the supporting infrastructure (templates, wrapper-package conventions, runtime loading, packaging, sample apps) reusable across every Apple framework that follows. Stretch: ship 2–3 Apple frameworks in 0.8.0 instead of just one.

### Phase 2 — macOS / Mac Catalyst / tvOS validation

Once Phase 1 is locked, turn to multi-platform. The architecture audit is done; the runtime proof is not. At least one shipping library running end-to-end on a non-iOS platform with a green test pass.

Deliverable: `Nuke.MacOSTests` (or equivalent) under `swift-dotnet-packages/tests/` running green on Mac Catalyst, then native macOS.

### Phase 3 — Stripe hardening + ship

Stripe is probably already good enough to have shipped with 0.7.0. Phase 3 isn't about getting it functional — it's about **really hammering it**: more test coverage, sample app polish, edge cases, real consumption patterns, confidence that what we ship is genuinely production-ready.

Deliverable: `SwiftBindings.Stripe` published to NuGet with high confidence, sample app, documented usage.

## Context

0.7.0 just shipped. It was an inward-facing stability/correctness release: constrained-generic metadata workarounds, deletion of 5 broken `Swift.*` ObjC wrapper classes, NativeAOT collection metadata fix, Mono finalizer crash fix, protocol auto-wrapping, multi-framework binding auto-discovery. None of it advanced real-world publishing breadth, multi-platform proof, or upstream bug reports.

0.8.0 should pivot **outward**: more shipping packages, more platforms, more strategic surface — and resolve the framing of what 1.0 actually means.

### What's actually shipping

| State | Libraries |
|---|---|
| **Published to NuGet** | Nuke, Lottie (2) |
| **Close to publish** | Stripe (1) |
| **Prepared but uncertain whether they should ever ship** | BlinkID, BlinkIDUX, GRDB, Kingfisher, Mappedin (5) |
| **Local validation only — would never ship** | Alamofire, RxSwift, GRDB, KeychainAccess, CryptoSwift, etc. |

### Why the roadmap needed refinement

`roadmap.md` Theme B lists Alamofire, Kingfisher, GRDB as "deep-dive flagship candidates". By the **real shipping criterion** — *would a .NET MAUI developer pick this Swift binding over an existing .NET library?* — Alamofire (HttpClient/Refit), GRDB (SQLite/EF Core/Dapper), and most of the third-party Swift ecosystem are out. .NET already has solid equivalents.

Validation breadth and shipping breadth are **two different goals** with two different criteria. The roadmap conflates them. This plan separates them.

| Goal | Yardstick | What counts |
|---|---|---|
| **Validation breadth** | Binding patterns exercised across diverse APIs | Anything in `sim-validation/` or `swift-dotnet-packages/tests` is fair game — Alamofire, GRDB, RxSwift all valuable here. Already 1,668 + 2,107 tests passing across both gates with sim Mono JIT + NativeAOT iPhone. |
| **NuGet shipping** | Fills a real .NET MAUI gap | Much narrower — SDK-style libs and Apple Swift-first frameworks. |

## The 1.0 Thesis (proposed reframing)

**Old framing**: "Any Swift xcframework → NuGet package", measured by skip rate and number of validated libraries.

**New framing**: **Bridge .NET MAUI to Apple's Swift-first platform APIs, plus select third-party Swift SDKs that fill real gaps.**

Under this framing:
- Third-party Swift libs remain valuable as **validation fodder** — they prove the generator handles diverse patterns. They are not the headline shipping deliverable.
- The headline shipping deliverable is **Apple's Swift-first frameworks** (StoreKit 2, WeatherKit, TipKit, App Intents, Foundation Models, etc.), plus a small set of commercial SDKs with no .NET equivalent (Stripe mobile UI, BlinkID, Mappedin).
- **Multi-platform** (macOS/Mac Catalyst/tvOS) is non-negotiable for 1.0. Today the entire shipping pool is iOS-only.

This is a far more compelling 1.0 story than "we shipped 8 niche third-party bindings". It is "we make every modern Apple platform API available to .NET MAUI developers."

## Phase Detail

### Phase 1 — Apple Frameworks: Strategy + Implementation

**Why this is first**: It's the most strategically valuable surface area we've identified, unlocks an entire class of APIs (StoreKit 2, WeatherKit, TipKit, App Intents, Foundation Models, etc.) that have no .NET binding today, and reframes what 1.0 means. It's also the work that requires the most thinking — not because feasibility is in doubt, but because the strategy for binding system frameworks at scale needs to be designed, not improvised.

Subscription monetization is the dominant business model on iOS. Microsoft.iOS exposes the old (StoreKit 1) ObjC API but **StoreKit 2 — the modern Swift-first replacement — has no .NET binding anywhere.** Every monetized iOS app needs this. The same gap exists for WeatherKit, TipKit, App Intents, Foundation Models, and the other frameworks listed in the shortlist below.

#### Working assumption

The basic technical pattern is feasible:
1. **Wrapper Swift package** does `@_exported import <SystemFramework>` and ships an xcframework via `spm-to-xcframework`
2. **The xcframework's `.swiftinterface`** describes the Apple framework's Swift API surface
3. **Our existing bindings generator** consumes that xcframework like any other
4. **At runtime**, P/Invokes resolve against the system framework already on-device (`/System/Library/Frameworks/<X>.framework/<X>`), not a bundled dylib

The hard work is **the strategy around that pattern**, not the pattern itself. The questions below define the strategy.

#### Strategy questions to answer in Phase 1

These don't block starting; they get answered in parallel as the first framework is built. Each one needs a documented decision before the strategy is reusable.

1. **Wrapper package convention**: One Swift wrapper repo per framework, or one monorepo with N packages? Where does the wrapper package source live (this repo? swift-dotnet-packages? a new dedicated repo)? Naming convention?
2. **Generator changes (if any)**: Does the existing generator handle the wrapper-only xcframework cleanly? Most likely yes — but we may discover the generator wants a flag like `--system-framework <name>` to suppress dylib expectations and route P/Invokes to system load paths.
3. **Runtime loading strategy**: Does the .NET runtime correctly `dlopen` system frameworks via the existing `SwiftFrameworkResolver`, or do we need a `SystemFrameworkResolver` that knows how to walk `/System/Library/Frameworks/`? Does this differ on simulator vs device vs Mac Catalyst vs macOS?
4. **NuGet package layout**: Does each Apple framework get its own NuGet package (`SwiftBindings.StoreKit2`, `SwiftBindings.WeatherKit`)? Does the runtime go in a shared dependency? How does versioning work as Apple adds APIs in new iOS versions?
5. **Naming convention**: `SwiftBindings.StoreKit2` vs `SwiftBindings.Apple.StoreKit2` vs something else. Pure ergonomics — Microsoft.iOS uses bare framework names, nominative use is well-established, no real trademark exposure.
6. **iOS version availability**: StoreKit 2 is iOS 15+, WeatherKit is iOS 16+, TipKit is iOS 17+, Foundation Models is iOS 18.1+. How do we surface `@available` constraints from Swift in the generated C# (compile-time errors? runtime guards? both)? How does this interact with MAUI's minimum-target settings?
7. **Entitlements and capabilities**: Each framework needs different entitlements (StoreKit needs IAP, WeatherKit needs Apple Developer service entitlement, etc.). Where does this get documented for consumers? Should sample apps demonstrate the entitlement setup?
8. **Async / AsyncSequence / Result patterns**: StoreKit 2 leans heavily on `async`, `AsyncSequence` (`Transaction.updates`), and `Result<Transaction, VerificationError>`. The generator already handles these in some form — confirm the surface area is complete enough, file gaps as Phase 1 sub-tasks if not.
9. **Macro-based frameworks**: SwiftData (`@Model`) and Observation (`@Observable`) expand at compile time. The `.swiftinterface` should contain the expanded form, but this needs verification. Probably defer macro-heavy frameworks until after the simpler ones land.
10. **Testing strategy**: How do we test bindings against system frameworks where the underlying API is hard to mock? StoreKit has Xcode StoreKit configuration files for sandbox testing. WeatherKit needs real Apple Developer service credentials. TipKit needs runtime UI. Each framework may need its own test approach.
11. **Sample app strategy**: Each shipping Apple framework needs at least one sample showing real consumption. Where do they live? Are they MAUI samples, .NET iOS samples, or both?
12. **Multi-platform**: Most Apple frameworks support iOS + macOS + Mac Catalyst + tvOS in different combinations. Phase 2 multi-platform work feeds back into this — Phase 1 deliverables may be iOS-first with multi-platform support arriving in Phase 2.

#### Concrete first framework: StoreKit 2

StoreKit 2 is the right first framework because:
- Highest single-framework strategic value (subscription monetization)
- Exercises async/await, `AsyncSequence`, `Result`, generics, error types — a broad surface that stresses the generator
- Has Xcode StoreKit configuration files for sandbox testing without real App Store dependencies
- Real consumers will reach for it immediately upon release
- iOS 15+ availability is broad enough for any modern MAUI app

**Implementation outline** (exploration history in `0.8.0-storekit2-exploration.md`; current bug list in `0.8.0-storekit2-followup-bugs.md`):
1. ~~Build `StoreKit2Wrapper` Swift package (`@_exported import StoreKit`)~~ — superseded. Direct mode against Apple's SDK + a `swift-api-digester` ABI dump is the actual source of truth. Wrapper-package approach was falsified during exploration (`@_exported import` does not inline declarations into the wrapper's swiftinterface).
2. ~~Build it through `spm-to-xcframework`~~ — superseded, see above.
3. **Generate bindings with the existing generator; capture and resolve any blockers** — *in progress*. Sessions 1–2 (commits `108f4f12` + `eafe252d`) landed Apple-framework target mode, parameter-position opaque type lowering, `@available` propagation across wrapper emitters, and per-case enum availability parsing. Swift wrapper now compiles cleanly to a 486 KB dylib. **Four C# emit bugs remain** (full brief: `0.8.0-storekit2-followup-bugs.md`) — each is its own session, recommended order: bug #2 (constrained-extension dedup, highest leverage) → bug #1 (nested type qualification) → bug #3 (property/nested-type collision) → bug #4 (Foundation registry gaps).
4. **Wire wrapper compilation into direct mode** — deferred until #3 lands. The wrapper compiles manually via `swiftc`; wiring it into the direct-mode CLI pipeline is mechanical once the C# binding actually compiles. Reuse `SwiftWrapperCompiler.cs`.
5. **Verify `SwiftFrameworkResolver` handles `/System/Library/Frameworks/` paths** — deferred until #4 lands. Open question: may need a small extension or a new `SystemFrameworkResolver` path.
6. **Simulator smoke test** — start with a non-throwing, non-async, non-heap-returning StoreKit method (property accessor or static type instantiation), then `Product.ProductsAsync`, then `Transaction.updates` (the first real test of async/AsyncSequence handling against StoreKit 2's headline API).
7. **Build the NuGet package**.
8. **Build a real sandbox-purchase sample** in MAUI (or .NET iOS) that completes a `Product.purchase()` flow and listens to `Transaction.updates`.
9. **Publish to NuGet**.
10. **Write `Future/apple-framework-binding-strategy.md`** capturing the strategy answers above so framework #2 onward is mechanical. **Do this last** — only after StoreKit 2 is genuinely shipping. Writing the strategy doc before there's evidence to ground it in produces speculation, not strategy.

#### Second + third frameworks (stretch for 0.8.0)

If StoreKit 2 lands cleanly and the strategy doc captures the pattern, ship a second (and ideally a third) Apple framework in 0.8.0 to prove the pattern is reusable, not a one-off:

- **WeatherKit** — second-best strategic value, similar surface (async-heavy, `Result`-style errors), no UI requirements, easy to demo
- **TipKit** — third candidate, exercises a different pattern (UI-driven, value types), proves the strategy generalizes beyond service APIs

If Phase 1 only ships StoreKit 2 in 0.8.0, that's still a success — the strategy doc and reusable infrastructure are the more important deliverables.

#### Phase 1 done criteria

- At least one published Apple-framework NuGet package (StoreKit 2 minimum)
- A real MAUI / .NET iOS sample app consuming it end-to-end (StoreKit 2: completes a sandbox subscription purchase)
- `Future/apple-framework-binding-strategy.md` written, capturing every answered strategy question above
- The pattern is reusable enough that adding the next Apple framework is a mechanical exercise, not another design effort

### Phase 2 — Multi-Platform Validation (macOS / Mac Catalyst / tvOS)

**Start once Phase 1 is locked.** This is the most desperately needed validation gap right now. The roadmap's Theme E completed the architecture audit — generator, SDK, runtime, and build infrastructure all properly support iOS, macOS, Mac Catalyst, tvOS. But the **only published packages run on iOS in practice.** "Any xcframework → NuGet" is a hollow claim until at least one shipping library is proven on a non-iOS platform end-to-end.

**Concrete first step for 0.8.0**:
1. Pick the simplest shipping library — **Nuke** (pure-Swift, no UIKit) is the obvious target
2. Wire a `Nuke.MacOSTests` or similar test project under `swift-dotnet-packages/tests/`
3. Get it running on Mac Catalyst first (smallest delta from iOS), then native macOS
4. Document any platform-specific gotchas surfaced
5. Stretch: do the same for Lottie

**Done for Phase 2** = at least one published library runs end-to-end on at least one non-iOS platform with a green test pass. **Done for 1.0** = all shipping libraries proven across iOS, macOS, Mac Catalyst, and tvOS where the underlying Swift library supports them.

This also informs the publishing pipeline: NuGet packages need to declare correct multi-TFM support (`net10.0-ios`, `net10.0-macos`, `net10.0-maccatalyst`, `net10.0-tvos`) and the SDK templates need to handle platform conditioning.

### Phase 3 — Stripe Hardening + Ship

**Start once Phase 2 is locked.** Stripe is probably already good enough to have shipped with 0.7.0 — the work in this phase is **confidence-building, not feature work**.

What "hammering it" means:
- Expand the existing `Stripe.SimTests` coverage to exercise more real consumption patterns (PaymentSheet flows, customer/setup intents, Apple Pay paths, error paths)
- NativeAOT iPhone validation through `/regression-validation` — confirm everything green
- Polish the sample app — a real consumer should be able to copy it and have a working integration
- Document any gotchas found during hammering (entitlements, capabilities, server-side requirements)
- Publish `SwiftBindings.Stripe` to NuGet with the same release rigor as Nuke and Lottie

If the hammering surfaces real generator/runtime bugs, those become Phase 3's actual work. If everything holds up, the package ships.

## Reframed 1.0 Definition of Done

A 1.0 release should look like:

**Apple frameworks** (the headline):
- StoreKit 2 (P0)
- WeatherKit (P0)
- TipKit (P1)
- App Intents (P1)
- Foundation Models (P1, if iOS 18.1+ scope is acceptable)

**Strategic third-party SDKs** (the real value-fillers):
- Nuke (shipped)
- Lottie (shipped)
- Stripe
- BlinkID / BlinkIDUX (if commercial story holds)
- Mappedin (if commercial story holds)
- Kingfisher (TBD vs Nuke)

**Multi-platform proven**:
- All shipping libraries running on iOS, macOS, and Mac Catalyst with green tests
- tvOS where the underlying library supports it
- One sample app per shipping package, not just `SwiftBindingsSamples`

**Quality bars**:
- Skip rate stays where it is (~15% — already not the constraint)
- Zero open upstream bugs unfiled
- All known bugs in the project's own code triaged and fixed or documented as out-of-scope
- Wiki documentation complete enough for a stranger to consume the bindings

The skip-rate metric in the current roadmap is **over-indexed**. It's already at a point where further reduction has diminishing returns on real consumers. 1.0 should be measured by **what shipping packages exist and where they run**, not by skip percentages.

## Open Decisions

These need answers as Phase 1 work commits in earnest. None are hard blockers — they're real decisions that benefit from being made deliberately rather than by default, but Phase 1 work can start before any of them are settled.

1. **Apple framework package naming convention**: `SwiftBindings.StoreKit2` vs `SwiftBindings.Apple.StoreKit2` vs something else. Pure ergonomics — pick whatever scans cleanest in `using` statements and consumer project files. Microsoft uses bare framework names (`Microsoft.iOS.StoreKit`), so the trademark surface is well-trodden; nominative use is legally fine and a sensible README disclaimer covers the rest.
2. **Where Apple framework wrapper Swift packages live**: this repo? `swift-dotnet-packages`? A new dedicated `swift-dotnet-apple-frameworks` repo? Lean toward a new dedicated repo if the count grows past a handful, otherwise start them in `swift-dotnet-packages` and move later.
3. **iOS-version availability surfacing**: how do `@available(iOS 15, *)` constraints translate to C#? Options: TFM-only (let `net10.0-ios15.0` gate it), runtime guards via `OperatingSystem.IsIOSVersionAtLeast`, `[SupportedOSPlatform]` attributes on the generated C#, or some combination. Probably want at least the attributes for tooling support. Not blocking the first framework — pick a reasonable default and refine across frameworks.
4. **Kingfisher**: ship as a NuGet package alongside Nuke (with a comparison doc), consolidate on Nuke alone, or defer the decision? *(Affects Background cleanup, not Phase 1.)*
5. **BlinkID / BlinkIDUX / Mappedin**: confirm they belong in the shipping pool. They're commercial verticals with no .NET alternative, but the audience is narrower than Apple framework bindings. *(Affects Background cleanup.)*
6. **Final cleanup list for `swift-dotnet-packages`**: which libraries beyond GRDB should move to `sim-validation`? *(Affects Background cleanup.)*
7. **Naming for `sim-validation` private repo**: e.g., `swift-bindings-sim-validation`? `swift-dotnet-internal-validation`? *(Affects Background backup task.)*

**Resolved**:
- ~~Should we run a feasibility spike before committing to Phase 1?~~ **No.** Feasibility is assumed; the strategy is the work. Commit and learn.
- ~~Is Apple trademark a blocker for publishing `SwiftBindings.StoreKit2` etc.?~~ **No.** Microsoft.iOS uses bare framework names and has for years. Nominative fair use covers it. README disclaimer handles the rest.

Explicitly deferred. The point of this doc is to be narrow — the roadmap was the place where every small idea accumulated, and that didn't serve planning well. For 0.8.0, we resist that gravity.
