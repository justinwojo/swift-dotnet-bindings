## D1 — The 1.x compatibility contract

**Question**: In the 1.x line, do Runtime/generated-binding contract breaks (the dispatch/ABI seam
between `Swift.Runtime` and generated bindings) wait for 2.0 — i.e., are minors additive-only?

**Recommendation**: **YES.** The dispatch contract has broken once in the observable record (the 0.16
floor bump); the epoch handshake and reflective backstops were designed for additive evolution; and a
"1.0" whose minors can still fracture consumers via NU1107 is branding, not a contract
(`version-coexistence.md` "Revisit at 1.0"; Claude review §4.1).

**Consequences if YES** (implemented in ranked action #7):
- `RuntimeVersionRange.Build` emits a next-**major** ceiling for 1.x inputs: `[1.Y.Z, 2.0.0)`.
- An ApiCompat baseline (or release-lane-only equivalent with explicit "skipped offline ≠ pass"
  handling) must be enforced **before the first post-1.0 release** — 1.0 itself needs no baseline.
- The written promise is published (wiki + release notes) as a commitment.

**Consequences if NO**: ship 0.18; keep the bounded-minor policy; revisit this record when ready.

**DECISION**: ☐ YES — major-only breaks in 1.x  ☒ **NO — stay 0.x (0.18 path)**

*Rationale (owner, 2026-07-10): not enough real-world feedback yet to commit to a strict versioning
contract — too many variables to risk digging a hole abiding by it prematurely. 1.0 comes after 0.18
has circulated and usage feedback gives a good signal.*

## D2 — RuntimeContract floor at 1.0

**Question**: Does `RuntimeContract.MinimumSupportedGeneratedVersion` reset from 16 to **1000** at 1.0
(rejecting 0.x-era bindings on the load-time gate's bypass paths)?

**Recommendation**: **YES.** NuGet restore already separates 0.x bindings from a 1.x runtime; keeping
the floor at 16 only preserves an unsupported bypass-path claim. Resetting buys the clean quantifier
"every binding a 1.x runtime loads was generated by a 1.x-era generator" — the same population D1
quantifies over. The floor↔minor unit guard is updated in lockstep (Claude review §4.2).

**DECISION**: **MOOT** — D1 = NO, staying 0.x; floor stays 16. Re-decide when the record is
revisited for 1.0.

## D3 — Package support tiers

**Question**: Adopt the four-tier support model for the shipped package portfolio, with claims (wiki,
README, release notes) required to match tiers?

**Tier definitions**:
- **Verified** — at least one headline functional round-trip test in the harness; known-dark paths
  documented; regressions here block releases.
- **Preview** — compile- and load-proven; documented dark/untested paths; issues triaged best-effort.
- **Community** — published as-generated; no functional claim; issues welcome, no SLA.
- **Parked** — not regenerated/republished until demand appears.

**Recommendation**: **YES.** Tier labels replace the "all 26 packages hardened" trap; only
Verified-tier packages get new functional tests pre-1.0 (Claude review §4.3). Initial per-package
assignments are made during ranked action #8 using `BindingAudit/_SUMMARY.md`; packages with open
trust findings (e.g. Stripe pending `AppInfo` classification; RealityFoundation/RoomPlan/BlinkIDUX
pending fail-closed regeneration) cannot sit above **Preview** until those close. Tier assignments are
owner calls and get appended to this record when made.

**DECISION**: ☐ YES — adopt tiers  ☒ **NO** (alternative: keep the current uniform claims — the
owner judges existing test depth sufficient for confidence on most packages; no public tier labels.
the tier proposal (`1.0-tier-and-claims-proposal.md`, deleted 2026-07-13, retrievable from git
history) stands as evidence/reference, not as pending work.)

## D4 — Certified platform/architecture matrix

**Question**: Which platforms does 1.0 *certify* (runtime-gated per release) versus support best-effort?

**Recommendation** — certify exactly what has a runtime gate in the harness today:

| Platform | Runtime | Proposed status |
|---|---|---|
| iOS Simulator | Mono JIT | **Certified** |
| iOS device | NativeAOT | **Certified** |
| macOS arm64 | CoreCLR | **Certified** |
| macOS x64 | CoreCLR | **Certified** (baseline-gated) |
| Mac Catalyst | Mono | **Certified** |
| tvOS Simulator | Mono JIT | **Certified** |
| tvOS device | NativeAOT | **Best-effort** — no device runner exists (post-1.0 roadmap item) |

Anything not listed (watchOS, visionOS, Windows host) is **unsupported** and stated as such.

**DECISION**: ☐ Adopt as proposed  ☒ **Amendments**: no formal certified-platform matrix is
published. iOS is the primary focus and expected user base; macOS, Mac Catalyst, and tvOS are
supported because they were sensible given the effort, without a formal certification claim. The
existing runtime gates keep running as-is.
