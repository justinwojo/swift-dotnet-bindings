# Claude Code Guide for Swift Bindings

Swift/.NET interop: generates C# bindings from compiled Swift libraries (`.dylib` + ABI JSON) for .NET 10.0 on Apple platforms. MIT licensed, maintained by Justin Wojciechowski.

## Repository Structure

- `build/` — Nuke Build targets (C#) + `validation-libraries.json` + `scripts/` (e.g. `coverage-report.py`)
- `src/Swift.Bindings/src/` — Generator: Parser → TypeDatabase → Marshaler → Emitter
- `src/Swift.Bindings.Sdk/` — MSBuild SDK (`SwiftBindings.Sdk`): `Sdk.props`, `Sdk.targets`
- `src/Swift.Bindings.Templates/` — `dotnet new swift-binding` template
- `src/Swift.Runtime/src/Swift/` — Runtime library (NuGet: `SwiftBindings.Runtime`)
- `BindingTests/` — End-to-end test library + runtime tests (Simulator + Device/NativeAOT)
- `src/docs/` — Internal design docs, roadmap, known issues
- Public docs: [GitHub wiki](https://github.com/justinwojo/swift-dotnet-bindings/wiki) (separate repo)

## Building & Testing

**Always use `nuke <target>`, not raw commands.** For slow targets, pipe to a temp file (`2>&1 | tee /tmp/<name>.txt`) and Read it — never re-run a slow command just to see a different slice of output.

| Target | Time | Purpose |
|---|---|---|
| `nuke compile` | fast | Build the project |
| `nuke test` | ~2 min | Unit + integration tests |
| `nuke validate` | ~5 min | Compile gate across real-world libs. Flags: `--tier N`, `--filter X` |
| `nuke fetch` | — | Download xcframeworks (first time only) |
| `nuke binding-tests [flags]` | varies | End-to-end BindingTests gate — see flag table below |
| `nuke pack --version X.Y.Z --apple-version A.B.C` | fast | Build all 4 NuGet packages (Runtime, Sdk, Templates, Apple) → `$TMPDIR/swift-nuget/` (macOS `/var/folders/...`, not `/tmp`). `--apple-version` is **required** (pack hard-fails without it so the Apple supplement can't silently ride an unrelated version); pass `--skip-apple` to ship the 3 SDK-lane packages only. The Runtime pack is **ApiCompat-diffed** against the last shipped `SwiftBindings.Runtime` (default: highest stable `sdk-v*` tag below `--version`; override with `--api-compat-baseline X.Y.Z`) — a removed or reshaped public member, including an optional parameter added to an existing method, fails the pack. The baseline nupkg is downloaded from NuGet; `--skip-api-compat` is the loud opt-out for offline local packs only. The Runtime and Apple packs are also checked for **transition evidence** from the nupkg alone (`Build.PackageTransitionEvidence.cs`, `PackageTransitionEvidence.Check`): every `lib/*/` assembly embeds a valid transition manifest, the transition gate's rules (R1 through the residual-guard check, R2–R5, routing and evidence gaps, twin count) pass against the manifest's own plans and guards, and every native slice holds the manifest hash and exports exactly the bridges it names (the runtime's linked-bridge check reads its plans from the packed manifest). Four negative controls run on every pack and must go red: a tampered manifest, a manifest removed from an assembly that imports bridges, a renamed bridge twin (runtime, R3), and the routing fixture removed. Policy, not baseline: nothing to reseed. Pack also runs the **packed residual-guard check** (`Build.PackedResidualGate.cs`, no flag, no baseline): every `lib/<framework>/` copy of `Swift.Runtime.dll` and `SwiftBindings.Apple.dll` must reach each known-unsafe direct Swift transition only through a member that refuses it first, the supplement's copies must agree with its guard sidecars, and a seeded unguarded package must fail the same check. |
| `nuke swift-transition-gate` | varies | Run after `binding-tests --compile-only`. Scans the compile-check assembly, `Swift.Runtime.dll` and `SwiftBindings.Apple.dll` for managed↔Swift transitions the .NET 11 interpreter mishandles (rules R1–R5), runs the residual-guard check on each and the ledger cross-check on the two with transition ledgers (the compile-check assembly and the Apple supplement), and writes `swift-transition-{report,inventory,summary}` under `BindingTests/output/.swift-transition-gate/`. The default run also builds, generates and scans a **thunk-only fixture** (`BindingTests/Sources/ThunkOnlyFixture/`, `Build.ThunkOnlyCensus.cs`), the one artifact shape the compile-check tree lacks: every member reaches Swift through a native assembly thunk, and the wrapper's Swift holds only module infrastructure. The census fails closed if that assembly is not scanned, a member moves to a `@_cdecl` wrapper, a member loses its thunk import, or the assembly imports a thunk the wrapper does not export. `--transition-gate-assembly` scans other assemblies instead (no census). R1 counts every non-primitive Swift-convention import, guarded or not, so the compile-check tree stays red on R1 while guarded residuals remain (they are listed in `swift-transition-residual-guards.CompileCheck.txt`); R2–R5, the cross-check, the residual-guard check and the census must pass. |
| `nuke swift-bridge-gate` | varies | Emits and validates the native bridge of every plan (corpus and hand-written tables) on arm64 and x86_64, plus the frame and unwind information of every generated native thunk. |
| `nuke swift-lowering-oracle` | varies | Opt-in, host-only: compiles the corpus with swiftc for the regenerated platform's slices, compares predicted signatures and layouts with the IR, and records lowering receipts into `build/baselines/swift-lowering-evidence.json`. Rerun under each toolchain profile, once per routed platform (`--platform tvos`, `--platform maccatalyst`), after a compile-only regeneration that changes plans. `nuke swift-bridge-products` rewrites the hand-written tables' plan sidecars and the runtime's bridge assemblies. |

### Toolchain profiles and supported pairings

The release supports three .NET/Xcode pairings, each pinned by a profile under `build/toolchains/` (that directory's `README.md` holds the exact SDK, workload and Xcode pins and the release cadence):

| Profile | Pairing | Role |
|---|---|---|
| `net10-xcode26` | .NET 10 + Xcode 26.3 | Compatibility lane; also what the unprofiled `nuke …` workflow runs (global `/usr/local/share/dotnet`, Xcode 26.3 selected) |
| `net10-xcode27` | .NET 10 + Xcode 27.2 | .NET 10 release anchor |
| `net11-xcode27` | .NET 11 + Xcode 27.2 | .NET 11 release anchor, including Debug builds on the CoreCLR interpreter |

Run any target through a profile with `bash build.sh --toolchain-profile <profile> -- <target> [flags]`. The launcher validates the installed SDK, workloads and Xcode, then runs Nuke in a disposable copy of the checkout at `artifacts/toolchains/<profile>/workspace/` with its own `DOTNET_ROOT`, `DEVELOPER_DIR`, NuGet cache and `TMPDIR`. Any source change rebuilds that workspace, which also wipes its `BindingTests/output`, so don't edit the tree while a profile gate runs. Profile runs refuse every baseline write (`seed-*`, validation promotion) except `--seed-runtime-identity-baseline` on a .NET 11 lane, whose result the launcher copies back to `build/baselines/runtime-identity-net11-baseline.json`; hand-merge any other baseline change. Before a release the full matrix runs on all three profiles; every change runs the unprofiled lane, plus `net11-xcode27` when it touches marshalling, calling conventions or runtime dispatch.

**.NET 11 lanes and their floors.** Under `net11-xcode27`, `nuke binding-tests` builds the RuntimeTestsApp for `net11.0` (the unprofiled default is `net10.0`; `--binding-test-framework net11.0` selects it explicitly). Each lane is graded against its own count-and-identity floor in `build/baselines/runtime-identity-net11-baseline.json`, keyed `net11.0_<platform>_<rid>_<engine>_<configuration>`:
- **Debug** (`--coreclr-interp`): the CoreCLR interpreter on the iOS and tvOS simulators, Mac Catalyst (arm64, and x86_64 under Rosetta) and a device (`--device --coreclr-interp`). Each class proves it ran on the interpreter (see `--coreclr-interp` below).
- **Release** (`--binding-test-configuration Release`): ReadyToRun on the iOS and tvOS simulators, with Release floors for Mac Catalyst and macOS too; `--device --core-clr --binding-test-configuration Release` is device ReadyToRun; plain `--device` is NativeAOT. macOS has no interpreter, so it has no Debug floor.
- A lane with no floor fails unless `--allow-unqualified-runtime` is passed, which reports the run UNQUALIFIED. Seed or raise a floor with `--seed-runtime-identity-baseline`; a Debug floor below the lane's previous Debug floor or its Release floor needs `--identity-floor-justification "<why>"`.
- The .NET 10 lanes keep their floors in `build/baselines/runtime-identity-baseline.json` (`simulator`, `device`, `device_monoaot`, `macos`, `maccatalyst`, `tvos_simulator`).

Other .NET 11 qualification targets: `nuke verify-managed-compatibility` (the .NET 10 generator hosted on 10-only, 11-only and mixed runtime installs, plus a .NET 11 desktop consumer of the .NET 10 Runtime), `nuke verify-net11-package-consumer` (restores .NET 11 Apple consumers of the .NET 10 packages and compiles their public APIs), `nuke core-clr-canary` (a package-only CoreCLR interop canary, Debug and trimmed Release) and `nuke toolchain-profile-tests` (the launcher's checkout and process isolation).

### `nuke binding-tests` flags

One target covers the compile gate and every runtime gate. Platform flags compose — `--sim --device` runs both pipelines back to back.

| Flag | What it does |
|---|---|
| *(no platform flag)* | Default: compile + run iOS Simulator (Mono JIT) — the common inner loop |
| `--compile-only` | Compile gate only: regenerate + compile-check. No app build, no tests. Used by CI. **Fail-closed by default**: generator non-zero exit, dependency-gen exit, and wrapper compilation give-up all hard-fail. |
| `--sim` | Explicit iOS Simulator (Mono JIT) |
| `--device` | Physical iOS device (NativeAOT) |
| `--mono-aot` | **Opt-in, requires `--device`.** Re-flavors the device lane: builds the RuntimeTestsApp under **Mono full-AOT** (`dotnet build -c Debug -r ios-arm64`, no `PublishAot`) instead of NativeAOT, installs, and runs the full suite. This is the .NET-for-iOS **default** device runtime — what a MAUI app ships on unless its author opts into `PublishAot` — and the fourth runtime in the taxonomy alongside Mono JIT (sim/Catalyst), CoreCLR (macOS) and NativeAOT (device). Fails fast without `--device`. See note below. |
| `--macos` | macOS |
| `--catalyst` | Mac Catalyst |
| `--tvos` | tvOS Simulator |
| `--strict` | Fail on non-zero generator exit (implied by `--compile-only`'s default; every regeneration path — all runtime lanes plus the standalone `regenerate-bindings` / `compile-check-bindings` / `build-async-wrapper` targets — is fail-closed on that exit by default too) |
| `--permissive` | Opt out of the fail-closed gates — `--compile-only`'s, and every regeneration path's non-zero-generator-exit gate (runtime lanes *and* the standalone regen targets). Local-exploration only. |
| `--skip-regen` (~17s) | Skip binding regeneration; assumes bindings are current |
| `--skip-build` (~5s) | Skip app build; just install + run. Every build records a receipt beside its app bundle (lane, toolchain, source state, bundle digest). `--skip-build` refuses an app with no receipt or one built for another lane or toolchain. It grades the run against the runtime baselines only when the receipt proves the app is the current build. Otherwise the results are reported as a partial run. |
| `--build-only` | **iOS and tvOS Simulator only.** The first half of a simulator run: regenerate (unless `--skip-regen`), build the app, inject its frameworks, record its receipt, then stop before install and launch. A later `--sim --skip-build` (or `--tvos --skip-build`) run installs and runs exactly that build, and is graded like a fresh build because the receipt proves it is one. CI uses the split to build before it boots a simulator, since a booted simulator slows builds on the hosted runners two- to three-fold. Composes with toolchain profiles and `--binding-test-configuration`. Refused with `--skip-build`, `--compile-only`, device, macOS and Catalyst flags, opt-in focused legs, `--abi-grid`, `--seed-runtime-identity-baseline` and smoke flags. Example: `nuke binding-tests --build-only --skip-regen`, then boot, then `nuke binding-tests --sim --skip-build`; for tvOS, `--tvos --build-only`, then `--tvos --skip-build --device-udid <tvOS UDID>`. |
| `--class-filter NAME` | Run only one test class (Simulator path) |
| `--harness-stall-probe` | **Harness self-test; the run fails by design.** Every runtime launcher (simulator, device, macOS, Mac Catalyst; every engine) takes the app's stacks when a launch's budget (`--timeout`, default 420 s) runs out with the app still running: lldb attaches twice, 5 s apart (`sample` is the host fallback), each run bounded (60 s on the host, 120 s on a phone) and killed if it overruns, before the stall kill. The samples land as `hung-stacks-{1,2}.txt` beside the attempt's `console.log`, `launch.json` records them, and the lane's timeout failure names them; the result and exit code stay the stall's. This flag makes the app block forever in its first test (first launch only), so the capture can be proven: e.g. `nuke binding-tests --sim --harness-stall-probe --class-filter OptionalProtocolMembersTests --timeout 60`. Never in a normal run. |
| `--skip-surface` | Layer B skip-surface **trend** gate. Final post-step in the `--compile-only` path (after the parity, API-manifest, resilience-kitchen and ingestion-kitchen gates): parses skip markers straight out of the generated `.cs` under `BindingTests/output/` and diffs against `build/baselines/skip-surface-baseline.json`, ratcheting skip-class counts downward over time. Run by CI in the release gate. Scans the generated files rather than a metrics sidecar on purpose — the markers ratcheted are exactly what a consumer reading the binding sees. |
| `--mixed-pack` | **Opt-in, heavyweight.** Packs a mixed (ObjC+Swift) binding into ONE nupkg and consumes it via a single `PackageReference` on iOS sim/device. Composes with `--sim`/`--device` (defaults to sim). Mutually exclusive with `--mixed-direct`/`--appstore-hygiene`/`--partial-success-kitchen`/`--apple-package-consumer`; never in the default run or `--compile-only`. See note below. |
| `--mixed-direct` | **Opt-in, heavyweight, sim-only.** Builds a mixed (ObjC+Swift) binding in **SDK-direct mode** — the app's OWN csproj imports `SwiftBindings.Sdk` + `<SwiftFramework>`, so the app IS the binding project (no PackageReference) — then runs it on the iOS Simulator. The runtime gate for consumption *path b*. Mutually exclusive with `--mixed-pack`/`--appstore-hygiene`/`--partial-success-kitchen`/`--apple-package-consumer`; never in the default run or `--compile-only`. See note below. |
| `--apple-package-consumer` | **Opt-in, heavyweight, device-only.** Rebuilds and packs `SwiftBindings.Runtime` + `SwiftBindings.Apple`, then NativeAOT-publishes a fresh iOS app whose only SwiftBindings dependency is one `PackageReference` to Apple. The app deliberately declares no `TrimmerRootDescriptor`, `IlcArg`, or other app-authored root, and passes only after `SwiftArray<Locale.Language>` materializes two canonical elements on a physical device. This is the D09 package-rooting regression gate. Mutually exclusive with `--mixed-pack`/`--mixed-direct`/`--appstore-hygiene`/`--partial-success-kitchen` and `--compile-only`; never in the default run. |
| `--appstore-hygiene` | **Opt-in, heavyweight, host-only.** TN2435 App Store hygiene gate (issue #42). Packs `SwiftBindings.Runtime` to a local feed and first asserts the runtime nupkg's native packaging *structurally* (cheap, no signing): the `SwiftBindingsRuntime.xcframework` device + simulator framework slices are present, `buildTransitive/` ships `SwiftBindings.Runtime.targets`, `SwiftBindings.MacFrameworkAnatomy.targets` and `deepen-mac-framework.sh`, there is **no** loose `libSwiftBindingsRuntime.dylib` and **no** `add-swiftsupport-folder.sh`, and `lipo -archs` on the extracted slices matches (device `arm64`, sim `arm64`+`x86_64`). Then, from one single-`PackageReference` consumer app, it runs an **IPA leg** (`ios-arm64`, `BuildIpa=true`) and asserts the finished `.ipa` is TN2435-compliant: the runtime embeds as a signed `Frameworks/SwiftBindingsRuntime.framework/SwiftBindingsRuntime` (install_name `@rpath/SwiftBindingsRuntime.framework/SwiftBindingsRuntime`, `codesign --verify --strict` passes), there is **no** loose `Frameworks/libSwiftBindingsRuntime.dylib`, **zero** `libswift*.dylib` embedded anywhere (a stable-ABI min-iOS-15 app links the OS-resident `/usr/lib/swift`), **no** top-level `SwiftSupport/` folder, no `.DS_Store`/`__MACOSX`, and the app signature verifies. It then runs **eight Mac framework-anatomy legs** — macOS and Mac Catalyst, each built, published, *and* published again after a forced framework re-copy (the workload's per-framework copy stamps wiped over the already-deepened bundle in `bin/`, which is what a package update or a lost `obj/` produces), plus a **universal** `osx-arm64;osx-x64` macOS app published and re-copy-published (the per-RID build-and-merge orchestration, where the step fires per inner build and again on the merged bundle) — which assert the opposite layout on those platforms: every framework embedded in the built `.app` must be a **deep versioned bundle** (`Versions/Current` → `A`, each root entry a relative symlink to exactly `Versions/Current/<name>`, the binary at `Versions/A/<Name>`, `Resources/Info.plist` resolving through the links, the binary's `LC_ID_DYLIB` install_name still resolving inside the rewritten bundle, every dylib in its dependency load commands either embedded under `Contents/Frameworks` or OS-resident with no `libswift*` outside `/usr/lib/swift`, and `codesign --verify --strict` passing on framework and app). Each publish leg additionally **expands the `.pkg`** the workload builds for a Mac publish (`pkgutil --expand-full`) and re-runs the same layout assertions on the payload app, since the installer package — not the `.app` in `bin/` — is what a Mac app is submitted as. Each leg then **launches the shipped `.app`** with a smoke argument that `dlopen`s every embedded framework through the rewritten layout and constructs a Swift string through the runtime framework — the one check that asks dyld directly. The fixture embeds the runtime package **and** a staged copy of the repo's `SBApple.xcframework` with an explicit `Resources/` marker as a positive control for a framework directory entry — the entry the workload's `ditto` copy cannot write onto once it is a root link. The Mac legs run **on the flag alone**, independent of `--macos`/`--catalyst`, and need no signing identity (those bundles sign ad-hoc). Builds + inspects on the build host (the IPA leg needs a signing identity; **no** device/sim — platform flags are ignored). Mutually exclusive with `--mixed-pack`/`--mixed-direct`/`--partial-success-kitchen`/`--apple-package-consumer`; never in the default run or `--compile-only`. |
| `--partial-success-kitchen` | **Opt-in, host-only, fast (~30s).** The *partial-success product gate*. Builds the deliberately-hostile `BindingTests/Sources/PartialSuccessKitchen/` fixture — a tiny pure-Swift module mixing three must-emit positive controls (`KitchenOk`, `KitchenOkClass`, and `KitchenForeignChildConfigurationProxy`, the proxy of a protocol whose parent lives in an SDK module the run never loads) with a dozen unsupported shapes (SwiftUI View, PATs/existentials, closure-bearing members, parameter packs, internal-parent members, synthesized Codable) — into a one-slice simulator xcframework, generates, and asserts five things fail-closed: the generator exits **0**, no `SWIFTBIND108` (dangling wrapper `EntryPoint`) in the log, the emitted C# **actually compiles** (a real `dotnet build`, not a string assert), every positive control is declared, and the skip report clears its design floors (`ReviewCount == 0`) **and matches `build/baselines/partial-success-kitchen-baseline.json` exactly**. No app build, no sim/device run. Mutually exclusive with `--mixed-pack`/`--mixed-direct`/`--appstore-hygiene`/`--apple-package-consumer`; never in the default run or `--compile-only`. See note below. |
| `--coreclr-interp` | **.NET 11 only** (`bash build.sh --toolchain-profile net11-xcode27 -- binding-tests --coreclr-interp ...`). Runs the RuntimeTestsApp as the ordinary **Debug** .NET 11 app on the **CoreCLR interpreter**, with no binding-specific ReadyToRun escape hatch, on whichever platform the run names: `--sim`, `--tvos`, or `--device` (where it implies `--core-clr`). Refuses .NET 10 and `--binding-test-configuration Release`. The matching precompiled legs are `--binding-test-configuration Release` (sim/tvOS ReadyToRun) and `--device --core-clr --binding-test-configuration Release` (device ReadyToRun); plain `--device` under net11 is NativeAOT. **Every .NET 11 RuntimeTestsApp lane proves its execution lane per test class**: the app (`--lane-identity`, passed automatically) calls a primitive Swift probe through the generated binding before each class, the probe reports its caller, and the harness requires every class with results to show the claimed lane (interpreter: `libcoreclr.dylib!CallJittedMethod*` and no precompiled app bodies in the crossgen2 map; ReadyToRun: a mapped body in `<App>.r2r[.dylib]`; NativeAOT: the executable, no map). A packaged device app is stripped of local symbols, so the host re-resolves each caller from its recorded offset against the build's unstripped copy under `obj/` (`dylibtoframework/`, `r2rframework/`). A lane that silently ran another mode, a class with no witness, or evidence also accepted under another lane fails the run before any baseline is graded. Crash recovery on .NET 11 lanes (sim, tvOS and device share one loop) budgets one relaunch per eligible class and also resumes after a crash in class setup or between tests, so a crash never hides the rest of the suite. Per-class results, interruptions and witnesses land in `artifacts/runtime-lanes/<platform>-<framework>-<engine>-<config>/lane-report.{txt,json}`. A Debug lane earns a runtime-identity floor only from its own run: `--seed-runtime-identity-baseline` on a Debug lane writes nothing unless the run proved the interpreter for every class, every negative control registered for the lane's interpreter architecture (`InterpreterNegativeControls`, chosen from the runtime identifier: arm64 runs the sret + self probe, x86_64, where that probe is fatal and excluded by name, runs a struct-lowering probe) was in the app, ran isolated and graded as expected, every class the set excludes matched the app, and the floor does not drop below the lane's previous Debug floor or its Release floor (pass count with the isolated and excluded control tests added back, and skip set) — a lowering needs `--identity-floor-justification "<why>"`, which is written into the entry. A seeded Debug lane is graded like any other; an unseeded one still needs `--allow-unqualified-runtime`. macOS has no interpreter (Debug runs the JIT) and gets no Debug floor. |
| `--interp-identity` | **Opt-in, .NET 11 only** (`bash build.sh --toolchain-profile net11-xcode27 -- binding-tests --interp-identity`). Lane-identity harness: generates a binding from `BindingTests/Sources/InterpIdentityFixture/`, builds `BindingTests/InterpIdentityApp` for four cells (iOS sim arm64 Debug interpreter / Release R2R, Mac Catalyst x86_64 under Rosetta Debug / Release) and runs each fixture in its own process. It proves each cell's lane per call from receipts (`dladdr` of the Swift entry point's caller, crossgen2's `--map` inventory and command line), never from process-wide flags, and rejects a seeded mislabel of every cell. Negative controls must reproduce today's interpreter defects, positive controls must pass. A measured `ReadyToRunGap` (a method crossgen2 leaves to the runtime) must still hold, or the cell fails. Receipts land in `artifacts/interp-identity/receipts/`. `--interp-identity-cells M1,M3` selects cells. Needs a booted simulator (`--device-udid`). Never in the default run or `--compile-only`, and mutually exclusive with the other opt-in legs. |
| `--bridge-consumer` | **Opt-in, iOS + Mac Catalyst + tvOS** (.NET 10: `binding-tests --bridge-consumer [--sim] [--device --device-udid <UDID> [--mono-aot]] [--catalyst] [--tvos]`; .NET 11: `bash build.sh --toolchain-profile net11-xcode27 -- binding-tests --bridge-consumer --coreclr-interp [--sim] [--device …] [--catalyst] [--tvos]`; iOS simulator when no platform is named). The ordinary consumer of the Swift bridges. It builds `BindingTests/Sources/BridgeConsumerFixture/` into a device + simulator xcframework (iOS), one universal arm64 + x86_64 slice (`--catalyst`), or an arm64 device slice plus a universal arm64 + x86_64 simulator slice (`--tvos`, run on the arm64 tvOS simulator) and binds it through `SwiftBindings.Sdk` with **default settings and no `<SwiftLoweringEvidence>`**: the SDK's wrapper compile collects the module's lowering receipt and routes what it authorizes in the same build. The binding is consumed in three modes against a throwaway Runtime/Sdk/Apple feed — `package` (packed, one `PackageReference`), `direct` (the app imports `SwiftBindings.Sdk` and declares the `<SwiftFramework>`) and `projectref` (a `ProjectReference` to the binding project). A fourth consumption mode, `cli`, generates the fixture through the generator CLI instead (`--xcframework`, the documented standalone path, no SDK), twice into one output directory, requires each generation to have collected its receipt and routed every routable member on its own (the standalone run takes the SDK's collection and routing defaults; see `src/docs/Design/swift-lowering-evidence.md` § Standalone generator runs), and consumes the generated project through a `ProjectReference` and its `.ProjectReference.targets`. `--bridge-consumer-modes package direct projectref cli rollback transition` narrows them. The `rollback` mode forces the SDK's bridge relink to roll back after it ran (`SWIFT_BINDINGS_FORCE_BRIDGE_ROLLBACK`, SWIFTBIND129, a warning naming the withdrawn members and the engines they refuse on). Such a binding must pack as a **partial binding**: its call plans record the withdrawal (`bridgeWithdrawal`: cause, reason, library, each restored transition with its shapes and refusing engines), and the pack and consumer checks accept the gaps it explains only when the assembly and every shipped slice hold up as that record (guarded restored imports, nothing still bridged, no bridge or manifest hash left in any slice; a receipt contradiction is never accepted, and the strict reading still refuses every gap). The mode packs a fresh rollback and a rollback after a routed build, checks both from the nupkg alone, runs five doctored controls (unrecorded gap, inconsistent record, dangling bridge import, missing guard, the routed build's wrapper) through the engine and the packaged SWIFTBIND133/132 tasks, each refused for its own reason, and builds a clean `PackageReference` consumer that must record the binding `Verified`, get correct results from the members that need no bridge, and see the withdrawn getter throw before Swift runs on every engine its record names. On a device NativeAOT runs both of that getter's shapes and Mono full-AOT refuses its `SelfRegister`. Contract: `src/docs/Design/consumer-transition-check.md` § Partial bindings. Another mode, `transition` (after `package`, which it needs), is the end-to-end gate of the **consumer transition check** that `SwiftBindings.Runtime`'s buildTransitive targets run in every app on Mono and the .NET 11 CoreCLR engines (SWIFTBIND132; `src/docs/Design/consumer-transition-check.md`): on each simulator or Catalyst family it builds Debug and Release consumers of the freshly packed binding (must build, and the check's cache must record it `Verified`), of a manifestless first-party fixture with an untyped-`SwiftSelf` Swift import (must fail with SWIFTBIND132 naming the assembly, package, member and remedy), and of a manifestless primitive-only fixture (must build, recorded `PrimitiveOnly`); the iOS family adds the unsafe fixture with `<SwiftBindingsTransitionSuppress>` (warning, not error) and from a macOS app (not checked), and builds the three consumers again for the device (`ios-arm64`, Debug and Release, unsigned and never installed, so no phone and no `--device`): Mono full-AOT on .NET 10, the CoreCLR interpreter (Debug) and ReadyToRun (Release) on .NET 11. Results land in `receipts/<platform>/transition/`. The `package` mode's pack also runs the SDK's pack-time check (SWIFTBIND133), which deletes a binding package its consumers would refuse. The oracle records the fixture's swiftc lowering as a cross-check only: each build's collected receipt must agree with it and show the bridged target on every slice, and its sidecar must route `BridgeAccount.settled` (a throwing getter on a custom-global-actor class, which the `@_cdecl` wrapper refuses). The app checks values and receiver state across success → error → success of that getter, an ordinary class's method whose optional existential result Swift returns indirectly (`BridgeLedger.ceiling()`, self in the self register), element reads through `SwiftArray`'s getter, the fixture's live-object count before and after, and a callee-saved-register sentinel around both bridges. Each measured call records its stack; the host requires the routed `SBSR_` bridge under the Swift code and the lane's managed caller under the bridge on every call: `CallJittedMethod*` (.NET 11 interpreter), code in the app executable (.NET 10: NativeAOT, and Mono, which the SDK AOT-compiles on the device, the arm64 iOS and tvOS simulators and arm64 Catalyst), and on .NET 10 Catalyst x86_64 the Mono interpreter's `do_icall` in the app for a package consumer (the package's targets default the interpreter on) or code the Mono JIT generated, in no image, for SDK-direct and ProjectReference apps, which import no such targets. Run it after changes to bridge emission or routing, the bridge assembly, the SDK's generation or wrapper-compile path, or the runtime's bridged imports. The compile gate (`--compile-only`) and the runtime gates are complementary: the first asks "does it compile?", the second asks "does it pass?". Generator/emitter changes want both — run `nuke binding-tests --compile-only` then `nuke binding-tests --skip-regen`. For runtime-only C# changes, `nuke binding-tests --skip-regen` alone is enough.

**Gates inside `--compile-only` that have no flag.** Several gates run on *every* `--compile-only` invocation and are deliberately not opt-in — there is no CLI switch to skip them, and `--skip-surface` is the only compile-gate step that is flag-gated. In run order: the wrapper-strip tripwire and the wrapper getter-parity oracle (inside the async-wrapper build), the **consumer-shape equivalence gate** (`Build.BindingTests.ConsumerShape.cs`, inside regen, right after the dependency is generated), the ObjC-umbrella xcframework build + regen (iOS only) and the CSM recovery-annotation assertion (inside build/regen), then the **artifact-parity gate**, the **API-manifest gate**, the **resilience-kitchen gate**, the **ingestion-kitchen gate**, and the **overload-name gate** (reads the resolver's own disambiguation records from the generated `binding-report.json`s and fails if any overload name is a bare numeric suffix — policy, not baseline, so it has no reseed target and no `--permissive` arm). The gate reads *two* record lanes and judges them differently: `OverloadRenames` is the one under the no-numeric-suffix policy, while `CaseOnlyRenames` (two sibling Swift names differing only by case — `url` alongside `URL` — which carry no labels or parameter types to name a member by) is **reported, not failed**, since a numeric suffix there is that arm's designed output. Both lanes carry a fail-closed empty-ledger positive control, so a lane that stops reaching the artifact reds the gate rather than passing it vacuously. Near the end of that unconditional run is the **thunk weak-link gate** (`Build.ThunkWeakLinkGate.cs`). Thunks name their targets in hand-written assembly, outside swiftc's availability weak-linking, so they carry `.weak_reference` directives. Without those, a member floored above the deployment target makes dyld refuse to load the wrapper, and the app with it, on an older OS (issue #49). The gate checks both wrappers at two levels:
- **Object level.** It assembles every emitted thunk file and fails if any undefined symbol of the object is strong.
- **Linked-binary level.** It reads the wrapper back with `dyld_info -imports` and fails if any import of the iOS 99 fixtures in `RuntimeAvailabilityGuard.swift` is strong, whether a thunk or Swift code references it, or if a fixture the generator binds through a thunk no longer arrives through one.

A thunk target that is still strong in the linked wrapper is not a failure on its own. The linker keeps an import strong when Swift code also references it unconditionally. The gate is policy, not baseline: no reseed and no `--permissive` arm.

Right after it runs the **cdecl ABI parity gate** (`Build.CdeclAbiParityGate.cs`, verdict in `build/Models/CdeclAbiParity.cs`). The generator emits each `@_cdecl` Swift function and the C# P/Invoke that calls it from separate code, so the two can disagree and still compile: a C# `int` against a Swift `Int` usually runs, because the upper half of the register is usually zero, and breaks on an engine that leaves it dirty (the .NET 11 device interpreter did). The gate reads the generated Swift (main wrapper, dependency wrapper, SwiftUI bridge) and every generated `.cs` under `BindingTests/output/`, pairs each `LibraryImport`/`DllImport` with the `@_cdecl` of the same library and entry point, and fails on any argument or return in a different register class (integer or floating-point) or width. Pointers, `ref`/`out`/`in`, `inout` and function pointers count as pointer-width, and C# `bool` follows its marshalling (`MarshalAs(U1)` is one byte). An argument whose lowering text can't decide (a struct or enum by value) is skipped and counted, and a pair holding one is not arity-checked. The gate logs pairs, checked and skipped arguments, and per-library counts. It fails below 10,000 pairs, when a library has no pairs, or when its positive control (the array-parameter `RawShadeView_Create` bridge call) is not checked argument by argument. It is policy, not baseline: no reseed and no `--permissive` arm.

Later in the run comes the **call-convention attribute gate** (`Build.CallConvAttributeGate.cs`). It reads `CompileCheck.dll`, `SwiftBindings.Apple.dll` and `Swift.Runtime.dll` from metadata and fails on any P/Invoke whose `[UnmanagedCallConv]` names `CallConvCdecl`, or names no convention at all. The Mono AOT compiler decodes the attribute of every P/Invoke that carries one, allocating as it goes and unable to collect, and aborts (exit 134) once an app carries a few tens of thousands of them. C is the platform default on every Apple target, so the generator writes the attribute only for the Swift convention, through `PInvokeEmitHelper.CallConvAttributeLine`. The gate logs the P/Invoke, attributed and Swift counts per assembly and fails an assembly whose census found no Swift attribute, so it cannot pass without reading anything. It is policy, not baseline: no reseed and no `--permissive` arm. Readers of generated code treat a missing attribute as C, and `AbiContractChecker` still flags a `$s…` entry point that lost its Swift attribute (CC-004).

Then it runs the **transition ledger cross-check** (`Build.SwiftTransitionGate.cs`), which the Mac Catalyst and tvOS runtime lanes also run over compile checks of their own output. It joins each module's transition ledger with the compiled assembly's Swift transitions, then checks the **shipped transition evidence**: `CompileCheck.dll`, `Swift.Runtime.dll` and `SwiftBindings.Apple.dll` must each embed valid transition manifests (`SwiftTransitionManifestReader`, state `PresentValid`), `CompileCheck.dll` must carry one manifest per BindingTests module, and on a routed platform at least one of them must route bridges. Every framework slice of each wrapper a manifest routes through must hold the manifest's `SBTM_<module>` hash and export exactly its `SBSR_` bridges. The format, the reader's four states and the pack-time check are in `src/docs/Design/swift-lowering-evidence.md` § "Shipped evidence". Policy, not baseline: no reseed and no `--permissive` arm.

The API-manifest gate is the two-sided ABI-contract check: it diffs the emitted public surface against `build/baselines/api-manifest-baseline.json` and is additive-tolerant (added members pass, removed members fail), reseeded by `nuke seed-api-manifest-baseline`. **When a fixture change legitimately moves both baselines, reseed the manifest baseline first** — the manifest gate runs before the skip-surface gate and throws first, so reseeding in the other order just re-reds. `--permissive` demotes only the gates explicitly wired to it (parity, API-manifest, wrapper give-up, generator/dep-gen exit); the resilience-kitchen, ingestion-kitchen and CSM-recovery assertions are fail-closed regardless.

**The consumer-shape equivalence gate.** The regen hands the generator the dependency fixture as an xcframework only, but an SDK consumer of a binding-backed dependency hands it the dependency's xcframework *and* the module database the dependency's binding published, in two-pass `--sdk-mode --skip-wrapper-compilation` generation with no verify-recover loop. The gate regenerates the main fixture in that shape from the same arguments and fails if any emitted `.cs`, `.swift` or `.s` file differs from the gated output, so every later gate also speaks for the consumer path. A positive control requires the consumer-shaped run's `binding-artifact-manifest.json` to record that it read the dependency's declarations next to its database. Equivalence, not baseline: fail-closed, no reseed, no `--permissive` arm.

**When/why to run `--mixed-pack`.** It closes the one gap the macOS-host PackGate cannot: a mixed (ObjC+Swift) binding, packed into a single NuGet package and consumed via one `PackageReference`, actually *linked and run* on the iOS runtimes where duplicate-ObjC-class registration bites — iOS Simulator (Mono JIT) and physical device (NativeAOT). This is the exact shape of the issue #40 "Class X is implemented in both …" report. PackGate proves the *nupkg structure* (static source dropped, wrapper sole-carrier, companion embedded in `lib/`) and runs the consumer on the macOS host; `--mixed-pack` adds the iOS loader + Mono-JIT/NativeAOT runtime coverage. It is **deliberately not part of the inner loop**: it packs the Runtime/SDK/Apple feed, builds a 2-slice iOS mixed xcframework, packs the fixture, then builds (sim) or NativeAOT-publishes (device) a fresh consumer — minutes, not seconds, and it needs a booted simulator (`--sim`) and/or a provisioned device (`--device`). Run it **before a release** and **after changes to native packaging policy, the ObjC companion pack path, calling conventions, or struct/P-Invoke marshalling** — not on every iteration. Examples: `nuke binding-tests --mixed-pack` (sim only), `nuke binding-tests --mixed-pack --device` (device only), `nuke binding-tests --mixed-pack --sim --device` (both).

**When/why to run `--mixed-direct`.** A mixed binding supports three consumption modes: (a) a single packed `PackageReference` — covered by `--mixed-pack`; (b) **SDK-direct**, where the consuming app's own csproj imports `SwiftBindings.Sdk` and declares `<SwiftFramework>` so the app *is* the binding; and (c) a local `ProjectReference` to a generated binding csproj. Paths b and c surface the ObjC companion's managed assembly to a *different* assembly's compile (path b via the SDK's `_ReferenceMixedObjCCompanion` target, path c via the emitted `{PackageId}.ProjectReference.targets`) rather than through a package's `lib/`. `--mixed-direct` is path b's runtime gate: it builds the SDK-direct app, runs it on the Simulator, and asserts the ObjC type round-trips **and** the class registers exactly once (no "Class X is implemented in both …") — both at runtime *and* structurally (the generated companion csproj dropped its source `NativeReference`). Because an SDK-direct app's code compiles into the binding's own assembly, it sees every non-private member the generator emits, so the leg also calls single-parameter `Int64`, `Double`, `Float` and `Int` initializers (one on an ObjC-rooted class) with an `int` variable and requires each value back: a visible handle-adopting constructor would capture the call and adopt the integer as an object pointer. **Coverage by path: a → `--mixed-pack` (sim+device runtime); b → `--mixed-direct` (sim runtime + structural); c → unit tests only** (`ConsumerTargetsEmitterTests` assert the emitted `.ProjectReference.targets` injects the companion `<Reference>` and the SWIFTBIND042 fail-closed guard) — path c has no dedicated iOS runtime leg, since it shares path b's `_BuildMixedObjCCompanion` build path and the same plain-`<Reference>` surfacing mechanism. It is **sim-only by design** — the native single-registration story is keyed on linkage, not consumer path, and is already device-proven by `--mixed-pack`; the new surface here (injecting the companion `<Reference>` into the app's compile + copy-local) is fully observed on the Mono-JIT simulator. Same trigger cadence as `--mixed-pack`: before a release and after changes to the ObjC companion build/reference path or native packaging policy. Example: `nuke binding-tests --mixed-direct`.

**When/why to run `--apple-package-consumer`.** The normal BindingTests app carries its own trimming roots, so it cannot prove that a released Apple supplement package preserves every manifest-generated opaque type for a third-party NativeAOT consumer. This focused leg builds a local Runtime/Apple feed, deletes only the exact throwaway versions from NuGet's global cache, and publishes a new app from one Apple `PackageReference`. The scratch app lives under the host temporary directory, outside the repository hierarchy, so it cannot inherit the repo's `Directory.Build.props` or `Directory.Build.targets`; it also rejects any app-authored descriptor or `IlcArg` before publish. It then creates and materializes `SwiftArray<Locale.Language>` on a physical device. Run it after changing the Apple manifest emitter, supplement linker descriptor, NativeAOT dispatch registration, or Apple native package contents. Example: `nuke binding-tests --apple-package-consumer --device --device-udid <UDID>`.

**When/why to run `--mono-aot`.** The device lane has always meant NativeAOT, which is an *opt-in* runtime: a .NET-for-iOS app only gets it when its author sets `PublishAot`. The default for a physical device is **Mono full-AOT** — `dotnet build -c Debug -r ios-arm64`, no `PublishAot` — and that is the runtime under the MAUI apps most consumers actually ship, including the iPhone that reported issue #46. Nothing in this repo ran it before this flag, so device coverage was entirely NativeAOT's. `--mono-aot` closes that: same regen, same device slice, same wrappers, same suite — only the managed app build differs. It is a third runtime rather than a blend of its neighbours, and the skips follow that: the runtime-detected Mono skips (`[SkipOnMonoJit]`) apply because the process *is* Mono, while the CLI-flag-keyed `[SkipOnDevice]` skips do **not**, because they describe the NativeAOT Release app rather than being on a phone (see `TestPlatform.DeviceMonoAot`). The property set is deliberately identical to `swift-dotnet-packages`' `nuke build-test-app --device` (without `--aot`) so the two repos gate the same runtime. Lane separation is structural, not by convention: NativeAOT publishes Release and Mono full-AOT builds Debug, so they never share a `bin/`/`obj/` tree, the built bundle is checked for the right shape before install (managed assemblies present ⇔ Mono), and the app's own runtime-flavor banner is read back off the device and must agree with the lane — a lane that silently ran the other runtime fails instead of reporting a green. Run it **before a release** and **after changes to marshalling, calling conventions, P/Invoke signatures, or the runtime's Mono/NativeAOT dispatch split** — not on every iteration; it is a second full device build, install and run. It reports under `Device/MonoAOT` and carries its own count-and-identity regression floor at `platforms.device_monoaot` in `runtime-identity-baseline.json` — graded, auto-updated on a green improvement, and reseeded by `--seed-runtime-identity-baseline` exactly as the NativeAOT lane is. It is deliberately keyed apart from `device`: the two lanes run the same suite on the same phone but their skip sets differ, so neither can grade or move the other's floor. It is also not an ABI-grid runtime — the grid declares sim and device/NativeAOT only. Example: `nuke binding-tests --device --mono-aot --device-udid <UDID>`.

**When/why to run `--multi-toolchain-package`.** Every other gate builds one copy on one toolchain. A released binding package carries a copy per supported pairing, and what can go wrong lives between copies: NuGet choosing `lib/` and `buildTransitive/` separately, a wrapper of one copy shipped beside another copy's assembly, a versionless library restoring a copy its app does not embed, a merge that drops or mislabels a copy. Only a real pack on each toolchain, a real merge and consumers on each toolchain observe that. It needs all three profiles installed (`build/toolchains/README.md`) and a simulator, and takes about 30 minutes. Run it **before a release** and **after changes to the copy layout, the copy declaration or selection (SWIFTBIND136/139), the merge (`PackageMerge.cs`), the wrapper identity, the pack or consumer transition checks, or a toolchain profile's pins**. Device coverage of the merged package (NativeAOT and Mono full-AOT on a phone) is not part of it. Example: `nuke binding-tests --multi-toolchain-package`.

**When/why to run `--partial-success-kitchen`.** Every other gate asks "does the *supported* surface work?" This one asks "does the *unsupported* surface fail honestly?" — the day-1 promise to a third-party consumer that a library containing shapes we can't bind still yields a clean partial binding rather than a hard failure or a silently-empty shell. **Don't confuse it with `--skip-surface`**: that one is an aggregate *trend* ratchet over the whole BindingTests corpus and runs in CI; this one is an *exact* frozen-baseline assertion over one small hostile fixture and runs nowhere in CI. It is cheap enough (~30s, host-only, no app build) to run on any generator/emitter change and belongs in the pre-release sweep. **Reseeding is a deliberate act, not a reflex**: the report compare is exact, so an intentional change to which members bind fails the gate exactly like a regression does. When it goes red, read the drift lines — if the change is intended, reseed `build/baselines/partial-success-kitchen-baseline.json` *in the same commit as the generator change* so the baseline's `git_sha` stays meaningful; if it isn't, you just caught a skip-surface regression that nothing else would have. Example: `nuke binding-tests --partial-success-kitchen`.

### Releasing

Releases are cut by GitHub Actions (`.github/workflows/release.yml`), triggered by pushing a `release/**` branch whose name encodes the lane + version(s):

| Branch | Lane | Publishes |
|---|---|---|
| `release/sdk-X.Y.Z+apple-A.B.C` | combined | All 4 packages — Runtime/Sdk/Templates at `X.Y.Z`, Apple at `A.B.C` |
| `release/sdk-X.Y.Z` | SDK only | Runtime/Sdk/Templates at `X.Y.Z` (Apple stays at its latest `apple-v*`) |
| `release/apple-A.B.C` | Apple only | SwiftBindings.Apple at `A.B.C` (SDK lane stays at its latest `sdk-v*`) |

- Append `-dryrun.N` (e.g. `release/sdk-0.15.0-dryrun.1`) to validate + pack **without** publishing, tagging, or releasing.
- A prerelease version (`-preview`/`-alpha`/`-beta`/`-rc`) marks the GitHub Release as a prerelease.
- Publish is gated on `nuke test`, `nuke binding-tests --strict --compile-only` + the full simulator suite, `nuke validate-blast-radius`, and a NuGet preflight, on the unprofiled net10-xcode26 lane and again (unit tests, compile gate, simulator suite) on each other toolchain profile (`profile-gates`). The net11 profile runs the simulator suite twice, **Debug (CoreCLR interpreter) and Release (ReadyToRun)**, each graded against its own floor in `runtime-identity-net11-baseline.json`, and adds the tvOS simulator Debug suite (`net11-tvos-debug`); the configurations come from `SIMULATOR_CONFIGURATIONS` in `build/scripts/ci/toolchain_ci.py`. PR CI (`ci.yml`) runs the same net11 Debug + Release simulator suites and the tvOS Debug suite. A Debug run also proves per class that the interpreter ran it and grades the interpreter's negative controls, so a Debug lane that silently ran something else, or a control that stopped reproducing its defect, fails the gate. On success the pipeline `dotnet nuget push`es each nupkg, pushes the lane tag(s) (`sdk-v*` / `apple-v*`), and creates the GitHub Release with nupkgs attached (notes from a branch `RELEASE-NOTES.md` if present, else auto-generated).
- The NuGet key is the repo's `NUGET_API_KEY` **GitHub Actions secret**, consumed directly by `dotnet nuget push` — there is no `nuke publish` target.

**Runtime-contract floor — decide it on every minor bump.** The load-time `RuntimeContract` gate accepts a binding whose epoch falls in `[MinimumSupportedGeneratedVersion, Version]` (`src/Swift.Runtime/src/Swift/Runtime/RuntimeContract.cs`). `Version` and the emitted epoch derive automatically from the package version; the **floor is the one hand-set value**, and the gate **fails open** — if a release breaks the module-init↔runtime dispatch contract and the floor is *not* raised, old bindings keep loading silently and the safety net becomes false confidence. So at every release, ask: did this version break the dispatch contract? Breaking changes happen only at a **minor** bump (a patch is additive-only). If yes → raise `MinimumSupportedGeneratedVersion` to the new minor (guarded by a floor↔minor unit test). **0.x → 1.0 is the high-stakes case**: epoch jumps from `<1000` to `1000`, so 0.x bindings would still pass a floor left at 16 — decide deliberately whether 1.0 is a compatibility reset (floor → 1000, 0.x bindings rejected) or a pure stability marker (floor stays low). That value is an owner decision; surface it, don't autopilot.

## Working Guidelines

- **No shortcuts.** Prefer the correct long-term solution over a patch that papers over the real issue — root-cause fixes, not symptom suppression, not "skip the failing test", not weakening an assertion to make it green. If you're unsure whether a fix addresses the root cause or whether a short-term workaround is acceptable, ask the user before proceeding.
- **Prediction-gate freeze policy.** Before adding a new hand-coded emission-time prediction gate (a `SkipReason.*` / `MemberValidationPipeline` / `WrapperValidation` predicate), apply the criterion: a new prediction gate is justified **iff the failure it prevents would _compile_**. A compile-error-catchable shape goes to the verify-recover loop, not a new predictor; only soundness conditions the compilers can't see (ABI mismatch, indeterminate layout, register-convention violations) warrant a new gate. Full policy: `src/docs/Design/engineering-policies.md` § "Prediction-gate freeze policy".
- Do NOT commit unless the user explicitly asks. Commit messages: subject + 1–3 sentences on the *why*. No numbered sub-changes, no "Session N handoff", no "Gates passing" footers. Don't reference session/phase numbers from docs.
- **Never `git stash`** — linter hooks detect reverted files; `stash pop` discards changes silently.
- When fixing a bug pattern, grep the whole codebase for ALL instances before finishing.
- After generator changes, verify generated output compiles — don't assume.
- Test files are organized by domain (closures, generics, …), not by milestone/session/SDK version.
- **Assert behavior, not implementation.** Prefer semantic checks (`output contains CallConvCdecl`, round-trip value preserved) over exact string matches of generated code. Use `[Theory]`/`[InlineData]` for input-only variations.
- **Bug-first testing**: when writing tests for untested code, read it first and look for bugs — don't assume existing behavior is correct. Flag suspected bugs explicitly.
- **New work ships with tests.** Every new feature, bug fix, and behavioral change needs coverage at the right layer — unit tests for generator/emitter/parser logic, runtime tests for marshalling and P/Invoke behavior, BindingTests for end-to-end ABI validation. Match the layer to what actually exercises the change (see *BindingTests are the real end-to-end gate* below). "It's covered by an existing test" is only true if you can point at the assertion.
- **Keep the main context clean**: offload exploration that needs >3 searches or spans multiple files to the `Explore` subagent.

### BindingTests are the real end-to-end gate

Unit tests catch logic bugs. **BindingTests** catch ABI mismatches, calling-convention bugs, and marshalling crashes that unit tests CANNOT. Required for generator, emitter, or runtime changes. Add Swift source to `BindingTests/Sources/SwiftBindingsTestLib/` and C# tests to the matching domain file in `BindingTests/RuntimeTestsApp/`. When fixing a `nuke validate` bug, reproduce the Swift pattern in BindingTests so it's permanently covered.

`nuke binding-tests` (default sim) is the everyday runtime gate. Also run `nuke binding-tests --device` when changes touch calling conventions, struct marshalling, or P/Invoke signatures (Mono and NativeAOT have different bugs), and after fixing any NativeAOT-skipped test.

### Final validation gates (run only what the change warrants)

`nuke test` (unit tests) and `nuke binding-tests` (BindingTests) are the everyday signals — fast, targeted, and the layers where new coverage should land. **`nuke validate` is opt-in**, not part of the routine inner loop: it takes ~5 minutes and re-runs the full real-world library sweep. Only run it for (a) larger refactors / cross-cutting generator or emitter changes where category-wide regression is plausible, (b) pre-release regression sweeps, or (c) when you genuinely want the insight from a validation-libraries run. Don't burn ~5 minutes per change "just in case" — that is what's hurting velocity.

| What changed | `nuke test` | `nuke binding-tests` | `nuke validate` |
|---|---|---|---|
| Generator / emitter / parser | Yes | Yes (default sim run). Add `--device` if calling conventions or marshalling changed. | Optional — only for cross-cutting changes or pre-release sweeps |
| Runtime (`Swift.Runtime`) | Yes | Yes (`--skip-regen`). Add `--device` if marshalling changed. | Optional — only if marshalling changed *and* the change plausibly affects multiple libs |
| Test infrastructure only | No | Just the target touched | No |
| Docs / research / external repos | No | No | No |

**Zero-regression policy**: BindingTests pass count and unit test pass count must be ≥ baseline before committing — these are the per-commit gates. `build/baselines/validation-baseline.json` (`cs_compile` + `swift_compile`) only needs to be ≥ baseline *when you actually run `nuke validate`*; if you didn't run validate this change, you don't need to defend against it. No "will fix later" for the gates that ran.

## Known Issues

- **ALL runtime crashes are OUR BUGS until proven otherwise.** 102/102 tests once labeled `[MonoJitCrash]` turned out to be generator/runtime bugs in our code. The authoritative list of confirmed upstream .NET bugs lives in memory at `feedback_mono_jit_blame.md` — anything not on that list is ours. Before blaming the runtime, verify the generated C# P/Invoke matches the Swift `@_cdecl` wrapper: calling convention (`CallConvCdecl` vs `CallConvSwift`), parameter count, parameter types, library name, entry point symbol.
- `DllImportResolver` conflict: `[ModuleInitializer]` + consuming app both call `SetDllImportResolver` → `InvalidOperationException`. `Swift.Runtime/.../SwiftFrameworkResolver.cs` wraps in try-catch.
- **Runtime native ships as a framework, never a loose dylib (Apple TN2435).** `SwiftBindings.Runtime` packages its native code as `SwiftBindingsRuntime.xcframework` (device + simulator framework slices) so it embeds into an `.ipa` as a signed `Frameworks/SwiftBindingsRuntime.framework`. A loose `Frameworks/lib*.dylib` (anything other than Apple's own `/usr/lib/swift` `libswift*`) fails App Store submission. Do **not** "fix" packaging by emitting a loose dylib, and do **not** re-introduce a top-level `SwiftSupport/`-folder injector (no `add-swiftsupport-folder.sh`) — a stable-ABI min-iOS-15 app links the OS-resident Swift and needs neither; both were tried and removed. The `--appstore-hygiene` gate enforces all of this structurally and on a built `.ipa`.
- **tvOS Mono apps bind P/Invokes through dlsym.** The .NET 10 bundler links a tvOS app's P/Invokes directly (iOS uses dlsym for every non-SDK assembly), and the app executable links neither `/usr/lib/swift` nor the system Swift frameworks those P/Invokes target. `SwiftBindings.Runtime.targets` (`_SwiftBindingsTvosDlsym`) therefore names every non-SDK assembly of a tvOS Mono app for dlsym, as iOS does by default. Without it an AOT-compiled tvOS consumer fails to link. `--bridge-consumer --tvos` builds one in every consumption mode.
- Intended work: `src/docs/roadmap.md`. Confirmed upstream cases: `src/docs/Future/upstream-blockers.md`. Deferred evidence: `src/docs/Future/notes/README.md`; search the relevant subsystem when needed, not as an automatic next-work queue.
- Consumer-facing limitations: [wiki Known Limitations](https://github.com/justinwojo/swift-dotnet-bindings/wiki/Known-Limitations).
